Semgrep - кастомные правила для поиска SQL-инъекций

Кратко о задаче

В этом задании вам нужно:





взять учебный файл sql_app.py, где есть и небезопасные, и безопасные SQL-запросы;



написать собственные кастомные правила Semgrep в формате YAML, которые находят подозрительные SQL-конструкции (конкатенация строк, f-строки и т.п.);



запустить свои правила на проекте и проанализировать результаты

 

Исходные материалы
АРХИВ

Проект:

sql_app.py

Файл sql_app.py содержит:





функции, которые строят SQL-запросы через конкатенацию строк и f-строки, используя строковые аргументы (потенциально уязвимые к SQL-инъекции);



функции, которые используют параметризованные запросы (? + кортеж параметров), что считается безопасной практикой.

 

Что нужно сделать





В файле sql_rules.yml опишите минимум два кастомных правила Semgrep, нацеленных на SQL-инъекции.
Примеры направлений:





правило, которое ищет вызовы cur.execute(...) (или просто execute(...)), где SQL-строка собирается через +;



правило, которое ищет f-строки в SQL-запросах;



правило, которое ловит простейшие признаки: WHERE ... = " +, "LIKE '%" + term + "%'", "LIMIT " + limit и т.п.

У каждого правила должны быть поля:





id



languages: [python]



message



severity



хотя бы один pattern (или pattern-either с набором паттернов).

Можно опираться на пример структуры:

rules:
  - id: my-sql-rule
    languages: [python]
    message: "Подозрительный SQL-запрос через конкатенацию строк"
    severity: WARNING
    pattern: ...





Запустите Semgrep с вашим файлом правил в корне проекта:



Посмотрите, какие участки кода были найдены вашими правилами.
Обратите внимание:





попали ли под правила все явно небезопасные функции (unsafe_*);



не попали ли под правила безопасные функции (safe_*);



нужно ли скорректировать паттерны, чтобы уменьшить количество ложных срабатываний.



Что нужно сдать

Сдаёте один файл (PDF или DOCX) со следующим содержимым.

1. Краткое описание проекта

Коротко (3–5 предложений):





что за файл sql_app.py;



какие функции в нём есть;



в чём разница между unsafe_* и safe_* функциями на уровне подхода к построению SQL-запросов.

2. Текст ваших кастомных правил

Полное содержимое файла sql_rules.yml.

Для каждого правила:





укажите, что оно должно находить (одним-двумя предложениями);



поясните, почему вы считаете такой паттерн опасным (где здесь риск SQL-инъекции).

3. Результаты запуска Semgrep

Опишите:





команду, которой вы запускали Semgrep;



были ли ошибки при запуске (если да — как вы их исправили).

Далее для каждого вашего правила приведите минимум по одному примеру срабатывания:





файл и строка, где правило сработало;



небольшой фрагмент кода (2–6 строк);



ваш комментарий

Если какое-то правило ничего не нашло, это тоже нужно указать и попытаться объяснить, почему так произошло (например, паттерн слишком узкий).

4. Короткий вывод

3–6 предложений:





какие ваши правила оказались полезными, а какие пришлось бы дорабатывать;



были ли ложные срабатывания и почему они возникли;



как вы могли бы улучшить эти правила в будущем

 

Требования к зачёту





В sql-rules.yml описано минимум два рабочих кастомных правила Semgrep, нацеленных на поиск подозрительных SQL-конструкций.



Semgrep был запущен на проекте sql_lab.py с этим набором правил.



Для каждого правила показан хотя бы один пример срабатывания или честно описано, почему совпадений нет.



В отчёте видно, что вы понимаете разницу между явно опасными запросами через конкатенацию и безопасными параметризованными запросами.

 

На «отлично»

Дополнительно оценивается, если:





вы сделали 3 и более осмысленных правила (например, отдельное правило для f-строк, отдельное для LIKE, отдельное для LIMIT);



вы постарались уменьшить ложные срабатывания (например, не трогать safe_* функции);
