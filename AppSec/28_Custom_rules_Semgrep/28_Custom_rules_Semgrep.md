# Написание кастомных правил в Semgrep
Написание кастомных правил — это «высшая лига» для AppSec-инженера. Именно этот навык позволяет вам превратить `Semgrep` из обычного сканера в персонального охранника вашей кодовой базы, который знает все специфические «болячки» и легаси-артефакты вашего проекта. Это по сути умение формально описать: «какой фрагмент кода я хочу находить» и «что про него сказать разработчику».

Почему недостаточно просто использовать готовый `Registry`? В каждой крупной компании есть свои внутренние библиотеки, специфические фреймворки или договорённости о том, какие функции использовать нельзя. Готовые правила о них не знают. Ваша задача — научить инструмент видеть эти нюансы

## Базовая структура правила
Ранее мы уже упоминали о правилах теперь давайте вспомним как они выглядят. Простейшее правило в `Semgrep` выглядит так:
```
rules:
  - id: rule-id
    languages: [python]
    severity: WARNING
    message: "Нашли что-то подозрительное"
    pattern: $X(...)
```
Здесь важно понимать роль каждого поля.
* `id` — уникальный идентификатор правила.
По нему потом фильтруют, отключают, ищут в отчётах. Хорошо, когда он осмысленный: `python.insecure.os-system`, `django.debug-true` и т.п.
* `languages` — список языков, для которых правило работает.
Например: `[python]`, `[javascript, typescript]`, `[go]`.
* `severity` — уровень важности.
Обычно используют `CRITICAL`, `ERROR`, `WARNING`, `INFO`. Это влияет на приоритизацию в отчётах и `CI`.
* `message` — читаемое описание. Кратко объясняет, что не так: «Небезопасный вызов os.system», «SQL без параметризации» и т.д.
* `pattern` — собственно паттерн: что именно ищем в коде. Это может быть одна строка, блок кода или более сложная конструкция.

## Логические операторы: Комбинирование паттернов
Иногда одного паттерна недостаточно. Для этого используются логические блоки:
1. `patterns`: (Логическое И). Все условия внутри должны быть выполнены.
2. `pattern-either`: (Логическое ИЛИ). Сработает, если подошел хотя бы один паттерн.
3. `pattern-not`: (Логическое НЕ). Позволяет исключать «хорошие» случаи (например, если функция используется с безопасными параметрами).

Пример сложной логики: Мы хотим найти использование `requests.get()`, но ТОЛЬКО если там отключена проверка SSL-сертификатов (`verify=False`).
```YAML
patterns:
  - pattern: requests.get(...)
  - pattern-inside: requests.get(..., verify=False, ...)
```
Теперь поговорим о каждом чуть подробней. `Semgrep` позволяет задавать условие разной сложности:
1. `pattern` — один паттерн.
Пример: ищем все вызовы `os.system`:
```
pattern: os.system($CMD)
```
2. `patterns` — несколько условий, которые должны выполняться одновременно (логическое И). Например: ищем `requests.get(...)` без параметра `timeout`:
```
patterns:
  - pattern: requests.get($URL)
  - pattern-not: requests.get($URL, timeout=$T, ...)
```
3. `pattern-either` — набор альтернатив (логическое ИЛИ). Например, хотим ловить и `os.system`, и `subprocess.Popen`:
```
pattern-either:
  - pattern: os.system($CMD)
  - pattern: subprocess.Popen($ARGS, ...)
```
Комбинируя `pattern`, `patterns`, `pattern-not`, `pattern-either`, можно достаточно точно описывать интересующие конструкции.

## Типы паттернов
В паттернах `Semgrep` используем три базовых идеи: конкретный код, метапеременные и эллипсис.

### Конкретный код
Это самый прямой вариант: пишем реальный фрагмент кода, который хотим найти.
```
pattern: os.system("rm -rf /")
```
Такое правило сработает только на точное совпадение. Для реальной жизни обычно слишком жёстко, но полезно для поиска конкретных конструкций (например, временных заглушек или тестового кода).

### Метапеременные ($X, $FUNC и др.)
`Метапеременные` — это «подстановочные» элементы в паттерне. Они означают ***«здесь может быть что угодно, но структура должна совпасть»***.

Примеры:
```
pattern: os.system($CMD)
```
Это правило найдёт любой вызов `os.system(...)`, независимо от того, что внутри скобок. `$CMD` — метапеременная, которая сопоставится с фактическим аргументом.
```
pattern: $FUNC($ARG1, $ARG2)
```
Здесь `$FUNC` может быть любой функцией, `$ARG1` и `$ARG2` — любыми выражениями. Такой паттерн уже ближе к «шаблону» и потом можно использовать дополнительные условия, например ограничить `$FUNC` по имени или типу.

Метапеременные позволяют описывать структуру кода, а не конкретные строки.

### Эллипсис (...)
Троеточие в Semgrep-паттернах означает ***«здесь может быть любой код»***.

Пример:
```
pattern: |
  def $FUNC(...):
    ...
    os.system($CMD)
    ...
```
Такое правило найдёт любые функции, внутри которых где-то вызывается `os.system(...)`, независимо от того, что ещё в этой функции происходит.

Эллипсис удобно использовать:
* внутри списков аргументов (func(a, ..., c)),
* внутри тел функций, циклов, условий,
* когда важна только ключевая операция, а окружение не имеет значения.

## Полный пример простого правила
Допустим, хотим находить в Python небезопасные вызовы `os.system` и подсвечивать их как предупреждение:
```
rules:
  - id: python.insecure.os-system
    languages: [python]
    severity: WARNING
    message: "Небезопасный вызов os.system. Проверьте, нет ли здесь пользовательского ввода."
    pattern: os.system($CMD)
```
Здесь:
* `id` даёт понятный ключ для этого правила;
* `languages` ограничивает область действия;
* `severity` показывает, что это не опечатка, а потенциальная уязвимость;
* `message` подсказывает разработчику, чего именно стоит опасаться;
* `pattern` ловит все вызовы `os.system(...)`, независимо от аргумента.

## Поле fix: автоисправление (опционально)
К правилам можно добавить поле `fix`, которое задаёт шаблон для автоматической замены кода. `Semgrep` тогда не только найдёт проблему, но и предложит готовый патч.

Пример (упрощённый): заменяем `os.system` на `subprocess.run`:
```
rules:
  - id: python.replace-os-system
    languages: [python]
    severity: INFO
    message: "Рекомендуется использовать subprocess.run вместо os.system"
    pattern: os.system($CMD)
    fix: subprocess.run($CMD, shell=True, check=True)
```
В реальной жизни `fix'и` нужно готовить аккуратно, но идея проста: те же метапеременные (`$CMD`) можно использовать и в шаблоне исправления.

## Тестирование ваших правил
Написание правила — это итеративный процесс. Чтобы не «выстрелить в ногу» и не заспамить коллег ложными срабатываниями, `Semgrep` поддерживает специальный режим тестирования. Вы создаете файл `test.py`, пишете там примеры «плохого» и «хорошего» кода, и с помощью комментариев `# todo: ok` или `# todo: error` указываете, где правило должно сработать.

Пример test.py
```py
# ruleid: no-eval
eval(user_input)
# ok: no-eval
print(user_input)
# ok: no-eval
len(data)
# ruleid: no-eval
eval("1+1")
```
Здесь комментарии — это твои ожидания. Здесь (ruleid) правило ДОЛЖНО сработать. Здесь (ok) правило НЕ должно сработать.

✅ Команда `semgrep --test` проверит, совпадает ли реальность с вашими ожиданиями. Он запускает правило и сравнивает результат с комментариями.

Написание правил в `Semgrep` — это декларативное программирование. Вы не пишете алгоритм поиска, вы описываете образ (паттерн) того, что хотите найти.

1. Используйте `...` для игнорирования лишнего.
2. Используйте `$X` для отслеживания одинаковых сущностей.
3. Всегда пишите тесты для своих правил.

Если свести всё к одному предложению: кастомное правило `Semgrep` — это YAML-запись, где вы задаёте идентификатор, уровень важности, описание и паттерн (или набор паттернов) с метапеременными и эллипсисом, который описывает именно те фрагменты кода, которые вы хотите систематически находить в своей кодовой базе.
