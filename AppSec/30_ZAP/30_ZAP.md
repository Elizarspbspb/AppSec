# ZAP
`ZAP` в этом курсе — второй «крупный игрок» рядом с `Burp Suite`. Если Burp часто ассоциируется с ручным и полуавтоматическим тестированием, то `ZAP` обычно берут там, где важны автоматизация, интеграция в пайплайны и полностью открытая лицензия.

## Что такое ZAP
`ZAP` (Zed Attack Proxy) — это бесплатный open-source инструмент для тестирования безопасности веб-приложений, который развивается под эгидой `OWASP`. По сути это тоже прокси-среда для анализа HTTP/HTTPS-трафика и автоматизированного поиска уязвимостей, но с акцентом на:
* доступность (полностью бесплатен, исходники открыты),
* автоматизацию и работу через API,
* удобство интеграции в процессы разработки и CI/CD.

Для специалиста по безопасной разработке `ZAP` — это, в первую очередь, удобный автоматизированный помощник: от «быстрого скана стенда» до встроенного этапа в конвейер сборки.

## Чем ZAP отличается от Burp Suite
С точки зрения задач, `ZAP` и `Burp` очень похожи: оба умеют перехватывать трафик, сканировать, фаззить, автоматически искать уязвимости. Разница — в акцентах и экосистеме.

Во-первых, модель распространения. `Burp Professional` — коммерческий продукт, Community ограничен. 

`ZAP` же:
* полностью бесплатен;
* распространяется с открытым исходным кодом;
* активно развивается сообществом OWASP.

Во-вторых, ориентация на автоматизацию. У `Burp` тоже есть API и интеграции, но `ZAP` изначально проектировался как инструмент, который:
* удобно запускать в фоне;
* удобно обращаться по HTTP-API;
* удобно разворачивать в Docker-контейнере для сканирования в пайплайне.

Отсюда большое количество примеров и готовых обвязок для `CI` (`GitLab CI`, `GitHub Actions`, `Jenkins` и т.д.).

В-третьих, экосистема. Вокруг `ZAP` сформировалось активное сообщество: плагины, скрипты, наборы профилей сканирования. Плюс он официально фигурирует в рекомендациях `OWASP` как базовый инструмент для динамического тестирования.

В результате типичная связка выглядит так: `Burp` — для глубокой ручной работы и точечной эксплуатации; `ZAP` — для регулярно запускаемого автоматизированного анализа.

## Сопоставление с Burp
Если до `ZAP` вы уже разбирали `Burp Suite`, полезно закрепить соответствия:
* прокси и история запросов в `ZAP` выполняют примерно ту же роль, что `Proxy` и `HTTP history` в `Burp`;
* дерево сайтов можно воспринимать как аналог `Site Map`;
* `spider` и `AJAX spider` — функциональный аналог разведки по ссылкам в `Burp` (частично через Proxy / Target);
* активный сканер `ZAP` — близкий по смыслу к `Burp Scanner`;
* `Fuzzer` решает те задачи, для которых в `Burp` используется `Intruder`.

Это упрощает переход между инструментами: меняется интерфейс и набор кнопок, но базовые идеи остаются теми же.

## Режимы работы ZAP
`ZAP` можно использовать по-разному в зависимости от задачи.

### Desktop app (графический интерфейс)
Классический режим, похожий на Burp:
* запускается десктопное приложение;
* вы настраиваете браузер на прокси `ZAP`;
* видите дерево сайтов, журналы запросов, результаты пассивного и активного сканера;
* запускаете пауки (`spider`), активный скан, фаззинг и т.п.

Этот режим удобен для обучения, ручного анализа и исследования отдельных приложений.

### Daemon mode
`ZAP` можно запустить без графики, в фоновом режиме. Тогда он:
* поднимает внутренний HTTP-API;
* принимает команды извне (запустить скан, добавить цель, выгрузить отчёт);
* выдаёт результаты в удобных форматах (HTML, XML, JSON).

Такой режим используют, когда нужно:
* интегрировать `ZAP` в `CI/CD`;
* запускать его как сервис в тестовой среде;
* автоматизировать регулярные сканы без участия человека.

### Docker-режим
Для `ZAP` есть готовые `Docker-образы`. Это упрощает:
* развёртывание в чистом окружении;
* запуск сканирования в конвейере сборки;
* отделение сканера от основной системы.

Чаще всего `ZAP` в `Docker` комбинируют с daemon-режимом и API: контейнер стартует, по `API` даётся команда на скан, затем результаты выгружаются и контейнер останавливается.

```
docker pull ghcr.io/zaproxy/zaproxy:stable
```

## Основные компоненты ZAP
Архитектурно `ZAP` очень напоминает Burp: у него те же базовые элементы, просто иногда с другими именами и акцентами.

### Прокси (Proxy)
Так же как в `Burp`, `ZAP` выступает в роли промежуточного прокси:
* браузер отправляет запросы в ZAP;
* ZAP пересылает их на сервер и фиксирует ответы;
* всё попадает в журнал и дерево сайтов.

Через прокси можно перехватывать и просматривать трафик, запускать сканирование по конкретным веткам, отправлять запросы в дополнительные инструменты.

### Spider (пауки, краулеры)
`Spider` — компонент, который обходит ссылки и формы на сайте, чтобы построить карту приложения. В `ZAP` обычно есть:
* классический `spider`, который анализирует HTML-страницы;
* `AJAX spider` для современных SPA-приложений, где часть функционала раскрывается через JavaScript.

Результат работы `spider`’а — наполнение дерева целей, по которому потом может пройтись сканер.

### Scanner (пассивный и активный)
`ZAP` всегда ведёт пассивный анализ: пока вы работаете с приложением, он просматривает трафик на предмет подозрительных заголовков, неправильных настроек, возможных уязвимостей, не генерируя дополнительных запросов.

В активном режиме сканер:
* сам отправляет различные payload’ы;
* изменяет параметры запросов;
* проверяет на наличие конкретных классов уязвимостей (XSS, SQLi, Path Traversal и т.д.).

***Запуск активного сканера по сути — это команда «попробуй атаковать найденные эндпоинты».***

### Fuzzer (фаззер)
`Fuzzer` в `ZAP` выполняет ту же роль, что `Intruder` в Burp:
* вы выбираете запрос и отмечаете области для подстановки;
* задаёте списки значений (словари, генераторы);
* `ZAP` автоматически отправляет запросы с вариациями.

Это полезно для брутфорса параметров, поиска нестандартных ответов, проверки устойчивости к необычным значениям.

## Сценарий работы с ZAP (desktop-режим)
Чтобы урок не был чистой теорией, полезно показать, как выглядит «обычный день» работы с `ZAP` при анализе одного веб-приложения.

Сначала запускаем `ZAP` в графическом режиме и подключаем браузер к его прокси. 
Это можно сделать так же, как с Burp: указать в настройках браузера HTTP/HTTPS-прокси 127.0.0.1:порт `ZAP` или воспользоваться браузером, который `ZAP` умеет запускать сам с уже настроенным прокси. После этого весь трафик браузера к целевому сайту начинает проходить через `ZAP`.

Дальше в браузере просто работаем с приложением: логинимся, переходим по страницам, отправляем формы. В `ZAP` при этом заполняется дерево сайтов и история запросов: становится видно, какие URL существуют, какие параметры используются, какие ответы приходят.

Когда у нас появилась минимальная карта приложения, логично запустить `spider` по целевому домену. Пауки пройдут по ссылкам и формам, дополнят дерево сайта. После окончания паука становится понятнее, что именно `ZAP` «видит» и какие точки можно отдать на активное сканирование.

Следующий шаг — запуск активного сканера на выбранной области дерева. Можно назначить сканирование на весь домен целиком или только на конкретную ветку (например, /app/ или только раздел после авторизации). `ZAP` начнёт отправлять дополнительные запросы, подставлять тестовые данные и собирать потенциальные уязвимости.

Параллельно с этим отдельные запросы можно брать из журнала и отдавать в `Fuzzer`, если требуется более тонкий ручной фаззинг конкретного параметра (например, проверки устойчивости к длинным значениям или специфическим payload’ам).

## Контексты и авторизация в ZAP
Во многих реальных приложениях интересные уязвимости находятся уже после логина: в личном кабинете, в админке, в API под токеном.

В `ZAP` для таких сценариев есть понятие контекста. Контекст — это:
* набор URL, которые относятся к одной логической зоне (например, весь домен или его часть);
* правила аутентификации и параметры сессии (куки, токены, параметры формы логина);
* иногда разные роли (один и тот же контекст, но с разными учётными данными).

Один раз настроив контекст и аутентификацию, можно запускать `spider` и активный скан уже «от лица» авторизованного пользователя. Это даёт значительно больше покрытия и позволяет находить уязвимости, которые для анонимного гостя просто недоступны.

## ZAP и автоматизация через API
Отдельно стоит подчеркнуть работу `ZAP` через API. В daemon-режиме практически всё, что вы делаете в GUI, можно:
* сформулировать как HTTP-запрос к `API ZAP`;
* встроить в скрипт (Python, Bash, PowerShell);

Типичный сценарий:
1. В пайплайне поднимается `ZAP` (как контейнер или отдельный процесс).   
Скачиваем образ (один раз):
```
docker pull ghcr.io/zaproxy/zaproxy:stable
```
Запускаем `ZAP` в daemon-режиме:
```
docker run -d \
  --name zap \
  -p 8080:8080 \
  ghcr.io/zaproxy/zaproxy:stable \
  zap.sh \
  -daemon \
  -host 0.0.0.0 \
  -port 8080 \
  -config api.disablekey=true
```
Проверяем, что контейнер работает:
```
docker ps
```
2. Тестируемое приложение разворачивается на тестовом домене;
3. по API:
    * настраивается контекст (scope, авторизация),
    * запускается spider и ждётся завершение;
    * запускается активный скан;
    * выгружается отчёт в выбранном формате.

Такой подход позволяет использовать `ZAP` не только вручную, но и как регулярный автоматический «барьер», который проверяет новые сборки на базовые уязвимости.

`ZAP` — это бесплатный и открытый инструмент от `OWASP` для тестирования безопасности веб-приложений, который по возможностям близок к Burp Suite, но делает упор на открытость и автоматизацию. В графическом режиме он удобно работает как прокси и сканер для ручного и полуавтоматического тестирования, а в daemon-/Docker-режимах превращается в компонент конвейера безопасной разработки, который можно дергать по API и встроить в регулярные проверки.

## Устаовка и запуск ZAP
### Скачать официальный архив
Сначала установи Java (ZAP требует Java):
```
sudo apt update
sudo apt install default-jre -y
```
Проверь:
```
java -version
```
Должно быть что-то вроде:
```
openjdk version "21.x"
```
Скачай `ZAP`:
```
cd ~/Downloads
wget https://github.com/zaproxy/zaproxy/releases/latest/download/ZAP_2_16_1_Linux.tar.gz
```
(Если версия уже изменилась, можно взять актуальную с GitHub OWASP ZAP.)

Распакуй:
```
tar -xzf ZAP_*.tar.gz
```
Перейди в папку:
```
cd ZAP_*
```
Запуск:
```
./zap.sh
```
### Потом проверь прокси в `ZAP`:  
Tools
  * → Options
  * → Network
  * → Local Servers/Proxies

должно быть:
```
localhost: 127.0.0.1
Port: 8080
```

### В FoxyProxy добавь новый профиль
В Firefox:
```
FoxyProxy → Options → Add
```
Создай:
```
Title: OWASP ZAP
Proxy Type: HTTP
IP Address: 127.0.0.1
Port: 8080
```
Сохрани.

### ZAP завис на сертификате HTTPS
При первом запуске `ZAP` должен создать свой CA-сертификат. Если HTTP работает, а HTTPS нет — надо установить сертификат `ZAP`.

В `ZAP`:  
Tools
 * → Options
 * → Network
 * → Server Certificates
 * → Save

Сохрани сертификат.

Потом `Firefox`:
```
Settings
 → Privacy & Security
 → Certificates
 → View Certificates
 → Import
```
Выбери сертификат `ZAP` и поставь галочку: ***Trust this CA to identify websites***.

Работай!!!

## Что такое Context в ZAP
`Context` — это просто группа правил для выбранного сайта.

В него можно добавить:
* какие URL считать целью (scope);
* какие URL исключать;
* какие пользователи используются;
* какие аутентификационные данные;
* какие сканеры запускать.

Например:
```
Context: sqlmap_lab

Внутри:
http://172.17.0.2:5000.*
```
Теперь `ZAP` понимает:

"Вот этот сайт — моя лабораторная цель. Не трогай Google, GitHub и прочее."

Но `Context` сам по себе НЕ собирает пакеты. Он не является прокси и не влияет на обычный просмотр сайта.

## Как обычно работают в ZAP
### Часть 1. Sites
Слева открывают вкладку `Sites`.

Там будет примерно так:
```
Sites
 ├── https://github.com
 ├── https://chat.openai.com
 └── http://172.17.0.2:5000
      ├── /
      ├── /login
      └── /search
```
Именно по дереву `Sites` обычно анализируют приложение. `History` используют скорее как общий лог.

Задайте область тестирования (scope) - то почти наверняка:
* Создать `Context`: ПКМ - Include in Context.
* Добавить туда http://172.17.0.2:5000.*
* Дальше запускать `Spider` или `Active Scan` только по этому `Context`.

### Часть 2. Spider
Теперь запускаем обход. В ZAP ПКМ по: http://172.17.0.2:5000. Дальше: Attack - Spider...

или Contexts - ПКМ - Spider - Start Scan.

ZAP начнёт искать:
* /
* login
* logout
* admin
* search

### Часть 3. AJAX Spider
Он нужен только если сайт сильно использует `JavaScript`. Запускается: Tools - AJAX Spider.

### Часть 4. Active Scan
ПКМ по сайту - Attack - Active Scan...

И ZAP спросит: Scan policy

Оставляешь: Default Policy

Запускаешь.

Он будет искать:
* SQL Injection
* XSS
* Path Traversal
* CSRF
* Security Headers
* и т.д.

### Часть 5. Alerts
В `ZAP` открой `Alerts` или снизу - Alerts. Там будут реальные находки:
```
High
  SQL Injection

Medium
  Missing Anti-CSRF Tokens

Low
  X-Content-Type-Options Missing
```
Именно это является результатом `Active Scan`.

### Часть 6. Сохранить отчёт ZAP в HTML
В ZAP 2.17.0. Меню: `Report - Generate Report...`

Дальше:
* Report type: HTML
Report title: SQLMap Lab - ZAP Security Scan Report
Выбираешь место сохранения: ~/Documents/zap_report.html

Нажимаешь `Generate`.

После этого получишь HTML-файл, который можно открыть в браузере.

### Как сделать HAR в ZAP
`HAR` (HTTP Archive) — это файл, в котором сохраняются HTTP-запрос и HTTP-ответ.

Есть несколько способов.
* Найди нужную уязвимость в Alerts.
* ПКМ или Дважды щёлкни по ней.
* Save as HAR...
* Найди этот запрос в History.
* ПКМ по запросу → `Export` или `Save Message` или `Export HAR`.
