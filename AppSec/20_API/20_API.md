# API
В этом уроке разберём безопасность `API`. Раньше мы уже говорили про отдельные уязвимости (`IDOR`, `SSRF` и т.д.), а теперь посмотрим, как они проявляются именно в контексте `API`. Чтобы всё было понятно, начнём с самого начала: что такое API и как оно вообще работает.

## Что такое API и как оно работает
`API` (Application Programming Interface) — это способ, которым одна программа «разговаривает» с другой. В вебе это чаще всего:
* клиент (браузер, мобильное приложение, другой сервис) ↓
* отправляет HTTP-запрос на сервер по адресу (`URL`) ↓
* сервер обрабатывает запрос и возвращает ответ (обычно `JSON` или `XML`).

Вместо «человеческих» страниц (HTML) ***API выдаёт структурированные данные***, чтобы их мог читать код:
например:
```
GET /api/user/123         
```
Ответ:
```json
{
  "id": 123,
  "email": "user@example.com",
  "role": "user",
  "is_admin": false
}
```
API часто работает между машинами, а не с человеком напрямую. Из-за этого многие разработчики «расслабляются»: интерфейс не виден в браузере, значит, «никто туда не полезет». На практике это даёт отличную почву для уязвимостей.

`REST API` (Representational State Transfer Application Programming Interface) — это архитектурный стиль взаимодействия между клиентом и сервером, использующий стандартный протокол `HTTP`. Он работает с ресурсами (данными), применяя методы `GET`, `POST`, `PUT`, `DELETE`, и обычно обменивается информацией в формате `JSON`.

`REST API` позволяет приложениям обмениваться данными независимо от языков программирования и платформ. Сервер предоставляет ресурсы в виде данных, а клиент получает к ним доступ с помощью стандартных HTTP-запросов. Каждый ресурс в `REST API` имеет уникальный идентификатор (`URI`) и управляется с помощью методов `HTTP`. 

`REST-API` — это просто набор HTTP-эндпоинтов, у каждого из которых есть свой `URL` и смысл: авторизация, работа с пользователями, заказы, файлы и так далее.

Классический пример: фронтенд (браузер или мобильное приложение) не лазит напрямую в базу данных, а всегда идёт через `REST-эндпоинты` вроде:
```
POST /api/login — вход в систему;
```
```
GET /api/users/me — информация о текущем пользователе;
```
```
GET /api/orders/123 — получить заказ с ID 123;
```
```
POST /api/orders — создать новый заказ.
```
Ответы чаще всего в `JSON`. Для нас важно вот что: `REST-API` — это голая бизнес-логика, без HTML, кнопок и «красивого интерфейса». Всё, что делает приложение, почти всегда есть в виде API-запроса.

Поэтому любой, кто видит эти запросы (через `Burp`, `Postman`, `curl`), может начать:
- менять параметры, ID, тела запросов;
- вызывать то, что не предусмотрено UI;
- автоматизировать перебор и атаки.

И если API не проверяет права, не ограничивает частоту, возвращает лишние данные — это почти гарантированная уязвимость.

## Ключевые термины, которые важно понимать
Чтобы хорошо ориентироваться в безопасности API, стоит твёрдо держать в голове эти слова:

`REST` — стиль построения веб-API, где ресурсы (пользователи, заказы, посты) представлены как `URL`, а действия описываются HTTP-методами.

`Endpoint` — конкретный адрес `API`, который принимает определённый тип запросов и выполняет конкретное действие (авторизация, получение списка, создание объекта и т.д.).

`CORS` (Cross-Origin Resource Sharing) — механизм в браузерах, который определяет, с каких доменов `JavaScript` может делать запросы к вашему API и читать ответы. Неправильная настройка `CORS` часто открывает дорогу атакам через браузер.

`Rate Limiting` — ограничение числа запросов за единицу времени от одного источника. Это один из основных способов защиты от брутфорса и DoS в API.

`JWT` (JSON Web Token) — формат токенов, которые часто используют для аутентификации в API. Это закодированная (и подписанная) структура `JSON`, содержащая информацию о пользователе и его правах. При неправильном использовании `JWT` может стать отдельным источником уязвимостей (подделка токенов, слишком долгий срок жизни, отсутствие проверки подписи и т.д.).

## Аутентификация и авторизация: где всё обычно ломается
Два базовых понятия, вокруг которых крутится безопасность API:
1) `аутентификация` — кто это к нам пришёл;
2) `авторизация` — что ему разрешено делать.

В `REST` аутентификация обычно выглядит так: пользователь логинится на `/api/login`, получает в ответ токен (часто `JWT`) и дальше в каждом запросе отправляет его в заголовке `Authorization`. Сервер по этому токену понимает, кто перед ним.

Проблема в том, что многие разработчики на этом останавливаются: «если токен валидный — значит, всё хорошо». Авторизация при этом либо минимальная, либо отсутствует. То есть сервер проверяет «пользователь залогинен», но не проверяет «этот пользователь имеет право именно к этому объекту».

Отсюда рождаются:
1. классический `IDOR`: `GET /api/users/10` возвращает профиль 10-го пользователя; если заменить на `/api/users/11`, а сервер не сверяет, что текущий пользователь — именно 11-й, мы видим чужие данные;
2. вертикальные обходы прав: обычный пользователь дергает что-то вроде `/api/admin/users`, и если на уровне эндпоинта нет проверки роли, он внезапно становится «псевдоадмином».

С точки зрения анализа API это одна из первых проверок: для каждого эндпоинта, где фигурирует какой-то ID или «чужой» ресурс, пробуем менять его на другие значения и смотрим, ограничивает ли сервер доступ по реальным правам, а не только по факту наличия токена.

## Чрезмерное раскрытие данных: когда API говорит лишнее
Следующая типичная проблема: API возвращает больше данных, чем нужно. Внутри приложения есть модель, например, пользователя: ID, e-mail, имя, хэш пароля, флаги ролей, внутренние заметки, служебные токены.

В базе есть модель пользователя:
```json
{
  "id": 123,
  "email": "user@example.com",
  "name": "Alex",
  "password_hash": "$2b$12$.....",
  "is_admin": false,
  "internal_notes": "VIP, не трогать",
  "reset_token": "..."
}
```
Для фронтенда реально нужны только несколько полей, но проще всего «отдать всё» и пусть UI сам решает, что показать.

Для обычного пользователя это выглядит нормально: он видит только e-mail и имя. Для атакующего, который смотрит прямо в JSON-ответ, картинка другая: там могут быть `password_hash`, `is_admin`, `секретные токены`, `внутренние комментарии`.

Это как поставить стекло вместо стены: формально всё ещё «закрыто», но видно абсолютно всё. С точки зрения безопасности любая лишняя информация — это:
* материал для атак (хэши паролей, ID внутренних систем, служебные токены);
* подсказки по структуре и ролям (флаги админа, флаги модератора, скрытые состояния).

При анализе `REST-API` всегда имеет смысл смотреть: какие поля реально нужны фронту и какие из возвращаемых полей явно «служебные», которые не должны уходить наружу.

## Rate limiting и автоматизация атак
`REST-API` идеально подходит для автоматизации: нет лишней разметки, только данные. Поэтому вопрос «есть ли лимиты на количество запросов» — критически важный.

`Rate limiting` — это механика, которая не даёт одному клиенту делать слишком много запросов за короткое время. Ограничивать можно по IP, по токену, по учётке, по комбинации факторов.

Если никаких лимитов нет, открывается путь для:
1. `брутфорса` логина и пароля: десятки, сотни запросов на /api/login с разными паролями без всякого сопротивления;
2. `перебора` одноразовых кодов и токенов: восстановление пароля, подтверждение операции, промокоды;
3. `массового обхода` ID: последовательный запрос `/api/users/1`, `/api/users/2`, `/api/users/3` — пока не соберём всю базу;
4. простого `DoS`: отправляем сотни запросов, пока сервер не начнёт падать или лагать.

При тестировании API полезно сознательно «переборщить» с количеством запросов к чувствительным точкам (логин, операции с деньгами) и посмотреть, где система хотя бы реагирует, а где позволяет отправлять без ограничений.

## CORS и атаки через браузер
`REST-API` часто вызывается из браузера, напрямую с фронтенда. Здесь появляется важный игрок — `CORS` (Cross-Origin Resource Sharing). Это механизм, который решает, может ли `JavaScript` с одного домена читать ответы другого домена.

Если `CORS` настроен бездумно, например «разрешаем всем и всё», сценарий может быть таким:
1. пользователь залогинен в `https://api.example.com`, его токен хранится в браузере;
2. он открывает вкладку с `https://evil.com`;
3. скрипт на `evil.com` из браузера пользователя отправляет запросы к `https://api.example.com` и, из-за слабого `CORS`, получает доступ к ответам.

С точки зрения API-сервера это «нормальный» запрос из браузера пользователя с валидным токеном. ***Но инициатором и потребителем данных становится чужой сайт***. Это не классический `CSRF` в виде POST-форм на другой домен, но `эффект похож`: чужой код выполняет действия и считывает данные от имени жертвы.

При анализе `REST-API` имеет смысл смотреть не только на сами эндпоинты, но и на то, какие `CORS-заголовки` сервер выставляет, особенно для эндпоинтов, которые возвращают приватную информацию.

## Как подходить к анализу REST API на практике
Если свести всё к последовательности шагов, примерно так выглядит здравый подход к анализу REST-API:
1. Сначала пытаемся понять `модель аутентификации`: как пользователь получает токен, как он его передаёт, есть ли разделение ролей. Уже здесь видно, есть ли защита от брутфорса и насколько легко злоумышленнику получить любой рабочий токен.
2. Затем переходим к `авторизации и правам`. Любой эндпоинт, где фигурирует ID ресурса, — кандидат на проверку: можно ли подставить чужой ID, можно ли вызвать «админские» функции обычным токеном, есть ли различие между ролями вообще или всё сводится к «токен есть — добро пожаловать».
3. После этого смотрим на `структуру ответов`. Мы не просто радуемся, что получили JSON, а внимательно изучаем все поля: есть ли хэши, внутренние флаги, конфиденциальная служебная информация, которая явно не нужна фронтенду.
4. Следующий слой — `поведение под нагрузкой`. Повторяем одни и те же запросы к критичным точкам и смотрим, включаются ли какие-то лимиты, блокировки, капчи, задержки. Если можно бесконечно подбирать логин и операции с токенами, это уже проблема.
5. И не забываем о `браузерном слое`: проверяем `CORS` для приватных эндпоинтов, смотрим, какие домены допущены и какие методы разрешены.

## Защита REST API: на что опираться
Чтобы `REST-API` было сложно ломать, его надо с самого начала строить с учётом нескольких принципов.

Во-первых, чёткая `авторизация на уровне объектов`. Эндпоинт не должен просто «верить» токену, он должен на каждый запрос проверять: имеет ли этот конкретный пользователь право на конкретный ресурс. Это относится и к «обычным» пользователям, и к админам.

Во-вторых, сознательная минимизация данных. `API не обязан отдавать все поля сущности`, которые есть в базе. Обычно полезно вводить отдельные «ответные» структуры: только те поля, которые реально нужны клиенту. Всё, что относится к паролям, токенам, внутренним флагам, должно оставаться внутри.

В-третьих, `лимиты и защита от автоматизации`. Для логина, подтверждений и других чувствительных действий должны быть ограничения по частоте, а в некоторых случаях — дополнительные факторы (капча, второй фактор, подтверждение по почте).

В-четвёртых, аккуратный `CORS`. Приватный API не должен быть открыт для любого Origin. Обычно у фронтенда ограниченное число доменов, и только им и нужно давать право читать ответы. Автоматическая «подстановка» `Origin` из запроса в `Access-Control-Allow-Origin` без проверки — прямой путь к проблемам.

По умолчанию браузер блокирует `AJAX‑запросы` с домена `site-a.com` на `site-b.com`. Чтобы разрешить такие запросы, сервер должен отправить специальные заголовки CORS:
* `Access-Control-Allow-Origin` — какие домены могут делать запросы;
* `Access-Control-Allow-Methods` — разрешённые HTTP‑методы;
* `Access-Control-Allow-Headers` — разрешённые заголовки;
* и другие.

### Опасная реализация автоматической подстановки `Origin` (неправильно):
```python
@app.route('/api/data')
def get_data():
    origin = request.headers.get('Origin')
    response = jsonify({'data': 'секретные данные'})
    response.headers['Access-Control-Allow-Origin'] = origin  # ОПАСНО!
    return response
```
Теперь любой сайт (evil.com, phishing‑site.net и т. д.) может сделать запрос к вашему API. Сервер автоматически копирует заголовок Origin из запроса в ответ. Браузер видит `Access-Control-Allow-Origin: evil.com` и разрешает доступ — злоумышленник получает данные.

Правильная реализация CORS
### Вариант 1. Белый список доменов
```python
ALLOWED_ORIGINS = [
    'https://trusted-frontend.com',
    'https://staging.trusted-frontend.com',
    'http://localhost:3000'  # для разработки
]
@app.route('/api/data')
def get_data():
    origin = request.headers.get('Origin')
    if origin in ALLOWED_ORIGINS:
        response = jsonify({'data': 'важные данные'})
        response.headers['Access-Control-Allow-Origin'] = origin
        return response
    else:
        # Не отправляем CORS‑заголовки — браузер заблокирует запрос
        return jsonify({'error': 'Доступ запрещён'}), 403
```
### Вариант 2. Использование библиотек 
Для `Flask` (с библиотекой flask-cors)
```python
from flask_cors import CORS
app = Flask(__name__)
CORS(app, origins=[
    'https://trusted-frontend.com',
    'https://staging.trusted-frontend.com'
])
```
Для `Node.js/Express` (с библиотекой cors):
```javascript
const cors = require('cors');
const whitelist = ['https://trusted-frontend.com'];
const corsOptions = {
  origin: function (origin, callback) {
    if (whitelist.indexOf(origin) !== -1 || !origin) {
      callback(null, true);
    } else {
      callback(new Error('Not allowed by CORS'));
    }
  }
};
app.use(cors(corsOptions));
```
### Вариант 3. Динамическая проверка (если домены меняются)
```python
def is_allowed_origin(origin):
    # Проверка по регулярному выражению
    allowed_patterns = [
        r'^https://[a-z0-9]+\.trusted-frontend\.com$',
        r'^http://localhost:\d+$'
    ]
    for pattern in allowed_patterns:
        if re.match(pattern, origin):
            return True
    return False

@app.route('/api/data')
def get_data():
    origin = request.headers.get('Origin')
    if is_allowed_origin(origin):
        response = jsonify({'data': 'данные'})
        response.headers['Access-Control-Allow-Origin'] = origin
        return response
    return jsonify({'error': 'CORS заблокирован'}), 403
```
И поверх всего этого — нормальное логирование и мониторинг: кто к каким ресурсам обращается, какие ошибки авторизации происходят, какие аномалии по частоте запросов появляются.

## Если совсем коротко: 
`REST-API` — это не «внутренняя часть для фронтенда», а полноценная внешняя граница системы. На ней живут те же `IDOR`, те же обходы прав, те же проблемы с лимитами, плюс свои особенности вроде `CORS`. Чем раньше это учитывается на этапе проектирования, тем меньше сюрпризов потом на этапе тестирования и эксплуатации.
