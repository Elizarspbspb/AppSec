# CSRF
`CSRF` (Cross-Site Request Forgery) — это атака, когда пользователь реально авторизован на сайте (у него есть рабочие куки/сессия), но его обманывают и заставляют отправить запрос на этот сайт без его осознанного согласия. В итоге сервер думает: «это сделал пользователь», а на самом деле запрос сгенерировал сайт злоумышленника.

Формула простая: `«ты авторизован → твой браузер сам подставит куки → значит, я могу заставить твой браузер сделать запрос за тебя»`.

## Проще разобраться на примере:
1. Жертва логинится в `bank.com`. Браузер сохраняет куку сессии: `session=abc123`.
2. Жертва не выходит из аккаунта (это нормально, все так делают).
3. Жертва открывает `сайт злоумышленника` или просто страницу с вредной рекламой/виджетом.
4. На странице злоумышленника есть скрытая форма или картинка/скрипт, которые отправляют запрос на `https://bank.com/transfer?to=attacker&amount=1000` (GET):
```http
GET /transfer?to=attacker&amount=1000
Cookie: session=abc123
``` 
или `POST` на тот же адрес.
```html
<form action="https://website.com/email/change" method="POST">
  <input type="hidden" name="email" value="attacker@mail.com">
</form>
<script>
  document.forms[0].submit();
</script>
```
Тогда браузер отправляет:
```http
POST /email/change HTTP/1.1
Host: website.com
Cookie: session=abc123

email=attacker@mail.com
```
5. Браузер жертвы сам прикрепляет к этому запросу куки от `bank.com`, потому что жертва там авторизована.
6. Сервер `bank.com` видит: запрос пришёл с валидной сессией → думает, что это сделал настоящий пользователь → выполняет действие (перевод, смена почты, покупка).

Другие POST:
```html
<!-- <form action="http://62.173.140.174:36102/dashboard/transfer" method="POST">-->
<form action="http://62.173.140.174:36102/transfer" method="POST">
  <select id="to" name="to">
    <option value="attacker">attacker</option>
  </select>
  <input id="amount" name="amount" type="number" step="0.01" value="11">
  <button type="submit">Отправить</button>
</form>

<script>
  document.forms[0].submit();
</script>
```

***Важный момент***: жертве не нужно кликать именно «перевести». Достаточно зайти на страницу, где это действие «тихо» от её имени отправили.

## Условия для атаки
Чтобы CSRF сработал, обычно достаточно четырех условий:
1. Действие меняет состояние: перевод, смена пароля/почты, удаление, создание заказа — то есть это не просто «посмотреть страницу», а «сделать что-то».
2. Аутентификация по кукам: `сайт определяет пользователя только по куке/сессии`, а куки браузер всегда шлёт сам.
3. Запрос предсказуемый: `злоумышленник знает URL`, метод и параметры (/transfer, /profile/change-email, /cart/checkout).
4. Сервер не ждёт в запросе энтропийный параметр, который неизвестен злоумышленнику. `Энтропийный параметр — это CSRF-токен`. Самая эффективная защита от CSRF.

Например, предположим, что в приложении есть функция, которая позволяет пользователю изменить адрес электронной почты в своей учётной записи. Когда пользователь выполняет это действие, он отправляет HTTP-запрос следующего вида:
```http
POST /email/change HTTP/1.1
Host: website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 30
Cookie: session=yvthwsztyeQkAPzeQ5gHgTvlyxHfsAfE

email=ivan@user.com
```
Это соответствует условиям, необходимым для CSRF:
* Изменение адреса электронной почты в учётной записи пользователя представляет интерес для злоумышленника. После этого злоумышленник, как правило, может сбросить пароль и получить полный контроль над учётной записью пользователя.
* Приложение использует файл cookie сеанса для определения того, какой пользователь отправил запрос. Злоумышленник может легко определить значения параметров запроса, необходимых для выполнения действия. Других токенов или механизмов отслеживания сеансов пользователей нет.

## Последствия
* Перевод денег на счёт злоумышленника.
* Смена e-mail/пароля (дальше злоумышленник может перехватить аккаунт).
* Покупка/оформление заказа от лица жертвы.
* Публикация/отправка сообщений от имени жертвы (спам уже «от доверенного пользователя»).
* Изменение настроек безопасности (например, отключение `2FA`).

То есть `CSRF` — это всегда про нежелательное действие от имени реального пользователя.

## Ключевые термины
`Межсайтовая подделка запроса` — то же самое, что CSRF: запрос уходит с другого сайта, но как будто от жертвы.

`Автоматическая отправка кук` — причина атаки: браузер по стандарту прикладывает куки к запросу на тот же домен, пользователь это не контролирует.

`Состояние` (state-changing request) — запрос, который что-то меняет на сервере. Именно их нужно защищать.

`Предсказуемый запрос` — URL и параметры можно угадать и собрать на чужом сайте.

## Как защищаться
`CSRF-токен`: токен CSRF — это уникальное, секретное и непредсказуемое значение, которое генерируется на стороне сервера и передается клиенту. В форму/запрос кладём секрет, который знает только сервер и текущая страница. Злоумышленник не может его сгенерировать. Сервер проверяет токен → нет токена или не тот → действие не выполняем.
```html
<input type="hidden" name="csrf_token" value="ABC123">
```
```http
email=test@mail.com&csrf_token=ABC123
```
Полный рабочий пример (с динамическим токеном на PHP)
```html
<?php
// Генерация CSRF-токена (упрощённо)
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}
?>
<form method="post" action="/process-payment">
  <label for="amount">Сумма:</label>
  <input id="amount" name="amount" type="number" step="0.01" value="11" required>
  <!-- Скрытое поле с динамически сгенерированным токеном -->
  <input type="hidden" name="csrf_token" value="<?php echo htmlspecialchars($_SESSION['csrf_token']); ?>">
  <button type="submit">Оплатить</button>
</form>
```

`SameSite` у кук: `SameSite` — это механизм безопасности браузера, который определяет, когда файлы cookie веб-сайта включаются в запросы, отправляемые с других веб-сайтов. Поскольку для выполнения конфиденциальных действий обычно требуется файл cookie сеанса с аутентификацией, соответствующие ограничения `SameSite` могут помешать злоумышленнику выполнить эти действия на другом сайте. Ставим кукам атрибут `SameSite=Lax` или `Strict`, чтобы они не уходили с чужих сайтов (помогает против простых CSRF).

В конфигурации приложения Python (Flask):
```python
app.config.update(
    SESSION_COOKIE_SAMESITE='Lax',
    SESSION_COOKIE_HTTPONLY=True,
    SESSION_COOKIE_SECURE=True  # HTTPS
)
```
После настройки сервер будет отправлять заголовок вида:
```http
Set-Cookie: session_id=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```
`HTTPS` обязателен для `Secure` и `SameSite=None`. На `HTTP` атрибут `SameSite` может игнорироваться браузерами.

Проверка `Origin/Referer`: некоторые приложения используют HTTP-заголовок `Referer` для защиты от CSRF-атак, если запрос на изменение приходит не с нашего домена — отклоняем.
