# Docker
`Docker` в этом уроке рассматривается с точки зрения специалиста по безопасной разработке: как удобный инструмент для управления окружениями и одновременно как источник новых рисков, если с ним обращаться невнимательно.

## Docker на простом примере
Представьте обычное веб-приложение: код, зависимости, интерпретатор, системные библиотеки, конфигурация. На машине разработчика оно работает, а на сервере - нет: другая версия Python, отсутствует нужная библиотека, отличающийся дистрибутив.

`Docker` решает именно эту проблему. Мы один раз описываем окружение в специальном файле `Dockerfile`, собираем из него образ, а дальше запускаем из этого образа контейнеры на любой машине, где установлена Docker-платформа. 

`Контейнер` в этом смысле - это обычный процесс операционной системы, но:
* с собственной «упакованной» файловой системой (образом),
* с ограниченным доступом к ресурсам,
* с отдельной сетевой и процессной «картиной».

Для безопасной разработки это даёт два важных эффекта: окружения становятся воспроизводимыми, а границы между сервисами - более чёткими, но при этом нужно понимать, что контейнер - не полноценная виртуальная машина.

## Контейнер и виртуальная машина: где проходит граница
`Виртуальная машина` запускает отдельную гостевую операционную систему со своим ядром поверх гипервизора. `Контейнер`, наоборот, использует ядро хостовой системы и опирается на механизмы изоляции в самом ядре Linux.

Чтобы понимать модель безопасности `Docker`, полезно назвать по имени два ключевых механизма:
1. `Namespaces` - это «пространства имён» в ядре, которые разделяют видимость ресурсов.

Процесс внутри контейнера видит свои `PID` (идентификаторы процессов), свои сетевые интерфейсы, свою файловую иерархию монтирования. Для него создаётся отдельное пространство для процессов, сети, точек монтирования и других сущностей. Благодаря этому контейнеру кажется, что он работает «на отдельной машине», хотя на самом деле это не так.

2. `cgroups` (control groups) - механизм управления ресурсами.

С его помощью ядро ограничивает использование процессорного времени, памяти, дискового ввода-вывода и других ресурсов отдельными группами процессов. Контейнер можно ограничить, чтобы он не мог, например, занять всю память хоста.

Вместе `namespaces` и `cgroups` создают изоляцию по видимости и по ресурсам. Однако ядро всё равно общее. Это означает, что уязвимость в ядре или чрезмерные привилегии контейнера могут привести к выходу за пределы контейнера. В этом смысле изоляция Docker объективно слабее, чем у виртуальной машины, и её нельзя воспринимать как «железную стену».

## Ключевые компоненты Docker
Чтобы уверенно разговаривать о безопасности Docker, важно понимать базовые понятия: `Dockerfile`, `образ`, `контейнер`, `Docker Daemon` и `Docker Hub`.

### Dockerfile
`Dockerfile` - это сценарий сборки образа. В нём описывается, из какого базового окружения мы стартуем, какие пакеты и зависимости устанавливаем, какой пользователь будет выполнять приложение внутри контейнера и какую команду запустить по умолчанию.

Пример простого `Dockerfile` для Python-приложения:
```docker
# Базовый образ с минимальной ОС и Python
FROM python:3.12-slim
# Рабочая директория внутри контейнера
WORKDIR /app
# Копируем файл с зависимостями
COPY requirements.txt .
# Устанавливаем зависимости без использования кэша
RUN pip install --no-cache-dir -r requirements.txt
# Копируем исходный код приложения
COPY . .
# Запускаем процессы от непривилегированного пользователя
USER nobody
# Команда по умолчанию: запуск приложения
CMD ["python", "app.py"]
```
Важно, что из такого файла хорошо видны ключевые моменты с точки зрения безопасности:
* строка `FROM` показывает, какой базовый образ используется и насколько он современен и доверен;
* через `RUN` становится ясно, какие системные зависимости и библиотеки устанавливаются внутрь образа;
* инструкция `USER` явно задаёт непривилегированного пользователя, вместо того чтобы запускать всё от `root`;
* обращает на себя внимание, какие файлы мы копируем внутрь (сюда не должны попадать секреты, файлы с ключами или временные артефакты).

`Dockerfile` - основной артефакт, по которому специалист по безопасной разработке может понять, из чего вообще состоит контейнерное окружение.

Еще пример. Создайте файл `Dockerfile` в папке проекта (команда одинакова для Linux и Windows):
```bash
touch Dockerfile  # Linux
type nul > Dockerfile  # Windows (в командной строке)
notepad Dockerfile  # открыть в редакторе Windows
```
Пример содержимого `Dockerfile` (универсальный):
```dockerfile
FROM ubuntu:20.04
RUN apt-get update && apt-get install -y python3
COPY app.py /app/app.py
WORKDIR /app
CMD ["python3", "app.py"]
```

### Образ (image)
`Образ` - это результат сборки по `Dockerfile`. Его можно представить как многослойную файловую систему плюс метаданные (базовый образ, команда запуска, пользователь и т.д.). Образ неизменяем: при запуске контейнера поверх образа добавляется слой записи, куда попадают изменения времени запуска.

Один и тот же образ можно:
* запускать несколько раз (создавая несколько контейнеров),
* переносить между машинами,
* хранить в реестрах.

С точки зрения безопасности образ - это сразу и упаковка зависимостей, и потенциальный «контейнер» уязвимостей, если в него попали старые библиотеки или конфиги.

Сборка `образа` из `Dockerfile` на Linux/Windows (командная строка и PowerShell):
```bash
docker build -t my-python-app .
```
* `-t` — задаёт тег (имя) образа;
* `точка в конце` — указывает на текущую директорию как контекст сборки.

Просмотр собранных `образов` Linux/Windows:
```bash
docker images
```
или
```bash
docker image ls
```

### Контейнер
`Контейнер` - это запущенный экземпляр `образа`. Это уже живой процесс в системе:
* у него есть собственный идентификатор,
* он может быть запущен, остановлен, удалён,
* к нему можно «подключать» тома, сетевые настройки, переменные окружения.

`Контейнер` - это то, что непосредственно взаимодействует с внешним миром: слушает порты, обрабатывает запросы, читает и пишет данные в примонтированные каталоги.

1. Запуск контейнера из существующего образа:
```bash
docker run -d --name my-container my-python-app
```
* `-d` — запуск в фоновом режиме (detached);
* `--name` — задание имени контейнера.

С пробросом портов:
```bash
docker run -d -p 8080:80 --name web-server nginx
```
* `-p 8080:80` — проброс порта хоста 8080 на порт контейнера 80.

2. Просмотр запущенных контейнеров Linux/Windows:
```bash
docker ps
```
Для просмотра всех контейнеров (включая остановленные):
```bash
docker ps -a
```
3. Остановка контейнеров:
```bash
docker stop my-container
```
Принудительная остановка контейнеров:
```bash
docker kill my-container
```
Удаление контейнеров:
```bash
docker rm my-container
```
Удаление всех остановленных контейнеров:
```bash
docker container prune
```
4. Запуск интерактивной оболочки:
```bash
docker exec -it my-container bash
```
Просмотр логов:
```bash
docker logs my-container
```
Просмотр использования ресурсов:
```bash
docker stats my-container
```
5. Работа с томами (volumes)

Создание тома:
```bash
docker volume create my-data
```
Запуск контейнера с томом:
```bash
docker run -v my-data:/data --name container-with-volume my-python-app
```
6. Работа с сетями

Просмотр сетей:
```bash
docker network ls
```
Создание сети:
```bash
docker network create my-network
```
Запуск контейнера в сети:
```bash
docker run --network my-network --name container-in-network my-python-app
```

### Docker Engine и Docker Daemon
`Docker Engine` - реализация серверной и клиентской части Docker. 

`Docker Daemon` (dockerd) - фоновый процесс, который принимает команды (например, через `docker run`, `docker build`), управляет образами, контейнерами, сетями и томами.

Доступ к `Docker Daemon` следует воспринимать как доступ к управляющему центру. Если кто-то может выполнять команды `Docker` на хосте, он может:
* запускать контейнеры с любыми правами,
* монтировать файловую систему хоста внутрь контейнера,
* читать и изменять данные других контейнеров.

Это критичная точка с точки зрения угроз.

### Docker Hub и другие реестры
`Docker Hub` - публичный реестр образов по умолчанию. Там размещаются как официальные образы (поддерживаемые вендорами или сообществом), так и пользовательские. Кроме него существуют частные и корпоративные реестры.

Для безопасности важно:
* понимать происхождение базовых образов,
* различать официальные (поддерживаемые) и случайные,
* не использовать неизвестные образы без проверки.

1. Авторизация в Docker Hub Linux/Windows:
```bash
docker login
```
Введите логин и пароль Docker Hub.

2. Отправка образа в реестр. Сначала пометьте образ:
```bash
docker tag my-python-app username/my-python-app:latest
```
Затем отправьте:
```bash
docker push username/my-python-app:latest
```
3. Загрузка образа из реестра
```bash
docker pull nginx:latest
```

## Полезные свойства Docker для безопасной разработки
Если смотреть на Docker как на инструмент, а не только как на источник рисков, он даёт несколько значимых преимуществ.

**Во-первых, изоляция сервисов**. Приложение можно разделить на компоненты (веб-сервер, база данных, очередь сообщений) и запускать каждый в отдельном контейнере. При этом сеть между ними можно явно описывать и ограничивать, а файловые системы разделять. В результате компрометация одного компонента не обязательно автоматически даёт доступ к остальным.

**Во-вторых, воспроизводимость окружений**. Один и тот же `Dockerfile` превращается в один и тот же образ, а из него - в предсказуемое окружение на разных машинах. Это важно и для тестов, и для анализа уязвимостей: то, что нашли в тестовом окружении, можно воспроизвести в другом месте без «магии» настройки.

**В-третьих, прозрачное управление зависимостями**. Все системные библиотеки и версии приложений описаны явно и лежат внутри образа. Это облегчает:
* инвентаризацию компонентов,
* применение сканеров образов на наличие уязвимых пакетов,
* планирование обновлений.

## Основные угрозы и типичные ошибки при использовании Docker
Преимущества Docker не отменяют того, что при неосторожной конфигурации контейнерная среда становится хорошей площадкой для атаки. Ниже - ключевые направления рисков.

### Устаревшие и уязвимые базовые образы
Если базовый образ не обновляется, он в буквальном смысле консервирует в себе старые версии библиотек и системных компонент. Например, в `Dockerfile` указан образ старой версии дистрибутива или интерпретатора, и он годами используется без пересборки.

Последствия очевидны: известные уязвимости в системных библиотеках, серверных компонентах и интерпретаторах автоматически распространяются во все окружения, где этот образ используется.

Практика безопасной работы с образами включает:
* выбор минимальных и поддерживаемых базовых образов (официальные образы языков и ОС),
* регулярную пересборку образов с актуальными обновлениями,
* встроенный в процесс разработки и CI скан уязвимостей в образах.

### Избыточные привилегии контейнеров
Одна из самых опасных ошибок - запуск контейнера с чрезмерными правами. Это проявляется двумя характерными способами:
* использование флага `--privileged`, который даёт контейнеру максимально возможные права на уровне ядра и доступа к устройствам;
* выполнение процессов внутри контейнера от root-пользователя по умолчанию, без смены пользователя.

Здесь важно понимать ещё одно понятие - `Linux capabilities`. В Linux набор действий, которые может выполнять суперпользователь, разделён на отдельные «способности». Приложению или контейнеру можно дать лишь часть из них. Если этого не делать и запускать всё от root с полным набором capabilities, то любой успешный захват контейнера резко увеличивает риск выхода на хост.

Базовые рекомендации для снижения рисков:
* избегать `--privileged`, использовать его только в специализированных служебных контейнерах и с полным пониманием последствий;
* в `Dockerfile` задавать непривилегированного пользователя (USER), а на уровне запуска контейнера не поднимать лишние привилегии;
* по возможности уменьшать набор доступных `capabilities`, оставляя только действительно необходимые.

### Компрометация Docker Daemon
`Docker Daemon` - сердце контейнерной инфраструктуры. На Linux он обычно слушает Unix-сокет `/var/run/docker.sock`, иногда - TCP-порт.

Любой пользователь или процесс, который может обращаться к этому сокету или открытым портам демона, получает практически полный контроль над:
* запуском и остановкой контейнеров,
* их параметрами и привилегиями,
* монтированием файловых систем хоста внутрь контейнеров.

Это делает `Docker Daemon` критической точкой защиты. Особенно опасны практики, когда сокет `docker.sock` монтируют внутрь контейнера для «удобства» автоматизации: компрометация такого контейнера даёт атакующему прямой доступ к управлению всей машиной.

Надёжный базовый подход:
* ограничивать круг пользователей, имеющих доступ к `Docker Daemon`, и контролировать `membership` в группе `docker`;
* не монтировать сокет демона в контейнеры без крайней необходимости;
* при сетевом доступе к демону обязательно включать шифрование и аутентификацию (TLS).

**Итог**

`Docker` - мощная платформа для контейнеризации, которая для специалиста по безопасной разработке одновременно является:
* инструментом для воспроизводимых и управляемых окружений,
* средством изоляции сервисов и управления зависимостями,
* дополнительной поверхностью атаки, требующей осознанной защиты.

Ключевые практики - понимать, как на самом деле устроена изоляция контейнеров, уметь читать и оценивать `Dockerfile`, работать с образами и базовыми образами как с потенциальными источниками уязвимостей, минимизировать привилегии контейнеров и серьёзно относиться к защите `Docker Daemon` и данным, которые через Docker проходят.
