# XSStrike
Переходим от SQL-инъекций к XSS-инструментам. Здесь нам нужен «аналог sqlmap, но для XSS» - и эту роль хорошо закрывает XSStrike.

## Что такое XSStrike
`XSStrike` — это инструмент на Python для автоматизированного поиска уязвимостей типа `Cross-Site Scripting (XSS)` в веб-приложениях. Он анализирует, как данные пользователя попадают в `HTML` и `JavaScript`, и пытается подобрать рабочие полезные нагрузки (payload’ы), учитывая контекст и фильтры.

В отличие от «общих» сканеров уязвимостей, `XSStrike` сознательно ограничен одной задачей — `XSS`, но решает её максимально глубоко.

## Чем XSStrike отличается от обычных XSS-сканеров
Ключевые особенности:
* Узкая специализация. `XSStrike` ориентирован именно на `XSS`: отражённый (`Reflected`), `DOM-XSS`, частично может помочь обнаружить хранимый (`Stored`), если проверить соответствующие точки.
* Контекстный анализ. Инструмент не просто подставляет готовый список строк. Он смотрит:
    * где именно появляется значение параметра (в тексте, атрибуте, JavaScript-строке и т.п.);
    * какие символы фильтруются или экранируются.

На основе этого строятся полезные нагрузки, подходящие для данного контекста.

* Обход фильтров и простых `WAF`. Внутри уже есть набор приёмов и полезных нагрузок, рассчитанных на типичные фильтры.
* Гибкость по источникам данных. `XSStrike` умеет работать с параметрами:
    * GET (строка запроса),
    * POST (в том числе JSON),
    * Cookie,
    * заголовки (Headers),
    * частью пути в URL.

## Общий принцип работы XSStrike
На концептуальном уровне `XSStrike` действует так:
1. Получает от вас исходный запрос:
* `URL` с параметрами;
* или `URL` + тело `POST`;
* при необходимости — свои заголовки и cookie.
2. Отправляет тестовые значения в выбранные параметры и анализирует ответ:
* где в `HTML/JavaScript` отражается это значение;
* в каком контексте оно находится (текст, атрибут, скрипт и т.п.);
* какие символы проходят, а какие фильтруются.
3. На основании этого подбирает полезные нагрузки, которые:
* разрывают опасный контекст (например, выход из атрибута или строки);
* обходят фильтрацию;
* в результате приводят к выполнению `JavaScript-кода`.
4. При включённом автоматическом обходе сайта может:
* переходить по ссылкам,
* собирать формы,
* проверять новые точки ввода на XSS.

**Важно**: результаты `XSStrike` всегда требуют ручной проверки. Это мощный помощник, но не заменяет анализ безопасности человеком.

**ВИДЕО**

## Когда имеет смысл использовать XSStrike
Практически `XSStrike` стоит применять:
* после первоначальной разведки (Burp, ручная проверка), когда вы уже нашли:
    * параметры, значение которых отражается в ответе;
    * подозрительные участки `DOM`;
    * когда простые `XSS`-payload’ы не проходят или искажаются фильтрами;
* когда нужно:
    * провести более глубокую проверку XSS в конкретных эндпоинтах;
    * автоматически проверить набор страниц и форм на наличие XSS;
    * протестировать фильтры/веб-экраны (WAF) на пропуск XSS-конструкций.

## Ограничения XSStrike
Несмотря на продвинутую логику, это всё равно автоматизированный инструмент:
* возможны ложные срабатывания, особенно при автоматическом обходе сайта (обнаруженные точки лучше перепроверять точечным сканированием);
* инструмент не видит бизнес-контекст и не всегда понимает сложные сценарии во «внутреннем» интерфейсе (SPA, многошаговые действия);
* при агрессивных режимах может создавать заметную нагрузку на приложение.

## Практические примеры использования
1. Проверка одного GET-параметра

Проверяем параметр `q` в строке поиска:
```
python3 xsstrike.py -u "http://example.com/search.php?q=test"
```
`XSStrike` попробует:
* выяснить, где и как отражается `q`;
* подобрать рабочие XSS-полезные нагрузки для этого контекста.

2. Проверка POST-параметра

Форма отправляет запрос методом POST:
```
python3 xsstrike.py -u "http://example.com/search.php" --data "q=test"
```
Здесь:
* `-u` — адрес обработчика формы;
* `--data` — тело POST-запроса.

`XSStrike` внедряет свои значения вместо `test` и анализирует ответ.

3. Проверка JSON-запроса (например, REST API)

Если приложение принимает `JSON`:
```
python3 xsstrike.py -u "http://example.com/api/search" --data '{"q":"test"}' --json
```
Флаг `--json` сообщает, что данные в `--data` — JSON-структура. Инструмент корректно выделяет параметр `q` и тестирует его.

4. Автоматический обход сайта и поиск `XSS`

Чтобы не запускать `XSStrike` по каждому адресу вручную, можно указать стартовый URL и разрешить обход ссылок:
```
python3 xsstrike.py -u "http://example.com" --crawl -l 2
```
Здесь:
* `--crawl` — включить автоматический переход по ссылкам и анализ форм;
* `-l 2` — глубина обхода (насколько «глубоко» заходить по переходам от начальной страницы).

`XSStrike` будет находить новые адреса и формы, отправлять туда тестовые значения и отмечать потенциальные XSS.

Таблица основных флагов `XSStrike`

|||
|---|---|
|Флаг|Назначение|
|`-u, --url`|Целевой URL. Пример: -u "http://example.com/page.php?q=test"|
|`--data`|Тело POST-запроса (application/x-www-form-urlencoded). Пример: --data "q=test&cat=1"|
|`--json`|Сообщает, что данные в --data — JSON. Пример: --data '{"q":"test"}' --json|
|`--path`|Тестирование части пути URL (а не только строки запроса).|
|`--crawl`|Автоматический обход сайта: переход по ссылкам, сбор форм и проверка новых точек на XSS.|
|`-l`, `--level`|Глубина обхода при `--crawl` (по умолчанию 2). Чем больше, тем глубже и дольше проверка.|
|`--seeds`|Файл со списком стартовых адресов, которые нужно проверить или использовать как точки входа.|
|`-f`, `--file`|Использовать внешний файл с полезными нагрузками вместо встроенной логики анализа контекста.|
|`-t`, `--threads`|Количество параллельных потоков (запросов). Ускоряет проверку, но может заметно нагружать приложение.|
|`--headers`|Задание собственных HTTP-заголовков (например, из Burp). Удобно для учётных данных и токенов.|
|`--blind`|Режим вставки заранее заданного `blind-XSS` payload во все найденные формы (в связке с собственным коллбэк-сервером).|
|`--fuzzer`|Режим фаззинга фильтров/`WAF`: последовательная проверка различных вариантов XSS-конструкций. Медленный, но полезный для анализа защиты.|
|`--params`|Нахождение скрытых параметров|


Таким образом, `XSStrike` хорошо подходит для того, чтобы:
* системно проверить веб-приложение на `XSS`-уязвимости;
* особенно — в сложных контекстах и при наличии фильтров;
* а потом уже вручную оценить найденные точки с точки зрения реальной эксплуатации и критичности.

## Устанвока
Сначала вам нужно будет клонировать его из репозитория git:
```
$ git clone https://github.com/s0md3v/XSStrike.git
```
Затем перейдите в каталог `XSStrike` и установите требования:
```
$ cd XSStrike
$ pip install -r requirements.txt
```
Чтобы запустить `XSStrike`:
```
$ python xsstrike.py
```
Использование: чтобы вывести список всех доступных аргументов, введите `--help`.

```
http://62.173.140.174:36115/?q=<D3v%0aonpOInterEnTER%0d=%0d[8].find(confirm)%0dx//v3dm0s>
```
Получает ответ. Допустим, сервер возвращает:
```html
<div>Результат поиска: <D3v onpOInterEnTER=[8].find(confirm) x//v3dm0s></div>
```
Анализирует:
* тег `<D3v>` сохранился;
* событие `onpOInterEnTER` не удалено;
* код `[8].find(confirm)` на месте;
* маркер `v3dm0s` присутствует.

Считает: 4 из 4 элементов → `Efficiency = 100%` (в вашем случае 92–94 %).  
Проверяет контекст: тег внутри `<div>` → может сработать при наведении курсора (событие `onpointerenter`).  
Выставляет `Confidence = 10`, так как все условия для `XSS` выполнены.

Краткий итог
* `92–94 % Efficiency` = сервер почти не фильтрует ваш ввод.
* `Confidence 10` = XSStrike уверен, что это реальная уязвимость, а не ложное срабатывание.
* Что делать: подтвердите вручную через `alert(1)` и устраните проблему на сервере (экранирование вывода, CSP).

`[~] Checking for DOM vulnerabilities` - инструмент проверяет, есть ли уязвимости в `DOM` (Document Object Model) — то есть возможность выполнить `JavaScript` через манипуляции с DOM‑элементами на стороне клиента (document.write(), eval(), innerHTML, setTimeout()). Если уязвимость найдена, `XSStrike` добавит DOM‑специфичные payload’ы. Если нет — сосредоточится на классических XSS.

`[+] WAF Status: Offline` - WAF (Web Application Firewall) не обнаружен. XSStrike отправил «подозрительные» запросы (например, с `<script>` или SQL‑инъекциями) и проанализировал ответы. Отсутствие `WAF` повышает шансы на успешную эксплуатацию уязвимости, так как нет активного фильтра, блокирующего вредоносные запросы.

`[!] Reflections found: 3` - сервер «отражает» (возвращает) пользовательский ввод в ответе 3 раза. Если отправить `$q=test$`, сервер может вернуть HTML, содержащий test в трёх местах:
```html
    <h1>Поиск по запросу: test</h1>
    <p>Найдено результатов: 0 для запроса "test"</p>
    <input type="text" value="test">
```
Чем больше отражений, тем выше шанс, что хотя бы одно из них окажется в уязвимом контексте. Каждое отражение — потенциальная точка для `XSS`.

`[~] Analysing reflections` - XSStrike детально изучает каждое место, где найден отражённый ввод. Цель определить, какие техники и payload’ы наиболее эффективны для каждого отражения.

`[~] Generating payloads` - создание набора payload’ов, оптимизированных под конкретный случай.

`[!] Payloads generated: 4608` - итоговый набор из 4 608 уникальных payload’ов готов к тестированию. XSStrike комбинирует разные теги (`<script>`, `<img>`, `<svg>`, `<body>`, `<a>`); разные события (`onload`, `onerror`, `onmouseover`, `onpointerenter`); разные методы вызова JS (`alert()`, `prompt()`, `confirm()`, `[8].find(alert)`); разные кодировки (URL‑encoding, Unicode, Hex); обфускацию регистра (`<ScRiPt>`); способы обхода фильтров (пробелы, табуляция, комментарии `//`). 

Цель - максимизировать шанс найти хотя бы один payload, который пройдёт через все фильтры и выполнится в браузере жертвы.
