# Свои правила nuclei
## Зачем нужны свои правила
Стандартные шаблоны `nuclei` и встроенные правила `ZAP` покрывают массу типовых уязвимостей. Но в реальной жизни быстро появляются ситуации, когда этого недостаточно:
* у вас своя типовая ошибка в архитектуре (например, специфичный способ хранить файлы или токены);
* вы нашли баг в одном сервисе и хотите проверить всю инфраструктуру на такой же паттерн;
* появился новый CVE, под который ещё нет шаблона, а проверять нужно уже сейчас;

`Кастомное правило` — это по сути «упакованный опыт»: один раз формализовали логику проверки, а дальше она работает на всех стендах и сервисах, каждый раз одинаково.

## Кастомные шаблоны nuclei
У `nuclei` всё завязано на шаблон: вы уже знаете, как он устроен, поэтому вместо теории — сразу к практическим примерам.

### От найденной LFI к шаблону nuclei
Представим, что при ручном тестировании ты нашёл типичный `path traversal` / `LFI`.

Есть эндпоинт:
```
GET /download?file=report.pdf HTTP/1.1
Host: vulnerable.local
```
Приложение скачивает файлы из некоторой директории. Ты пробуешь изменить параметр:
```
GET /download?file=../../etc/passwd HTTP/1.1
Host: vulnerable.local
```
и в ответе видишь знакомые строки:
```
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
```
Это ручное подтверждение `LFI`. Теперь задача — превратить это в шаблон `nuclei`, чтобы:
* проверить остальные хосты на такую же проблему;
* не повторять каждый раз ручные шаги.

**Шаг 1. Зафиксировать ручной запрос и признаки**

Нам нужно минимум:
* URL и параметр: `/download?file=;`
* полезная нагрузка: `../../etc/passwd` (можно сразу взять URL-кодированный вариант);
* признаки успеха в ответе:
  * наличие строки root❌0:0;
  * желательно код ответа 200.

**Шаг 2. Перенести это в YAML-шаблон**

Простой рабочий шаблон:
```
id: custom-lfi-etc-passwd
info:
  name: Custom LFI /etc/passwd via file parameter
  author: internal-security-team
  severity: high
  description: >
    Проверка локального включения файлов через параметр file и чтения /etc/passwd.
http:
  - method: GET
    path:
      - "{{BaseURL}}/download?file=..%2f..%2fetc%2fpasswd"
    matchers-condition: and
    matchers:
      - type: word
        part: body
        words:
          - "root:x:0:0"
      - type: status
        status:
          - 200
```

Что здесь практично:
* полезная нагрузка сразу URL-кодирована, чтобы совпадать с реальными запросами;
* matchers-condition: and — требуем одновременно и код 200, и характерную строку в теле;
* описание говорит, что именно проверяется (LFI через file и доступ к /etc/passwd).

**Шаг 3. Проверка шаблона**

Дальше:
* запускаешь `nuclei` по тестовому хосту, где уязвимость точно есть;
* убеждаешься, что шаблон срабатывает;
* запускаешь по «чистому» тестовому хосту (без LFI) и проверяешь, что срабатываний нет.

Если на чистом стенде появляются ложные срабатывания (например, где-то в ответе случайно встречается строка `root❌0:0`), усложняешь условия: можно добавить проверку `Content-Type`, уменьшить область поиска (не весь body, а только некоторые части), добавить дополнительные слова-«якоря».

Идея здесь простая:
* вы зашили конкретный вектор: `..%2f..%2fetc%2fpasswd;`
* явно указали целевой параметр (file в примере);
* в `matchers` проверяете наличие строки, характерной для `/etc/passwd` (root❌0:0).

Такой шаблон удобно переносить между проектами, где используется одинаковый паттерн «`загрузки/скачивания»` файлов. Если в другом сервисе путь к обработчику другой, меняете только `path`, остальное остаётся тем же.

***Важно: этот пример намеренно упрощён.*** В боевом шаблоне вы бы:
* описали несколько вариантов путей и параметров,
* возможно, добавили `status-matcher` (ожидаемый код ответа),
* ограничили применение шаблона по доменам/тегам.

Но принцип остаётся: запрос + признак, упакованные в YAML.

### Практика: nuclei-шаблон с извлечением секретов
Второй пример — не «есть/нет уязвимости», а извлечение потенциально чувствительных данных.

**matchers** отвечают на вопрос: "Есть ли проблема?"

**extractors** отвечают на вопрос: "Какое конкретно значение нужно вытащить из ответа?"

Пусть есть внутренний сервис, который в некоторых ответах по ошибке возвращает JSON с полями вида:
```json
{
  "user": "alice",
  "api_token": "abc123-secret-value",
  "role": "admin"
}
```
Ручной поиск по логам и ответам показывает, что встречаются паттерны вроде:
* token: "...",
* secret = "...",
* key: '...'.

Задача — вынести это в шаблон `nuclei`, чтобы:
* автоматически искать такие поля на разных сервисах;
* сразу собирать значения в extracted-results.

Фрагмент шаблона:
```
id: custom-secret-leak

info:
  name: Potential secret leak in JSON/HTML
  author: internal-security-team
  severity: medium
  description: >
    Поиск возможных секретов по ключевым словам: secret, key, token.

http:
  - method: GET
    path:
      - "{{BaseURL}}"

    matchers:
      - type: regex
        part: body
        regex:
          - "(?i)(secret|key|token)[\"']?\\s*[:=]\\s*[\"']([^\"']+)"

    extractors:
      - type: regex
        part: body
        regex:
          - "(?i)(secret|key|token)[\"']?\\s*[:=]\\s*[\"']([^\"']+)"
        group: 2
```
Что делает эта конструкция:
* `(?i)` — регистронезависимый поиск (Secret, SECRET, token и т.д.);
* `(secret|key|token)` — ключевые слова, которыми часто называют секреты;
* `[\"']?\s*[:=]\s*[\"']` — допуски в оформлении (secret = "...", token:"..." и т.п.);
* `([^\"']+)` — собственно значение между кавычками, которое попадает в группу.

Если такой `extractor` добавить в шаблон, `nuclei` будет:
* не только сигнализировать о совпадении,
* но и сохранять найденные значения в `extracted-results`.

На практике это удобно, например, для внутренних проверок конфигурации: можно быстро увидеть, не утекли ли в ответах какие-то ключи/токены. При этом важно договориться, как хранить такие отчёты (доступ к ним должен быть ограничен, потому что они уже сами по себе могут содержать чувствительные данные).

Практические моменты:
* один и тот же паттерн используется и для `matcher’а`, и для `extractor’а`;
* в `extractors` указан `group: 2`, чтобы `nuclei` вытаскивал именно значение (без слова token и без разделителей);
* в описании явно сказано, что это только индикатор возможной утечки, а не гарантированная уязвимость.

## Кастомные правила ZAP: активные, пассивные, auth
У `ZAP` механизм другой: там нет YAML-шаблонов, но есть понятие **активных** и **пассивных правил** сканера, а также скриптов, связанных с аутентификацией. Их обычно пишут как скрипты (JavaScript, Python и др.) или встраивают как расширения.

Смысл можно свести к трём группам.

### Пассивные правила
`Пассивное правило` ничего не отправляет от себя, оно анализирует уже проходящий трафик. Например, вы хотите найти в ответах те же потенциальные секреты, что и в примере с `nuclei`.

Логика пассивного правила:
* получать каждый HTTP-ответ;
* проверять `Content-Type`, `размер` и `контекст` (например, не анализировать большие бинарные файлы);
* применять к телу ответа регулярное выражение (тот же паттерн для secret|key|token);
* если есть совпадения — поднимать алерт с указанием URL и коротким фрагментом.

Такое правило не ломает функционал приложения и позволяет постоянно мониторить утечки конфиденциальных фрагментов в HTML, JSON, debug-выводах и т.д.

### Активные правила
Активное правило, наоборот, специально модифицирует запросы и смотрит на реакцию сервера. Оно ближе по духу к шаблонам `nuclei`.

Например, вы хотите встроить в `ZAP` аналог проверки `path traversal`:
* правило перехватывает исходный запрос с параметром file;
* формирует несколько вариантов значения: `../../etc/passwd`, URL-кодированный вариант и т.п.;
* отправляет модифицированные запросы;
* анализирует ответы на наличие характерных строк (root❌0:0 и др.);
* при успехе поднимает алерт с указанием оригинального запроса, модификации и «доказательства».

Это то же самое, что шаблон `nuclei`, но работает уже внутри процесса прокси-сканера ZAP, с учетом контекста сессии, авторизации и прочего.

## Auth-скрипты и связанные правила
Отдельная категория — скрипты, связанные с аутентификацией и проверкой авторизации. Они позволяют:
* автоматизировать логин в приложении;
* отслеживать, когда сессия истекла или сломалась;
* проверять доступность определённых URL как у авторизованного, так и у неавторизованного пользователя.

На основе этого можно делать свои проверки «обхода прав»: например, скрипт, который для каждой «закрытой» страницы пробует открыть её без куки или с куки другого пользователя и фиксирует случаи, когда доступ всё равно разрешён.

## Организация репозитория правил
Когда правил становится больше трёх–пяти, держать их «каждый в своей папке» быстро перестаёт работать. Проще всего сразу завести отдельный репозиторий (или каталог в основном репозитории) под все кастомные правила.

Предлагаемая структура:
```
custom-rules/
├── zap/
│   ├── active/
│   ├── passive/
│   └── auth/
├── nuclei/
│   ├── cves/
│   ├── exposures/
│   └── custom/
└── tests/
    └── test-targets.txt
```
Идея:
* `zap/active` — скрипты активных правил ZAP (отдельно по типам уязвимостей, если нужно);
* `zap/passive` — пассивные правила;
* `zap/auth` — скрипты для аутентификации и проверок прав;
* `nuclei/cves` — ваши шаблоны под конкретные CVE, которые важны именно вам;
* `nuclei/exposures` — свои проверки экспозов (учитывающие особенности инфраструктуры);
* `nuclei/custom` — всё остальное: проверки внутренних паттернов, бизнес-логики, специфичных багов;
* `tests/test-targets.txt` — список целей (локальные стенды, демо-приложения), на которых правила можно безопасно прогонять в автоматическом режиме.

## Проверка синтаксиса и простых ошибок
**Для `nuclei`** есть встроенная проверка:
```
nuclei -validate -t nuclei/
```
Она позволяет поймать:
* синтаксические ошибки в YAML;
* отсутствующие обязательные поля;
* базовые несоответствия структуре.

**Для `ZAP`-скриптов** можно использовать:
* встроенные средства проверки в самом ZAP (запуск в тестовом режиме);
* линтеры для языка (JavaScript, Python);
* небольшие утилиты, которые проверяют наличие нужных полей/метаданных в каждом скрипте.

## Метрики эффективности правил
Чтобы правила не превращались просто в «коллекцию скриптов», а реально работали, полезно следить за несколькими показателями.

### True Positive / False Positive
Проще всего считать:
* сколько срабатываний правила в итоге подтверждаются как реальные уязвимости;
* сколько отменяются как ложные.

Если правило даёт много `FP`, его нужно дорабатывать: уточнять matchers, добавлять контекст (статусы, заголовки), ограничивать область применения.

### Покрытие бизнес-логики
Технические правила — это хорошо, но отдельно стоит смотреть, как кастомные правила покрывают именно вашу бизнес-логику:
* есть ли правила под типовые критичные операции (платежи, изменение прав, экспорт данных);
* есть ли правила, проверяющие уже найденные ранее уязвимости, чтобы не поймать их снова через год.

***Здесь удобно вести небольшую карту: «функция → какие правила её хотя бы частично покрывают».***
