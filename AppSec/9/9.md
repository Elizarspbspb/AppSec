### Короткое напоминание
Мы уже прошли `Reflected XSS` (вредный ввод приходит в запросе и сразу «отражается» сервером в ответ) и `Stored XSS` (вредный ввод сохраняется на сервере и срабатывает у всех, кто видит «заражённый» контент). Теперь — `DOM XSS`: уязвимость живёт в браузере в клиентском JavaScript.

# DOM
`DOM` (Document Object Model) — это «дерево» страницы в браузере. Каждый тег — узел дерева (`<div>`, `<span>`, `текст` и т.д.). Скрипт может читать/менять это дерево: добавлять элементы, менять текст, подставлять куски HTML. Когда мы говорим `«вставить в DOM»` — это значит изменить страницу прямо в браузере пользователя.

## Что такое DOM XSS
`DOM XSS` возникает, когда скрипт на странице берёт пользовательский ввод из браузера — это источник (source: `location.search`, `location.hash`, `document.referrer`) — и без безопасной обработки вставляет его в приёмник (sink: `innerHTML`, `insertAdjacentHTML`, `document.write`). В результате чужой код исполняется в контексте вашего сайта. Атака выполняется исключительно в браузере жертвы — дополнительные запросы на сервер не нужны.

## Что такое «источник» и «приёмник»
`Источник` (source) — место в браузере, откуда фронтенд берёт внешнее значение, которое `может контролировать пользователь`.  
***Популярные источники:*** location.search (параметры `?q=...`), location.hash (`#...`), document.referrer (адрес предыдущей страницы).

`Приёмник` (sink) — место, куда это значение вставляется в `DOM/JS`. Если приёмник «понимает» HTML/JS и вставка небезопасна, получится выполнение кода. Опасные приёмники — те, что воспринимают строку как HTML или код. Для нашего примера это `innerHTML`.

## Почему некоторые приёмники особенно опасны
* `innerHTML` / `insertAdjacentHTML` — вставляют строку как HTML. Если там будет `<script>` или событие `onload=...`, браузер его исполнит.
* `document.write` — напрямую пишет HTML в документ. Он тоже рендерит и исполняет `<script>` и обработчики событий:
```html
document.write('... <script>alert(document.domain)</script> ...');
```
* Атрибуты с обработчиками `on*` (например, `element.setAttribute`(`'onclick'`, `userInput`)): если в атрибут попадёт злоумышленный код, он выполнится при клике/загрузке/и т.д.
* `eval` / `setTimeout` со строкой — эти функции выполняют строку как JavaScript-код. Если туда попадёт пользовательская строка (напрямую или через конкатенацию), это приводит к выполнению произвольного кода.

**Коротко**: приёмники, которые трактуют строку как `разметку` или `код`, — опасны при любой вставке необработанного пользовательского ввода.

`Источник` (source) — откуда берём внешнее значение.  
`Приёмник` (sink) — куда вставляем это значение в DOM/JS.  
`Небезопасная вставка` — когда значение попадает в HTML/JS без экранирования/валидации.

## Как работает DOM XSS (на примере `innerHTML`)
Представим страницу поиска, которая «подсвечивает» запрос:
1. Есть источник. Пользователь открывает ссылку вида:
```
https://site.example/search?q=hello
```
Значение `hello` — в `location.search`.

2. Скрипт читает источник. Фронтенд достаёт `q` и хочет показать `«Вы искали: …»`.
3. Опасная вставка. Разработчик делает так:
```
resultBox.innerHTML = q;
```
То есть строка из `URL` попадает в `innerHTML`, а это HTML-вставка.

4. Выполнение кода. Если вместо «hello» злоумышленник подставит `фрагмент с кодом` (например, через параметр q), браузер воспримет его как часть HTML и выполнит:
```html
element.innerHTML = '<img src=x onerror=alert(document.domain)>';
```
Здесь `onerror` — обработчик события, который запускает `JavaScript`, как только браузер попытается загрузить «картинку».

5. Итог. Код выполняется в контексте сайта (есть доступ к данным страницы, кэшированным ответам, запросам с куками и т.д.).

**Важно**: `innerHTML` всегда трактует строку как разметку. Если это должен быть просто текст — нужно использовать текстовую вставку (например, `textContent`), тогда браузер не будет интерпретировать теги/скрипты.

## Чем DOM XSS отличается от Reflected и Stored
`Reflected/Stored`: изъян на стороне сервера — сервер формирует опасный HTML и отдаёт его в ответе.

`DOM`: изъян на стороне клиента — сервер может вернуть «чистую» страничку, но клиентский код сам берёт опасный ввод и небезопасно вставляет в DOM.

## Когда появляется нагрузка
`Reflected`: сразу в ответе на ваш запрос.  
`Stored`: позже, когда кто-то просмотрит сохранённый контент.  
`DOM`: может появиться без изменения ответа сервера, просто из-за того, что фронтенд прочитал URL/реферер/хранилище и вставил значение.

## Как диагностировать и фиксить
`Reflected/Stored`: фокус на шаблонах и экранировании на сервере.  
`DOM`: фокус на местах во фронтенде, где строка попадает в приёмник. Даже идеальная серверная фильтрация не поможет, если JS вставляется «как HTML/код».

## Практический вывод
Для защиты от `DOM XSS` одного серверного экранирования мало: нужно переписать клиентский код так, чтобы внешние значения вставлялись как текст, а не как HTML/код.

## Условия для атаки
Есть доступный источник: `location.search`, `location.hash`, `document.referrer`, `localStorage`.  
Есть уязвимый приёмник: `innerHTML`, `insertAdjacentHTML`, `document.write` и т.д.

Между ними нет корректной валидации/экранирования/белых списков.  
Дополнительно усугубляет: отсутствует строгая `CSP` (разрешены inline-скрипты), используется `склейка HTML-строк`.

## Последствия
* Кража сессии/токенов, доступ к защищённым запросам (ваш браузер отправит куки/заголовки).
* Действия от лица пользователя (смена e-mail, операции в профиле, действия в админке).
* Фишинг внутри доверенного UI (подмена формы/кнопок, перехват 2FA).
* Захват админ-панели, если DOM XSS срабатывает у администратора.

## Базовые способы защиты
1. Вставляйте внешние значения как `текст`, не как HTML (textContent/безопасные функции фреймворка).
2. Если нужен HTML, используйте проверенный `санитайзер` и `белые списки допустимых тегов/атрибутов` для конкретного контекста.
3. Избегайте `document.write`, `инлайн`-обработчиков и `eval`-подобных вызовов.
4. `CSP` (Content Security Policy) как второй ремень: запрет `unsafe-inline`, жёсткие источники для скриптов.
5. Проверяйте источник `postMessage` (сравнивайте `event.origin`), не доверяйте `document.referrer`.
6. Разделяйте данные и шаблоны: никакой «склейки HTML-строк» из кусочков пользовательского ввода.

## Мини-шпаргалка
* `DOM XSS` — уязвимость на клиенте: источник (URL/реферер/хранилище) → опасный приёмник (HTML/JS).
* Опасные приёмники: `innerHTML`, `insertAdjacentHTML`, `document.write`, атрибуты `on*`, `eval`/`new Function`/`setTimeout` со строкой.
* Отличие от reflected/stored: сервер может быть «чистым», проблема в `JS`.
* Условия: есть источник + есть приёмник + нет экранирования/валидации.
* Последствия: те же, что у XSS на сервере (кража сессии, действия, фишинг).
* Защита: только текстовая вставка, санитайзер + белые списки, без опасных API, CSP.
