# Аутентификация vs Авторизация  
Сначала напомним термины, чтобы дальше не путаться.

`Аутентификация` отвечает на вопрос **«кто это?»**. Система проверяет, что перед ней именно тот пользователь или сервис, за которого он себя выдаёт: логин/пароль, сертификат, токен и т.д.

`Авторизация` отвечает на вопрос **«что этому субъекту разрешено?»**. Допустим, пользователь успешно прошёл аутентификацию, система знает, кто он; дальше нужно решить, можно ли ему читать этот ресурс, выполнять операцию перевода денег, менять настройки и т.п.

Во многих протоколах аутентификация и авторизация переплетены (тот же `OAuth 2.0` + `OIDC`), но концептуально это разные этапы.

**ВИДЕО**

## Эволюция методов авторизации
Исторически методы авторизации развивались от максимально простых к более сложным и гибким. Полезно понимать, как каждый из них работает и какие у него ограничения.

### 1 HTTP Basic Authentication
Самый простой вариант, встроенный в протокол `HTTP`. Клиент отправляет в заголовке `Authorization` строку вида:
```
Authorization: Basic base64(login:password)
```
**Логин** и **пароль** кодируются в `Base64` и передаются на каждый запрос. `Base64` — это не шифрование, это лишь преобразование формата, поэтому без HTTPS такие учётные данные легко перехватить. Даже с HTTPS остаётся проблема в том, что пароль отправляется при каждом запросе, а модель авторизации практически не поддерживает тонкую настройку прав.

**Плюс** — в простоте: ничего дополнительного реализовывать не нужно, всё есть в браузерах и библиотеках. **Минусов** намного больше: требование обязательного HTTPS, отсутствие полуобновления прав (кроме как сменой пароля), неудобство в пользовательских интерфейсах.

### 2 HTTP Digest Authentication
`Digest` был попыткой улучшить Basic. Вместо передачи пароля в виде `base64(login:password)` используются хэши: сервер отправляет «случайное значение» (`nonce`), клиент считает хэш от пароля и этого `nonce` и отправляет результат. Пароль в чистом виде по сети не ходит.

На практике Digest почти вышел из употребления: 
* поддержка в браузерах и библиотеках не развивалась, 
* гибкость низкая, 
* интеграция со сложными фронтендами и `SPA` (тип веб-приложения, которое подгружает одну страницу и обновляет контент в ответ на действия пользователя) неудобна. 

В современных приложениях это скорее `«legacy-технология»`, с которой можно столкнуться при аудите старых систем.

### 3 API Keys
Для программного доступа к API долгое время доминировали `ключи API`. Клиент получает строку (ключ) и прикладывает её к каждому запросу, например:
```
Authorization: ApiKey 1234567890abcdef
```
или в виде параметра `?api_key=...`.

Это удобно для сценариев «машина–машина»: интеграция с внешними сервисами, скрипты, микросервисы. Однако API-ключ сам по себе не несёт информацию о пользователе, ролях, ограничениях. Если один ключ используется разными компонентами, тяжело понять, кто именно что сделал. Делегирование прав (разрешить третьему приложению ограниченный доступ от имени пользователя) на API-ключах реализуется плохо.

### 4 Cookie-based Session Authentication
Классический подход для веб-приложений. После успешного логина сервер создаёт сессию в своём хранилище (в записи хранит идентификатор пользователя, роли, дополнительные атрибуты) и отправляет клиенту cookie с идентификатором сессии:
```
Set-Cookie: SESSION_ID=abcdef123456; HttpOnly; Secure
```
Дальше браузер автоматически отправляет эту cookie с каждым запросом, а сервер по `SESSION_ID` находит сессию и понимает, кто перед ним и какие у этого пользователя права. При выходе из системы или принудительном отзыве можно просто удалить/пометить сессию на сервере — это даёт полный контроль над временем жизни.

Преимущество этого подхода — относительная простота и чёткий механизм инвалидации. Сложности появляются при масштабировании: несколько серверов должны разделять общее хранилище сессий. Также **cookie-основанная аутентификация требует защиты от CSRF**, потому браузер сам прикладывает cookie к запросам — вне зависимости от того, откуда JavaScript инициировал запрос.

### 5 Token-based Authentication (JWT)
Здесь состояние в базе сессий заменяется на сам токен. После аутентификации сервер выпускает, например, `JWT` (о нём был предыдущий урок), подписывает его и отдаёт клиенту. В токене уже содержатся утверждения о пользователе: идентификатор, роли, срок действия и т.п. Клиент прикладывает его к запросам:
```
Authorization: Bearer <jwt-токен>
```
Сервер, получив токен, проверяет подпись и срок действия, читает утверждения и на основе этого принимает решение по авторизации, при этом отдельная таблица сессий не нужна.

Такой подход облегчает масштабирование и интеграцию микросервисов, но делает сложнее отзыв: если токен уже выдан, он будет считаться валидным до истечения exp (времени жизни). Ещё один практический минус — `размер JWT`: при активном использовании токенов с множеством дополнительных полей заголовки запросов могут заметно вырасти.

## Современные протоколы делегированной авторизации
Когда появляется задача «разрешить одному приложению действовать от имени пользователя в другом», простых схем уже недостаточно. Для этого используются протоколы `OAuth 2.0`, `SAML` и `OpenID Connect`.

### 1. OAuth 2.0
`OAuth 2.0` — это протокол делегированного доступа. Пользователь (`Resource Owner`) может разрешить внешнему приложению (`Client`) доступ к своим данным на другом сервисе (`Resource Server`), при этом пароль нигде не передаётся — авторизация проходит через доверенный `Authorization Server`.

Основа идеи такова: 
1. пользователь подтверждает согласие на стороне `Authorization Server`, 
2. `Authorization Server` выпускает ограниченный `access token`, которым клиент пользуется для запросов к `Resource Server`. 
3. Внутри токена можно ограничить права (`scopes`), `срок` действия, `контекст`.

`OAuth 2.0` не описывает аутентификацию пользователя в полном смысле; он отвечает именно за делегированный доступ к ресурсам.

* **OAuth 2.0** → `авторизация` — отвечает на вопрос: «Что этому приложению разрешено делать?»

### 2. SAML 2.0
`SAML 2.0` (Security Assertion Markup Language) — XML-стандарт для обмена данными об аутентификации и авторизации. Активно используется в корпоративных `SSO`-сценариях.

В типичной схеме есть `Identity Provider` (IdP), который аутентифицирует пользователя, и множество `Service Provider` (SP), которые доверяют утверждениям IdP. IdP формирует `SAML`-ассерцию (XML-документ), подписывает её и передаёт SP. Тот проверяет подпись, читает данные (кто пользователь, какие у него атрибуты) и на этой основе предоставляет доступ.

Какой признак указывает на риск `“Mix-Up Attack”` в сценариях с несколькими IdP?
- Клиент не различает, от какого провайдера пришел ответ, и не проверяет соответствие issuer/endpoint.

`SAML` зрел и хорошо поддерживается в корпоративных окружениях (AD, корпоративные порталы), но из-за `XML`, сложных реализаций и особенностей работы в браузерах не всегда удобен для мобильных клиентов и современных `SPA`.

### 3. OpenID Connect (OIDC)
`OpenID Connect` — это надстройка над `OAuth 2.0`, которая добавляет полноценную аутентификацию. Если `OAuth` говорит **«клиенту выдан токен доступа с такими-то scopes»**, то `OIDC` говорит *«пользователь X прошёл аутентификацию у такого-то провайдера, вот его идентификатор и атрибуты»*.

По сути, `OIDC` добавляет к `OAuth` понятие `ID Token` — токен (обычно `JWT`), в котором содержится информация о пользователе и контексте аутентификации. Также определены стандартные scope’ы (`openid`, `profile`, `email`) и endpoint `UserInfo` для получения дополнительных данных о пользователе.

На практике `OIDC` стал де-факто стандартом для `SSO` и аутентификации в современных веб- и мобильных приложениях: Google Sign-In, вход через GitHub, многие корпоративные `IdP` — всё это вариации `OIDC`.

Если совсем по шагам:
1. Ты нажал **«Войти через Google»**.
2. Google просит тебя ввести пароль → **аутентификация**: 
    * Google проверяет, что ты действительно владелец аккаунта.
3. После успешной проверки Google возвращает сайту **ID Token (OIDC)** → сайт узнаёт, кто ты.
4. Если сайт запрашивает доступ к каким-то ресурсам Google (например, профиль, почта, Drive), Google выдаёт **access token** (`OAuth 2.0`) с определёнными разрешениями (`scope`).
5. Сайт создаёт у себя твою сессию и считает тебя вошедшим.

## Сравнение методов
Обобщим ключевые свойства разных подходов в виде таблицы:

|Метод|Состояние на сервере|Подходит для|Безопасность (при корректной настройке)|Сложность реализации|
|---|---|---|---|---|
|**Basic Auth**|Нет|Простые, legacy-сценарии|Низкая, только при строгом HTTPS|Очень низкая|
|**API Keys**|Как правило нет|Взаимодействие сервисов, скрипты|Средняя|Низкая|
|**Session Cookie**|Да|Классические веб-приложения|Высокая|Средняя|
|**JWT**|Нет|Распределённые системы, API|Высокая, зависит от реализации|Средняя|
|**OAuth 2.0**|Частично (refresh)|Делегированный доступ, интеграции|Высокая|Высокая|
|**SAML**|Зависит от реализации|Корпоративный SSO|Высокая|Очень высокая|
|**OIDC**|Частично (refresh)|Современные веб/мобильные приложения|Высокая|Средняя–высокая|

Здесь «состояние на сервере» означает необходимость отдельного хранилища сессий. `OAuth 2.0` и `OIDC` в базовой части `stateless`(без сохранения состояния), но на практике используют `refresh`-токены и могут хранить состояние авторизаций.

## Выбор метода по сценарию
Для внутреннего монолитного веб-приложения, где всё запущено на одном домене и нет сложной логики сервисов, логичный выбор — `session cookies`. Этот подход прост, хорошо поддерживается фреймворками и позволяет легко выполнять `logout` и принудительную инвалидацию.

В микросервисной архитектуре, где десятки компонентов должны доверять одному источнику аутентификации, удобнее использовать `JWT` или `OAuth 2.0` с выделенным `auth`-сервисом. Тогда каждый сервис умеет проверять токен и не держит свою таблицу сессий.

Если речь про публичный API для сторонних разработчиков, базовый слой часто строят на `API Keys` для машинного доступа (без участия пользователя). Когда нужно делегировать доступ к данным конкретного пользователя (например, «дай стороннему приложению доступ к моему календарю»), подключают `OAuth 2.0`.

Для мобильных приложений и входа через соцсети стандартный выбор — `OAuth 2.0` / `OpenID Connect`, обычно с потоком `Authorization Code + PKCE`. Это сочетание решает вопросы и аутентификации пользователя, и делегирования доступа.

`PKCE` (Proof Key for Code Exchange) — это защита потока `Authorization Code` от кражи `authorization code`.

Идея очень простая:
1. Приложение генерирует случайный секрет **code_verifier** - code_verifier = ABC123.
2. Из него делает **code_challenge** и отправляет его в `Google/IdP` при авторизации - code_challenge = SHA256(ABC123).
3. Пользователь проходит вход.
4. Google возвращает приложению **authorization code**.
5. Приложение отправляет этот **authorization code** + исходный **code_verifier** для получения токена.
6. Google проверяет, что **code_verifier** соответствует ранее переданному **code_challenge**.
7. Если да → Google выдаёт токены: `access token` и `ID token` (OIDC)

* **code_challenge** — доказательство владения секретом, 
* **authorization_code** — временный код, который потом обменивается на токены.

Зачем? Если злоумышленник перехватит `authorization code`, одного этого кода недостаточно — у него нет исходного **code_verifier**.

> `PKCE` защищает `Authorization Code` от перехвата: только приложение, создавшее **code_verifier**, сможет обменять полученный code на токен.

Корпоративные приложения с единым входом чаще всего интегрируются через `SAML` или `OIDC`, в зависимости от стека и возможностей существующей инфраструктуры. Новые системы всё чаще выбирают `OIDC`.

## Общие проблемы безопасности при авторизации
Независимо от выбранного протокола и формата токенов есть набор типичных ошибок.
1. Все учётные данные и токены должны передаваться только по защищённым каналам. Без `HTTPS` любой из обсуждаемых методов становится уязвим для перехвата.

2. Хранение токенов на клиенте должно учитывать `XSS` и другие клиентские атаки. `JWT` или `OAuth`-токены в `localStorage` и `sessionStorage` уязвимы при внедрении произвольного JS-кода, `cookie` без флага `HttpOnly` — тоже. Выбор места хранения должен согласовываться с моделью угроз: что страшнее в конкретной системе — `XSS` или `CSRF`.
* `HttpOnly` защищает cookie от чтения через JavaScript:
    * `XSS` → JS не может прочитать HttpOnly cookie.
    * `CSRF` это не останавливает, потому что браузер всё равно может автоматически прикрепить cookie к запросу
* `XSS`  → злоумышленник выполняет JS внутри твоего сайта
* `CSRF` → злоумышленник заставляет твой браузер отправить запрос

3. Любой реальный протокол нуждается в механизмах отзыва. Слишком длинный срок жизни токенов, делает компрометацию токена проблемой.

4. Авторизация на стороне сервера не должна сводиться к «если токен валидный, то всё можно». **Проверка конкретных прав** (ролей, scopes, атрибутов) и корректная реализация **проверки доступа к ресурсам** остаются обязанностью бизнес-логики. Ошибка здесь превращает любой, даже идеально подписанный токен в инструмент для обхода контроля доступа.

Если суммировать, протокол и формат токена — это лишь фундамент. Без корректной конфигурации, безопасной передачи, продуманного хранения и строгой проверки прав сама по себе технология авторизации не гарантирует безопасности.
