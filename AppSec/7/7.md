## UNION-инъекция
`UNION` склеивает результаты двух SELECT в один список. Чтобы сработало, оба запроса должны возвращать одинаковое количество колонок и совместимые типы по позициям.

|Шаг|Что делаем|Пояснение (коротко)|
|---|---|---|
|1|Найти параметр, который влияет на SELECT|Поле поиска/фильтра: ввод меняет выдачу → есть точка инъекции.|
|2|Проверить, что ввод попадает внутрь SQL|Пробуем добавить одинарную кавычку `'` и наблюдаем: ошибка/странное поведение = хороший знак.|
|3|Определить число колонок результата|Последовательно пробуем: `UNION SELECT NULL` затем `UNION SELECT NULL, NULL` и т.д., пока страница не начнёт отвечать без ошибки. Столько NULL — столько колонок.|
|4|Выяснить, какие позиции видны на странице|Подставляем метки:  `UNION SELECT 'X', NULL, ...` затем `UNION SELECT NULL, 'Y', ...n`. Где метка появилась — та колонка отображается.|
|5|Совместить типы колонок|В SQLite NULL часто подходит; если нужна строка — используем литералы (`'A'`), число — `0`. При конфликте — приводим тип: `CAST(0 AS TEXT)`|
|6|Узнать версию/движок для уверенности|В SQLite можно вывести `sqlite_version()` через видимую колонку: `UNION SELECT sqlite_version()`, ...остальные позиции — NULL.|
|7|Получить список таблиц|Читаем таблицу `sqlite_master`. Выводим name там, где колонка видна: `UNION SELECT name, NULL, ... FROM sqlite_master WHERE type='table'`|
|8|Узнать колонки нужной таблицы|Через `PRAGMA table_info(users)` напрямую не всегда получится в UNION. В SQLite можно: `UNION SELECT sql, NULL, ... FROM sqlite_master WHERE name='users'` и разобрать `DDL` (в нём перечислены столбцы).|
|9|Подготовить итоговый UNION SELECT|Собираем столько выражений, сколько колонок у первичного запроса; в видимой позиции ставим нужные поля (например, (например, email), в остальных — совместимые заглушки (NULL/0).|
|10|Экcфильтровать данные|Пример идеи: `UNION SELECT email, NULL, ... FROM users`|
|11|Обрубить «хвост» при необходимости|Если после параметра идёт остаток SQL, комментарий `--` или `/* ... */` в SQLite поможет проигнорировать хвост.|
|12|Стабилизировать вывод|При необходимости добавляем `LIMIT`/условия в нашей части UNION, чтобы выдача была читаемой и не «плавала».|
|13|Зафиксировать артефакты|Записываем: число колонок, видимые позиции, рабочие конструкции и финальные пейлоады для отчёта.

### Подсказки для SQLite:
1. Комментарии: `--` до конца строки и `/* … */`.
2. Конкатенация строк: оператор `||`.
3. Список таблиц/DDL: `sqlite_master` (поля type, name, sql).
4. Версия: `sqlite_version()`.

Time-based

Напоминаем: Это ситуация, когда страница ничего не печатает и не даёт ошибок, но её время ответа меняется, если условие в SQL истинно. Мы встраиваем выражение «если правда — подожди N секунд; если ложь — отвечай сразу» и читаем тайминг как «да/нет». На экране — всё та же страница, но одна версия приезжает за ~200–400 мс, а другая — за 5–10 секунд.

Важно: в SQLite нет встроенного SLEEP(). Задержку имитируем «тяжёлой» операцией (например, рекурсивным CTE с большим числом итераций) и включаем её только, если условие истинно.

Error-based

Это ситуация, когда приложение показывает текст ошибки из СУБД (полностью или частично). Мы намеренно провоцируем ошибку в SQL-выражении и используем текст этой ошибки как «экран» для наших данных: подмешиваем значение внутрь функции, которая падает, — и видим нужный фрагмент прямо в сообщении. Иногда ошибку не печатают напрямую, но показывают «кусочки»: имя колонки, функции, часть строки — их тоже можно использовать.

Шаг

Пояснение (коротко)





1



Находим параметр, где видны ошибки БД



Проверяем, что приложение показывает текст ошибок (а не «что-то пошло не так»). Это наш «канал».





2



Провоцируем синтаксическую ошибку



Даём «битый» ввод (например, незакрытую кавычку). В ответах SQLite часто видно syntax error / unrecognized token — подтверждение инъекции.





3



Распознаём движок по формулировкам



У SQLite характерные сообщения: no such table: ..., no such column: ..., no such function: .... Их стиль помогает отличить SQLite от других СУБД.





4



Проверяем no such function



Пытаемся вызвать несуществующую функцию (например, из расширений: json_*, если они не подключены). Ошибка вида no such function: json_extract подтверждает SQLite и сборку без JSON1.





5



Проверяем системную таблицу



Обращаемся к sqlite_master. Если при опечатке видим no such table: sqlite_mastr, а при правильном имени ошибка исчезает/меняется, значит это SQLite и таблица существует.





6



Вызываем ошибку по ограничениям



Пытаемся спровоцировать UNIQUE constraint failed: users.email (например, «дублирующую» регистрацию через уязвимый путь). Такие ошибки «подсказывают» имена таблиц/колонок.





7



Пробуем типовые type mismatch



В SQLite многие несоответствия не падают, а приводятся автоматически. Если удаётся получить datatype mismatch, фиксируем сообщение — оно подтверждает контекст и точку.





8



Фиксируем маркеры из текста ошибок



Выписываем точные формулировки (название СУБД, no such ..., имена ограничений/колонок). Это пригодится для выбора пейлоадов в следующих техниках.





9



Переходим к эксфильтрации



Для «слива» данных в SQLite используем UNION (через sqlite_master → таблицы/DDL) или blind-подходы (boolean/time). Error-based здесь — про подтверждение и разведку.
