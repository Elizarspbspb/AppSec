Что такое «первичная разметка» в Trivy

Ты запускаешь Trivy, он выдаёт список уязвимостей. Первичная разметка — это первый проход по этому списку, когда ты для каждой записи решаешь:





Чинить сейчас



Чинить позже



Принять риск



Ложное срабатывание / неприменимо

 

Перед практикой: три простых вопроса

На каждую уязвимость смотри так:





Насколько она серьёзная?
Смотрим Severity: CRITICAL, HIGH, MEDIUM и т.д.



Где находится уязвимый компонент?
В грубом приближении бывает три варианта:





в реально работающем приложении (то, что запущено на сервере / в контейнере);



только на этапе сборки (утилиты, которые нужны, чтобы собрать приложение, но не попадают в конечный образ);



в dev-инструментах (тесты и т.п., которые вообще не попадают в прод).



Насколько важен этот сервис и куда он выходит?





Доступен из интернета и обрабатывает важные данные → выше приоритет.



Внутренний вспомогательный сервис → ниже.

Этого достаточно, чтобы уже разумно размечать.





Пример 1. Скан контейнерного образа

Запускаем:

trivy image --format table registry.local/backend:1.0.0

Допустим, кусок вывода выглядит так:

TARGET                    VULNERABILITY  PKG      INSTALLED   FIXED      SEVERITY

registry.local/backend    CVE-2022-0778  openssl  1.1.1k-r0   1.1.1n-r0  HIGH

registry.local/backend    CVE-2021-1234  curl     7.68.0-r0   7.70.0-r0  MEDIUM

registry.local/backend    CVE-2019-9999  build-tools 0.9.0    1.0.0      HIGH

Пусть это боевой backend, который:





работает в Kubernetes;



доступен из интернета;



обслуживает пользователей.



 1. CVE-2022-0778 — openssl, HIGH

Это библиотека шифрования. Обычно через неё идут HTTPS, TLS и т.п.

Что делаем:





сервис доступен снаружи;



openssl используется по назначению (TLS).

Решение:
Обновить в первую очередь.

Практика:





заводишь задачу: «обновить базовый образ/openssl до 1.1.1 или выше»;



в задачу прикладываешь кусок отчёта и ссылку на CVE.



2. CVE-2021-1234 — curl, MEDIUM

Описание уязвимости (читаем ссылку из отчёта) говорит, что проблема только в FTP-функциях.

Теперь важный момент: а curl вообще есть в работающем контейнере, или он нужен только при сборке?

Если у тебя multi-stage Dockerfile, он может выглядеть так:

# Стадия сборки
FROM golang:1.20 AS build
RUN apt-get update && apt-get install -y curl
# тут что-то скачиваем curl'ом, собираем бинарник

# Финальный образ
FROM alpine:3.18
COPY --from=build /app /app
ENTRYPOINT ["/app"]

Тогда утилита curl есть только на стадии build, а в финальном образе её нет.

Проверяем:

docker run --rm registry.local/backend:1.0.0 sh -c "which curl || echo 'no curl'"





если получаем no curl → curl в работающем контейнере нет;



значит, уязвимость относится к инструменту, который использовался только при сборке, а в финальной версии его нет.

Разметка:





для боевого контейнера → по сути «не применимо»;



чтобы Trivy не срабатывал по этому CVE каждый раз, можно добавить его в .trivyignore: 
#curl используется только на стадии сборки, в боевом контейнере отсутствует CVE-2021-1234

Если же curl реально есть в контейнере и приложение им пользуется — ставим задачу «обновить позже» (не срочно, но в план работ).



3. CVE-2019-9999 — build-tools, HIGH

Пакет build-tools в имени уже намекает: это инструменты сборки.

FROM node:18 AS build
RUN npm install -g build-tools
# собираем фронтенд

FROM nginx:1.23
COPY --from=build /dist /usr/share/nginx/html

В nginx-образе build-tools не нужен и туда не попадает.

Проверка аналогична:

docker run --rm registry.local/backend:1.0.0 sh -c "which build-tools || echo 'no build-tools'"

Если «no build-tools», уязвимость не относится к реально работающему контейнеру.

Разметка:





для боевого окружения → считаем это ложным срабатыванием (False Positive) в нашем контексте;



снова фиксируем это в .trivyignore с комментарием:
#build-tools только на стадии сборки, в боевой среде не используется CVE-2019-9999

Итог по примеру:





openssl → обновить;



curl → либо «не применимо» (если только на сборке), либо «исправить позже»;



build-tools → ложное срабатывание для боевого окружения.

Пример 2. Скан проекта (fs): прод-зависимости vs dev-зависимости

Теперь без контейнеров. Сканируем Node.js-проект:

trivy fs --format table .

Пусть Trivy нашёл уязвимости в зависимостях:

Target: package-lock.json

VULNERABILITY  PKG      INSTALLED  FIXED    SEVERITY
CVE-2023-1111  express  4.17.1     4.18.0   HIGH
CVE-2022-2222  jest     28.0.0     29.0.0   HIGH



Смотрим package.json:

{
  "dependencies": {
    "express": "4.17.1"
  },
  "devDependencies": {
    "jest": "28.0.0"
  }
}

Тут важно что в dependencies, а что в devDependencies:





dependencies → то, что нужно приложению, когда оно работает на сервере;



devDependencies → то, что нужно для разработки и тестов, но в боевую среду обычно не ставится.

1. CVE-2023-1111 — express, HIGH

Express — это фреймворк, на котором крутится твой backend.





HIGH,



прод-зависимость,



принимает запросы от пользователей.

Решение:
Заводим задачу «обновить express до 4.18.0 или выше» (в зависимости от рекомендаций).



2. CVE-2022-2222 — jest, HIGH

Jest — это фреймворк для тестов. В боевом контейнере его обычно нет.

Разметка:





для боевого риска → Not Applicable;



с точки зрения репозитория в целом можно завести отдельную, менее приоритетную задачу «обновить dev-зависимости».

Если отчёты Trivy по прод-коду не должны учитываться dev-зависимости, есть два варианта:





прогонять Trivy в режиме, где ты явно сканируешь собранный образ, а не только исходники;



или после скана по package-lock.json фильтровать dev-пакеты (скриптом или правилами обработки).

 



Как это фиксировать в процессе

Обычно делают так:





Все исправить → в задачи.
Например:





«Обновить openssl в образе backend до версии X»



«Обновить express до 4.18.0»

В задаче — кусок отчёта Trivy + ссылка на CVE.





То, что признано FP / Not Applicable → в .trivyignore.

Пример файла:

# Пакет только на стадии сборки, в боевой среде его нет
CVE-2019-9999

# Jest — dev-зависимость, не попадает в прод
CVE-2022-2222

Главное — всегда оставлять комментарий: через 6 месяцев ты сам себе скажешь спасибо, когда будешь вспоминать «почему мы это игнорируем».

 

Вывод:

Первичная разметка в Trivy — это:





взять отчёт,



для каждой уязвимости понять:





насколько она серьёзная (Severity),



в каком месте она живёт (боевой код, сборочные инструменты, dev-зависимости),



насколько важен сервис,



всё серьёзное и реально задействованное → в задачи на фикс,



всё, что не относится к боевой среде или очевидно неиспользуемо → аккуратно в .trivyignore с пояснением.
