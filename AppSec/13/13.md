Directory Traversal — уязвимость, при которой приложение позволяет пользователю «выбраться» из разрешённой папки и читать произвольные файлы на сервере. Делается это с помощью последовательностей вроде ../ (или их экранированных вариантов), которые поднимают нас «выше» по дереву каталогов.



Как работает

Представьте интернет-магазин. Картинки товаров подтягиваются так:

<img src="/loadImage?filename=18.png">

На сервере есть папка с изображениями: /var/www/images/. Приложение берёт параметр filename и строит путь:

fullPath = "/var/www/images/" + filename

Далее читает файл с диска и отдаёт браузеру.





Атака на Linux/macOS

Злоумышленник подставляет «подъём вверх» по каталогам через ../:

GET /loadImage?filename=../../../etc/passwd

Сервер (без проверок) попытается прочитать:

/var/www/images/../../../etc/passwd

Файловая система нормализует путь: каждая пара ../ поднимает нас на уровень выше. Три подъёма из /var/www/images/ приводят к корню, и в итоге читается:

/etc/passwd

Это стандартный системный файл с информацией о пользователях. По тому же принципу можно читать и другие файлы: конфиги (/etc/nginx/nginx.conf), переменные окружения (/proc/self/environ), логи и даже исходники приложения.



Обходы простых фильтров

Если бэкенд «режет» только прямой текст ../, его часто обходят:





URL-кодирование слэшей/точек: ..%2f..%2f..%2fetc%2fpasswd



Двойное кодирование: %252e%252e%252f%252e%252e%252fetc%252fpasswd
(после первого декодирования становится %2e%2e%2f..., после второго — ../...)



Смешанные формы: ....//etc/passwd (два лишних символа «склеиваются» при нормализации)

Ещё один трюк — абсолютный путь. Если приложение не запрещает его, можно запросить:

/loadImage?filename=/etc/passwd

и склейка "/var/www/images/" + "/etc/passwd" у некоторых реализаций фактически превратится в /etc/passwd.





Атака на Windows

Те же идеи работают со слэшем \:

GET /loadImage?filename=..\..\..\Windows\win.ini

Или в URL-коде:

..%5c..%5c..%5cWindows%5cwin.ini

Итог — чтение C:\Windows\win.ini вместо картинки.





Почему это происходит





Приложение доверяет параметру и «склеивает» путь строкой.



Нет нормализации и проверки, что канонический путь остаётся внутри «разрешённой» папки.



 (Часто) фильтрация сделана до декодирования или слишком поверхностно.





Что видит атакующий

В ответе вместо изображения приходит содержимое системного файла (текст). Если ресурс отдаёт «как есть», это будет прямо в браузере; иногда — в виде скачиваемого файла


ВИДЕО

Ключевые векторы





Подъём наверх: ../../../../etc/passwd (Linux/macOS), ..\\..\\Windows\\win.ini (Windows).



Кодирование слэшей/точек: ..%2f..%2fetc%2fpasswd, двойное кодирование (%252f), смешанные варианты: ....// (две точки + два слэша).



Обратные слэши: ..%5c..%5cWindows%5cwin.ini (%5c = \).



Абсолютные пути: /etc/passwd, C:\Windows\win.ini — если бэкенд принимает их как есть.

Отдельно: Zip Slip — та же идея при распаковке архивов, когда имена файлов внутри .zip содержат ../ и распаковка уходит за пределы целевой папки.





Короткий разбор «как атакуют»





Найти параметр, который управляет именем файла: file, path, name, download, сегмент пути.



Проверить простое: ../../etc/passwd, ..%2f..%2fetc%2fpasswd, ..%5c..%5cWindows%5cwin.ini.



Если «похоже на фильтр» — пробовать двойные кодирования, смешанные слэши / + \, ....//, абсолютные пути.



Если сервер отдаёт только «белые» расширения — пробовать без расширения (многие конфиги без него) или искать другие конечные точки.



Успех — когда получаем содержимое файла вне ожидаемой папки (логи, конфиги, системные файлы).

 

Где это встречается





Просмотр/скачивание файлов: отчёты, аватарки, экспорт логов.



«Рендер по имени шаблона»: ?template=....



Конвертеры/превьюеры: «дай URL/файл — верну превью».



Админ-утилиты «посмотреть лог/конфиг».



Последствия





Конфиденциальные данные: ключи, токены, .env, конфиги приложений.



Системные файлы: /etc/passwd, журналы /var/log/..., конфиги Nginx/Apache.



Исходники приложения: утечка секретов, логики, паролей к БД.



Дальнейшая компрометация: чтение приватных ключей, «челночные» атаки (читать логи → находить сессии/токены → входить от лица пользователей).


ВИДЕО


Защита

Самый эффективный способ предотвратить уязвимости, связанные с обходом пути, — вообще не передавать пользовательский ввод в API файловой системы. Многие функции приложений, которые это делают, можно переписать так, чтобы они работали безопаснее.

Если вы не можете избежать передачи пользовательских данных в API файловой системы, мы рекомендуем использовать два уровня защиты для предотвращения атак:

1) Валидация ввода (до файловой системы)





Используем белый список: только разрешённые имена/расширения (.png, .pdf и т.д.).



Запрещаем разделители и подъёмы: никаких /, \, .., нулевых байтов.



Ограничиваем длину и формат (регэксп вида ^[A-Za-z0-9._-]+$).



Не принимаем абсолютные пути.

2) Канонизация и проверка корня





Склеиваем путь только через pathlib.



Делаем канонический путь (resolve) и проверяем, что он реально лежит внутри базовой директории.



Если вышли за пределы — отклоняем.

 

 

Пример (Python):
```python
from pathlib import Path

BASE = Path("/var/www/images").resolve()
user = user_input  # строка из запроса
p = (BASE / user).resolve()

if not str(p).startswith(str(BASE)):
    raise ValueError("path traversal")

# безопасно работать с файлом p
```
          

 

❗ Важный нюанс: проверку делайте после всех декодирований, а не до. И не полагайтесь только на «выкинуть ../ строкой» — это легко обходится.
