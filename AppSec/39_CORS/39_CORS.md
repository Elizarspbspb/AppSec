# CORS
`CORS` (Cross-Origin Resource Sharing) — это механизм в браузерах, который позволяет серверу явно указать, с каких других сайтов (`origin`) можно обращаться к его ресурсам с помощью JavaScript и читать ответы.

По сути, это надстройка над базовым правилом безопасности браузера — `Same-Origin Policy` (SOP). Поэтому сначала разберём `SOP`, а потом `CORS`.

Наиболее опасные:
* **Access-Control-Allow-Origin: `*`** 
* **Access-Control-Allow-Credentials: true**.

**ВИДЕО**

## Same-Origin Policy (SOP): базовое правило браузера
`Origin` (источник) определяется как тройка:
* протокол (scheme): http или https;
* хост (host): example.com, api.example.com;
* порт (port): 80, 443, 8080 и т.п.

Если хоть один элемент отличается, `origin` считается другим.

Примеры разных `origin`:
* https://example.com
* https://api.example.com
* http://example.com:8080

`SOP` говорит: скрипт, загруженный с одного `origin`, не имеет доступа к данным другого `origin`. Это выражается в том, что:
* нельзя читать тело ответа `cross-origin` запроса средствами `JS` (через fetch, XMLHttpRequest);
* нельзя читать или менять `DOM` другой страницы из `iframe`, если у нее другой `origin`;
* нельзя читать чужие `localStorage`, др.

> *Важно*: ***отправить запрос на другой origin браузер может (например, img, form, script), но JS не получит доступ к содержимому ответа, если SOP не разрешает.***

`SOP` изначально придумали, чтобы:
* сайт А не мог читать приватные данные сайта Б, если оба открыты в одном браузере пользователя;
* снизить риск того, что случайная вкладка будет тайно смотреть за другой вкладкой (банк, почта и т.д.).

### Почему одного SOP стало недостаточно
Современные приложения часто устроены так:
* фронтенд на одном домене (https://app.example);
* API на другом (https://api.example);
* часть ресурсов — на CDN (https://cdn.example или вообще другой домен);
* интеграция с внешними сервисами (оплата, сторонние API).

***С точки зрения SOP все эти домены — разные origin.***

Если оставить только `SOP`, сценарии вида «Приложение на одном домене обращается к своему API на другом домене и читает JSON» работать не будут — браузер будет блокировать доступ JS к ответу.

Нужно было:
* оставить `SOP` как базовую защиту;
* разрешать доступ к API с других `origin`.

***Эту роль выполняет CORS.***

## Что такое CORS
`CORS` — это соглашение между браузером и сервером:
* браузер при `cross-origin` запросах отправляет заголовок `Origin`;
* сервер отвечает особыми заголовками `Access-Control-*`, в которых описывает политику;
* браузер, опираясь на эти заголовки, решает: разрешать ли JS-коду доступ к ответу.

Если политика сервера не разрешает запрос с данного `origin`, браузер сам блокирует доступ JS к ответу, даже если сервер технически ответил 200 OK.

## Основные понятия CORS
### Origin
Мы уже определили его выше: **протокол** + **домен** + **порт**. Именно его браузер посылает в заголовке `Origin` при запросе.

### Simple requests (простые запросы)
Часть запросов считаются «простыми», к ним `CORS` относится немного проще:
* методы: GET, HEAD, POST;
* заголовки только из стандартного набора;
* `Content-Type` только: **application**/x-www-form-urlencoded, **multipart**/form-data, **text**/plain.

Для таких запросов браузер:
* сразу отправляет запрос;
* потом смотрит на заголовки ответа и решает, отдавать ли его JS-коду.

### Preflight requests (предварительный запрос)
Если запрос сложнее (например, метод PUT, DELETE, нестандартные заголовки, иной тип Content-Type), перед основным запросом браузер отправляет дополнительный запрос методом `OPTIONS`. Это и есть `preflight`.

Назначение `preflight`: «согласовать» с сервером, можно ли отправлять основной запрос.

Если запрос сервер разрешает отправить основной запрос то браузер потом смотрит на заголовки ответа и решает, отдавать ли его JS-коду.

***«Отдать ответ JS-коду»*** означает не запустить или заблокировать JavaScript, а **дать JS-коду доступ к данным ответа от сервера**.

Пример:
```js
fetch("https://api.example.com/user")
```
Запрос ушёл → сервер ответил:
```
{ "name": "Alex" }
```
Если `CORS` разрешён, браузер передаст эти данные в JavaScript:
```
data.name // Alex
```
Если `CORS` запрещён — браузер скроет ответ от JS:
```
CORS policy blocked
```
То есть:
* ✅ JavaScript всегда запускается.
* ✅ Запрос может уйти на сервер.
* ❌ Но браузер может не дать JS прочитать ответ.

### Credentials (учётные данные)
В контексте `CORS` под этим понимаются:
* cookies;
* заголовки авторизации (Authorization);
* клиентские TLS-сертификаты.

При `cross-origin` запросах отдельный вопрос — разрешено ли:
* отправлять эти данные;
* и отдавать ответ JS-коду, если они использовались.

## CORS-заголовки: как сервер управляет доступом
Сервер использует несколько заголовков, чтобы настроить `CORS`.

### Access-Control-Allow-Origin
Ключевой заголовок. Задаёт, какому `origin` разрешено читать ответ.

Примеры:
```
1. Access-Control-Allow-Origin: https://app.example
```
Ответ может прочитать JS-код только с сайта https://app.example.
```
2. Access-Control-Allow-Origin: *
```
Любой сайт может прочитать ответ. При наличии приватных данных это опасно.

### Access-Control-Allow-Methods
Список методов, которые разрешены для `cross-origin` запросов. Используется в ответе на `preflight`.
```
Access-Control-Allow-Methods: GET, POST, DELETE
```
Браузер сравнит нужный метод с этим списком.

### Access-Control-Allow-Headers
Список нестандартных заголовков, которые можно использовать в запросе (например, Authorization, X-Requested-With).
```
Access-Control-Allow-Headers: Authorization, X-Custom-Header
```
 
### Access-Control-Allow-Credentials
Разрешение на использование `cookies` и других учётных данных в `cross-origin` контексте:
```
Access-Control-Allow-Credentials: true
```
Если этот флаг true, браузер может:
* отправлять cookies и заголовки авторизации;
* отдавать ответ JS-коду при выполнении остальных условий `CORS`.

> ***Важный момент: при Allow-Credentials: true нельзя указывать Access-Control-Allow-Origin: `*`. Должен быть конкретный `origin`.***

### Access-Control-Max-Age
Сколько секунд браузер может кэшировать положительный ответ на `preflight`.
```
Access-Control-Max-Age: 600
```
Это значит, что 600 секунд браузер не будет повторять `preflight` для запросов с теми же параметрами.

### Access-Control-Expose-Headers
Определяет, какие заголовки ответа будут доступны JS-коду. По умолчанию доступен только ограниченный набор. Этот заголовок позволяет расширить список.
```
Access-Control-Expose-Headers: X-Request-Id, X-Rate-Limit-Remaining
```
 
## Как работает preflight-запрос: разбор примера
Сценарий: страница с `origin` https://evil.com пытается отправить запрос `DELETE` на https://api.example/api/data.

Браузер сначала отправляет `preflight`:
```
OPTIONS /api/data HTTP/1.1
Host: api.example
Origin: https://evil.com
Access-Control-Request-Method: DELETE
```
Значения:
* `Origin` — откуда пришёл запрос;
* `Access-Control-Request-Method` — какой метод планируется.

Сервер отвечает, например:
```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://trusted.com
Access-Control-Allow-Methods: GET, POST
```
сравнивает:
* `Origin` запроса: https://evil.com;
* `Access-Control-Allow-Origin`: https://trusted.com → не совпадает;

кроме того, среди разрешённых методов нет `DELETE`.

*Результат: браузер считает, что запрос не разрешён. Основной DELETE не отправляется, и JS-код не получает доступ к данным.*

Если бы сервер ответил:
```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Credentials: true
```
и браузер делал запрос с куками/авторизацией, то такой сценарий был бы разрешён.

## Типичные уязвимости и ошибки конфигурации CORS
Теперь к тому, что важно при аудите и защите.

### Слишком широкий Access-Control-Allow-Origin
Если сервер отвечает:
```
Access-Control-Allow-Origin: *
```
для API, который:
* возвращает приватные данные;
* работает с авторизацией (cookies, токены),

то это создаёт возможность для злоумышленника читать эти данные через браузер пользователя.

Особенно опасно, если одновременно:
```
Access-Control-Allow-Credentials: true
```
(современные браузеры ограничивают сочетание `*` и `true`, но на практике остаются связки, где риск всё равно есть, особенно с токенами, которые JS сам отправляет).

Правильный подход: для приватного API — всегда конкретные `origin`’ы, а не `*`.

### Динамическое отражение Origin без проверки
Паттерн уязвимости в котором нет никакой проверки:
```php
// псевдокод сервера, небезопасная логика
const origin = request.headers.origin;
response.setHeader('Access-Control-Allow-Origin', origin);
response.setHeader('Access-Control-Allow-Credentials', 'true');
```
Сервер без проверки доверяет любому `Origin`, присланному клиентом.

Атака:
* злоумышленник размещает JS-код на своём домене;
* браузер жертвы отправляет запрос с Origin: https://attacker.example;
* сервер копирует это значение в `Access-Control-Allow-Origin`;
* браузер видит совпадение `origin` и разрешённого значения → отдаёт ответ JS-коду на стороне злоумышленника.

Безопасный вариант — только белый список:
```php
const allowedOrigins = [
  'https://app.example',
  'https://admin.example',
];

const origin = request.headers.origin;

if (allowedOrigins.includes(origin)) {
  response.setHeader('Access-Control-Allow-Origin', origin);
  response.setHeader('Access-Control-Allow-Credentials', 'true');
}
```

### Ошибочная обработка Origin: null
Заголовок `Origin: null` встречается в специфических случаях (например, `file://` страницы, некоторые типы `iframe` с `sandbox`).

Если сервер построен по принципу «раз Origin не наш, значит можно разрешить», то `null` может попасть в разрешённую категорию по ошибке. Или null не находится в blacklist.

Корректный подход: явно перечислять допустимые `origin`’ы и не воспринимать `null` как доверенный `origin`.

### Слишком большой Access-Control-Max-Age
Если `Access-Control-Max-Age` выставлен на очень большое значение (например, несколько часов или дней), а конфигурация `CORS` на сервере оказалась ошибочной, то:
* даже после исправления конфигурации часть пользователей продолжит работать с кэшированным, небезопасным вариантом `preflight`-ответа;
* отзыв неправильной политики становится затруднённым.

Поэтому имеет смысл выбирать умеренные значения и помнить, что обновление `CORS`-политики не применяется к уже кэшированным `preflight`-ответам мгновенно.

## CORS и CSRF: разные модели угроз
`CSRF` (Cross-Site Request Forgery) — про то, что:
* вредоносный сайт может заставить браузер жертвы отправить запрос на другой сайт с её `cookies`;
* цель — выполнить действие: перевод денег, изменение настроек, и т.п.;
* при этом злоумышленник не обязательно видит ответ — ему важно, что действие выполнено.

`CORS-мисконфигурации` — в первую очередь про чтение данных:
* вредоносный сайт не просто инициирует запрос;
* он получает возможность прочитать тело ответа через `JS`, если `CORS` настроен слишком широко.

Связь:
* **правильно настроенный CORS** может ограничивать некоторые `CSRF`-сценарии, но не заменяет `CSRF`-защиту (токены, проверка заголовков и т.п.);
* **неправильный CORS**, наоборот, добавляет новый риск: утечка данных через API, которые должны быть защищены `SOP`.

## Примеры атак на основе CORS
### 1. Кража данных через API
Условия:
* https://api.bank.local — API интернет-банка;
* авторизация по cookies;
* `CORS`:
  * Access-Control-Allow-Origin: *
  * Access-Control-Allow-Credentials: true

Сценарий:
1. Пользователь авторизован в банке.
2. Открывает вредоносный сайт.
3. JS на вредоносном сайте делает запрос к https://api.bank.local/accounts с `credentials`: 'include'.
4. Браузер отправляет `cookies` банка.
5. Из-за настроек `CORS` браузер отдаёт тело ответа JS-коду.
6. Скрипт отправляет полученные данные злоумышленнику.

### 2. Intranet-атаки
Условия:
* внутренняя панель администрирования доступна только из локальной сети по http://intranet.local;
* на панели по ошибке настроено:
  * Access-Control-Allow-Origin: *

Сценарий:
1. Сотрудник в офисе заходит на вредоносный сайт в интернете.
2. JS на вредоносной сайте отправляет запросы к http://intranet.local.
3. Так как внутри сети этот ресурс доступен, браузер получает ответы.
4. Из-за `*` в `CORS` JS-код может прочитать ответы и отправить конфигурацию/данные вне сети.

### 3. Token theft / утечка через CORS
Типичная связка:
* фронтенд хранит токен (например, `JWT`) в JavaScript-контексте (localStorage);
* backend разрешает `CORS` для слишком широкого набора доменов, либо отражает `Origin` без проверки.

Если злоумышленнику удаётся выполнить JS-код в контексте фронтенда (`XSS`), и `CORS` настроен слишком мягко, он может:
* использовать токен для запросов к API;
* читать тела ответов и вытягивать чувствительные данные, которые должны были быть недоступны другим сайтам.

## Резюме
`SOP` — базовое правило: скрипт с одного `origin` не имеет доступа к данным другого `origin`.

`CORS` — механизм, который позволяет точечно разрешать доступ к API с других origin через заголовки `Access-Control-*`.

Браузер всегда сравнивает `Origin` запроса с политикой в ответе и решает, отдавать ли ответ JS-коду.

Основные источники уязвимостей — слишком широкие настройки (`*`), динамическое `отражение Origin без проверки`, некорректная работа с `null` и слишком `долгий кэш preflight`.

`CORS` и `CSRF` решают разные задачи: 
* `CSRF` — про несанкционированные действия, 
* `CORS` — про доступ к данным. 

Неправильный `CORS` может привести к утечке данных, даже если `CSRF` формально закрыт.
