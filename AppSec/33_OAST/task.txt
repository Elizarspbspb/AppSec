Большая практика DAST — ZAP + Burp

Цель

Провести динамическое тестирование двух готовых учебных веб-стендов:





найти уязвимости автоматическим сканированием в OWASP ZAP,



подтвердить ключевые находки вручную в Burp Suite,



оформить отчёт и рекомендации по устранению.

Исходные данные





2 готовых стенда (из материалов курса).



OWASP ZAP (desktop).



Burp Suite Community.



Что нужно сделать

Часть 1. Подготовка

Для каждого стенда:





Запустите стенд и убедитесь, что он доступен по URL.



Настройте прокси в браузере на ZAP (чтобы трафик проходил через ZAP).



В ZAP задайте область тестирования (scope): только домен/хост вашего стенда.



Руками пройдите основные страницы, чтобы ZAP увидел реальные запросы.

 

Часть 2. Сканирование в ZAP

Для каждого стенда:





Запустите Spider (и при необходимости AJAX Spider).



Запустите Active Scan по целевой области (в пределах scope).



После завершения сохраните отчёты:





отчёт ZAP в формате HTML,



Составьте список находок и отсортируйте их по приоритету.

 

Часть 3. Подтверждение находок в Burp

Для каждой выбранной находки:





Повторите воспроизведение через Burp.



Отправьте запрос в Repeater.



В Repeater измените параметр(ы)/заголовки/тело запроса так, чтобы:





доказать, что уязвимость воспроизводится (Confirmed), либо



показать, что это ложное срабатывание (False Positive).



Зафиксируйте итоговый статус для находки.

 

Часть 4. HAR-файлы и доказательства

Для каждой находки со статусом Confirmed:





Сформируйте HAR-файл, который содержит запрос и ответ при воспроизведении уязвимости:



Дополнительно приложите доказательства (достаточно одного варианта на уязвимость):





скриншот окна ZAP с alert (risk/confidence, URL/parameter),



скриншот Burp Repeater (виден запрос и ответ).

 

Часть 5. План устранения

Для каждой Confirmed уязвимости опишите, как её устранить.

Для каждой уязвимости в отчёте должны быть:





Название и краткое описание.



Где найдено: URL, метод, параметр/точка ввода.



Как воспроизвести: краткие шаги + имя HAR-файла.



Фактическое доказательство: что именно наблюдается в ответе/поведении.



Риск/влияние: что может сделать атакующий.



Рекомендации по исправлению:





конкретные меры (валидация/экранирование/настройки заголовков/контроль доступа и т.п.),



при необходимости — несколько вариантов (быстрое исправление и правильное).





Что нужно сдать

1) Отчёт (PDF или DOCX) со структурой





Перечень стендов (какие адреса тестировались).



Методика:





как сканировали в ZAP,



как подтверждали в Burp.



Сводная таблица находок:



Confirmed уязвимости (подробно по шаблону из части 5).



Общая приоритизация исправлений (что чинить первым и почему).

2) Папка с файлами (архивом)

Рекомендуемая структура:





zap-reports/stand1/ (HTML + JSON/XML)



zap-reports/stand2/ (HTML + JSON/XML)



har/ (HAR на каждую Confirmed)



screenshots/ (ZAP/Burp доказательства)

 

Требования к зачёту





2 стенда протестированы в пределах scope.



По каждому стенду выполнены Spider и Active Scan.



По каждому стенду сданы отчёты ZAP: HTML + JSON/XML.



Уязвимости подтверждены вручную в Burp (Confirmed).



На каждую Confirmed уязвимость есть HAR-файл.



False Positive и спорные случаи вынесены отдельно.

 

На отлично

Запустить сканирование одного из стендов через контейнер ZAP и приложить отдельные отчёты.

Минимум:





команда запуска,



отчёт из контейнера (HTML) и/или JSON,



короткое сравнение результатов контейнерного запуска и GUI-запуска (в отчёте 5–10 строк).

Пример (один из вариантов):





Подготовка:





docker pull owasp/zap2docker-stable



Запуск baseline-скана:





docker run --rm -t owasp/zap2docker-stable zap-baseline.py -t http://TARGET -r report.html -J report.json



Сохраните полученные файлы в zap-reports-docker/ и добавьте в сдачу.

 

Это задание тренирует полный рабочий цикл DAST: автоматическое выявление находок, ручная валидация, корректная фиксация доказательств и практичный план устранения, который можно отдавать разработчикам.
