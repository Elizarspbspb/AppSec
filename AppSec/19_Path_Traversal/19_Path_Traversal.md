# Path Traversal
До этого мы уже разбирали базовый `directory` / `path traversal`: когда через последовательности  `../` выбираемся из «разрешённой» папки и читаем системные файлы вроде  `/etc/passwd`. Теперь перейдём к более сложным, практическим случаям, когда разработчики пытаются защититься, вводят проверки и фильтры, но их всё равно можно обойти. Почти весь урок будет про реальные приёмы и полезные нагрузки.

## Проверка расширения и обход через нулевой байт
Один из популярных защитных костылей выглядит так: приложение принимает имя файла в параметре  `filename`  и проверяет, что оно заканчивается на нужное расширение. Например, разрешают только картинки `.png`. Простейшая логика на сервере может быть такой:
```py
filename = request.args.get("filename")

if not filename.endswith(".png"):
    return "Bad extension"

path = "/var/www/images/" + filename
return send_file(path)
```
Выглядит разумно: пользователь якобы всегда получает только PNG. Мы же хотим прочитать, например, `/etc/passwd`.

Здесь пригодится приём с нулевым байтом. В старых и уязвимых реализациях, особенно когда под капотом используются `C-строки`, байт `\x00`  воспринимается как «конец строки». 
В `HTTP` его можно передать как `%00`. В результате строка, которую видит проверка, и строка, которую реально использует файловая функция, могут отличаться.

**Идея простая:** приложение проверяет суффикс строки целиком, но библиотека работы с файлами обрежет путь по нулевому байту. Тогда для проверки строка выглядит как:
```
 ../../../etc/passwd%00.png
```
формально она заканчивается на `.png`, и условие `endswith(".png")` выполняется. Но при открытии файла путь может превратиться в `../../../etc/passwd`, потому что всё после нулевого байта отбрасывается.

Пример полезной нагрузки (payload — это просто специально сформированное значение параметра, которое мы отправляем, чтобы протестировать уязвимость):
```
GET /download?filename=../../../etc/passwd%00.png HTTP/1.1
Host: vulnerable.app
...
```
Если приложение действительно уязвимо к такому сценарию, в ответе вместо картинки придёт содержимое `/etc/passwd`. В реальных современных фреймворках нулевой байт часто либо запрещён, либо корректно обрабатывается, но как практический паттерн это всё равно важный кейс: сначала проверяем, потом смотрим, как именно сервер реагирует на `%00`.

## Проверка `«должно начинаться с базовой папки»` и `escape` наружу
Другой тип защиты — требование, чтобы параметр начинался с конкретного префикса. Например, разработчик хочет разрешить скачивание только из папки `/var/www/imagesи` пишет что-то вроде:
```py
filename = request.args.get("filename")

if not filename.startswith("/var/www/images"):
    return "Bad path"
 
return send_file(filename)
```
С точки зрения строки проверка жёсткая: `../../../etc/passwd` сразу отсеется. Но строковая проверка ничего не знает о нормализации пути на уровне файловой системы. Её можно обмануть: сначала указать правильный префикс, а потом выйти из него через `..`.

Классический пример полезной нагрузки:
```
/var/www/images/../../../etc/passwd
```
Строка действительно начинается на `/var/www/images`, так что проверка `startswith` пропускает её. Дальше операционная система нормализует путь: папка `images`, потом `..` возвращает нас в `/var/www`, следующее `..` в  `/var`, потом ещё одно `..` в корень. В итоге реальный файл, который открывается, — это `/etc/passwd`.

Соответствующий запрос будет выглядеть так:
```
GET /download?filename=/var/www/images/../../../etc/passwd HTTP/1.1
Host: vulnerable.app
...
```
На практике вариант с префиксом стоит пробовать всегда, когда вы прямо видите в параметре некий «жёстко заданный» путь. Часто разработчики просто проверяют строку, а затем целиком передают её файловой функции, не заботясь о нормализации и проверке итогового пути.

## Когда сервер сам вырезает `../` и игра с кодировками
Иногда обойти всё становится сложнее не из-за кода приложения, а из-за самого веб-сервера или фреймворка. В некоторых контекстах (например, путь в URL или значение filename в multipart-запросе) сервер может автоматически вычищать любые последовательности обхода каталога вроде `../` до того, как запрос попадёт в ваш код.

Из-за этого вы отправляете что-то вроде `../etc/passwd` а приложение уже получает «подчищенное» `/etc/passwd`. Чтобы обойти такую нормализацию, используют разные варианты кодирования.

Термин `«URL-кодирование»` означает замену специальных символов на последовательность `%XX`, где XX — шестнадцатеричный код байта. Например, `.` превращается в `%2e`, а `/` в `%2f`. Тогда последовательность `../` можно записать как `%2e%2e%2f`. Иногда фильтры смотрят только на сырые символы  `.` и `/` и не обращают внимания на закодированный вариант.

Полезная нагрузка в таком стиле может выглядеть так:
```
GET /download?file=%2e%2e%2f%2e%2e%2fetc%2fpasswd HTTP/1.1
Host: vulnerable.app
...
```
Если запрос проходит через несколько слоёв, каждый из которых делает своё URL-декодирование, можно использовать и двойное кодирование. Это когда символ `%` сам закодирован как  `%25`. Тогда `../` превращается в `%252e%252e%252f`. На первом этапе сервер раскодирует `%25` в `%` и передаст дальше строку вида `%2e%2e%2f`, а уже следующий слой превратит её в привычный  `../`.

Пример такой полезной нагрузки:
```
GET /download?file=%252e%252e%252fetc%252fpasswd HTTP/1.1
Host: vulnerable.app
...
```
Кроме обычной URL-кодировки, в практике используют и более экзотические варианты на основе Юникода и особенностей обработки `UTF-8`. Встречаются последовательности вида `..%c0%af`  или `..%ef%bc%8f`, где символы `/` кодируются нестандартным способом. Одни серверы такие строки сразу отклоняют, другие считают их валидным слэшем. Поэтому при тестировании пробуют набор разных вариантов и смотрят, какой именно приведёт к реальному обходу.

Важно понимать общий принцип: фильтр или веб-сервер может смотреть на одну форму строки, а конечная функция работы с файлами — на уже декодированную. Мы пытаемся найти такую комбинацию кодировок, при которой фильтр «не узнает» обход, а до файловой системы дойдёт нормальный `../`.

## Path traversal в filename при загрузке файлов
`Path traversal` интересен не только при скачивании, но и при загрузке. При отправке файла через `multipart/form-data` в запросе есть заголовок `Content-Disposition` с полем `filename`. 

Например:
```
POST /upload HTTP/1.1
Host: vulnerable.app
Content-Type: multipart/form-data; boundary=----123

------123
Content-Disposition: form-data; name="file"; filename="avatar.png"
Content-Type: image/png

...байты файла...
------123--
```
Иногда приложение доверяет значению `filename` и сохраняет файл по пути, который собирается из какой-то базовой папки и этого имени. В идеале любое `../` и странные символы должны быть вырезаны, а имя — нормализовано до простого файла, но в реальности фильтрация бывает неполной.

Здесь работают те же приёмы: вместо `avatar.png` можно попробовать передать `../../../etc/passwd`, `%2e%2e%2fetc%2fpasswd`, `%252e%252e%252fetc%252fpasswd` и похожие варианты. Если приложение не обрежет путь как следует, оно может сохранить или открыть файл не в предполагаемой директории, а в произвольном месте. В лабораторных условиях это удобная точка, чтобы отработать навыки: через `filename` потренироваться выбираться из «законной» папки хранения.

## Использование Burp Suite и готовых payload’ов для обхода путей
`Burp Suite` мы разберем в отдельном уроке.
Слово `«fuzzing»` обычно означает автоматический перебор множества вариантов входных данных, чтобы увидеть, при каких именно система ведёт себя иначе. В контексте `path traversal` это перебор разных вариантов `../`, их кодировок и обфускаций, чтобы найти тот, который пройдёт фильтры.

В `Burp Suite Professional`, в модуле `Intruder`, есть предопределённый набор полезных нагрузок для такой задачи — список `Fuzzing`, посвящённый обходу пути. Он содержит десятки вариантов закодированных `../`, нестандартных слэшей и т.п. Практическая схема примерно такая: перехватываете запрос с параметром, связанным с именем файла или пути (`file`, `path`, `filename`, `page`), отправляете его в `Intruder`, выделяете параметр как позицию для атаки и выбираете нужный список payload’ов. `Intruder` автоматически подставит каждый вариант и выполнит запрос. В ответах можно сравнивать коды статуса, длину, фрагменты тела и искать те комбинации, при которых начинает раскрываться что-то вроде содержимого `/etc/passwd` или другого системного файла.

Это очень удобный способ не придумывать все последовательности вручную. Вы сначала прогоняете стандартный набор, а потом уже углубляетесь в те варианты, которые дали отличающийся результат, и разбираете, почему именно они «проскочили» через фильтр.

Продвинутый `path traversal` — это не только `../../etc/passwd`, но и игра с ограничениями, которые накладывает приложение и сервер. Если проверяют только расширение, пробуем вставить нулевой байт и завершить путь раньше. Если требуют, чтобы путь начинался с базовой папки, добавляем эту папку и затем вылезаем наружу через `../`. Если сервер вычищает очевидные `../`, пробуем `URL-кодирование`, двойное кодирование и нестандартные варианты. Всё это можно делать руками, а можно ускорить с помощью фреймворков вроде `Burp Intruder` и готовых списков полезных нагрузок для обхода пути.
