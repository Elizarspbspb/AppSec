# Nuclei
В предыдущих уроках мы говорили про `ZAP` и `Burp` как про «интерактивные» инструменты: ты смотришь трафик, меняешь запросы, пошагово исследуешь одно конкретное приложение.

`Nuclei` — это другой класс. Его задача — быстро и автоматически пройтись по большому количеству хостов и проверить их на набор известных уязвимостей и типичных ошибок, которые описаны в шаблонах.

Его удобно воспринимать как «инструмент, который запускает проверки, описанные в YAML-файлах». Сами проверки находятся в отдельной коллекции шаблонов, которую можно обновлять и расширять.

## Что такое nuclei в двух словах
`Nuclei` — это сканер уязвимостей от `ProjectDiscovery`, который работает по простой схеме:
* есть набор целей (домены, IP, URL);
* есть набор шаблонов-проверок в формате YAML;
* `nuclei` последовательно применяет шаблоны к целям и фиксирует, где условия сработали.

Логика того, что именно считается уязвимостью, не зашита внутрь программы жёстко — она вынесена в шаблоны. Поэтому инструмент можно настроить под свои задачи: использовать готовые шаблоны, писать свои, включать и выключать нужные группы проверок.

## Где nuclei реально используют
Для специалиста по безопасной разработке `nuclei` полезен в ситуациях, где нужно быстро получить отчет о множестве хостов.

Классический пример — проверка своего внешнего периметра. Есть список доменов и серверов, опубликованных наружу. Раз в какое-то время можно запускать `nuclei` по этому списку и смотреть, не появились ли:
* известные уязвимости по свежим CVE;
* открытые панели администрирования;
* лишние директории с бэкапами или логами;
* ошибки конфигурации.

Внутри компании `nuclei` можно встроить и в процесс разработки. После деплоя тестового стенда запускается `nuclei` с выбранным профилем шаблонов. Это не заменяет ручное тестирование, но позволяет быстро отловить типовые проблемы: забытые тестовые панели, дефолтные конфигурации, устаревшие компоненты.

## Ключевые особенности nuclei
Главная идея `nuclei` — подход на основе шаблонов. Каждая проверка описана в отдельном `YAML-файле`: там указано, к какому протоколу она относится, какие запросы нужно отправить и по каким признакам понимать, что цель уязвима. Это делает проверки прозрачными: их можно прочитать, понять и при необходимости адаптировать.

`Nuclei` поддерживает несколько протоколов. Чаще всего используется `HTTP(S)` для проверки веб-приложений и API, но есть и шаблоны для DNS, TCP, SSL/TLS и других контекстов. Это значит, что можно искать проблемы как на уровне веб-слоя, так и на уровне инфраструктуры.

Ещё один важный момент — `расширяемость`. Чтобы добавить свою проверку, не нужно писать код на Go или другом языке. Достаточно описать её в YAML: запросы, ожидаемые статусы, строки в ответе, структуру JSON и так далее. Это позволяет быстро реагировать на новые уязвимости: как только появляется описание проблемы, можно почти сразу сделать под неё шаблон.

И, наконец, вокруг `nuclei` есть большая коллекция готовых шаблонов — `nuclei-templates`. Её поддерживает сообщество: туда регулярно добавляются проверки на новые CVE, ошибки конфигурации, используемые технологии. На практике это означает, что установив `nuclei` и подтянув шаблоны, ты уже можешь запускать сотни и тысячи осмысленных проверок, не создавая ничего с нуля.

## Пример простого шаблона
Чтобы понимать, чем именно занимается `nuclei`, полезно один раз взглянуть на структуру простого шаблона.
```
id: example-exposed-panel
info:
  name: Example Admin Panel Exposure
  author: security-team
  severity: medium
  description: Проверка доступности панели администрирования по предсказуемому пути.

http:
  - method: GET
    path:
      - "{{BaseURL}}/admin/"

    matchers:
      - type: word
        part: body
        words:
          - "Admin Panel"
```
По смыслу здесь всего несколько частей.

* Наверху блок `id` и `info` — служебная информация. `id` даёт шаблону уникальное имя, по которому его можно искать и фильтровать. В `info` указывается человекочитаемое название проверки, автор, уровень серьёзности и краткое описание.

* Дальше идёт блок `http`. Он говорит `nuclei`, что эта проверка относится к HTTP и нужно отправить GET-запрос на адрес  `{{BaseURL}}/admin/`. Переменная `{{BaseURL}}` при запуске подставляется для каждой цели.

Наконец, `{{BaseURL}} matchers` описывает условие срабатывания: если в теле ответа  (`part: body`) будет обнаружена строка `Admin Panel`, nuclei считает, что шаблон «сработал» и цель попадает в отчёт.

На уровне курса этого достаточно: шаблон — это формальное описание того, что отправить и что поискать в ответе. Остальные детали синтаксиса можно разбирать уже в практическом модуле.

## Установка nuclei в Linux
На практике чаще всего используют готовый бинарник с GitHub и стандартный путь `/usr/local/bin`. Сначала убедись, что есть утилиты curl или wget, а также unzip:
```
sudo apt update
sudo apt install curl unzip
```
(для других дистрибутивов используются свои команды пакетного менеджера, суть та же — установить curl/wget и unzip).

Далее можно скачать текущую стабильную сборку nuclei прямо с страницы релизов ProjectDiscovery.
```
cd /tmp
curl -L -o nuclei.zip "https://github.com/projectdiscovery/nuclei/releases/latest/download/nuclei-linux-amd64.zip"
unzip nuclei.zip
sudo mv nuclei /usr/local/bin/
```
После этого имеет смысл проверить, что бинарник доступен в `PATH` и запускается:
```
nuclei -h
```
Если команда выводит справку по параметрам, значит установка прошла успешно.

Отдельно нужно один раз подтянуть или обновить шаблоны. Проще всего сделать это встроенной командой:
```
nuclei -update-templates
```
По умолчанию `nuclei` создаст каталог с шаблонами (обычно в домашней директории пользователя, например ~/.local/nuclei-templates или похожий путь) и будет использовать его при запуске. Если в инфраструктуре принято хранить шаблоны в другом месте (например, в общем каталоге или репозитории), можно либо перенастроить переменную окружения `NUCLEI_TEMPLATES`, либо явно указывать путь к шаблонам флагом `-t` при запуске.

## Основной цикл работы
Работа с `nuclei` строится вокруг четырёх вещей:
* список целей, 
* набор шаблонов, 
* параметры запуска,
* анализ результата.

Сначала нужно определить, что именно мы будем проверять. Это может быть один домен, несколько URL или большой перечень хостов в текстовом файле. Часто такой список получается как результат работы других инструментов разведки.

Затем выбирается набор шаблонов. Иногда имеет смысл запускать всё `nuclei-templates` (например, на отдельном стенде), но чаще отбирают только нужные категории: шаблоны под свежие CVE, проверки конфигураций. Это помогает контролировать как время сканирования, так и релевантность результатов.

После этого `nuclei` запускается с указанием файла целей, набора шаблонов и параметров параллелизма. Инструмент сам перебирает комбинации «цель + шаблон», отправляет запросы и применяет описанные в шаблоне условия. Там, где условия выполнены, он записывает срабатывание.

Результаты можно выводить в консоль или сохранять в файл. Каждое срабатывание содержит идентификатор шаблона, информацию о цели и базовое описание проблемы. Дальше по этим результатам уже принимаются решения: какие находки проверять руками через ZAP/Burp, какие дефекты заводить в трекер задач, какие настройки инфраструктуры пересмотреть.

## Базовые команды nuclei
Самый простой запуск по одному URL может выглядеть так:
```
nuclei -u https://target.example
```
Эта команда:
* берёт указанный URL как цель,
* применяет к нему шаблоны по умолчанию (из установленных nuclei-templates),
* выводит срабатывания в консоль.

**Для работы со списком целей** обычно используют файл, например `targets.txt`, где каждая строка — домен или URL. Тогда запуск будет таким:
```
nuclei -l targets.txt
```
**Если нужно ограничиться определённым набором шаблонов**, `nuclei` позволяет задавать путь:
```
nuclei -l targets.txt -t cves/
```
Здесь `-t` указывает каталог с шаблонами (в данном случае — все шаблоны CVE). Можно указать и конкретный файл шаблона.

Часто важен формат вывода. **Для интеграции с другими инструментами** используют, например, JSON:
```
nuclei -l targets.txt -t cves/ -json -o results.json
```
В этом случае:
* `-json` в старой венрии включает JSON-вывод,
* `-jsonl` — сохраняет результаты в формате JSON Lines (один JSON-объект на строку).
* `-o results.json` записывает результаты в файл.

Параметры параллелизма (`-c`, `-rate` и т.п.) стоит подбирать с осторожностью и уже на практике. В теоретическом блоке достаточно понимать, что `nuclei` умеет отправлять много запросов одновременно, и это регулируется флагами запуска.

Запустить `Nuclei` с базовым набором шаблонов и **сохранить результаты в файлы**:
```
nuclei -u http://TARGET1 -o baseline-target1.txt
```

`Nuclei` умеет **определять технологии приложения Wappalyzer и сопоставлять их с тегами шаблонов** через:
```
nuclei -u http://62.173.140.174:36103/ -automatic-scan
```
В исходниках `Nuclei` этот режим описан как автоматическое сканирование с использованием определения технологий `Wappalyzer` и сопоставления их с тегами шаблонов.

Очень вероятно, что массовая параллельная проверка **Nuclei перегружает/подвешивает** учебный стенд.

`-rl 2` сильно ограничит количество запросов в секунду:
```
nuclei \
  -u http://62.173.140.174:36103/ \
  -rl 2 \
  -timeout 15 \
  -retries 1 \
  -o 103.txt
```

Для обычного веб-приложения сначала попробуй **headless**. Обычный HTTP-шаблон получает HTML, но не исполняет JavaScript в браузере. Это особенно полезно для DOM XSS, потому что такая уязвимость может проявляться только после выполнения JavaScript. `Headless`-шаблоны запускают браузерный движок. `Nuclei` требует отдельного флага `-headless`.

Посмотреть, есть ли headless-шаблоны:
```
find ~/nuclei-templates -type f -name "*.yaml" | xargs grep -l "headless:" | head -20
```
Запустить их:
```
nuclei \
  -u http://62.173.140.174:36103/ \
  -headless \
  -o 103-headless.txt
```

## Как nuclei дополняет ZAP и Burp
По подходу `nuclei` и `ZAP/Burp` решают разные задачи. `ZAP` и `Burp` удобны, когда есть конкретное веб-приложение и нужно разобраться, как оно работает: какие запросы отправляет браузер, как устроена авторизация, какие параметры влияют на бизнес-логику. Там основная работа идёт через `прокси`, `Repeater`, `Intruder` и похожие инструменты.

**Nuclei** не работает как прокси и не встраивается в браузер. Он сам отправляет запросы к целям и проверяет объективные технические признаки: присутствует ли уязвимость такой-то CVE, доступна ли определённая панель, выставлены ли защитные заголовки, не оставлены ли открытыми служебные файлы.

Сценарий работы выглядит так: 
1. На верхнем уровне `nuclei` пробегает по большому перечню хостов и выдаёт список «подозрительных совпадений». 
2. После этого отдельные интересные случаи открываются уже через `ZAP` или `Burp`, чтобы внимательно посмотреть на контекст, проверить влияние на данные, воспроизвести атаку вручную и подготовить нормальное описание для отчёта.

## Типы шаблонов в nuclei
Коллекция `nuclei-templates` логически делится на несколько групп.

Часть шаблонов ***ориентирована на конкретные CVE***. Они содержат точные условия для проверки уязвимости в определённых продуктах и версиях. Это полезно, когда выходит новый CVE, и нужно быстро понять, задевает ли он ваши сервисы.

Есть шаблоны, которые ищут экспозиции — открытые каталоги, панели, служебные файлы, резервные копии. ***Такие проверки часто выявляют*** не столько «уязвимости» в строгом смысле, сколько ***последствия неаккуратной конфигурации***.

Отдельная группа — `misconfigurations`. Эти шаблоны ***обращают внимание на небезопасные настройки***: 
* лишние заголовки с информацией о сервере, 
* отсутствие защитных заголовков, 
* небезопасные режимы работы.

На основе таких находок формируются задачи по укреплению конфигурации.

Наконец, есть ***шаблоны для определения технологий***. Они по характерным признакам в заголовках и теле ответов пытаются понять: 
какой веб-сервер используется, 
какая панель управления стоит за приложением. 

Это полезно как подготовительный этап: зная стек, проще выбирать релевантные проверки и CVE.

## Ограничения и здравые ожидания
Важно честно понимать границы применения `nuclei`. Он не умеет анализировать бизнес-логику приложения, последовательность действий пользователя, сложные сценарии авторизации и переходов. Его сильная сторона — формализуемые, повторяемые проверки по техническим признакам.

Качество результатов напрямую зависит от шаблонов. Если шаблоны устарели или подобраны без учёта контекста, можно либо пропустить важную проблему, либо получить много второстепенных срабатываний.

Наконец, даже при использовании хороших шаблонов критичные находки нужно проверять руками. Особенно в боевых системах с чувствительными данными: перед тем как делать выводы и планировать работу по устранению, стоит открыть конкретный кейс в ZAP/Burp, убедиться в воспроизводимости и оценить реальный риск.
