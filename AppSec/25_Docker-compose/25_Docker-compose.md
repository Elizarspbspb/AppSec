# docker-compose
В этом уроке разберём `docker-compose` как инструмент для описания и запуска целых стендов на `Docker`: уязвимые приложения для обучения, тестовые инфраструктуры, временные среды для экспериментов.

```bash
sudo apt install docker-compose
```

## Что такое docker-compose на практике
Обычный `docker run` хорош, когда нужно запустить один контейнер. Но реальное приложение почти всегда состоит минимум из двух частей: веб-сервис и база данных, иногда ещё очередь, прокси, система логирования.

`docker-compose` - это инструмент, который позволяет описать такое многокомпонентное приложение в одном файле формата `YAML` и управлять им одной командой. `YAML` - это текстовый формат, в котором данные задаются отступами и ключами, примерно как структурированный конфиг.

Схема работы проста:
1. пишем файл `docker-compose.yml`, где описываем все сервисы, сети и тома;
2. запускаем `docker-compose up`;
3. получаем весь стенд целиком: контейнеры поднимаются, подключаются к нужным сетям и томам, порт приложения прокидывается наружу;
4. когда стенд больше не нужен, выполняем `docker-compose down -v` и убираем и контейнеры, и данные томов.

В отличие от одиночных команд Docker, compose-файл удобно хранить в системе контроля версий, ревьюить и воспроизводить на других машинах.

## Зачем docker-compose специалисту по безопасной разработке
`Compose` решает сразу несколько задач, важных именно в контексте безопасности.

Во-первых, это быстрый подъём уязвимых стендов для обучения и экспериментов. Типичные примеры - `DVWA`, `WebGoat`, `OWASP Juice Shop`. Обычно это не один контейнер, а связка «приложение + база», иногда с дополнительными сервисами. Описав такой стенд в `docker-compose.yml`, можно поднимать его за одну команду на занятиях, в лаборатории или на своём ноутбуке.

Во-вторых, `compose` удобен для инфраструктуры тестирования безопасности. Например, связка `ZAP + Selenium` для автоматизированного сканирования веб-приложений, или стек для сбора логов и метрик (`ELK` / `OpenSearch`) для анализа атак. Все зависимые контейнеры описываются в одном файле, и такой стенд легко развернуть на любой машине.

В-третьих, это способ создавать изолированные среды под разные типы тестов. Например, один compose-файл - для `динамического тестирования` конкретного приложения, другой - для `нагрузочного тестирования`, третий - для воспроизведения конкретного инцидента. Каждый из них - отдельное, воспроизводимое окружение.

Отдельное преимущество - управляемость жизненным циклом. Стенд можно поднять командой `docker-compose up -d`, а затем полностью убрать вместе с томами командой `docker-compose down -v`, не оставляя «мусора» на машине.

## Пример docker-compose.yml и разбор
Посмотрим на упрощённый пример файла `docker-compose.yml`, который поднимает учебное уязвимое веб-приложение и базу данных для него:
```
version: "3.9"
services:
  web:
    image: vulnerables/web-dvwa
    ports:
      - "8080:80"
    environment:
      DB_HOST: db
      DB_USER: dvwa
      DB_PASS: secret
    depends_on:
      - db
    networks:
      - labnet

  db:
    image: mysql:5.7
    environment:
      MYSQL_ROOT_PASSWORD: rootpass
      MYSQL_DATABASE: dvwa
      MYSQL_USER: dvwa
      MYSQL_PASSWORD: secret
    volumes:
      - db_data:/var/lib/mysql
    networks:
      - labnet

volumes:
  db_data:

networks:
  labnet:
```

Разберём важные части этого файла и заодно те директивы, которые чаще всего встречаются в `docker-compose` конфигурациях.

### services
Этот блок описывает логические сервисы стенда. В примере их два: ***web*** и ***db***. Каждый сервис - это по сути шаблон для одного или нескольких контейнеров. Здесь `задаётся, какой образ использовать`, какие порты публиковать, какие переменные окружения передать контейнеру, к каким сетям его подключить. ***web*** и ***db*** как примеры сервисов!!!

Сервис ***web*** использует готовый образ `vulnerables/web-dvwa` - это учебное уязвимое приложение `DVWA`. 

Сервис ***db*** использует образ `mysql:5.7` и разворачивает базу данных с заданными параметрами. Оба сервиса объединены в одну сеть `labnet`, чтобы видеть друг друга по именам.

### image
Ключ `image` указывает, какой Docker-образ использовать. В контексте безопасности важно понимать, откуда этот образ: официальный он или пользовательский, поддерживается ли, какие у него уязвимости. В примере это учебные образы, предназначенные для лабораторий.

### ports
Направление "8080:80" означает: порт 80 внутри контейнера ***web*** опубликован как порт 8080 на хостовой машине. То есть стенд будет доступен по адресу `http://localhost:8080`. Это точка входа для тестирования. С точки зрения безопасности через секцию `ports` контролируется, что именно выходит «наружу», а что остаётся доступным только внутри сети контейнеров.

### environment
Переменные окружения задают конфигурацию приложений. В сервисе ***web*** через `DB_HOST: db` указываем, что база данных доступна по имени ***db*** (это имя сервиса в той же сети). В сервисе ***db*** переменные `MYSQL_ROOT_PASSWORD`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` конфигурируют MySQL. Здесь сразу видно один из рисков `docker-compose`: секреты и пароли часто оказываются прямо в YAML-файле. В учебном стенде это допустимо, но в реальных проектах такие значения следует выносить в отдельные механизмы управления секретами или хотя бы в внешние файлы.

### depends_on
Эта директива описывает зависимость между сервисами. Запись `depends_on: - db` у сервиса ***web*** означает, что при запуске `docker-compose up` сервис ***db*** будет стартовать раньше веб-сервиса. Это не гарантия полной готовности базы (для этого используют дополнительные механизмы проверки), но как минимум задаётся правильный порядок запуска.

### volumes
Внизу файла объявлен именованный том `db_data`, а в сервисе ***db*** он монтируется в `/var/lib/mysql`. Это означает, что ***данные базы переживут перезапуск контейнера и будут храниться отдельно от слоя контейнера.*** Для безопасной разработки тома важны тем, что они могут содержать реальные данные, логи, дампы. В учебном стенде удобно удалять такой том вместе со стендом через `docker-compose down -v`, чтобы не накапливать чувствительные данные.

### networks
Секция `networks` в конце файла объявляет сеть `labnet`, а в сервисах ***web*** и ***db*** прописано подключение к этой сети. В результате эти контейнеры могут общаться друг с другом по внутренним именам (как ***db*** или ***web***), но из-вне доступом управляют только через секцию `ports`. Это основа сетевой изоляции внутри compose-проекта: при необходимости можно добавить отдельные сети для разных групп сервисов.

## Преимущества docker-compose с точки зрения безопасности и процессов
У `docker-compose` есть несколько свойства, которые особенно полезны в контексте безопасной разработки.

**Во-первых, воспроизводимость.**   
`docker-compose.yml` - это единый текстовый сценарий, который можно положить в Git, просматривать на код-ревью и запускать на разных машинах. Лабораторный стенд, однажды настроенный, через год можно поднять заново в том же виде, чтобы воспроизвести уязвимость или эксперимент.

**Во-вторых, управляемая изоляция.**  
Через блоки `services`, `networks` и `volumes` чётко видно, какие компоненты есть в системе, как они связаны, какие данные они разделяют. Это помогает оценивать риски: какие сервисы не должны иметь общий том, какие порты не стоит публиковать наружу, какие значения не должны быть прописаны в переменных окружения.

**В-третьих, простой жизненный цикл стенда.**  
Для учебных и тестовых сценариев важно, чтобы окружение можно было не только создать, но и полностью убрать. `docker-compose up -d` поднимает стенд в фоне, `docker-compose down -v` остановит контейнеры, удалит их и очистит связанные тома. Это уменьшает риск того, что устаревшие данные или сервисы останутся включёнными и превратятся в непредсказуемую точку атаки.

В результате `docker-compose` становится удобным инструментом именно для специалиста по безопасной разработке: он позволяет задавать сложные стенды, держать их под контролем версий, быстро поднимать и так же быстро уничтожать, при этом явно фиксируя все связи, данные и параметры, которые могут влиять на безопасность тестируемых приложений.

## Основные команды для перезапуска (в командной строке - docker-compose)
### 1. Простой перезапуск существующих контейнеров (без пересборки):
```bash
docker compose up -d
```
* `-d` — запуск в фоновом режиме;
* если контейнеры уже есть, они перезапустятся;
* если нет — создадутся из текущих образов.
### 2. Пересборка и перезапуск (если меняли Dockerfile или код):
```bash
docker compose up -d --build
```
* `--build` — принудительно пересобирает образы перед запуском.
### 3. Жёсткая пересборка без кеша (если изменения не применяются):
```bash
docker compose build --no-cache
docker compose up -d
```
* `--no-cache` — игнорирует кеш сборки, собирает всё заново.
### 4. Обновление образов + пересборка + перезапуск:
```bash
docker compose pull
docker compose build
docker compose up -d
```
* `pull` — скачивает свежие версии образов из реестра;
* `build` — пересобирает локальные образы;
* `up -d` — запускает контейнеры.
### 5. Перезапуск конкретного сервиса (если в docker-compose.yml их несколько):
```bash
docker compose up -d --build <service-name>
```
Пример:
```bash
docker compose up -d --build web
```

## Полный цикл действий: от остановки до запуска
Если нужно полностью перезапустить всё с нуля:
### 1.  Остановить и удалить все контейнеры, сети, тома (полная очистка):
```bash
docker compose down
```
***Важно: команда удалит тома по умолчанию. Чтобы сохранить тома (например, с данными БД), используйте:***
```bash
docker compose down --volumes
```
### 2. При необходимости — очистить неиспользуемые образы и кеш:
```bash
docker image prune -f
docker builder prune -f
```
### 3. Пересобрать образы и запустить контейнеры:
Вариант 1 (быстрый):
```bash
docker compose up -d --build
```
Вариант 2 (с обновлением базовых образов):
```bash
docker compose pull
docker compose build --no-cache
docker compose up -d
```
## Полезные команды для контроля
### Проверить статус контейнеров:
```bash
docker compose ps
```
### Посмотреть логи (в реальном времени):
```bash
docker compose logs -f
```
### Чтобы посмотреть логи конкретного сервиса:
```bash
docker compose logs -f <service-name>
```
### Подключиться к контейнеру (например, для отладки):
```bash
docker compose exec <service-name> bash
```
Пример:
```bash
docker compose exec web bash
```
