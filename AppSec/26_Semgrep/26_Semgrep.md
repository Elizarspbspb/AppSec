# Semgrep
До этого мы фокусировались на инструментах, которые ищут уязвимости в запущенном приложении. Теперь мы переходим к `SAST` (Static Application Security Testing) — анализу исходного кода без его выполнения. 

И начнём с Semgrep.

## Что такое Semgrep
`Semgrep` — это быстрый и легковесный инструмент статического анализа с открытым исходным кодом. Если sqlmap — это «оркестр» для SQL-инъекций, то `Semgrep` — это «швейцарский нож» для поиска багов и уязвимостей прямо в коде.

Его главная особенность — декларативный подход. Вы описываете паттерн уязвимого кода почти так же, как он выглядит в реальности, а `Semgrep` находит его, понимая структуру программы.

***Философия Semgrep: «Код как данные»***

В AppSec-индустрии долгое время доминировали «тяжёлые» SAST-решения, которые сканировали проект часами и требовали сложной настройки. `Semgrep` изменил правила игры:

1. Скорость: он работает молниеносно, что позволяет встраивать его прямо в `CI/CD` (например, проверять код на каждом Git-коммите).
2. Простота правил: вам не нужно быть экспертом по компиляторам, чтобы написать своё правило.
3. Огромная база (Registry): сообщество уже написало тысячи правил для поиска уязвимостей в `Python`, `JS`, `Go`, `Java` и других языках.

## Чем Semgrep отличается от «классических» SAST-инструментов
Статических анализаторов много. `Semgrep` занял свою нишу за счёт нескольких особенностей.

**Во-первых, простота написания правил.**
Правила описываются в `YAML`-файлах и выглядят почти как обычный кусок кода с небольшими дополнениями. Вместо сложных DSL или собственных языков описания вы используете знакомый синтаксис (Python, JS, Java и т.д.) и специальные «метапеременные» вида `$X`, `$Y`:
```
rules:
  - id: python-eval
    languages: [python]
    pattern: eval($EXPR)
    message: "Небезопасный eval"
    severity: WARNING
```
Такое правило найдёт любые вызовы `eval(...)` в Python-коде, независимо от конкретного аргумента. Похожий принцип работает для других языков: вы пишете паттерн «как код», `Semgrep` сопоставляет его с реальными фрагментами исходников.

**Во-вторых, ориентация на синтаксис, а не на компиляцию.** `Semgrep` разбирает код до `AST`, но не требует:
* полноценной сборки проекта,
* наличия всех зависимостей,
* запуска компилятора или интерпретатора.

За счёт этого он работает быстро и подходит не только для `CI`, но и для интерактивного использования при разработке.

**В-третьих, широкая поддержка языков.**
Из коробки `Semgrep` работает с несколькими десятками языков и диалектов: `Python`, `JavaScript`/`TypeScript`, `Java`, `Go`, `PHP`, `C`, `C#`, `Ruby` и др. Для практики безопасной разработки это удобно: можно применять единый инструмент к разным сервисам в микросервисной архитектуре.

**Наконец, открытый исходный код и удобство в открытых проектах.**  
`Semgrep` — свободный инструмент, им можно пользоваться в открытых репозиториях без лицензий и сложных развёртываний, подключая как свою собственную базу правил, так и готовые наборы из сообщества.

## Основные концепции: правило, паттерн и AST
Чтобы грамотно использовать `Semgrep`, достаточно разобраться в трёх базовых понятиях.

**1. Правило (Rule).**  
`Правило` — это запись в YAML-файле, которая описывает:
* на каких языках и файлах оно действует,
* какой паттерн искать,
* какое сообщение вывести,
* сколько это критично (severity),
* при необходимости — дополнительные условия (исключения, контекст и т.п.).

Структурно правило можно представить так:
```
rules:
  - id: insecure-request
    languages: [python]
    message: "HTTP-запрос без таймаута"
    severity: WARNING
    pattern: requests.get($URL)
```
Здесь:
* id — уникальный идентификатор правила;
* languages — список языков;
* message — текст, который появится в отчёте;
* severity — уровень серьёзности;
* pattern — собственно паттерн (о нём ниже).

Файл с такими правилами `Semgrep` воспринимает как «набор проверок», который нужно применить к коду.

**2. Паттерн (Pattern)**  
Паттерн описывает, что именно мы ищем в коде. Главное, что он:
* записывается в привычном синтаксисе целевого языка,
* может содержать метапеременные `$X`, `$URL`, `$ANYTHING`, которые соответствуют произвольным подвыражениям.

Например:
```
pattern: requests.get($URL, timeout=None)
```
найдёт вызовы `requests.get`, где явно указано `timeout=None`. Если мы хотим отловить любые вызовы без таймаута, можно использовать более сложные паттерны или комбинацию `pattern` / `pattern-not`.

Паттерн не ограничивается строкой кода: `Semgrep` умеет сопоставлять целые блоки, функции, цепочки вызовов, а также различные формы записи (например, с переносом строк, разными форматами аргументов).

**3. AST (Abstract Syntax Tree)**  
`Абстрактное синтаксическое дерево` — это дерево, в которое парсер превращает исходный код. В узлах дерева хранится структура программы:
* вызов функции с аргументами;
* объявление переменной;
* условный оператор;
* блок кода в теле функции.

Для человека код — это текст. Для `Semgrep` код — это дерево, где он ищет узлы, соответствующие паттернам. Именно поэтому он не путает код с комментариями, различает разные конструкции, понимает порядок аргументов и вложенность, а не просто «совпадение по тексту».

Практически это означает, что:
* правило на `eval($X)` не сработает на слове eval в комментарии;
* паттерн на `if ($COND) { ... }` не будет цепляться за случайные фигурные скобки;

Semgrep понимает различие между `foo(bar())` и `bar(foo())` даже при сложном форматировании.

## Основные возможности и CLI (Command Line Interface)
`Semgrep` управляется через консоль, аналогично инструментам, которые мы разбирали ранее.

Таблица основных команд Semgrep:

|||
|---|---|
|Команда / Флаг|Назначение|
|`semgrep scan`|Запускает проверку кода в текущей директории.|
|`--config auto`|Автоматически подбирает правила на основе языков, найденных в проекте.|
|`--config p/default`|Использует стандартный набор правил безопасности от разработчиков Semgrep.|
|`--config p/django`|Использует набор правил безопасности на `Django`.|
|`--error`|Завершает работу с ошибкой, если найдены уязвимости (полезно для CI/CD).|
|`--json`|Выводит результат в формате JSON для дальнейшей автоматизации.|

## Работа с Semgrep Registry
Вам не обязательно сразу писать свои правила. У `Semgrep` есть публичный `Registry` — библиотека готовых пресетов.

Например, если вы разрабатываете на `Django`, вы можете запустить проверку именно под этот фреймворк:
```
semgrep scan --config p/django
```
Инструмент скачает актуальные правила по безопасности (поиск жестко заданных секретов, небезопасных настроек `middleware` и т.д.) и проверит ваш код.

## Когда использовать Semgrep
***На ранних этапах (Shift Left):*** чтобы разработчик видел баги ещё до того, как код попадёт на сервер.

***В CI/CD пайплайнах:*** для блокировки коммитов с явными уязвимостями.

***При аудите кода:*** чтобы быстро «подсветить» все подозрительные функции (например, использование `dangerous_eval()` или `shell=True`).

`Semgrep` — это не замена глубокому ручному аудиту, но это лучший способ автоматизировать поиск 80% типичных ошибок безопасности.

## Установка
Установить `Semgrep` локально на macOS, Linux, Windows можно с помощью командной строки:
```bash
python3 -m pip install semgrep
```
Подтвердите установку следующей командой:
```bash
semgrep --version
```

## Использование
```bash
semgrep scan --config=../semgrep-rules/python -j 4 -v  ./ > test.txt
```
Можно запустить `Semgrep` локально. Вы можете протестировать правила реестра `Semgrep` с помощью следующей команды, где PATH/TO/SRC путь с исходному коду:
```
semgrep --config=auto PATH/TO/SRC
```
Запустить правила `Semgrep` одновренно с локальными правилами можно с помощью команды:
```
semgrep --config="RULESET-ID" --config=PATH/TO/MYRULE.YAML PATH/TO/SRC
```
Запускает проверку кода в текущей директории:
```
semgrep scan
```
Автоматически подбирает правила на основе языков, найденных в проекте:
```
semgrep scan --config auto
```
Автоматически подбирает правила на основе языка python:
```
semgrep scan --config p/python
```

`Semgrep` автоматически рекурсивно сканирует все подпапки, если указать корневую директорию. Вам не нужно вручную перечислять все папки.

Базовая команда:
```bash
semgrep scan --config=<правило> /путь/к/вашей/папке/проекта
```
Используйте команду:
```bash
semgrep scan --config=/путь/к/папке/с/правилами /путь/к/папке/с/кодом
```
* `--config=/путь/к/папке/с/правилами` — указывает Semgrep искать все `.yaml-файлы` внутри этой папки и всех её подпапок.
* `/путь/к/папке/с/кодом` — целевая директория для сканирования.
* `Semgrep` автоматически рекурсивно обходит все подпапки в обеих директориях.

### Сканирование всех файлов с набором правил из реестра
```bash
semgrep scan --config=p/kubernetes /путь/к/папке/проекта
```
* `p/kubernetes` — набор правил для проверки Kubernetes‑манифестов (.yaml).
* `Semgrep` сам найдёт все `.yaml‑файлы` во всех подпапках указанной директории.

### Сканирование с локальным файлом правил для .yaml
Если у вас есть собственный файл правил (например, my-yaml-rules.yaml):
```bash
semgrep scan --config=my-yaml-rules.yaml /путь/к/папке/проекта
```
### Сканирование с несколькими файлами правил
```bash
semgrep scan --config=rule1.yaml --config=rule2.yaml /путь/к/папке/проекта
```
### Автоматическое определение правил (--config=auto)
`Semgrep` попытается сам подобрать подходящие правила для языков и форматов в вашей папке:
```bash
semgrep scan --config=auto /путь/к/папке/проекта
```
### Сканирование только конкретных файлов (явное указание)
Чтобы ограничить сканирование только файлами с расширением `.yaml`, используйте флаг `--include`:
```bash
semgrep scan --config=p/kubernetes --include="*.yaml" /путь/к/папке/проекта
```
### Исключение некоторых папок
Если нужно исключить определённые директории (например, vendor, node_modules), используйте `--exclude`:
```bash
semgrep scan --config=p/kubernetes --include="*.yaml" --exclude=vendor --exclude=node_modules /путь/к/папке/проекта
```
## Полезные флаги для больших папок
* `-j N` — запуск в несколько потоков (ускоряет сканирование). Замените N на число ядер процессора:
```bash
semgrep scan -j 4 --config=p/kubernetes /путь/к/папке
```
* `--verbose` или `-v` — подробный вывод (покажет, какие файлы сканируются):
```bash
semgrep scan -v --config=p/kubernetes /путь/к/папке
```
* `--quiet` — только найденные проблемы, без лишней информации:
```bash
semgrep scan --quiet --config=p/kubernetes /путь/к/папке
```
* `--text --text-output=results.txt` - сохранение результатов в текстовый файл:
```bash
semgrep scan --text --text-output=results.txt --config=p/kubernetes /путь/к/папке
```
НО НЕ СРАБОТАЛ. Проще `>`. 

## Встраивание в CI/CD
Для того чтобы использовать этот инструмент в `CI/CD`, нужно указать переменные `CI/CD`:
* `REPO_URL` <-- переменная для сканирования, удаленных репозиториев. Она нужна если вы хотите просканировать проект, который находится в удаленном репозитории
* `PROJECT_PATH` <-- указывает директорию, где будет находится проект в вашем репозитории. Например если ваш код не лежит в главной директории репозитория, то нужно явным образом указать путь к этой директории.

Пример встраивания `semgrep` в ваш CI/CD:
```
SEMGREP:
  stage: semgrep
  variables:
    REPO_URL: ""
    PROJECT_PATH: "."
  trigger:
    include:
      - project: '1105/sast/semgrep'
        ref: 'master'
        file: '.gitlab-ci.yml'  
```
