Мы шли от простого учебного стенда к более реалистичному приложению. В реальной жизни данные живут в СУБД, и безопасность приложения во многом начинается с того, как вы описали схему, какие запросы пишете и как управляете правами. Если вы храните пароли «как есть», склеиваете запросы из строк и выдаёте приложению права суперпользователя, то SQL-инъекции и утечки у вас точно будут.

В этом уроке последовательно пройдём четыре важных шага, которые связывают базы данных и безопасность приложения:

1.     Как устроены данные – что такое таблицы, строки, столбцы, первичные и внешние ключи, и почему структура влияет на надёжность системы.

2.     Какие правила защищают данные – разберём ограничения и типы данных, которые помогают базе не принимать некорректные или опасные значения.

3.     Как работать с данными через SQL – вспомним основные команды.

4.     Где и почему возникают уязвимости – поймём, на каком этапе появляются SQL-инъекции и почему параметризация запросов – это вопрос безопасности, а не стиля кода.

 



Реляционная модель простыми словами

Реляционная база данных – это способ хранения данных в виде связанных таблиц. 
Представьте обычную таблицу в Excel:





Таблица – это набор однотипных записей (например, пользователи или заказы).



Строка – одна конкретная сущность (один пользователь, один заказ).



Колонка – характеристика этой сущности (email, дата регистрации, статус).

Чтобы база могла отличать одну строку от другой, используется первичный ключ. Обычно это поле id. Его задача – гарантировать, что каждая строка уникальна. Внешний ключ связывает таблицы между собой и не позволяет потерять целостность данных.

Ограничения – это правила, которые база применяет автоматически. Они помогают ей не принимать «кривые» данные.
Два самых нужных ограничения:





NOT NULL – поле не может быть пустым.



UNIQUE – значение не должно повторяться.



Основные типы данных в таблицах:





INT / BIGINT – целые числа (например, ID, счётчики).



CHAR(n) – строки фиксированной длины. Используйте только когда длина строго постоянна (например, код страны CHAR(2)).



VARCHAR(n) / TEXT – строки переменной длины. Обычно VARCHAR(n) используют для логинов и e-mail; TEXT – для длинных описаний. Ограничение длины помогает контролировать ввод и защищает от «мегастрок».



BOOLEAN — логические флаги (например, is_admin). Храните как булев тип, не как строки '0'/'1'.



DATE / TIMESTAMP — дата и время (например, для аудита действий пользователей).



Пример:

CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  email         VARCHAR(255) NOT NULL UNIQUE, -- не пусто и без повторов
  password_hash CHAR(60)     NOT NULL         -- не пусто
);






Если попытаться вставить пользователя без email → база откажет (NOT NULL).



Если вставить второй раз такой же email → база откажет (UNIQUE).

В контексте AppSec эти правила снижают риск багов (например, «пустой логин» или «дубликаты аккаунтов»). Но важно помнить: ограничения — не защита от SQL-инъекций. Они лишь иногда «подсвечивают» проблему ошибкой базы данных. Хорошая практика – валидация ввода приложением и страховка базы данных.





Из чего состоит SQL и как это помогает безопасности

SQL — декларативный. Вы говорите, что нужно получить или изменить данные, а база сама решает, как это сделать. Сейчас важно понять основы:





DDL (Data Definition Language) — команды структуры данных: CREATE, ALTER, DROP. С их помощью задаём форму таблиц и простые правила, чтобы база не принимала мусор и дубликаты.



DML (Data Manipulation Language) — повседневные действия: SELECT, INSERT, UPDATE, DELETE. Здесь чаще всего возникают SQL-инъекции, поэтому используем параметры вместо склейки строк.

Этого достаточно на старте: аккуратная структура снижает ошибки, а безопасные запросы не дают злоумышленнику вмешаться в логику.



Теперь разберемся с основными командами, которые мы будем использовать в следующем модуле про SQL инъекции.





SELECT — команда для чтения. Вы указываете, какие столбцы показать, из какой таблицы, по какому условию отобрать строки, как отсортировать и сколько вернуть. Основа списков, поисков, отчётов.
Пример (выбираем из  таблицы users поля id и username):

SELECT id, username FROM users;







WHERE — фильтр строк. Вы задаёте условие, и в результат попадают только те записи, которые ему подходят (равно, больше/меньше, по набору, по подстроке, пусто/не пусто).
Пример (Вытаскиваем пароль пользователя alice):

SELECT password FROM users WHERE username = 'alice';







INSERT — добавляет новую строку в таблицу.
Пример (Добавляем пользователя в таблицу users):

INSERT INTO users (username, email, password_hash) 
VALUES ('alice', 'alice@example.com', '<hash>');







UPDATE — меняет данные в существующих строках. Обычно с WHERE, чтобы не тронуть всё.
Пример (Меняем email пользователя с id = 1):

UPDATE users SET email = 'new-alice@example.com' WHERE id = 1;







DELETE — удаляет строки. Обычно тоже с WHERE.
Пример (Удаляем конкретное сообщение. Без WHERE удалились бы все строки):

DELETE FROM messages WHERE id = 123;

JOIN — соединяет строки из двух таблиц. JOIN объединяет данные из двух таблиц по связанным полям (обычно users.id = messages.user_id). Это нужно, чтобы в одном результате получить и данные сообщения, и имя автора.

Проще разобраться на примере:

У нас две таблицы:

users: id, username

messages: id, user_id, text

user_id в messages — это ссылка на автора (то же число, что id у пользователя).

Запрос:

SELECT m.id, u.username, m.text
FROM messages m
JOIN users u ON u.id = m.user_id;

Разберём построчно:





SELECT m.id, u.username, m.text — что показать:





m.id — номер сообщения



u.username — имя автора



m.text — текст сообщения



FROM messages m — берём таблицу messages и даём ей короткое имя m.



JOIN users u — присоединяем таблицу users и называем её u.



ON u.id = m.user_id — правило соединения.

Читаем так:
соединяй строки, где id пользователя равен user_id в сообщении.

Пример:
если у сообщения user_id = 2, база ищет в users строку с id = 2 и подставляет username.



Что будет, если автора нет?





В обычном JOIN (это INNER JOIN) строка пропадёт — нет пары, нет результата.



Если нужно показать сообщение даже без найденного автора, используем LEFT JOIN:

SELECT m.id, u.username, m.text
FROM messages m
LEFT JOIN users u ON u.id = m.user_id;

Теперь все сообщения будут в выдаче. Если автора нет — u.username будет NULL.

Типичная ошибка

Если забыть часть ON u.id = m.user_id, база «перемножит» все сообщения на всех пользователей.
Получится огромное количество неверных строк (декартово произведение). Всегда явно указывайте правило соединения.









UNION — объединяет результаты двух SELECT в один список.

Важно:





одинаковое количество столбцов



совместимые типы данных

Это ключевая тема для AppSec: при SQL-инъекции атакующий часто пытается добавить свой UNION SELECT, чтобы получить лишние данные.

Пример (объединяем два набора пользователей в один):

SELECT id, username FROM users WHERE is_admin = TRUE
UNION
SELECT id, username FROM users WHERE email LIKE '%@example.com';

Результат: список без дубликатов — админы плюс пользователи с почтой @example.com.

В контексте AppSec запоминаем: Если приложение позволяет внедрить свой UNION, злоумышленник может добавить другой SELECT и увидеть данные, которые не должны отображаться.

 









ORDER BY — сортирует результат (влияет на то, какая строка «первая»)

Это критично, например, если используется LIMIT 1: порядок решает, какая строка будет «первой». Если имя столбца в ORDER BY берётся из пользовательского ввода без проверки, возможны ошибки и инъекции (например, подмена имени столбца).

Пример (Лента сообщений: новые сверху):

SELECT id, text, created_at
FROM messages
ORDER BY created_at DESC
LIMIT 10;

Мы упорядочили сообщения по времени (DESC — это порядок по убыванию, противоположность — ASC о возрастанию) и взяли первые 10.









LIMIT — говорит базе, сколько строк вернуть

Важно для AppSec: LIMIT не защищает от SQL-инъекции. Если запрос уже скомпрометирован, атакующий всё равно получит данные, просто ограниченным количеством.

Пример (Берём первые 5 пользователей по алфавиту):

SELECT id, username
FROM users
ORDER BY username
LIMIT 5;

Берём первых 5 пользователей по алфавиту.







Группировки и агрегаты (что это и зачем при SQLi)

GROUP BY собирает строки в группы. Агрегатные функции (COUNT, MIN, MAX, SUM, AVG) выполняют расчёты по этим группам.

В контексте SQL-инъекций это важно в «слепых» (blind) сценариях: можно менять условие так, чтобы изменялось число строк или групп, и по ответу приложения понимать — условие истинно или ложно.





WHERE фильтрует строки до группировки



HAVING фильтрует уже готовые группы после подсчёта

Пример (Посчитать активных авторов и оставить только тех, у кого 10 и более сообщений):

SELECT u.username, COUNT(*) AS msg_count
FROM users u
JOIN messages m ON m.user_id = u.id
GROUP BY u.username
HAVING COUNT(*) >= 10
ORDER BY msg_count DESC;

Почему это важно для AppSec:

если приложение показывает «сколько найдено», меняя условие в WHERE или HAVING, можно получать сигналы о данных. Это классическая техника для boolean/blind SQLi.





Типы и приведения (почему это всплывает в пейлоадах)

Чёткие типы уменьшают сюрпризы. В инъекциях часто требуется «подружить» типы: число с числом, дату с датой и т.д. 
В PostgreSQL приведение типа делается через ::тип.
Это полезно, когда исходный запрос ожидает конкретный тип, а злоумышленник пытается подставить выражение другого типа.

Пример (фильтр «сообщения за сегодня» и приведение даты-времени к дате):

SELECT id, text
FROM messages
WHERE created_at::date = CURRENT_DATE;

Полезно знать:





В UNION нужно совпадение числа колонок и совместимых типов



NULL часто используют как универсальный заполнитель



Приведение типа помогает «подогнать» выражение под ожидаемый формат





Права и роли: принцип минимальных привилегий

У приложения должен быть отдельный пользователь базы данных с минимально необходимыми правами:





подключение к базе



SELECT / INSERT / UPDATE / DELETE в своих таблицах

Если злоумышленник получит доступ к таким учётным данным, ущерб будет ограничен. Административные права (SUPERUSER, CREATEDB, CREATE EXTENSION) приложению не выдаём.





Как хранить пароли и секреты

Пароли никогда не храним в открытом виде. Храним только хеш пароля, причём адаптивный:





приоритет — Argon2 (требует много памяти на попытку, что делает брутфорс значительно дороже)



обязательна соль для каждого пользователя

Такие хеши специально «медленные», чтобы даже при утечке базы брутфорс был экономически невыгоден.

Все секреты (строка подключения к БД, JWT-ключи и т.п.) храним в переменных окружения или в секрет-менеджере. Никогда не размещаем в репозитории.



Что чаще всего ломает новичков





Хранят пароль «как есть» или используют быстрый хеш (например, SHA-256).



Склеивают SQL-запросы из строк с пользовательскими данными.



Не задают UNIQUE и получают дубликаты в таблицах.



Выдают приложению слишком широкие права в базе данных.

Именно на эти моменты стоит обращать внимание в первую очередь.







Короткая шпаргалка под рукой





SELECT … FROM … WHERE … ORDER BY … LIMIT … — читаем данные:
что показать → откуда → по какому условию → в каком порядке → сколько строк.



JOIN / LEFT JOIN — связываем таблицы (например, сообщения + автор).



UNION — объединяем результаты двух SELECT (база для эксфильтрации при SQLi).



GROUP BY — считаем по группам (например, сколько сообщений у пользователя).



IN / EXISTS — проверяем «входит в список» и «есть ли хотя бы одна строка» (часто используются в фильтрах и подзапросах).



INSERT / UPDATE / DELETE — добавляем, изменяем, удаляем строки (для UPDATE и DELETE всегда аккуратно используем WHERE).
