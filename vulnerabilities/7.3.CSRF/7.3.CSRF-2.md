# CSRF (Cross-site request forgery) — краткое руководство для AppSec специалиста

## Что такое CSRF?
**CSRF** — уязвимость, позволяющая злоумышленнику заставить браузер пользователя выполнить нежелательные действия от его имени. При этом браузер автоматически отправляет куки сессии, но ответ сервера злоумышленник получить не может.

## Условия успешной атаки
* **Наличие действия** — в приложении есть функция, выгодная для атаки (смена email, перевод денег)
* **Аутентификация через cookie** — приложение использует только сессионные куки
* **Отсутствие защиты** — нет непредсказуемых параметров в запросе

## Пример атаки
Злоумышленник создает HTML-форму:
```html
<form action="https://target.com/action" method="POST">
    <input type="hidden" name="param" value="attack">
    <script>document.forms[0].submit()</script>
</form>
```

## Способы поиска уязвимостей
* Проверка всех изменяющих состояние действий (POST, PUT, DELETE)
* Использование Burp Suite для генерации PoC-атак
* Поиск действий без CSRF-токенов
* Проверка настроек SameSite для куков

## Методы эксплуатации
* Через HTML-формы с автоматическим сабмитом
* Через GET-запросы (например, через тег ```<img>```)
* Через JavaScript ```XMLHttpRequest```
* Через социальные инженерию для доставки эксплойта

## Защита от CSRF
1. **CSRF-токены**:
* Генерируются на сервере
* Передаются в скрытых полях форм
* Проверяются при каждом защищенном запросе
Пример реализации:
```html
<input type="hidden" name="csrf-token" value="unique-token">
```

2. **Настройки куков**:
* ```SameSite=Strict``` для важных куков
* ```Secure``` атрибут для всех куков
* ```HttpOnly``` для защиты от XSS

3. **Дополнительные меры**:
* Проверка Referer (как дополнительный слой)
* Использование разных доменов для статического контента
* Регулярная ротация токенов

## Типичные ошибки защиты
* Проверка токена только для POST-запросов
* Отсутствие привязки токена к сессии
* Хранение токена в куке
* Использование одинаковых токенов для разных пользователей

## Важные замечания
* CSRF не позволяет читать ответ сервера
* Уязвимость работает только при активной сессии пользователя
* Защита должна быть реализована на всех изменяющих состояние запросах
* `SameSite=Strict` обеспечивает максимальную защиту, но может влиять на UX
