# Web Cache Deception (Обман веб-кэша)
## 1. Что такое
`Web Cache Deception` (Обман веб-кэша) — это уязвимость, возникающая из-за `расхождения в интерпретации URL` (Path Parser Differential) `между кэширующим прокси` (Nginx, CDN, Cloudflare) `и исходным сервером` (Origin). В результате кэш считает динамический конфиденциальный ответ статическим ресурсом и сохраняет его, делая доступным для злоумышленника.

> **Отличие от Web Cache Poisoning**: При `Deception` цель — украсть чужие данные (кэшируется ответ жертвы). При `Poisoning` цель — доставить вредоносный контент всем пользователям (изменяется ключ кэша).

## 2. Методы поиска (Recon & Detection)
* **Анализ заголовков и времени ответа**: Проверка кэширования через повторные GET/HEAD/OPTIONS запросы (уязвимы только методы, не меняющие состояние). Ищем: `X-Cache: hit` (ответ из кэша), `X-Cache: miss` (промах).
* Использование **Cache-Buster**: Добавление уникальных параметров к URL (`/account?x=123`), чтобы обойти старый кэш при тестах. Автоматизируется через плагин `Param Miner`.
* **Смена путей и разделителей**: Добавление к целевому URL /profile тестовых расширений или символов и отслеживание заголовков кэша. Автоматизируется плагином `Web Cache Deception Scanner`.

## 3. Векторы эксплуатации и примеры кода
### А. Расхождение в сопоставлении путей (Path Mapping Differential)
* **Суть**: RESTful-сервер отбрасывает лишнюю часть пути, а кэш ориентируется на традиционную структуру и расширение.
* **Вектор**: Запрос `/api/profile/wcd.css`. Сервер вернет `/api/profile`, а кэш сохранит это как `CSS`.

```py
# Django (Origin Server) — уязвимая конфигурация REST API
# Сервер использует re_path и игнорирует суффикс, отдавая профиль
from django.urls import re_pathfrom django.http import JsonResponse
def user_profile(request):
    # Возвращает конфиденциальные данные пользователя
    return JsonResponse({"user": "victim", "balance": "9999$", "secret_token": "XYZ123"})
urlpatterns = [
    # Регулярка совпадает даже если в конце приписать /anything.css
    re_path(r'^api/profile.*$', user_profile), 
]
```
### Б. Расхождение в обработке разделителей (Delimiter Differential)
* **Суть**: Символы `;`,`.`, `?`, `%00` воспринимаются сервером как конец пути (разделитель), а кэш видит их как часть имени файла.
* **Вектор**: `/profile;wcd.js`. Java Spring обработает `;` как разделитель параметров и отдаст `/profile`, а CDN закэширует как JS.
```js
// Node.js/Express (Origin Server) — уязвимый ручной парсинг
const express = require('express');
const app = express();
app.get('/api/account*', (req, res) => {
    // Уязвимость: сервер очищает путь до точки/точки с запятой, игнорируя остаток
    const cleanPath = req.url.split(';')[0].split('?')[0];
    
    if (cleanPath === '/api/account') {
        return res.json({ email: "victim@mail.com", phone: "+79991112233" });
    }
    res.status(404).send('Not Found');
});
```
### В. Расхождение в нормализации путей (Path Traversal в кэш)
* **Суть**: Использование закодированных переходов `..%2f` (`../`).
* **Вектор** (Origin нормализует, Кэш — нет): `GET /static/..%2fprofile $\rightarrow$` Кэш видит префикс `/static` и кэширует. Сервер декодирует до `/profile` и отдает личные данные.
* **Вектор** (Кэш нормализует, Origin — нет): `GET /profile;%2f%2e%2e%2fstatic $\rightarrow$` Кэш нормализует до `/static` и сохраняет. Сервер спотыкается о `;`, отдавая `/profile`.

## 3. Методы защиты (Mitigation)
1. Управление заголовками (Защита на уровне приложения): Выставлять жесткие инструкции `Cache-Control: no-store`, `private` для всего динамического контента.
2. Запрет переопределения (Настройка прокси/CDN): Сконфигурировать CDN так, чтобы правила кэширования статики никогда не игнорировали заголовки `Cache-Control`, пришедшие от `Origin`.
3. Валидация `Content-Type` (Content Awareness): Прокси-сервер должен проверять соответствие: если URL запрашивает `.css`, а Origin возвращает `Content-Type: application/json` или `text/html`, такой ответ нельзя кэшировать. В `Cloudflare` для этого есть функция `Cache Deception Armor`.
4. Синхронизация парсеров: Обеспечить идентичную нормализацию URL на уровне балансировщика (Nginx) и бэкенда (декодирование %2f, %00, обработка ; и ..).
