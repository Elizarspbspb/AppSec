# 5. Cryptographic failures
`Cryptographic failures` — это класс уязвимостей, возникающие из-за некорректного применения криптографии, что приводит к раскрытию чувствительных данных. Они могут возникать из-за слабых или устаревших алгоритмов, ошибок в управлении ключами, неправильной настройки протоколов или ошибок в реализации криптографических механизмов. Такие уязвимости позволяют злоумышленникам читать, модифицировать или перехватывать данные, которые должны быть защищены. 

## 1. Основные причины криптографических сбоев
### 1.1 Использование слабых или устаревших алгоритмов. 
Например, алгоритмы MD5, SHA-1 и DES считаются небезопасными и легко поддаются взлому. Их использование для хеширования паролей или шифрования данных создаёт уязвимости. 
Примеры устаревших алгоритмов:

* MD5 - возможность быстрого перебора и коллизий
* SHA-1 - практические атаки на коллизии
* DES - слишком маленький размер ключа
* RC4 - известные криптографические слабости
* SSLv2/SSLv3 - уязвимости протокола

При аудите приложения **необходимо проверить**:
* Исходный код:
```
grep -R "MD5" .
grep -R "SHA1" .
grep -R "DES" .
```
* Инструменты Semgrep:
```
rules:
- id: insecure-md5
  pattern: hashlib.md5(...)
  message: MD5 is insecure
  severity: ERROR
  languages:
    - python
```
* Анализ зависимостей:
Python:
```
pip-audit
```
Java:
```
mvn dependency-check:check
```
**Защита**  
Для хранения паролей нельзя использовать обычные хеш-функции. Используются:
* Argon2;
* bcrypt;
* scrypt;
* PBKDF2.

Пример:
```
from argon2 import PasswordHasher
ph = PasswordHasher()
hash = ph.hash("MyPassword123")
```
Результат:
```
$argon2id$v=19$m=65536,t=3,p=4...
```
Преимущества:
* соль создаётся автоматически;
* высокая стоимость перебора;
* защита от GPU-атак.

### 1.2 Неправильное управление ключами. 
К ошибкам относятся:
1. жёсткое кодирование ключей в исходном коде; 
```
AES_KEY="83hd82hd82hd82hd"
encrypt(data,AES_KEY)
```
Проверка репозитория:
```
grep -R "password" .
grep -R "secret" .
grep -R "apikey" .
grep -R "private_key" .
```
Используются инструменты:
* GitLeaks;
* TruffleHog;
* GitGuardian.

Пример:
```
gitleaks detect

Potential secret detected:
AWS_SECRET_KEY:
AKIA****************
```
**Защита**

Использовать:
* Hashicorp Vault;
* AWS Secrets Manager;
* Azure Key Vault;
* Kubernetes Secrets.

2. повторное использование ключей в разных системах;
3. отсутствие ротации ключей;
4. хранение ключей в открытом виде в конфигурационных файлах. 

### 1.3 Отсутствие шифрования при передаче данных. 
Использование HTTP вместо HTTPS позволяет злоумышленникам перехватывать данные с помощью атак типа «человек посередине» (MITM). 

**Защита**

Использовать:
* TLS 1.2+
* TLS 1.3
* HSTS

Пример заголовка:
```
Strict-Transport-Security:
max-age=31536000;
includeSubDomains
```
### 1.4 Ошибки в реализации криптографии.
Например, неправильное использование криптографических API, ошибки в логике шифрования, использование небезопасных генераторов случайных чисел. 

**Пример: неправильный режим AES**

Плохо:
```
AES-ECB
```
`ECB` сохраняет структуру данных.

Правильно:
```
AES-GCM
AES-CBC + HMAC
```
**Использование слабого генератора случайных чисел**

Ошибка:
```
import random
token=random.randint(0, 999999)
```
Проблема - `random` не является криптографически безопасным. Атакующий может предсказать:
```
token=123456
```
Правильно:
```
import secrets
token=secrets.token_hex(32)

a91fd83f9282d91a7bc93...
```
### 1.5 Неправильная настройка протоколов. 
К этому относятся:
* разрешение устаревших версий протоколов (например, SSL или TLS 1.0);
* использование слабых наборов шифров;
* отсутствие проверки сертификатов;
* отсутствие критически важных заголовков безопасности (например, HSTS). 

Проверка. Инструменты:
* SSL Labs

Проверяет:
* версии TLS;
* сертификаты;
* шифры.

**testssl.sh**

Пример:
```
testssl.sh https://site.com
```
Результат:
```
TLS 1.0 enabled
TLS 1.1 enabled

Weak cipher:
3DES
```
**Защита**

Отключить:
* TLS 1.0
* TLS 1.1

Оставить:
* TLS 1.3
* TLS 1.2

Использовать:
* AES-GCM
* ChaCha20-Poly1305

**Некоторые приложения отключают проверку TLS:**

Плохо:
```
requests.get(url,verify=False)
```
Теперь возможна MITM-атака.

Атакующий создаёт: Fake certificate. Приложение принимает его.

**Защита** 

Всегда включать:
```
verify=True
```
Использовать:
* certificate pinning;
* правильное хранилище CA.

### 1.6 Атаки по побочным каналам. 
Злоумышленники могут использовать информацию о времени выполнения операций, потребляемой мощности, акустических шумах или электромагнитном излучении для извлечения секретных данных. 

## 2. Последствия криптографических сбоев
* Утечка чувствительных данных: паролей, кредитных карт, персональных данных. 
* Кража идентичности и финансовое мошенничество. 
* Компрометация учётных записей. 
* Нарушение нормативных требований (GDPR, PCI-DSS, HIPAA и др.). 
* Репутационные и финансовые потери для организации. 

## 3. Меры предотвращения
1. Использование современных алгоритмов. Например, `AES-256` для шифрования, `RSA` с безопасной подстановкой для обмена ключами, `SHA-256` или более современные хеш-функции. 
2. Шифрование данных в покое и при передаче. Необходимо использовать `TLS 1.2` или выше, включать `HSTS` для предотвращения понижающих атак. 
3. Безопасное управление ключами. Ключи следует хранить в защищённых системах (`HSM`, `vaults`), регулярно их ротировать, генерировать с достаточной случайностью. 
4. Использование надёжных генераторов случайных чисел (`CSPRNG`) для ключей, инициализационных векторов, токенов и других чувствительных операций. 
5. Применение современных методов хеширования паролей (`bcrypt`, `scrypt`, `Argon2`) с использованием соли и достаточного количества итераций. 
6. Регулярное обновление криптографических библиотек и протоколов для устранения известных уязвимостей. 
7. Аудит конфигураций и тестирование на проникновение для выявления слабых мест в криптографической защите.
