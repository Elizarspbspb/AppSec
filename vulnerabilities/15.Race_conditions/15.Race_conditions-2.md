# Race Conditions (Условия гонки)
> Единственный надежный способ — сделать операцию **атомарной** (чтобы проверка и изменение происходили как один неделимый шаг на уровне БД) или использовать жесткую синхронизацию потоков.

## 1. Что такое
`Race Condition` (Условия гонки) — это архитектурная уязвимость (часто относится к Business Logic Flaws), возникающая, когда приложение одновременно обрабатывает несколько запросов к одним и тем же данным без должной синхронизации. Период времени между проверкой состояния данных и их изменением называется «окном гонки» (Race Window). 

Если злоумышленник успевает отправить другой запрос в это окно, приложение переходит в непредусмотренное промежуточное состояние. Подтип уязвимости, основанный на этом принципе, называется TOCTOU (Time-of-Check to Time-of-Use).

## 2. Методы поиска и обнаружения (Black-Box / Grey-Box)
* **Анализ бизнес-логики** (Predict): Поиск критических точек, где бизнес-логика накладывает ограничения (одноразовые промокоды, баланс счета, капчи, лимиты брутфорса, MFA).
* **Параллельная отправка** (Probe): Сравнение ответов при последовательной и параллельной отправке группы запросов.
* Инструменты автоматизации:
    * **Burp Repeater** (HTTP/2 Single-Packet Attack): Позволяет **упаковать до 20–30 запросов в один TCP-пакет**, полностью нивелируя сетевой джиттер (задержки сети) для идеальной синхронизации. Для HTTP/1 используется техника Last-Byte Sync.
    * **Turbo Intruder**: Расширение для Burp Suite (на базе Python). Применяется для сложных условий гонки с использованием механизма gate (группировка и одновременное «открытие шлюза» для запросов).

## 3. Примеры уязвимостей и уязвимого кода 
### Пример 1: Превышение лимита баланса / Промокода (TOCTOU)
Логика: Запросы проходят проверку if до того, как первый запрос успеет перезаписать состояние в БД.

```Python
@app.route('/apply_coupon', methods=['POST'])
def apply_coupon():
    user_id = session.get('user_id')
    # 1. TIME OF CHECK (Проверка)
    used = db.execute("SELECT is_used FROM coupons WHERE user_id=:id", {"id": user_id}).scalar()
    
    if not used:
        # <-- ОКНО ГОНКИ (Параллельный поток заходит сюда же)
        apply_discount_to_cart(user_id) 
        
        # 2. TIME OF USE (Изменение состояния)
        db.execute("UPDATE coupons SET is_used=True WHERE user_id=:id", {"id": user_id})
        db.commit()
        return "Скидка применена", 200
    return "Код уже использован", 400
```
### Пример 2: Одноконечные условия гонки (Multi-Threading / Event Loop Collision)
Логика: Смена состояния сессии в рамках одного контекста при параллельных запросах. Злоумышленник инициирует сброс пароля для жертвы и для себя одновременно, путая переменные в сессии.

```JavaScript
// Общий объект сессии может перезаписываться параллельными асинхронными запросами
app.post('/request-reset', async (req, res) => {
    // Входящий запрос 1 (жертва) и запрос 2 (атакующий)
    req.session.resetUser = req.body.username; 
    
    // Асинхронная операция создания токена (дает окно гонки)
    const token = await generateSecureToken(); 
    
    // Из-за коллизии в сессию запишется username атакующего, но токен уйдет жертве (или наоборот)
    req.session.resetToken = token; 
    
    await sendEmail(req.session.resetUser, `Ваш токен: ${token}`);
    res.send("Инструкции отправлены");
});
```

## 3. Методы защиты и исправления
Защита должна строиться не на попытках сделать код быстрее, а на обеспечении атомарности операций и синхронизации доступа к разделяемому ресурсу.
1. Атомарность на уровне СУБД (Рекомендуется):
    * **Использование блокировок строк при чтении**: SELECT ... FOR UPDATE в PostgreSQL/MySQL (блокирует строку до завершения транзакции).
    * **Условные обновления** (Atomic Updates): UPDATE users SET balance = balance - 100 WHERE id = 1 AND balance >= 100;. Если баланса не хватает, запись не обновится, даже если проверка if в коде была пройдена.
    * Ограничения целостности: **Использование UNIQUE индексов и PRIMARY KEY на уровне таблиц**.
2. Распределенные блокировки (Distributed Locks):
    * **Если приложение развернуто в нескольких экземплярах (микросервисы), локальные мьютексы не помогут**. Необходимо использовать распределенный `lock-менеджер` (например, Redis (Redlock) или ZooKeeper) для синхронизации бизнес-операций по ключу (например, lock:user_id).
3. Локальная синхронизация (в рамках одного инстанса):
    * Python: **threading.Lock()** для многопоточных приложений или **asyncio.Lock()** для асинхронного кода.
4. Архитектурный подход:
    * Идемпотентность API: Внедрение обязательных **Idempotency-Key** для финансовых и чувствительных транзакций.
    * **Stateless** архитектура: Перенос хранения состояний на сторону клиента с помощью подписанных токенов (JWT), чтобы избежать конкуренции за сессию на сервере.
   

### «Как защитить микросервисы от условий гонки, если у каждого инстанса своя память и они запущены на разных серверах?»
Локальные мьютексы языка (`threading.Lock` или `asyncio.Lock`) бесполезны. Нужно использовать внешний распределенный lock-менеджер (Distributed Lock). Чаще всего это реализуется через **Redis** (алгоритм Redlock) или с помощью механизмов самой базы данных (например, транзакции с общим кластером PostgreSQL или использование семафоров в **ZooKeeper/Consul**).

### «Как обнаружить окно гонки в несколько миллисекунд при Black-Box тестировании (без исходного кода)?»
С помощью атаки с одним пакетом (Single-Packet Attack) через HTTP/2 (инструменты Burp Repeater). Мы упаковываем 20–30 запросов в один TCP-пакет и отправляем на сервер.
