# Неправильная обработка исключительных условий (Mishandling of Exceptional Conditions)
## 1. Что это такое?
`Mishandling of Exceptional Conditions` — это архитектурная ошибка и уязвимость, возникающая, когда приложение некорректно обрабатывает непредвиденные ошибки и исключения (exceptions). С точки зрения AppSec, некорректная реакция системы создает два главных риска: 
* утечка конфиденциальных данных (через reflected error messages, раскрывающие stack trace, пути к файлам, структуры БД);
* нарушение доступности (Denial of Service, если серия тяжелых ошибок перегружает CPU/БД). Напрямую пересекается с классами `Insecure Design` и `Security Misconfiguration`.

## 2. Методы поиска
* Динамическое тестирование (DAST / Негативные тесты): Намеренное провоцирование сбоев. Векторы: передача некорректных типов данных, деформированный JSON/XML, слишком длинные строки, спецсимволы инъекций, вызов несуществующих ID. Цель — проверить, выйдет ли наружу сырое исключение.
* Статический анализ (SAST / Code Review): Поиск конструкций, где текст системной ошибки транслируется напрямую клиенту (например, **catch (Exception e) { return e.getMessage(); }**). Проверка наличия глобальных перехватчиков (Global Exception Handlers).
* Анализ конфигураций (Infra as Code / Compliance): Проверка флагов отладки (DEBUG=True) для production-окружения, проверка доступности диагностических эндпоинтов.

## 3. Примеры уязвимостей (Грязный код vs. Чистый код)
```Python
# Плохо (Утечка внутренней логики и структуры БД):
@app.route('/user/<id>')def get_user(id):
    try:
        # При передаче id='10.4.1' СУБД выбросит ошибку
        user = db.execute(f"SELECT * FROM users WHERE id={id}").fetchone()
        return jsonify(user)
    except Exception as e:
        # КРИТИЧНО: Возврат сырого текста ошибки и SQL-запроса наружу
        return jsonify({"error": str(e)}), 500
```
В случае ошибки СУБД (например, Error-based SQLi), атакующий увидит имена таблиц и колонок в HTTP-ответе.
```py
# Хорошо (Безопасная обработка):
@app.route('/user/<id>')def get_user(id):
    try:
        # Использование параметризованного запроса для защиты от SQLi
        user = db.execute("SELECT * FROM users WHERE id=:id", {"id": id}).fetchone()
        return jsonify(user)
    except Exception as e:
        # Логируем детали внутри системы, пользователю отдаем generic-ответ
        logger.exception(f"Database error during user fetch. Request UUID: {request.uuid}")
        return jsonify({"error": "Internal server error", "code": "INTERNAL_ERROR"}), 500
```
```JavaScript
//Плохо (Раскрытие Stack Trace в JSON-ответе):
app.get('/api/data', async (req, res) => {
    try {
        let result = await apiService.fetch(req.query.path);
        res.json(result);
    } catch (err) {
        // КРИТИЧНО: Отправка всего объекта ошибки со Stack Trace клиенту
        res.status(500).json({ success: false, message: err.message, stack: err.stack });
    }
});
```
```js
// Хорошо (Централизованный глобальный обработчик middleware):
// В эндпоинте просто передаем ошибку дальше через next()
app.get('/api/data', async (req, res, next) => {
    try {
        let result = await apiService.fetch(req.query.path);
        res.json(result);
    } catch (err) {
        next(err); 
    }
});
// Централизованный Error Handler Middleware
app.use((err, req, res, next) => {
    logger.error({ message: err.message, stack: err.stack, requestId: req.id }); // Внутренний лог
    
    res.status(500).json({
        error: "Internal server error",
        request_id: req.id // Позволяет сопоставить лог без раскрытия деталей
    });
});
```

## 4. Методы защиты (Уровень архитектуры)
1. **Разделение потоков** (Принцип барьера): Текст внутреннего исключения никогда не должен попадать в HTTP-ответ. Наружу — стандартизированные безопасные коды (400, 401, 500) и request_id, внутрь логов — полный контекст.
2. **Централизация**: Реализация паттерна `Global Exception Handler` на уровне фреймворка. Ни один сбой не должен обрабатываться компонентами хаотично.
3. **Hardening конфигураций**: Жесткое отключение debug mode, отладочных страниц фреймворков и трассировок стека в production-среде.
4. **Безопасное логирование**: Запись инцидентов обязательна, но с маскированием чувствительных данных (паролей, токенов, ПДн) во избежание Log Injection или утечки секретов в SIEM.
5. Защита от DoS на ошибках: Ограничение интенсивности запросов (Rate Limiting) и использование автоматического восстановления (оркестрация контейнеров) для предотвращения отказа сервиса из-за цикличных сбоев.
