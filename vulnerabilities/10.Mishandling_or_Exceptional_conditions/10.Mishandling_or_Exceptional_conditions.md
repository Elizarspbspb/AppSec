# 10. Неправильная обработка исключительных условий (Mishandling of exceptional conditions) 
`Mishandling of exceptional conditions` — это критическая архитектурная ошибка, которая возникает из-за неправильной обработки ошибок и исключительных ситуаций в веб-приложении. Такие проблемы могут привести как к утечке конфиденциальных данных, так и к нарушению доступности сервиса (Denial of Service).

Уязвимость появляется, когда приложение сталкивается с ошибкой или исключением (`exception`), которое разработчик не предусмотрел, либо обработал некорректно. Вместо безопасного завершения операции и возврата контролируемого ответа **приложение может раскрыть внутреннюю информацию**, изменить логику выполнения или перейти в нестабильное состояние.

С точки зрения AppSec, ошибки являются потенциальным каналом взаимодействия с внутренней логикой приложения. Атакующий намеренно вызывает ошибочные ситуации, анализирует полученное поведение системы и использует его для поиска возможностей эксплуатации. Например, сообщения об ошибках могут раскрывать структуру базы данных, пути к файлам, внутренние классы приложения, настройки сервера или другую техническую информацию, которая упрощает дальнейшую атаку.

Одним из ярких примеров является **error-based SQL injection**. Несмотря на то, что SQL-инъекции занимают отдельную категорию уязвимостей и находятся среди наиболее распространенных проблем веб-приложений, данный тип атаки также связан с **mishandling of exceptional conditions**, так как эксплуатация строится на неправильной обработке ошибок базы данных.

При **error-based SQL injection** атакующий отправляет специально сформированный SQL-запрос, который вызывает ошибку на стороне базы данных. Если веб-приложение выводит эту ошибку пользователю без корректной обработки, злоумышленник может получить информацию о структуре базы данных, используемой СУБД или даже извлечь данные через специально созданные SQL-ошибки. Таким образом, сама ошибка становится каналом утечки информации и инструментом дальнейшей эксплуатации.

## 10.1 Error-based SQL injection
Когда атакующий передает в `SQL`-запрос значение, которое приводит к ошибке преобразования типов, некорректной обработке данных или нарушению логики выполнения запроса, база данных генерирует исключение. Если веб-приложение неправильно обрабатывает такие исключения и возвращает пользователю исходное сообщение об ошибке, атакующий получает дополнительную информацию о внутреннем устройстве системы.

Например, при **error-based SQL injection** злоумышленник намеренно вызывает ошибку преобразования типов:
* в **MySQL** — используя функции, которые заставляют СУБД сформировать ошибку и включить в нее данные:
```sql
select 1,2 
union select count(*),concat((select content from docs limit 1),floor(rand(0)*2)) x 
from information_schema.tables 
group by x;
```
В данном примере атакующий использует особенности обработки ошибок в `MySQL`. Запрос вызывает ошибочную ситуацию при выполнении группировки, а данные из таблицы docs добавляются в сообщение об ошибке. Если приложение возвращает пользователю текст ошибки базы данных, значение поля content может быть раскрыто через ответ сервера.

* в **MSSQL** атакующий пытается привести строковое значение к числовому типу с помощью CAST():
```sql
SELECT CAST((select name from PurchaseOrderDetail) as int);
```
Так как значение из таблицы PurchaseOrderDetail имеет несовместимый тип данных, MSSQL генерирует ошибку преобразования.

**PostgreSQL** — выполняя попытку привести строковое значение к числовому типу через `CAST()`:
```sql
SELECT CAST((SELECT kind from films limit 1) as integer);
```
Значение из таблицы films передается в CAST() с преобразованием в тип integer. Если строковое значение невозможно преобразовать в число, база данных создает ошибку.

Если приложение выводит полученную ошибку напрямую (**reflected error message**), атакующий может извлечь часть данных из текста ошибки и использовать эту информацию для дальнейшей эксплуатации SQL-инъекции.

## 10.2 UNION-based SQL injection
Данный подход похож на **UNION-based SQL injection**, поскольку целью также является получение данных через ответ приложения. Однако отличие заключается в механизме передачи информации:
* при **UNION-based SQL injection** атакующий добавляет дополнительный `SELECT` и получает данные через обычный результат выполнения запроса;
* при **error-based SQL injection** данные передаются через сообщение об ошибке, которое формирует база данных.

Основное ограничение **error-based SQL injection** заключается в том, что объем и формат получаемой информации зависят от конкретной СУБД и текста ошибки. Тем не менее даже небольшая утечка может раскрыть структуру базы данных, имена таблиц и колонок или другие данные, необходимые для дальнейшей атаки.

## 10.3 Как защититься от Mishandling of Exceptional Conditions
Защита от подобных проблем заключается не только в устранении конкретной SQL-инъекции, но и в правильной архитектуре обработки ошибок:
* **1. Не возвращать пользователю внутренние сообщения об ошибках.**
  Ошибки базы данных, исключения фреймворка и системные сообщения должны логироваться внутри приложения, но пользователю необходимо возвращать только общее сообщение, например: *"Произошла внутренняя ошибка сервера"*.

* **2. Использовать централизованный механизм обработки исключений.**
  Все необработанные исключения должны перехватываться единым обработчиком ошибок, который контролирует формат ответа и предотвращает утечку внутренней информации.

* **3. Использовать параметризованные запросы (prepared statements).**
  Это основной способ защиты от SQL-инъекций, так как пользовательские данные передаются отдельно от SQL-кода и не могут изменить структуру запроса.

* **4. Минимизировать права учетной записи базы данных.**
  Даже при наличии SQL-инъекции ограниченные права пользователя БД уменьшают возможный ущерб.

* **5. Разделять обработку ошибок для разных сред.**
  В режиме разработки можно показывать расширенную информацию для отладки, но в production-среде необходимо отключать подробные сообщения об ошибках.

* **6. Регулярно проверять обработку исключений.**
  При тестировании безопасности необходимо проверять, что приложение корректно обрабатывает:
  * ошибки SQL-запросов;
  * ошибки преобразования типов;
  * некорректные входные данные;
  * ошибки файловой системы;
  * исключения сторонних библиотек и API.

Таким образом, **Mishandling of Exceptional Conditions** возникает не из-за самого факта появления ошибки, а из-за неправильной реакции приложения на эту ошибку. Любое исключение должно рассматриваться как потенциальный канал утечки информации и контролироваться на уровне архитектуры приложения.

## 10.3 Обработка исключений
Важно заранее определить и корректно обработать все возможные ошибки и исключительные ситуации, чтобы не допустить утечки внутренней информации и сохранить стабильную работу приложения.

В безопасной архитектуре исключения не должны обрабатываться хаотично. Обычно они классифицируются и разделяются на отдельные категории с использованием **error-кодов** или **типов ошибок**. Это позволяет контролировать поведение приложения при различных сценариях сбоя.

Для каждой группы ошибок могут настраиваться:
* **централизованный сбор и мониторинг событий** — ошибки фиксируются в системах логирования и анализа (например, SIEM, системы мониторинга приложений);
* **контроллеры обработки исключений** — специальные механизмы, которые определяют, как приложение должно реагировать на конкретный тип ошибки;
* **алерты и уведомления** — критические ошибки автоматически передаются ответственным специалистам для расследования;
* **автоматическое восстановление** — при необходимости система может перезапустить отдельный компонент, ограничить нагрузку или временно отключить проблемный модуль.

При этом важно разделять внутреннюю и внешнюю обработку ошибок. Внутри системы необходимо сохранять максимально подробную информацию для анализа и поиска причин сбоя, но пользователю нельзя возвращать технические детали: SQL-ошибки, stack trace, пути файловой системы, конфигурационные параметры или другие сведения, которые могут помочь атакующему.

Таким образом, правильная обработка исключений решает сразу две задачи: повышает устойчивость веб-приложения к сбоям и предотвращает использование ошибок как канала утечки информации.

## 10.4 Практический план защититься от Mishandling of Exceptional Conditions
Важно заранее определить и корректно обработать все возможные ошибки и исключительные ситуации, чтобы предотвратить утечку внутренней информации и сохранить стабильность приложения.

С точки зрения AppSec защиту необходимо проверять на нескольких уровнях: **обработка исключений в коде, формат ответов API, логирование, мониторинг и автоматическое восстановление после сбоев**.

### 10.4.1. Централизованно обрабатывать исключения
В приложении должен существовать единый механизм обработки необработанных исключений. Вместо того чтобы каждый компонент самостоятельно формировал ответ пользователю, приложение должно перехватывать исключения и преобразовывать их в безопасный ответ.

Например, вместо:
```text
500 Internal Server Error

java.sql.SQLException:
SELECT * FROM users WHERE id='...'

at com.example.UserRepository.findUser(UserRepository.java:42)
at com.example.UserService.getUser(UserService.java:87)
...
```
пользователь должен получить:
```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{
  "error": "Internal server error"
}
```
При этом подробная информация об исключении должна сохраняться во внутренних логах.

Для AppSec это означает, что при тестировании необходимо намеренно вызывать ошибки и проверять ответы приложения:
* передавать некорректные типы данных;
* отправлять слишком длинные значения;
* передавать неожиданные символы и кодировки;
* использовать несуществующие идентификаторы;
* нарушать формат JSON/XML;
* вызывать ошибки авторизации и доступа;
* провоцировать ошибки SQL, файловой системы и других компонентов.

Основная проверка: **может ли пользователь увидеть внутреннее исключение или технические детали его возникновения?**

### 10.4.2. Не раскрывать stack trace и внутреннюю информацию
В production-среде необходимо отключить подробные сообщения об ошибках. Следует проверять, не раскрывает ли приложение:
* stack trace;
* SQL-запросы;
* названия таблиц и колонок;
* пути к файлам;
* имена внутренних классов и методов;
* версии библиотек и фреймворков;
* переменные окружения;
* конфигурацию серверов;
* IP-адреса внутренних сервисов;
* токены, ключи и другие секреты.

Например, ответы вида:
```text
Traceback (most recent call last):
  File "/app/api/users.py", line 42...
```
или:
```text
SQLSTATE[42S22]: Column not found: 1054 Unknown column 'password'
```
являются потенциальным источником информации для дальнейшей атаки.

### 10.4.3. Использовать безопасные error-коды
Ошибки необходимо разделять по категориям и использовать предсказуемые коды ответа:
```text
400 — некорректный запрос
401 — требуется аутентификация
403 — доступ запрещен
404 — ресурс не найден
409 — конфликт состояния
429 — слишком много запросов
500 — внутренняя ошибка сервера
503 — сервис временно недоступен
```
При этом внутренний код ошибки может быть более детальным:
```json
{
  "error": "INTERNAL_ERROR",
  "request_id": "7f83a..."
}
```
Такой подход позволяет пользователю получить безопасный ответ, а разработчику и AppSec-команде — определить конкретную причину проблемы по `request_id` в логах.

### 10.4.4. Разделять ошибки для пользователя и внутренние ошибки
Одна из важных практик — **не использовать текст внутреннего исключения непосредственно в HTTP-ответе**.

Небезопасный вариант:
```python
except Exception as e:
    return {"error": str(e)}, 500
```
В этом случае приложение фактически превращает любое исключение в канал утечки информации.

Безопаснее разделить эти два потока:
```python
except Exception:
    logger.exception("Unexpected application error")
    return {"error": "Internal server error"}, 500
```
Внутри системы сохраняется подробная информация для расследования, а наружу возвращается только контролируемый ответ.

### 10.4.5. Проверять режим production
Для AppSec важно отдельно проверить конфигурацию production-окружения. Необходимо убедиться, что отключены:
* debug mode;
* developer exception pages;
* подробные ошибки framework;
* автоматический вывод stack trace;
* диагностические endpoints, доступные без авторизации.

Например, включенный `DEBUG=True` в production может превратить обычную ошибку приложения в серьезную информационную утечку.

### 10.4.6. Безопасно логировать ошибки
Полностью отключать логирование ошибок также неправильно. Подробная информация необходима для расследования инцидентов. Однако в логах нельзя без необходимости сохранять:
* пароли;
* access token;
* session ID;
* API keys;
* персональные данные;
* содержимое HTTP-запросов, если оно содержит секреты.

Для каждого события желательно сохранять:
```text
timestamp
severity
application
component
error_code
request_id
user/session context
source IP
```
При этом сами логи должны быть защищены от несанкционированного доступа и изменения.

### 10.4.7. Настроить мониторинг и alerts
Одинаковая ошибка, возникающая один раз, и тысячи одинаковых ошибок за несколько минут — совершенно разные события с точки зрения безопасности.

Поэтому необходимо отслеживать:
* количество ошибок `4xx` и `5xx`;
* резкий рост количества `500`;
* повторяющиеся ошибки одного типа;
* ошибки аутентификации и авторизации;
* ошибки доступа к критическим ресурсам;
* ошибки базы данных;
* ошибки загрузки и обработки файлов;
* повторяющиеся исключения в одном endpoint.

Например, резкий рост `500 Internal Server Error` после серии необычных запросов может указывать не только на программный сбой, но и на попытку эксплуатации уязвимости.

Для критических событий необходимо настроить **alerts** в системе мониторинга или SIEM.

### 10.4.8. Проверять устойчивость приложения к ошибкам
AppSec-специалисту важно проверить не только утечку информации, но и то, **что происходит с приложением после возникновения ошибки**:
1. Отправить специально сформированный запрос.
2. Вызвать исключение.
3. Проверить HTTP-ответ.
4. Проверить, появилась ли чувствительная информация.
5. Проверить логи.
6. Проверить состояние приложения.
7. Повторить запрос несколько раз.
8. Проверить, не приводит ли серия ошибок к отказу в обслуживании.

Если один пользователь может отправить несколько запросов, которые вызывают дорогостоящие исключения и полностью загружают CPU, память или соединения с БД, неправильная обработка исключений может привести уже к **Denial of Service**.

### 10.4.9. Использовать автоматическое восстановление
Для критических сервисов мониторинг может быть связан с механизмами автоматического восстановления. Например, при постоянном падении отдельного экземпляра приложения оркестратор может:
* перезапустить контейнер;
* удалить неисправный экземпляр из балансировщика;
* создать новый экземпляр;
* ограничить количество запросов;
* временно отключить проблемный компонент.

Однако автоматический restart не должен использоваться как замена исправлению ошибки. Если атакующий может постоянно вызывать исключение, автоматический перезапуск может даже превратиться в дополнительный вектор DoS.

### 10.4.10. Что проверять AppSec-специалисту
При `security testing` обработки исключений полезно составить отдельный набор негативных тестов:
* [ ] Проверить все основные API на некорректные входные данные.
* [ ] Проверить `4xx` и `5xx` ответы.
* [ ] Проверить отсутствие `stack trace`.
* [ ] Проверить отсутствие SQL-ошибок в ответах.
* [ ] Проверить отсутствие путей к файлам и внутренних имен классов.
* [ ] Проверить production-конфигурацию на включенный debug mode.
* [ ] Проверить, что исключения корректно записываются в логи.
* [ ] Проверить отсутствие секретов в логах.
* [ ] Проверить наличие `request_id` или другого идентификатора события.
* [ ] Проверить мониторинг и alerts для критических ошибок.
* [ ] Проверить возможность вызвать DoS большим количеством ошибочных запросов.
* [ ] Проверить поведение приложения после серии исключений.
* [ ] Проверить механизмы автоматического восстановления.

Таким образом, **Mishandling of Exceptional Conditions** следует рассматривать не просто как проблему отображения ошибок. Для AppSec это целый класс проблем, включающий **утечки информации, неправильную обработку исключений, небезопасное логирование, отсутствие мониторинга и возможность довести приложение до отказа в обслуживании через специально вызываемые ошибки**.

## 10.5 Сходства
Категория `Mishandling of Exceptional Conditions` тесно связана с такими классами проблем, как `Insecure Design` и `Security Misconfiguration`, поскольку неправильная обработка ошибок часто является результатом архитектурных решений или неверной настройки приложения.

Связь с `Insecure Design` проявляется в том, что безопасность обработки исключений должна закладываться еще на этапе проектирования системы. Если архитектура приложения изначально не предусматривает централизованную обработку ошибок, разделение внутренних и внешних сообщений, безопасное логирование и сценарии восстановления после сбоев, то в дальнейшем это может привести к появлению множества уязвимостей.

Связь с `Security Misconfiguration` заключается в том, что даже правильно разработанное приложение может стать уязвимым из-за неправильной настройки окружения.

Типичные примеры:
* включенный debug mode в production;
* активные страницы подробных ошибок фреймворка;
* вывод stack trace пользователю;
* неправильная настройка логирования;
* отсутствие мониторинга критических исключений;
* хранение логов с чувствительной информацией без защиты.

Например, приложение может иметь корректный механизм обработки исключений, но включенный параметр `DEBUG=True` в production способен полностью нарушить эту защиту и раскрыть внутреннюю информацию.

Таким образом, `Mishandling of Exceptional Conditions` находится на пересечении трех областей:
* **Insecure Design** — ошибки проектирования механизмов обработки исключений;
* **Security Misconfiguration** — неправильная настройка уже существующих механизмов защиты;
* **Implementation Bugs** — конкретные ошибки в коде, приводящие к некорректной обработке исключений.

Для AppSec-специалиста важно проверять не только наличие отдельных ошибок, но и весь жизненный цикл обработки исключений: от архитектуры приложения и настроек окружения до поведения системы при реальных сбоях и попытках эксплуатации.
