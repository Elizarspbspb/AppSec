# 2.1. SSRF (Server-Side Request Forgery)
Подделка запросов на стороне сервера (SSRF)
![alt text](image.png)
## 1. Что такое SSRF?
Подделка запросов на стороне сервера (`Server-Side Request Forgery, SSRF`) — это уязвимость веб-безопасности, при которой злоумышленник может заставить серверное приложение отправлять запросы туда, куда оно не должно обращаться.

Обычно сервер сам выполняет запросы к различным ресурсам: получает изображения, обращается к API, загружает файлы и т.д. При наличии `SSRF` атакующий может изменить параметры запроса так, чтобы сервер обращался к нужному ему адресу.

В типичной атаке `SSRF` злоумышленник может заставить сервер подключаться к внутренним сервисам организации, которые недоступны из внешней сети. Например, сервер может обратиться к внутренней панели управления, базе данных или служебному API.

Также сервер можно заставить выполнять запросы к произвольным внешним системам. Это может привести к раскрытию конфиденциальной информации, например внутренних данных, токенов доступа или учетных данных.

## 2. Каковы последствия атак SSRF?
Успешная атака `SSRF` может позволить злоумышленнику выполнять действия от имени сервера или получать доступ к данным, которые должны быть недоступны.

Последствия могут включать:
* доступ к внутренним системам организации;
* получение конфиденциальной информации;
* обход ограничений сетевого доступа;
* выполнение запросов к внутренним API;
* кражу учетных данных или токенов авторизации.

В некоторых случаях `SSRF` может привести к выполнению произвольных команд на сервере, если уязвимое приложение взаимодействует с небезопасными внутренними сервисами.

`SSRF-атаки`, при которых сервер подключается к внешним системам, также могут использоваться для проведения атак от имени организации. Например, злоумышленник может заставить сервер отправлять вредоносные запросы к другим ресурсам, создавая видимость, что запросы исходят от самой организации.

## 3. Общие атаки SSRF
`SSRF-атаки` часто используют доверительные отношения между сервером и другими компонентами системы. Благодаря этому злоумышленник может использовать уязвимое приложение как промежуточный сервер и выполнять действия, которые обычно ему недоступны.

Такие доверительные отношения могут существовать:
* между пользователем и сервером приложения;
* между сервером приложения и внутренними системами организации;
* между различными сервисами внутри одной сети.

### 3.1 SSRF-атаки на сервер
При `SSRF`-атаке на сам сервер злоумышленник заставляет приложение отправить HTTP-запрос обратно на тот же сервер, где оно работает.

Для этого обычно используется специальный адрес `loopback`-интерфейса:
* 127.0.0.1 — IP-адрес, который всегда указывает на текущий компьютер;
* localhost — имя, которое обычно используется для обращения к этому же адресу.

Например, представим интернет-магазин, в котором пользователь может проверить наличие товара на складе. Чтобы получить информацию о наличии товара, приложение обращается к внутреннему API склада:
```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded

stockApi=http://stock.weliketoshop.net:8080/product/stock/check?productId=6&storeId=1
```
Сервер получает этот URL, отправляет запрос к внутреннему API и возвращает пользователю результат.

Однако злоумышленник может изменить параметр stockApi и указать адрес самого сервера:
```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded

stockApi=http://localhost/admin
```
Теперь сервер вместо проверки склада обращается к своему административному интерфейсу:
```
http://localhost/admin
```
После этого сервер получает страницу `/admin` и отправляет её содержимое злоумышленнику.

На первый взгляд это может показаться бесполезным, потому что административная панель обычно требует авторизации. Однако запрос к `/admin` выполняется от имени самого сервера, то есть с локального адреса.

Если приложение доверяет локальным запросам, то стандартная проверка доступа может быть обойдена. В результате злоумышленник получает доступ к административным функциям без необходимости входа в систему.

#### Почему сервер доверяет локальным запросам?
Такое поведение может возникать по нескольким причинам:
* Проверка доступа выполняется отдельным компонентом. Например, внешний сервер проверяет права пользователя, но при внутреннем запросе через `localhost` эта проверка может быть пропущена.
* Механизм восстановления системы. Иногда разработчики специально разрешают доступ администраторам с локального сервера без авторизации, чтобы можно было восстановить систему при потере учетных данных.
* Административная панель работает на другом порту. Например, основной сайт доступен пользователям, а панель администратора работает только локально и не должна быть доступна извне.

Такие доверительные отношения делают `SSRF` особенно опасной уязвимостью. Если система по-разному обрабатывает обычные и локальные запросы, злоумышленник может использовать это для обхода ограничений доступа.

### 3.2 SSRF-атаки на внутренние системы
В некоторых случаях сервер приложения может иметь доступ к внутренним системам, которые недоступны обычным пользователям из интернета.

Такие системы часто используют внутренние IP-адреса, например:
```
192.168.x.x
10.x.x.x
172.16.x.x
```
Внутренние сервисы обычно защищены сетевой инфраструктурой и не предназначены для прямого доступа пользователей. Поэтому их защита иногда слабее, чем у внешних приложений.

Кроме того, внутренние системы могут содержать административные функции, которые доступны без дополнительной авторизации, если запрос приходит из доверенной внутренней сети.

Например, предположим, что внутри организации находится административная панель:
```
http://192.168.0.68/admin
```
Пользователь не может открыть этот адрес напрямую, потому что он находится во внутренней сети.

Но через `SSRF` злоумышленник может заставить сервер выполнить запрос:
```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded

stockApi=http://192.168.0.68/admin
```
В результате сервер самостоятельно обращается к внутреннему ресурсу и возвращает его содержимое злоумышленнику.

Таким образом, `SSRF` позволяет использовать сервер приложения как «мост» между внешним пользователем и внутренней инфраструктурой организации.

## 4. Обход общих защит SSRF
Во многих приложениях, где присутствует возможность `SSRF`, разработчики пытаются добавить защиту от злоумышленного использования.

Например, приложение может проверять введённые пользователем URL и блокировать подозрительные адреса:
* 127.0.0.1;
* localhost;
* внутренние IP-адреса;
* административные страницы вроде /admin.

Однако такие защиты часто можно обойти, используя особенности обработки URL.

### 4.1 SSRF с фильтрами входных данных на основе чёрного списка
`Чёрный список (blacklist)` — это подход, при котором приложение блокирует только известные опасные значения.

Например, приложение может запрещать запросы к:
* 127.0.0.1
* localhost
* /admin

Но злоумышленник может использовать другие способы записи этих же адресов.

**Возможные способы обхода:**

*1. Использование альтернативного представления IP-адреса*. Один и тот же IP-адрес может быть записан разными способами.

Например, адрес:
```
127.0.0.1
```
можно представить как:
```
2130706433
017700000001
127.1
```
Если фильтр проверяет только стандартную запись IP, он может не распознать альтернативный вариант.

*2. Использование собственного домена*. Злоумышленник может создать доменное имя, которое будет указывать на нужный IP-адрес.

Например:
```
evil-example.com → 127.0.0.1
```
***Для фильтра это будет обычный внешний домен, но после DNS-разрешения запрос попадёт на локальный сервер.***

*3. Обход фильтров с помощью кодирования*. Заблокированные строки можно скрыть с помощью URL-кодирования или изменения регистра символов.

Например:
```
localhost
```
может быть передан в другом виде, который фильтр не распознает. 

Также иногда используется двойное кодирование, если разные компоненты системы по-разному обрабатывают закодированные данные.

*4. Использование перенаправлений*. Можно указать URL, который разрешён фильтром, но затем перенаправляет запрос на запрещённый адрес.

Например:
```
https://allowed-site.com
```
может вернуть перенаправление:
```
http://127.0.0.1/admin
```
Если сервер автоматически следует перенаправлениям, `SSRF-защита` будет обойдена.

Также иногда помогает изменение протокола:
* http → https
* или наоборот.

### 4.2 SSRF с фильтрами входных данных на основе белого списка
`Белый список (whitelist)` работает наоборот: приложение разрешает только заранее указанные безопасные значения.

Например, приложение может разрешать запросы только к:
```
stock.weliketoshop.net
```
На первый взгляд такой подход безопаснее, но его тоже можно обойти из-за особенностей обработки URL.

#### Использование особенностей URL
Разные компоненты приложения могут по-разному анализировать один и тот же URL. Например, разработчик может проверить только начало строки:
```
https://trusted-site.com
```
но HTTP-клиент позже обработает URL иначе.

Возможные методы обхода:
#### 4.2.1. Использование символа @
В URL можно указать данные авторизации перед настоящим адресом сервера.

Например:
```
https://trusted-site.com:password@evil-site.com
```
Фильтр может увидеть:
```
trusted-site.com
```
и разрешить запрос.

Однако браузер или сервер отправит запрос на:
```
evil-site.com
```
#### 4.2.2. Использование символа #
Символ `#` обозначает фрагмент URL. Например:
```
https://evil-site.com#trusted-site.com
```
Некоторые фильтры могут ошибочно считать, что запрос выполняется к:
```
trusted-site.com
```
хотя реальный адрес:
```
evil-site.com
```
#### 4.2.3. Использование поддоменов
Можно создать домен, который содержит разрешённую строку:
```
trusted-site.com.evil-site.com
```
Если фильтр просто ищет наличие текста:
```
trusted-site.com
```
он может ошибочно разрешить такой адрес.

#### 4.4.4. Использование URL-кодирования
Специальные символы можно заменить на их закодированный вариант. Например:
```
/admin
```
может быть передан как:
```
%2Fadmin
```
Если фильтр и сервер по-разному обрабатывают кодирование, это может привести к обходу защиты.

Также можно использовать комбинацию нескольких методов одновременно.

### 4.3 Обход SSRF-фильтров через открытое перенаправление
Иногда `SSRF-защиту` можно обойти с помощью другой уязвимости — открытого перенаправления (Open Redirect).

Открытое перенаправление возникает, когда приложение позволяет пользователю указать адрес, куда нужно выполнить переход.

Например:
```
/product/nextProduct?currentProductId=6&path=http://evil-user.net
```
Сервер выполнит перенаправление:
```
http://evil-user.net
```
Представим, что приложение проверяет URL для `SSRF` и разрешает только домен:
```
weliketoshop.net
```
Однако внутри этого домена есть открытое перенаправление.

Тогда злоумышленник отправляет запрос:
```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded

stockApi=http://weliketoshop.net/product/nextProduct?currentProductId=6&path=http://192.168.0.68/admin
```
Процесс атаки выглядит так:
1. Приложение проверяет URL.
2. Видит разрешённый домен:
    * weliketoshop.net
3. Отправляет запрос по этому адресу.
4. Получает перенаправление:
    * http://192.168.0.68/admin
5. Автоматически выполняет запрос к внутренней системе.

В результате `SSRF-защита` обходится, потому что первоначальный URL был разрешён, но после перенаправления сервер обращается уже к нужному злоумышленнику внутреннему ресурсу.


## 5. Запутывание атак с использованием кодировок
### 5.1 Контекстное декодирование
Клиенты и серверы используют различные виды кодирования для передачи данных между системами.

Перед использованием данных приложение обычно сначала выполняет их декодирование. Однако порядок и способ декодирования зависят от того, где именно используются эти данные.

Например:
* параметры URL обычно декодируются сервером;
* содержимое HTML-страниц может декодироваться браузером;
* данные XML могут обрабатываться самим серверным приложением.

При создании атаки важно учитывать контекст, в котором находится ваша полезная нагрузка.

Если понять, как приложение будет обрабатывать и декодировать введённые данные, можно найти другой способ представить ту же самую нагрузку так, чтобы она прошла защитные механизмы.

### 5.2 Ошибки при декодировании (расхождения)
Многие атаки внедрения (Injection) используют специальные конструкции:
* HTML-теги;
* JavaScript-код;
* SQL-команды.

Например:
```html
<script>alert(1)</script>
```
или:
```sql
SELECT * FROM users
```
Так как пользователи обычно не должны передавать такой код, веб-приложения часто используют фильтры, которые блокируют подозрительные данные.

Однако перед проверкой фильтр должен сначала выполнить декодирование входных данных.

Проблема возникает, если:
* фильтр декодирует данные одним способом;
* сервер или браузер обрабатывает их другим способом.

В этом случае злоумышленник может передать опасную нагрузку в закодированном виде.

Фильтр её не обнаружит, а приложение позже автоматически декодирует и выполнит.

### 5.3 Обфускация через URL-кодирование
В URL некоторые символы имеют специальное значение. Например:
* `&` используется для разделения параметров;
* `=` используется для разделения имени параметра и значения.

Но иногда эти символы являются обычными данными. Например, пользователь ищет:
```
Fish & Chips
```
Если передать это напрямую:
```
search=Fish&Chips
```
сервер может неправильно понять запрос:
* search = Fish
* отдельный параметр Chips

Чтобы избежать этого, браузер автоматически кодирует специальные символы. Например:
```
search=Fish+%26+Chips
```
Здесь:
* `%26` — это код символа `&`;
* `+` обычно используется вместо пробела.

Сервер после получения URL обычно автоматически выполняет декодирование. Например:
```
%22 → "
%3C → <
%3E → >
```
Поэтому для приложения следующие значения обычно одинаковы:
```html
<script>
```
и
```
%3Cscript%3E
```
Иногда `Web Application Firewall (WAF)` или другие фильтры неправильно обрабатывают URL-кодирование. В таком случае можно скрыть вредоносную нагрузку с помощью кодирования.

Например, SQL-команду:
```
SELECT
```
можно представить как:
```
%53%45%4C%45%43%54
```
Если фильтр проверяет только обычный текст, он может не обнаружить такую нагрузку.

### 5.4 Обфускация через двойное URL-кодирование
Некоторые приложения выполняют декодирование URL два раза. Само по себе это не является ошибкой, если защитные механизмы также выполняют двойное декодирование.

Но если `WAF` декодирует данные только один раз, возникает проблема.

Рассмотрим `XSS`-нагрузку:
```html
<img src=x onerror=alert(1)>
```
После обычного URL-кодирования она будет выглядеть так:
```
%3Cimg%20src%3Dx%20onerror%3Dalert(1)%3E
```
`WAF` декодирует её:
```html
<img src=x onerror=alert(1)>
```
и блокирует запрос.

Но если выполнить двойное кодирование:
```
%253Cimg%2520src%253Dx%2520onerror%253Dalert(1)%253E
```
то после первого декодирования `WAF` получит:
```
%3Cimg%20src%3Dx%20onerror%3Dalert(1)%3E
```
Он может не распознать атаку.

Если сервер затем выполнит второе декодирование, вредоносный код восстановится.

### 5.5 Обфускация через HTML-кодирование
В HTML специальные символы должны быть закодированы, чтобы браузер не воспринимал их как часть разметки. 

Например:
```
<
```
может быть заменено на:
```
&lt;
```
HTML-кодирование может использовать:

#### Именованные сущности:
```
&colon;
```
представляет символ:
* `:`
#### Десятичные коды:
```
&#58;
```
#### Шестнадцатеричные коды:
```
&#x3a;
```
Браузер автоматически декодирует такие значения при отображении страницы. Это можно использовать для обхода защитных механизмов.

Например, стандартная XSS-нагрузка:
```html
<img src=x onerror="alert(1)">
```
может быть изменена:
```html
<img src=x onerror="&#x61;lert(1)">
```
Здесь:
```
&#x61;
```
будет преобразовано браузером в:
* a

В результате браузер выполнит:
```
alert(1)
```
#### 5.5.1 Использование ведущих нулей
При HTML-кодировании можно добавлять дополнительные нули в числовые значения.

Например:
```
&#x61;
```
можно записать как:
```
&#x00000061;
```
Некоторые `WAF` и фильтры неправильно обрабатывают такие значения.

Например:
```html
<a href="javascript&#00000000000058;alert(1)">
Click me
</a>
```
После декодирования браузер преобразует это в:
```html
javascript:alert(1)
```
### 5.6 Обфускация через XML-кодирование
`XML` использует похожий механизм кодирования символов, как HTML. 

Например:
```
&#x53;
```
представляет символ:
* `S`

Это позволяет скрывать определённые части полезной нагрузки.

Например, SQL-команда:
```sql
SELECT * FROM information_schema.tables
```
может быть передана так:
```html
<stockCheck>
    <productId>
        123
    </productId>
    <storeId>
        999 &#x53;ELECT * FROM information_schema.tables
    </storeId>
</stockCheck>
```
После обработки `XML` сервер декодирует значение:
```
&#x53; → S
```
и получает:
```sql
SELECT * FROM information_schema.tables
```
Таким образом, кодирование `XML` может использоваться для обхода `WAF` и других фильтров, которые блокируют опасные SQL-команды или другие признаки атак внедрения.

### 5.7 Обфускация через Unicode-кодирование
Unicode escape-последовательности. `Unicode escape` — это способ записи символов с помощью их числового кода.

Формат:
```
\uXXXX
```
где:
* `\u` — обозначение Unicode-кода;
* `XXXX` — четырёхзначный шестнадцатеричный код символа.

Например:
```
\u003a
```
представляет символ:
* `:`

Современный JavaScript также поддерживает другой формат:
```
\u{3a}
```
Когда приложение обрабатывает строки, многие языки программирования автоматически декодируют Unicode-последовательности.

Это также делает `JavaScript`-движок браузера.

Поэтому Unicode можно использовать для скрытия вредоносного кода от фильтров.

Например, при `DOM XSS` предположим, что пользовательский ввод передаётся в функцию:
```js
eval()
```
как строка.

Обычная нагрузка:
```js
alert(1)
```
может быть заменена:
```js
eval("\u0061lert(1)")
```
Здесь:
```
\u0061
```
будет преобразовано в:
* `a`

В результате браузер выполнит:
```js
alert(1)
```
Если серверный фильтр проверяет только исходный текст, он может не обнаружить такую нагрузку.

***Примечание - Внутри строк можно заменять Unicode-кодами практически любые символы.***

Однако вне строк некоторые символы могут вызвать синтаксические ошибки.

Например, нельзя произвольно заменять такими escape-последовательностями элементы структуры JavaScript:
* (
* )
* {
* }

Также Unicode в формате `ES6` поддерживает добавление ведущих нулей.

Например:
```html
<a href="javascript:\u{00000000061}alert(1)">
Click me
</a>
```
После декодирования браузер получит:
```
javascript:alert(1)
```
Некоторые `WAF` могут неправильно обработать такое значение и пропустить его.

### 5.8 Обфускация через Hex-кодирование
Ещё один способ скрыть код — использовать шестнадцатеричные escape-последовательности.

Формат:
```
\xXX
```
Например:
```
\x61
```
представляет символ:
* `a`

Использование в JavaScript:
```js
eval("\x61lert(1)")
```
После декодирования:
```js
eval("alert(1)")
```
Такой подход может использоваться не только в JavaScript.

Например, в SQL можно использовать шестнадцатеричное представление строк:
```
0x53454c454354
```
После декодирования это значение превращается в:
```
SELECT
```
Таким образом можно скрывать SQL-команды от простых фильтров.

### 5.8 Обфускация через Octal-кодирование
`Octal escape` использует восьмеричную систему счисления.

Формат:
```
\XXX
```
Например:
```
\141
```
представляет символ:
* `a`

Пример использования:
```js
eval("\141lert(1)")
```
После обработки JavaScript получит:
```js
eval("alert(1)")
```
### 5.9 Обфускация с использованием нескольких кодировок
Для обхода фильтров можно комбинировать несколько способов кодирования одновременно. Например, рассмотрим `XSS-нагрузку`:
```js
javascript:alert(1)
```
Она может быть скрыта с помощью HTML и Unicode-кодирования:
```html
<a href="javascript:&bsol;u0061lert(1)">
Click me
</a>
```
Процесс обработки происходит поэтапно.  
**1. Браузер сначала декодирует HTML:**
* `&bsol;`  
превращается в:
* `\`  
Получается:
```html
<a href="javascript:\u0061lert(1)">
Click me
</a>
```
**2. Затем JavaScript декодирует Unicode:**
* `\u0061`  
становится:
* `a`  
В результате браузер получает:
```html
<a href="javascript:alert(1)">
Click me
</a>
```
И выполняет `XSS-код`.

Чтобы успешно использовать такие методы, необходимо понимать:
* какие кодировки применяются;
* в каком порядке выполняется декодирование;
* какой компонент системы обрабатывает данные.

### 5.10 Обфускация через функцию SQL CHAR()
`CHAR()` не является классическим способом кодирования, но может использоваться для скрытия SQL-команд.

Функция `CHAR()` принимает числовой код символа и возвращает соответствующий символ.

Например:
* CHAR(83)
* CHAR(0x53)

вернут:
* `S`

Используя несколько вызовов `CHAR()`, можно собрать запрещённое ключевое слово.

Например, вместо:
```
SELECT
```
можно использовать:
```
CHAR(83)+CHAR(69)+CHAR(76)+CHAR(69)+CHAR(67)+CHAR(84)
```
После обработки SQL-сервер преобразует это выражение:
* CHAR(83) → S
* CHAR(69) → E
* CHAR(76) → L
* CHAR(69) → E
* CHAR(67) → C
* CHAR(84) → T

и получает:
```
SELECT
```
Если фильтр блокирует слово SELECT, но не анализирует выражения `CHAR()`, такая техника может позволить обойти защиту.

Таким образом, кодирование и обфускация позволяют скрывать вредоносные нагрузки от простых фильтров. Защита должна анализировать данные после всех необходимых этапов декодирования, иначе злоумышленник может передать тот же код в изменённом представлении.

## 6. Слепые уязвимости SSRF
`Слепые SSRF-уязвимости` возникают в тех случаях, когда злоумышленник может заставить приложение отправить внутренний HTTP-запрос на указанный им адрес, но результат этого запроса не возвращается пользователю.

Такие уязвимости сложнее использовать, чем обычный `SSRF`, потому что атакующий не видит ответ от внутреннего сервера. Однако в некоторых случаях слепой SSRF может привести к удалённому выполнению кода на сервере приложения или других внутренних системах.

### 6.1 Что такое слепой SSRF?
При обычной SSRF-атаке злоумышленник отправляет серверу вредоносный URL и получает ответ от внутреннего ресурса.

Например:
```
http://localhost/admin
```
Сервер выполняет запрос и возвращает страницу администратора.

При слепом SSRF сервер также выполняет запрос:
```
http://internal-server/admin
```
но его ответ не отображается пользователю.

То есть злоумышленник знает только то, что сервер сделал запрос, но не видит полученные данные.

### 6.2 Каково влияние слепых SSRF-уязвимостей?
`Слепой SSRF` обычно менее опасен, чем обычный `SSRF`, потому что невозможно напрямую получить данные из внутренних систем.

Например, злоумышленник не сможет просто отправить запрос:
```
http://192.168.0.68/admin
```
и увидеть содержимое административной панели.

Однако `слепой SSRF` всё равно может быть опасным.

Его можно использовать для:
* обнаружения внутренних серверов;
* проверки наличия уязвимых сервисов внутри сети;
* атак на внутренние компоненты системы;
* выполнения удалённых команд при наличии дополнительных уязвимостей.

В некоторых случаях `слепой SSRF` может привести к полному компрометированию сервера.

### 6.3 Как найти и использовать слепые SSRF-уязвимости
Самый надёжный способ обнаружения `слепого SSRF` — использование внеполосного взаимодействия (`OAST` — Out-of-Band Application Security Testing).

Суть метода:
* Создать внешний сервер или домен, который контролируется тестировщиком.
* Передать этот адрес в уязвимое приложение.
* Проверить, сделал ли сервер запрос к этому адресу.

Если приложение обращается к контролируемому домену, это означает, что оно выполняет запросы по URL, предоставленным пользователем.

Самый удобный инструмент для таких проверок — `Burp Collaborator`.

С его помощью можно:
* Создать уникальный домен:
    * example.burpcollaborator.net
* Передать его приложению:
    * stockApi=http://example.burpcollaborator.net
* Отслеживать входящие соединения.

Если сервер приложения отправил HTTP-запрос на этот домен, значит существует `SSRF-уязвимость`.

***Примечание - При тестировании слепых SSRF часто можно увидеть только DNS-запрос, но не сам HTTP-запрос.***

Например:
* DNS запрос:
    * example.burpcollaborator.net

Но HTTP-соединение отсутствует.

Это обычно происходит следующим образом:
* Приложение пытается выполнить HTTP-запрос.
* Сначала выполняется DNS-разрешение домена.
* Затем сетевой фильтр блокирует HTTP-соединение.

Во многих организациях исходящие DNS-запросы разрешены, потому что они необходимы для работы системы, но прямые HTTP-соединения к неизвестным адресам могут быть запрещены.

### 6.4 Использование слепого SSRF
Сам факт обнаружения `слепого SSRF` ещё не означает, что можно сразу получить доступ к данным.

Так как ответ внутреннего запроса недоступен, невозможно напрямую просматривать содержимое внутренних систем. Однако такую уязвимость можно использовать другими способами.

#### 6.4.1 Поиск внутренних уязвимых систем
Злоумышленник может выполнять скрытое сканирование внутренней сети. Например, отправлять запросы к разным IP-адресам:
* http://192.168.0.1
* http://192.168.0.2
* http://192.168.0.3

и проверять реакцию через внешние контролируемые серверы.

Если внутренний сервис содержит известную уязвимость, её можно обнаружить даже без просмотра ответа.

### 6.4.2 Проверка известных уязвимостей
Можно отправлять специальные запросы, которые проверяют наличие конкретных уязвимостей.

Например:
* SSRF заставляет сервер обратиться к внутреннему сервису.
* В запросе используется тестовая нагрузка.
* Результат отправляется через внешний канал связи.

Так можно обнаружить критические проблемы во внутренних системах, которые недоступны напрямую.

### 6.5 Использование вредоносных ответов от контролируемого сервера
Другой вариант эксплуатации `слепого SSRF` — заставить приложение подключиться к серверу злоумышленника и получить от него специально подготовленный ответ.

Схема атаки:
* Приложение делает запрос к серверу злоумышленника.
* Сервер отправляет специально сформированный HTTP-ответ.
* Уязвимый HTTP-клиент приложения неправильно обрабатывает этот ответ.

Если в HTTP-клиенте есть серьёзная уязвимость, такая атака может привести к удалённому выполнению кода внутри инфраструктуры приложения.

Таким образом, даже без возможности увидеть ответ внутреннего запроса `слепой SSRF` может стать серьёзной точкой входа для атаки.

## 7. Поиск скрытой поверхности атаки для уязвимостей SSRF
Во многих случаях `SSRF`-уязвимость обнаружить достаточно просто. Например, если приложение принимает полный URL от пользователя и затем обращается по нему.

Однако не все `SSRF` настолько очевидны. Иногда возможность заставить сервер выполнить запрос скрыта в других частях приложения, которые на первый взгляд не выглядят опасными.

### 7.1 Частичные URL в запросах
Некоторые приложения не позволяют пользователю указать полный URL. Вместо этого они принимают только часть адреса, например:
* имя хоста;
* путь;
* имя файла.

Затем сервер самостоятельно формирует полный URL и выполняет запрос. Например, пользователь передаёт только имя сервера:
```
stock-api.internal
```
А приложение формирует полный адрес:
```
http://stock-api.internal/api/check
```
или пользователь передаёт только путь:
```
/api/check
```
а приложение создаёт запрос:
```
http://stock.weliketoshop.net/api/check
```
На первый взгляд такая схема выглядит безопаснее, поскольку пользователь не контролирует весь `URL`.

Однако если приложение недостаточно проверяет входные данные, злоумышленник всё равно может изменить адрес назначения или заставить сервер обратиться к нежелательному ресурсу.

Поэтому даже параметры, содержащие лишь часть URL, следует рассматривать как потенциальную поверхность атаки.

### 7.2 URL внутри различных форматов данных
Иногда URL передаются не напрямую, а внутри различных форматов данных. Некоторые форматы позволяют указывать ссылки на внешние ресурсы, которые приложение затем автоматически загружает.

Наиболее распространённый пример — `XML`.

Если приложение принимает `XML-документ` и обрабатывает его, парсер XML может самостоятельно обращаться к указанным в документе URL.

Это может привести не только к уязвимости `XXE` (XML External Entity), но и к `SSRF`, поскольку сервер будет выполнять запросы к указанным адресам.

Именно поэтому при анализе XML-приложений необходимо проверять не только наличие `XXE`, но и возможность эксплуатации `SSRF` через внешние сущности XML.

### 7.3 SSRF через заголовок Referer
Ещё одной неожиданной точкой входа может быть HTTP-заголовок: `Referer`.

Некоторые веб-приложения используют системы аналитики, которые собирают информацию о том, откуда пришёл пользователь.

Для этого они сохраняют значение заголовка `Referer` и могут автоматически переходить по указанному в нём адресу.

Это делается, например, чтобы:
* определить источник перехода;
* проанализировать страницу, с которой пришёл пользователь;
* собрать текст ссылок (анкорный текст);
* получить дополнительную информацию о внешнем сайте.

Если аналитическая система автоматически открывает `URL` из заголовка `Referer`, злоумышленник может подставить собственный адрес.

Например:
```
Referer: http://attacker.example
```
В результате сервер самостоятельно выполнит запрос к этому адресу. Если значение `Referer` можно изменить произвольно, а сервер без проверки обращается по указанному URL, это может привести к `SSRF`.

Поэтому при тестировании приложений следует проверять не только параметры запросов, но и различные HTTP-заголовки, включая `Referer`, так как они также могут использоваться сервером для выполнения сетевых запросов.

## 8. Защита от SSRF
Для предотвращения `SSRF` необходимо исключить возможность того, чтобы пользователь управлял адресами, к которым обращается сервер. Основная задача защиты — ограничить доступ сервера только к доверенным ресурсам и не допустить выполнения произвольных запросов.

Основные меры защиты:
* Использовать белый список (Whitelist).  Разрешать обращения только к заранее определённым доменам, IP-адресам или API. Проверка должна выполняться после всех этапов нормализации и декодирования URL.
* Не использовать чёрные списки (Blacklist). Блокировка отдельных адресов (localhost, 127.0.0.1 и др.) недостаточна, поскольку существует множество способов их обхода (альтернативная запись IP-адресов, URL-кодирование, DNS-подмена и т.д.).
* Проверять итоговый адрес назначения. После разрешения DNS необходимо убедиться, что запрос не направляется на внутренние сети, loopback-адреса, link-local, multicast или другие запрещённые диапазоны IP.
* Запретить автоматическое следование перенаправлениям. Если это невозможно, необходимо повторно проверять каждый URL после получения HTTP-редиректа.
* Ограничить исходящие соединения. На уровне межсетевого экрана (Firewall), прокси-сервера или облачных политик безопасности следует разрешать серверу подключаться только к необходимым внешним сервисам.
* Защитить внутренние сервисы. Административные панели, API, базы данных и другие внутренние ресурсы не должны доверять только тому, что запрос поступил из локальной сети. Для доступа необходимо использовать аутентификацию и авторизацию.
* Защитить облачные метаданные. Если приложение работает в облаке, необходимо ограничить доступ к сервисам метаданных (например, AWS IMDS, Azure IMDS, Google Cloud Metadata), поскольку они часто становятся целью SSRF-атак.
* Отключить необязательные функции загрузки удалённых ресурсов. Если приложение не должно автоматически загружать внешние URL, такую возможность следует отключить.
* Логировать исходящие запросы. Необходимо фиксировать обращения к внешним ресурсам и отслеживать попытки подключения к внутренним IP-адресам, необычным доменам или запрещённым диапазонам.

### 8.1 Рекомендации для AppSec
При анализе приложения следует проверять все места, где сервер может выполнять сетевые запросы:
* параметры, содержащие URL, домены или IP-адреса;
* загрузку файлов по ссылке;
* интеграции с внешними API;
* обработку XML, PDF, изображений и других форматов, которые могут обращаться к внешним ресурсам;
* HTTP-заголовки (Referer, Host, X-Forwarded-* и др.);
* механизмы веб-хуков (Webhooks), callback-URL и функции импорта данных;
* возможность обхода ограничений с помощью URL-кодирования, двойного кодирования, альтернативной записи IP-адресов, DNS Rebinding и открытых перенаправлений (Open Redirect).

Эффективная защита от `SSRF` строится по принципу многоуровневой безопасности: `строгая валидация входных данных`, `проверка конечного адреса назначения`, `ограничение исходящих сетевых соединений` и `отсутствие доверия к запросам` только потому, что они исходят из внутренней сети. Такой подход значительно снижает риск эксплуатации `SSRF` даже при наличии ошибок в приложении.
