# Path Traversal
## 1. Что это такое (Определение для собеседования)
`Path Traversal` (Directory Traversal) — это уязвимость, возникающая из-за недостаточной валидации пользовательского ввода, когда данные напрямую или после конкатенации передаются в API файловой системы.

* **Суть**: Позволяет злоумышленнику выйти за пределы корневого каталога приложения с помощью последовательностей обхода (`../` или `..\`).
* **Риски**: 
    * **Чтение** конфиденциальных файлов ОС (например, /etc/passwd, win.ini), исходного кода, токенов и конфигураций. 
    * При наличии прав на запись — **перезапись файлов**, модификация логики приложения и **Remote Code Execution** (RCE).

## 2. Методы поиска
* Статический анализ (SAST) / Code Review: Ищем в коде функции чтения/записи файлов, куда пробрасываются параметры запроса (`req.query`, `GET/POST`).
* Динамический анализ (DAST) / Fuzzing: Автоматизированное тестирование параметров (`?file=`, `?image=`) с помощью Burp Suite Intruder (лоад Fuzzing - path traversal).
* Техники обхода фильтров (Bypass), о которых нужно упомянуть:
    * `Использование абсолютных путей` вместо относительных (filename=/etc/passwd).
    * Вложенные последовательности (`....//`), если приложение делает простой стриппинг `../` один раз.
   * URL-кодирование (`%2e%2e%2f`) и двойное URL-кодирование (`%252e%252e%252f`) для обхода WAF/серверных фильтров.
   * Использование Null-байта (`%00.png`) в старых версиях языков (например, Node.js < 0.11, старый PHP/Java) для обхода проверки расширения файла.

## 3. Примеры уязвимостей с кодом
```python
from flask import Flask, request, send_fileimport os
app = Flask(__name__)IMAGE_DIR = "/var/www/images/"
@app.route('/loadImage')
def load_image():
    # Уязвимо: прямая конкатенация ввода с путем файловой системы
    filename = request.args.get('filename')
    return send_file(os.path.join(IMAGE_DIR, filename)) 
```
Payload: `/loadImage?filename=../../../etc/passwd`

JavaScript
```JavaScript
const express = require('express');
const fs = require('fs');
const path = require('path');
const app = express();

app.get('/loadImage', (req, res) => {
    const filename = req.query.filename;
    // Уязвимо: path.join не защищает от '../'
    const safePath = path.join('/var/www/images', filename); 
    fs.readFile(safePath, (err, data) => {
        if (err) return res.status(404).send('Not Found');
        res.send(data);
    });
});
```
Payload: ``/loadImage?filename=..\..\..\windows\win.ini``

## 4. Методы защиты
1. Основное правило: Полный **отказ от передачи пользовательского ввода** в API файловой системы (например, использование ID файлов в БД или хэшированных имен).
2. **Белый список** (White-listing): Если отказаться нельзя, валидировать ввод строго по белому списку (разрешать только буквы и цифры, без спецсимволов).
3. Канонизация и **верификация пути** (Path Normalization): Приведение пути к абсолютному виду с последующей проверкой префикса базовой директории.

## 5. Правильное исправление кода
```Python 
# Используйте os.path.abspath или pathlib.Path.resolve().

if not target_dir.startswith(base_dir):
    return "Access Denied", 403
```

}

## 6. Вопросы
### 6.1 Разница между `path.join()` и `path.resolve()`
* `path.join()` просто объединяет сегменты пути и нормализует результат (удаляет лишние слэши). 
* `path.resolve()` обрабатывает сегменты справа налево и создает абсолютный путь.
* Оба метода требуют обязательной последующей проверки через `.startsWith(baseDir)`, но `path.resolve()` предпочтительнее, так как он сразу возвращает абсолютный путь, готовый к сравнению.

### 6.2 Тестирование в JSON / XML
* В **JSON** спецсимволы и последовательности `../` могут передаваться напрямую внутри строковых значений. Дополнительно тестируется Unicode-экранирование - `\u002e\u002e\u002f` вместо `../`.
* В **XML** уязвимость может проявляться в двух местах: в значениях тегов/атрибутов (аналогично JSON) и через механизм XXE (XML External Entities). Если парсер XML не сконфигурирован безопасно, злоумышленник может объявить внешнюю сущность `<!ENTITY xxe SYSTEM "file:///etc/passwd">`, что технически является чтением произвольных файлов, родственным `Path Traversal`.

### 6.3 Уязвимость Zip Slip
* `Zip Slip` — это специфическая разновидность Path Traversal, которая происходит на этапе распаковки архивов (zip, tar, jar).
* Имена файлов внутри архива могут содержать последовательности `../../`. Если код распаковщика конкатенирует целевую директорию и имя файла из архива без валидации, файл будет записан за пределами легитимной папки.
* Опасность: Злоумышленник может перезаписать критические файлы (например, `.bashrc`) и получить `RCE`.

### 6.4 Шифрование и хэширование имен файлов
* Если приложение использует внутренние идентификаторы (например, UUID или хэш файла в БД Hash -> Real_Path, может брать хэш пути к директории с файлами), то пользователь вообще не контролирует имя файла, и `Path Traversal` невозможен.
* Но есть нюанс: Если приложение просто шифрует/расшифровывает путь на стороне клиента (передает клиенту зашифрованный токен с путем), то безопасность зависит от криптостойкости алгоритма и защиты ключа. Если ключ утечет или алгоритм уязвим (например, слабый режим шифрования), злоумышленник сможет сгенерировать валидный зашифрованный payload с `../`.

### 6.5 Защита на уровне инфраструктуры
* Конфигурация веб-сервера: Использование директивы `alias` в Nginx требует осторожности. Ошибка `location /certs { alias /etc/nginx/certs/; }` (отсутствие слэша после /certs) приводит к Path Traversal через запрос `/certs../`. WAF помогает блокировать известные паттерны обхода.
* Права доступа (Principle of Least Privilege): Процесс веб-сервера (например, www-data или nginx) должен иметь доступ на чтение только к тем директориям, которые ему необходимы. Он ни в коем случае не должен работать под root.
* Изоляция: **Запуск приложения в изолированных контейнерах (Docker)** или chroot-окружении ограничивает корень файловой системы. Даже если злоумышленник выйдет в корень контейнера, он не получит доступ к реальным файлам хост-системы.
