# CORS-уязвимостям
> Запрет `CORS` защищает данные от чтения чужими сайтами, но он НЕ защищает от CSRF-атак (выполнения действий).

## 1. Что это такое?
* `SOP` (Same-Origin Policy) — фундаментальный механизм безопасности браузера. Он запрещает скриптам одного источника (комбинация протокол + домен + порт) читать ответы от другого источника.
* `CORS` (Cross-Origin Resource Sharing) — это контролируемое ослабление политики `SOP` с помощью HTTP-заголовков ответа сервера. Он указывает браузеру, каким сторонним сайтам разрешено читать данные.
* **Суть уязвимости**: Ошибки конфигурации CORS, из-за которых сервер выдает конфиденциальные данные (Access-Control-Allow-Credentials: true) невалидным или вредоносным источникам.

* **Access-Control-Allow-Origin: evil.com** - Говорит браузеру: «Я разрешаю сайту evil.com читать мои данные».
* **Access-Control-Allow-Credentials: true** - «Я разрешаю сайту evil.com делать это в рамках авторизованной сессии пользователя (с куками и сессиями)».

## 2. Примеры CORS-уязвимостей
1. **Динамическое отражение Origin**: Сервер берет заголовок `Origin` из запроса клиента и без валидации подставляет его в ответ `Access-Control-Allow-Origin: <клиентский_origin>` вместе с `Access-Control-Allow-Credentials: true`. Это дает любому сайту в сети доступ к сессии пользователя.
```py
# УЯЗВИМОСТЬ: Origin из запроса идет в ACAO
origin = request.headers.get('Origin')
if origin:
    response.headers['Access-Control-Allow-Origin'] = origin
    response.headers['Access-Control-Allow-Credentials'] = 'true'
```
2. **Ошибки регулярных выражений (RegEx)**: Плохая валидация белого списка поддоменов.
   * Проверка окончания строки: normal-website.com поддается обходу через attacker-normal-website.com.
   * Проверка начала строки: normal-website.com обходится через ://attacker.com.
```js
// УЯЗВИМОСТЬ: Небезопасная регулярка
if (origin && origin.match(/https:\/\/.*://target.com)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
}
```
3. **Доверие к значению null**: Добавление `Origin: null` в белый список (часто делают для локальной отладки). Злоумышленник может триггернуть null через песочницу `iframe sandbox` или `data: URL` и прочитать данные.
```js
// УЯЗВИМОСТЬ: Доверие источнику null
if (origin === 'null' || origin === 'https://target.com') {
    res.setHeader('Access-Control-Allow-Origin', origin);
}
```
4. **XSS на доверенном поддомене**: Главный сайт `api.com` доверяет поддомену `://api.com`. Но на форуме есть уязвимость, и атакующий смог внедрить туда свой скрипт (например, в комментарий).

Браузер честно скажет главному сайту: `Origin: https://api.com`. Главный сайт доверяет форуму, поэтому разрешит `CORS`. В итоге скрипт атакующего прочитает секреты пользователя.

5. **Обход TLS (HTTP внутри CORS)**: Если HTTPS-сайт доверяет своему старому HTTP-поддомену через CORS, атакующий в рамках одной Wi-Fi сети (MiTM) перехватит незащищенный HTTP-трафик поддомена, внедрит туда JS-код и вытащит данные с HTTPS-сайта.

## 3. Методы поиска
* `Blackbox` / Анализ трафика (Burp Suite):
    * Подмена заголовка **Origin: evil.com** в запросах, где передаются сессионные cookie/токены. Смотрим на ответ: возвращается ли **Access-Control-Allow-Origin: evil.com** и есть ли там **Access-Control-Allow-Credentials: true**.
   * Проверка спец-символов и некорректных поддоменов в **Origin** (тест регулярных выражений).
   * Отправка запроса с **Origin: null**.
* `Whitebox` / Анализ кода (SAST / Code Review):
    * Анализ конфигурационных файлов веб-серверов (Nginx, Apache) и CORS-мидлварей в коде приложения.
   * Поиск регулярных выражений, валидирующих Origin, и проверка их на уязвимости (отсутствие экранирования точек, слабые привязки ^ и $).

## 4. Методы защиты (Remediation)
1. **Строгий белый список**: Запретить динамическое отражение `Origin` без сверки с жестким белым списком (white-list).
2. **Отказ от `*` с Credentials**: Если на эндпоинте требуется **Access-Control-Allow-Credentials: true**, использование подстановочного знака `*` запрещено стандартами браузеров.
3. **Запрет null**: Никогда не добавлять `null` в список разрешенных источников.
4. Защита интранета: Не использовать `Access-Control-Allow-Origin: *` на внутренних ресурсах, чтобы внешние сайты не использовали браузер жертвы как прокси во внутреннюю сеть.
5. **Глубокая защита (Defense in Depth)**: `CORS` — это ограничение для браузера, а не замена авторизации на сервере. Защищайте чувствительные API сессиями, токенами и CSRF-защитой независимо от настроек CORS.
