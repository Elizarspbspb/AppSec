# Web Cache Poisoning (Отравление веб-кэша)

## 1. Что такое ? 
`Web Cache Poisoning` (Отравление веб-кэша) — это продвинутая атака, при которой злоумышленник манипулирует неключевыми входными данными запроса, чтобы заставить сервер сгенерировать вредоносный HTTP-ответ, который затем сохраняется в кэше и транслируется другим пользователям с таким же кэш-ключом.

* **Кэш-ключ** (Cache Key): Набор компонентов запроса (обычно метод, путь и заголовок Host), по которому кэш идентифицирует запрос.
* **Неключевые данные** (Unkeyed inputs): Части запроса (например, заголовки X-Forwarded-Host, User-Agent, Cookie), которые кэш игнорирует при поиске совпадений, но которые обрабатываются бэкенд-приложением.

## 2. Методы поиска
1. Поиск кэш-оракула: **Нахождение страницы/конечной точки, которая возвращает заголовки состояния кэша** (например, `X-Cache: HIT`, `Cache-Status: miss`), либо меняет время/контент ответа в зависимости от кэширования.
2. Выявление Неключевых-параметров:
    * Вручную: Добавление случайных заголовков и отслеживание изменений в ответе. Применение `Cache Buster` (уникального параметра в URL/заголовках), чтобы случайно не отравить кэш реальным пользователям во время тестов.
    * Автоматически: Использование расширения `Param Miner` для Burp Suite (функция Guess headers).
3. Анализ обработки **Cache Key**: Тестирование того, как кэш нормализует или усекает данные (например, исключает ли он порт из Host или отбрасывает параметры строки запроса).

## 3. Примеры уязвимостей и уязвимый код
### 1. Использование X-Forwarded-Host для XSS (Недостаток дизайна)
Бэкенд берет неключевой заголовок `X-Forwarded-Host` для генерации путей к медиафайлам или мета-тегам без фильтрации.
```Python
from flask import Flask, request, render_template_string
app = Flask(__name__)

@app.route('/en')
def index():
    # Плохая практика: заголовок X-Forwarded-Host берется напрямую и не входит в кэш-ключ
    xfh = request.headers.get('X-Forwarded-Host', request.host)
    
    # Значение подставляется в HTML-шаблон без санитизации
    template = f'<meta property="og:image" content="https://{xfh}/cms/social.png" />'
    return render_template_string(template)
```
Запрос атакующего:
```
GET /en HTTP/1.1
Host: innocent-website.com
X-Forwarded-Host: a."><script>alert(1)</script>"
```
Ответ с XSS-нагрузкой сохраняется в кэше для ключа `GET /en innocent-website.com`.

### 2. Маскировка параметров из-за разницы парсинга (Недостаток реализации)
Кэш и приложение по-разному считывают разделители. Например, приложение на Node.js/JavaScript принимает точку с запятой `;` или лишний знак `?` как разделитель параметров, а кэш — нет.

```JavaScript
const express = require('express');const app = express();
app.get('/jsonp', (req, res) => {
    // Если в кэш уходит только первый callback, а Node.js берет ПОСЛЕДНИЙ из дубликатов
    // Запрос: /jsonp?callback=safeFunc;callback=payload
    const callback = req.query.callback; 
    
    res.type('text/javascript');
    res.send(`${callback}({"status":"ok"});`);
});
```
Запрос атакующего:
```
GET /jsonp?keyed_param=abc&excluded_param=123;callback=alert(1) HTTP/1.1
```
Кэш удаляет `excluded_param` и считает, что ключ чист, а бэкенд выполняет `alert(1)` из-за особенностей парсинга разделителей.

## 4. Методы защиты (Remediation)
* **Полное отключение кэширования для динамических страниц**, где это возможно, или ограничение кэша только строго статическими ресурсами.
* Запрет на использование Unkeyed-данных: **Бэкенд никогда не должен доверять и использовать для формирования ответа заголовки, не входящие в Cache Key**. Если заголовок не нужен приложению, его нужно удалять/игнорировать на уровне CDN/WAF.
* **Перезапись запросов (URL rewriting)**: Если необходимо исключить параметр из кэширования для оптимизации производительности, запрос должен физически переписываться на стороне прокси перед отправкой на бэкенд.
* **Синхронизация парсеров**: Настройки кэширующего прокси (CDN) и логика обработки параметров веб-сервером/фреймворком должны полностью совпадать во избежание маскировки параметров (Parameter Smuggling).
* **Строгая санитизация**: Защита от классических клиентских уязвимостей (XSS, Open Redirect), так как кэш способен превратить отраженную (Reflected) уязвимость в постоянную (Stored).
