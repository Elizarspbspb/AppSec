# 6. Insecure Design (A04:2021 в OWASP Top 10).
`Insecure Design` (небезопасный дизайн) — это класс уязвимостей, возникающих из‑за отсутствия или неэффективности мер безопасности на этапе проектирования, разработки архитектуры, бизнес-логики и пользовательских процессов веб‑приложения.

Главная особенность данного класса уязвимостей заключается в том, что проблема возникает ещё до написания программного кода. Разработчики могут реализовать приложение без ошибок программирования, использовать современные библиотеки, применять безопасные методы разработки, но сама архитектура системы может оставаться уязвимой.

Ключевое отличие от других уязвимостей:
1. `Небезопасный дизайн` — проблема архитектуры и логики приложения, заложенная ещё до начала разработки. Её нельзя полностью исправить качественной реализацией.
2. `Небезопасная реализация` — ошибки, допущенные при кодировании (например, отсутствие валидации ввода). Их можно устранить исправлением кода.

## 1. Почему возникает Insecure Design
Одной из главных причин появления небезопасного дизайна является неправильное распределение приоритетов во время разработки.

Во многих проектах основной целью становится максимально быстрое создание функциональности:
* добавить регистрацию пользователей;
* реализовать оплату;
* создать личный кабинет;
* выпустить приложение на рынок.

Безопасность при этом рассматривается как дополнительная функция, которую можно внедрить позже.

Такой подход приводит к ситуации, когда приложение создаётся вокруг удобства пользователя, но не учитывает действия злоумышленника.

Например, при проектировании системы скидок бизнес может сформулировать требование: "Пользователь должен иметь возможность применить промокод".

Однако отсутствует анализ вопросов безопасности:
* сколько раз можно использовать промокод;
* можно ли использовать чужой промокод;
* можно ли применить несколько скидок одновременно;
* что произойдёт при изменении параметров запроса.

В результате злоумышленник может найти способ получить незаконную выгоду.

Основные причины
1. Отсутствие оценки бизнес‑рисков на этапе проектирования.
2. Недостаточное моделирование киберугроз (не проанализированы потенциальные векторы атак).
3. Игнорирование принципов безопасного проектирования (например, «защита по умолчанию», «минимальные привилегии»).
4. Фокус на функциональности в ущерб безопасности (безопасность «добавляется» позже, а не проектируется изначально).
5. Отсутствие требований к защитному функционалу (конфиденциальность, целостность, доступность данных не заложены в ТЗ) [1].

## 2. Отсутствие моделирования угроз
Одной из наиболее важных причин появления `Insecure Design` является отсутствие `Threat Modeling` (моделирования угроз).

`Threat Modeling` — это процесс анализа приложения с точки зрения потенциального атакующего. Во время такого анализа специалисты отвечают на вопросы:
* какие данные являются ценными;
* кто может атаковать систему;
* какие существуют точки входа;
* какие действия должен быть запрещены;
* какие последствия будут при компрометации.

Например, рассматривается интернет-банк. Безопасный анализ должен учитывать:
Что произойдет, если пользователь изменит параметры запроса?
Например:
```
{
    "amount":1000,
    "receiver":"user123"
}
```
Атакующий может попытаться изменить:
```
{
    "amount":1000000,
    "receiver":"attacker"
}
```
Если система не имеет механизмов проверки, значит проблема была заложена ещё на этапе проектирования.

## 3. Основные виды уязвимостей Insecure Design
### 3.1 Отсутствие правильной модели контроля доступа. 
Например, приложение позволяет врачу видеть историю болезни только своего пациента, но в дизайне не заложена проверка принадлежности пациента врачу — это даёт возможность получить доступ ко всем данным.

Проблема заключается не только в отсутствии проверки в коде. Основная ошибка заключается в том, что архитектура не учитывает связь: `Врач → Его пациенты → Медицинские данные`. Правильная модель должна хранить отношения между объектами. Перед выдачей информации система должна проверить:
* Кто выполняет запрос?
* Какие пациенты принадлежат этому пользователю?
* Имеет ли он право получать эти данные?

### 3.2 Возможность обхода бизнес-процессов
Сценарии, где пользователь может пропустить шаги (например, этап оплаты) или выполнить действия в неверном порядке.

***Ошибка дизайна возникает, когда приложение не контролирует порядок выполнения действий.***

Правильный процесс: `Выбор товара - Корзина - Оплата - Создание заказа - Доставка`.

Но разработчики сделали API:
```
POST /api/create-order
```
который принимает:
```
{
"product":"Laptop",
"payment_status":"success"
}
```
Система доверяет параметру:
```
payment_status=success
```
Но пользователь полностью контролирует запрос. Он может отправить:
```
{
"product":"Laptop",
"payment_status":"success"
}
```
и получить товар без оплаты.

***Причина заключается не в отсутствии фильтрации данных, а в неправильном проектировании процесса.***

Сервер должен самостоятельно проверять факт оплаты: `Пользователь - Платёжная система - Подтверждение оплаты - Создание заказа`.

### 3.3 Отсутствие обработки ошибок безопасности. 
Приложение выдаёт подробные сообщения об ошибках, раскрывающие структуру БД или код.

### 3.3. Доверие данным от клиента.
Логика приложения опирается на данные, присланные браузером (роли пользователя, флаги доступа), без проверки на сервере.

Например, мобильное приложение отправляет:
```
{
"user":"alex",
"role":"admin"
}
```
Сервер анализирует:
```py
if role == "admin":
    open_admin_panel()
```
Пользователь может изменить запрос:
```
{
"user":"guest",
"role":"admin"
}
```
и получить административные права.

Правильная архитектура должна работать иначе: `Клиент - Токен пользователя - Сервер - База данных - Определение реальной роли.`

Роль пользователя должна храниться только на стороне сервера.

**Главный принцип:** *Клиент может сообщить данные, но только сервер принимает решение.*

### 3.4 Жёстко закодированные секреты (ключи, пароли) в логике приложения.
Например:
```
DATABASE_PASSWORD="admin123"
API_KEY="secret-key"
```
Такие данные могут попасть:
* в GitHub;
* в резервные копии;
* в логи;
* в мобильное приложение.

Если злоумышленник получает исходный код, он получает доступ к инфраструктуре. Правильный подход: `Приложение - Secret Manager - Получение ключа во время работы`.

Для хранения секретов используются:
* HashiCorp Vault;
* облачные Secret Manager;
* защищённые переменные окружения.

### 3.5 Отсутствие механизмов защиты от автоматизированных атак. 
Например, капчи, лимитов запросов там, где они нужны. Проблема заключается в том, что при проектировании не был рассмотрен сценарий автоматизированной атаки.

Правильный дизайн должен включать:
* Rate Limiting;
* CAPTCHA;
* временные ограничения;
* мониторинг подозрительной активности;
* блокировка;
* дополнительная проверка.

### 3.6 Последствия
* Утечка конфиденциальных данных (персональные данные, платёжная информация).
* Несанкционированный доступ к функциям (повышение привилегий).
* Финансовые потери и штрафы за нарушение (GDPR, PCI DSS).
* Репутационный ущерб.
* Компрометация всей инфраструктуры через цепочку уязвимостей.

## 4. Как искать уязвимости Insecure Design
Поиск `Insecure Design` отличается от поиска классических ошибок вроде SQL Injection или XSS.

Автоматические сканеры плохо обнаруживают такие проблемы, потому что они находятся в бизнес-логике.

***Основной метод поиска — анализ поведения приложения.***

### 4.1. Анализ ролей пользователей
Необходимо определить:
* какие существуют роли (Guest, User, Manager, Administrator);
* какие действия доступны каждой роли;
* можно ли выполнить действия другой роли.

Проверяется:
* может ли обычный пользователь выполнить:
```
/admin/users
```
или:
```
DELETE /api/account/500
```
### 4.2. Проверка изменения параметров
Необходимо изменять:
* идентификаторы;
* цены;
* роли;
* статусы;
* флаги.

Было:
```
{
"price":1000
}
```
Проверка:
```
{
"price":1
}
```
Если приложение принимает изменение — возможно нарушение бизнес-логики.

### 4.3. Проверка последовательности действий
Необходимо проверять:
* можно ли пропустить шаг;
* можно ли выполнить действие раньше времени;
* можно ли повторить действие.

Обычный сценарий: `Регистрация - Подтверждение email - Создание аккаунта`.

## 5. Как предотвратить Insecure Design
### 5.1. Внедрить безопасное проектирование (`Secure by Design`)
* Сформулировать требования к безопасности на этапе сбора бизнес‑требований.
* Согласовать сценарии угроз с заинтересованными сторонами.
* Запланировать бюджет и ресурсы на безопасность на всех этапах (проектирование, разработка, тестирование, эксплуатация).

### 5.2. Моделировать угрозы (Threat Modeling)
* Использовать методики STRIDE или DREAD.
* Анализировать потоки данных и точки входа.
* Идентифицировать потенциальные уязвимости на этапе проектирования архитектуры.
* Интегрировать моделирование угроз в процесс разработки (например, в рефайнмент‑сессии).

### 5.3. Применять принципы безопасного проектирования
* Защита по умолчанию. Все функции и данные изначально закрыты; доступ даётся только явно.
* Минимальные привилегии. Пользователь/процесс имеет только те права, которые строго необходимы.
* Отказ по умолчанию. При ошибке система блокирует доступ, а не разрешает его.
* Разделение обязанностей. Критические операции требуют подтверждения нескольких ролей.

### 5.4. Использовать проверенные шаблоны и компоненты
* Готовые библиотеки безопасных компонентов.
* Стандарты проектирования (например, OWASP Application Security Verification Standard — `ASVS`).
* Проверенные фреймворки с встроенной защитой.

### 5.5. Внедрить «сдвиг влево» (Shift Left)
* Тестирование безопасности начинать как можно раньше (на этапе дизайна и написания кода).
* Проводить статический анализ кода (`SAST`) и анализ зависимостей (`SCA`) до сборки.
* Автоматизировать проверки безопасности в `CI/CD`‑пайплайне.

### 5.6. Проводить независимое тестирование
* Динамическое тестирование (DAST) и пентесты на ранних стадиях.
* Ревизия архитектуры безопасности сторонними экспертами.
* Анализ бизнес‑логики на наличие «дыр» (например, возможность обойти оплату).

### 5.7. Обучать команду
* Тренинги по безопасному проектированию для архитекторов и разработчиков.
* Обмен знаниями о типовых уязвимостях и методах защиты.
* Создание культуры безопасности в команде.

Уязвимости `insecure design` невозможно исправить патчем или обновлением фреймворка, а также от них нельзя защититься при помощи какого-либо `WAF` или `RASP`. Проблема в том, что с точки зрения безопасности архитектура и бизнес-логика веб-приложения изначально спроектированы неправильно, из чего следует, что необходимо привлекать специалистов по кибербезопасности как на этапе проектирования архитектуры, так и на этапе ревью кода приложения.
