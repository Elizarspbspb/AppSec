# Information Disclosure (Раскрытие информации)

## 1. Что это такое?
`Information Disclosure` — это уязвимость, при которой веб-приложение непреднамеренно раскрывает конфиденциальные данные пользователям, не имеющим к ним прав доступа.

* Бизнес-риски: Утечка персональных данных, коммерческой тайны или финансовых данных.
* Технические риски: Раскрытие инфраструктуры, версий ПО, путей на сервере или структуры БД. 

Сама по себе техническая утечка часто имеет низкий приоритет (Low/Informational), но она критически расширяет поверхность атаки, помогая злоумышленнику выстроить вектор для RCE, SQLi или обхода аутентификации.

Что обычно раскрывается через **SSRF**:
* Облачные метаданные (Cloud Metadata): данные конфигурации инстанса. Через SSRF злоумышленник может прочитать их и украсть IAM-токены доступа к облаку.
* Внутренняя инфраструктура.

Что обычно раскрывается через **IDOR** 
* Когда злоумышленник меняет ID в запросе (например, с id=101 на id=102) и видит данные чужого профиля

## 2. Методы поиска
* Фуззинг (Fuzzing): Отправка аномальных данных, спецсимволов и fuzz-строк в параметры для вызова нештатного поведения (например, Stack Trace).  Автоматизируется через `Burp Intruder` (анализ кодов ответа, длины и времени обработки).
* Инструменты `Burp Suite` (**Engagement Tools**): Автоматический поиск комментариев разработчиков, скрытого контента, резервных копий и файлов сканеров (`/robots.txt`, `/.git/`, `~backup.php`).
* SAST / Секреты в коде: Сканирование репозиториев (инструментами типа TruffleHog, Gitleaks) на предмет зашитых API-ключей, токенов и паролей.

## 3. Примеры уязвимостей с кодом

### Пример 1: Избыточный вывод ошибок в API
* `Vulnerable Code`: При возникновении ошибки приложение отдает клиенту весь traceback, раскрывая структуру кода и используемые библиотеки.
```py
@app.route('/user/<id>')def get_user(id):
    try:
        return db.fetch_user(id)
    except Exception as e:
        # ПЛОХО: Вывод сырого исключения клиенту
        return {"error": str(e), "traceback": traceback.format_exc()}, 500
```

* `Secure Code`: Перехват ошибок и логирование деталей на сервере, а клиенту — generic-ответ.
```py
@app.route('/user/<id>')def get_user(id):
    try:
        return db.fetch_user(id)
    except Exception as e:
        logger.error(f"DB Error: {e}") # Лог для AppSec/Dev
        return {"error": "Internal Server Error", "code": "ERR_500"}, 500 # Безопасный ответ
```
### Пример 2: Утечка чувствительных данных в JSON
* `Vulnerable Code`: Избыточное раскрытие (Over-fetching). Объект пользователя из БД отдается целиком, включая хэш пароля, который затем просто «прячется» на фронтенде (но доступен в трафике).
```js
app.get('/api/user/:id', async (req, res) => {
    const user = await db.findUser(req.params.id);
    // ПЛОХО: Отправка всего объекта, включая password_hash и api_key
    res.json(user); 
});
```
* `Secure Code`: Data Sanitization перед отправкой.
```js
app.get('/api/user/:id', async (req, res) => {
    const user = await db.findUser(req.params.id);
    // ХОРОШО: Явное выделение только публичных полей (Data Transfer Object)
    const safeUser = {
        id: user.id,
        username: user.username,
        email: user.email
    };
    res.json(safeUser);
});
```
## 4. Методы защиты
1. **Глобальный Error Handling**: Настройка веб-сервера (Nginx, Apache) и фреймворка так, чтобы отключать **debug-mode** в production-среде. Использование generic-страниц ошибок (404/500) без технических деталей.
2. **Безопасная конфигурация среды** (Hardening): Отключение небезопасных HTTP-методов (например, TRACE), ограничение доступа к служебным каталогам (.git, .env) на уровне веб-сервера. Исключение файлов бэкапов из веб-директории.
3. **CI/CD и SAST**: Внедрение статического анализа кода для автоматического удаления комментариев (TODO, FIXME) перед релизом и блокировка коммитов с хардкод-секретами (pre-commit hooks).
4. **Принцип минимальных привилегий данных**: Возврат только строго необходимых полей в API (Data Sanitization).
