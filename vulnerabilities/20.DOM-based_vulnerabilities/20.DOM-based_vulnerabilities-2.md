# DOM-based Vulnerabilities
`DOM-based уязвимости` — это класс уязвимостей клиентской стороны (Client-Side), возникающих, когда JavaScript на странице небезопасно обрабатывает контролируемые злоумышленником данные в браузере пользователя.

## 1. Что это такое? (Core Concept)
В основе лежит концепция Загрязненного потока данных (Taint Analysis):
* **Источник** (Source): Свойство JS, через которое злоумышленник внедряет данные (например, location.search, `location.hash`, document.referrer, document.cookie).
* **Приемник** (Sink): Опасная функция или DOM-объект, выполняющий переданную строку (например, `eval()`, document.write(), innerHTML, window.location).

> Главное правило: Уязвимость возникает, когда данные **из Source без валидации и санитизации попадают напрямую в Sink**.

## 2. Методы поиска (Taint Tracking & Detection)
1. **Статический анализ** (SAST): Анализ исходного кода (греппинг регулярными выражениями или AST-парсинг) на предмет связей source -> sink. Инструменты: `Semgrep`, `Burp Suite` (`Static Analysis`).
2. **Динамический анализ** (DAST/IAST): Отслеживание потока данных в рантайме браузера. Внедрение уникальных строк (маркеров) в параметры URL/хеша и проверка их появления в контексте выполнения скриптов.
3. **Code Review веб-сообщений**: Проверка обработчиков window.addEventListener('message', ...) на наличие строгой валидации происхождения (e.origin).

## 3. Топ-3 уязвимости: Примеры кода (JS / Python)### А. DOM Open Redirect (Открытое перенаправление)
* Слабость: Данные из URL управляют логикой перенаправления.
* Уязвимый JS:
```js
// Source: location.hash | Sink: window.location
let goto = location.hash.slice(1); 
if (goto.startsWith('https:')) { window.location = goto; } // Оборот: https:evil.com
```
* Безопасный JS (Белый список):
```js
const allowed = ["/home", "/profile"];
if (allowed.includes(goto)) { window.location = goto; }
```

### Б. DOM XSS / JS Injection via Web Messages
* Слабость: Отсутствие или некорректная валидация `origin` при передаче данных между окнами.
* Уязвимый JS:
```js
window.addEventListener('message', function(e) {
    if (e.origin.indexOf('normal-website.com') > -1) { eval(e.data); } 
}); // Обход через: http://evil.net
```
* Безопасный JS:
```js
window.addEventListener('message', function(e) {
    if (e.origin === 'https://normal-website.com') { // Строгое соответствие
        // Вместо eval() используем безопасный парсинг данных
        let data = JSON.parse(e.data); 
    }
});
```

### В. Client-Side SQL Injection
Сами SQL-инъекции выполняются на стороне БД (на бэкенде), но DOM-код может формировать строку запроса. Ниже классический пример безопасной обработки данных на бэкенде (Python), куда пришел загрязненный параметр из DOM.

* Уязвимый Python (Бэкенд):
```py
# Прямая конкатенация строк данных из DOM-запроса
query = f"SELECT * FROM users WHERE name = '{user_input}'"
cursor.execute(query)
```
* Безопасный Python (Параметризованный запрос):
```py
# Использование плейсхолдеров (Подготовленные выражения)
query = "SELECT * FROM users WHERE name = %s"
cursor.execute(query, (user_input,))
```

## 4. Методы защиты (Remediation)
* **Контекстное кодирование и Санитизация**: Использование проверенных библиотек (например, DOMPurify) для очистки HTML-элементов перед вставкой в innerHTML.
* Использование безопасных Sink API: **Замена опасных методов на их безопасные аналоги**:
    * Вместо `innerHTML` -> `textContent` или innerText (не выполняют скрипты).
    * Вместо `eval()` -> `JSON.parse()`.
* **Строгая валидация Origin**: При работе с postMessage всегда проверять `e.origin` **через строгое равенство (===)**, а не *indexOf* или *endsWith*. При отправке не использовать `*`, указывать конкретный целевой домен.
* **Защита от DOM Clobbering**: Избегать глобальных переменных и логического ИЛИ (|| {}) при инициализации объектов конфигурации скриптов. Проверять типы объектов (например, через instanceof NamedNodeMap).
* **CSP** (Content Security Policy): Внедрение заголовков политики безопасности (например, ограничение script-src, запрет unsafe-eval), как эшелонированная оборона (Defense in Depth).

## Вопросы
1. **«В чем принципиальное отличие DOM XSS от Reflected (отраженной) XSS?»**:
* При `Reflected XSS` вредоносный скрипт прилетает в ответе от сервера (сервер сам вставляет его в HTML-код). 
* При `DOM XSS` сервер вообще может быть не в курсе: весь цикл уязвимости (получение данных из URL и вставка в опасную функцию) **происходит исключительно в браузере пользователя силами клиентского JavaScript**.

2. **«Разработчик написал проверку для postMessage: if (e.origin.indexOf('my-site.com') > -1). Безопасно ли это и как обойти?»**
* Это небезопасно. Метод `indexOf` просто ищет подстроку в любом месте. Я могу зарегистрировать домен my-site.com.evil.ru или evil-my-site.com, и проверка пропустит мое вредоносное сообщение. Защита — только строгое сравнение через `===`.

3. `«Как защитить приложение, если разработчику нужно вставлять HTML-код, приходящий от пользователя, на страницу?»`
* Использовать проверенную библиотеку санитизации, например **DOMPurify**. Она вычистит все опасные теги (вроде `<script>`) и атрибуты (вроде `onerror`, `onclick`), оставив только безопасный HTML. 

4. **«Поможет ли CSP (Content Security Policy) полностью предотвратить DOM-уязвимости?»**
* CSP — частично, директива `unsafe-eval` запретит работу `eval()`, а белый список доменов для скриптов не даст загрузить чужой JS. Но `CSP` не предотвратит уязвимости вроде `DOM Open Redirect` (открытое перенаправление) или манипуляции с логикой страницы.
