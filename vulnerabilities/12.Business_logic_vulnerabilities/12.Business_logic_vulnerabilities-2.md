# Уязвимости бизнес-логики (Business logic vulnerabilities)

## 1. Что это такое
Уязвимости бизнес-логики — это архитектурные и логические ошибки в дизайне или реализации приложения, позволяющие злоумышленнику использовать легитимную функциональность системы для достижения вредоносных целей.

**Главная причина**: Ошибочные предположения (assumptions) разработчиков о поведении пользователей и вера в то, что система будет использоваться только «как задумано».

Их **практически невозможно обнаружить автоматическими сканерами** (DAST/SAST), так как код формально корректен, синтаксических ошибок (типа SQLi/XSS) нет, нарушается именно логика процессов. Находятся только ручным тестированием (бизнес-логика уникальна для каждого домена).

## 2. Методы поиска
Тестирование ведется `с помощью перехватывающего прокси` (например, Burp Suite Proxy & Repeater) с целью нарушить ожидания разработчика:
* **Тестирование параметров**: `Удаление обязательных параметров запроса` по одному, отправка пустых значений параметров.
* **Нарушение последовательности** (Workflow Bypass): `Пропуск промежуточных шагов` в многоэтапных процессах (оплата, корзина, 2FA), изменение порядка шагов или их повторение.
* **Нетрадиционный ввод** (Boundary & Negative values): `Передача отрицательных чисел`, критически больших/маленьких значений, аномально длинных строк, неожиданных типов данных (Type Juggling).
* **Анализ доменной логики**: `Изучение правил` скидок, бонусов, переходов состояний (State Machine) с целью найти несоответствие логики предметной области.

## 3. Примеры уязвимостей с кодом
```Python
# Сервер слепо доверяет цене, пришедшей из формы от клиента: price = request.form["price"]  
# Злоумышленник через Burp меняет в HTTP-запросе price=1000 на price=1
charge_user(price) # Товар куплен за 1 рубль вместо 1000
```
* Как исправить: Брать эталонную цену только из защищенной БД на стороне сервера на основе item_id.

```JS
// Неспособность обрабатывать отрицательные значения
let transferAmount = Number(req.body.amount); // Пришло значение -1000
let currentBalance = user.getBalance();       // Баланс: 500
if (transferAmount <= currentBalance) {       // Условие выполнится: -1000 <= 500 это True!
    user.setBalance(currentBalance - transferAmount); // 500 - (-1000) = 1500 (Баланс увеличился!)
    recipient.decreaseBalance(transferAmount);
}
```
* Как исправить: Добавить строгую валидацию входного диапазона: `if (transferAmount <= 0) return error;`.

```Python
# Нарушение последовательности (Обход 2FA на Python)
@app.route("/verify-2fa")
def verify_2fa():
    # Критическая ошибка: Проверяется только код, но нет проверки, был ли вообще шаг 1 (логин/пароль)
    if request.args.get("code") == user_2fa_code:
        session["logged_in"] = True  # Злоумышленник переходит сразу сюда, минуя ввод пароля
        return "Welcome!"
```
* Как исправить: Проверять состояние сессии на каждом шаге: `if not session.get("user_authenticated_step1"): return 403`.

## 4. Методы защиты
* Принцип **нулевого доверия к клиенту** (Zero Trust to Client): Любые данные от клиента (параметры, cookies, заголовки, цены) — враждебны и `должны валидироваться на сервере`.
* **Валидация бизнес-границ** (Input & State Validation): Проверка не только типов данных, но и их логической допустимости (целостности, знака, диапазонов) перед выполнением операции.
* **Проверка состояний** (State Machine Enforcement): Каждый шаг многоэтапного процесса должен проверять, завершены ли предыдущие шаги в легитимном порядке (не доверять «флагам» из сессии без контекста времени).
* **Документирование инвариантов бизнес-логики**: Четкое описание в архитектурных схемах (Data Flow Diagrams) всех предположений и взаимосвязей между компонентами. Код должен быть максимально прозрачным.
