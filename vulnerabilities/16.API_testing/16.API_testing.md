# 16. Тестирование API
`API` (Application Programming Interface) позволяют программам и приложениям обмениваться данными. Тестирование API важно, поскольку уязвимости в API могут нарушить **конфиденциальность**, **целостность** и **доступность** веб-сайта.

Все динамические веб-сайты используют `API`, поэтому классические веб-уязвимости, например SQL-инъекции, также могут рассматриваться как часть тестирования `API`. 

Чтобы показать связь между тестированием `API` и обычным тестированием веб-приложений, ниже приведено соответствие между темами Академии веб-безопасности и **OWASP API Security Top 10 (2023)**.

## 1. Разведка API
Чтобы начать тестирование API, сначала нужно собрать как можно больше информации о нём. Это поможет определить его поверхность атаки.

Для начала необходимо найти **конечные точки (endpoints) API**. Это адреса, на которые API получает запросы для работы с определённым ресурсом. Например:
```http
GET /api/books HTTP/1.1
Host: example.com
```
В этом случае конечная точка API — `/api/books`. Запрос обращается к API, чтобы получить список книг из библиотеки. Другой конечной точкой может быть, например, `/api/books/mystery`, которая возвращает список детективных книг.

После определения конечных точек нужно выяснить, **как с ними взаимодействовать**. Это позволяет создавать корректные HTTP-запросы для тестирования API. Например, нужно узнать:
* Какие **входные данные** обрабатывает API, включая обязательные и необязательные параметры.
* Какие **типы запросов** принимает API, включая поддерживаемые методы HTTP и форматы данных.
* Какие **существуют ограничения скорости** запросов и механизмы аутентификации.

## 2. Документация API
`API` обычно документируют, чтобы разработчики понимали, как с ним работать и интегрировать его в свои приложения.

Документация может быть **читаемой человеком** или **машиночитаемой**. Читаемая человеком документация помогает разработчикам понять работу `API` и может содержать объяснения, примеры и сценарии использования. Машиночитаемая документация предназначена для программ, которые автоматически выполняют такие задачи, как интеграция и проверка `API`. Она записывается в структурированных форматах, например JSON или XML.

Документация `API` часто доступна публично, особенно если API предназначен для внешних разработчиков. Поэтому при разведке `API` всегда стоит сначала проверить его документацию.

### 2.1 Поиск документации API
Даже если документация `API` не опубликована открыто, её иногда можно найти через приложения, которые используют этот `API`.

Для этого можно использовать **Burp Scanner** для сканирования API или вручную просматривать приложение через **Burp Browser**. Ищите конечные точки, которые могут вести к документации `API`, например:
* `/api`
* `/swagger/index.html`
* `/openapi.json`

Если вы нашли конечную точку ресурса, обязательно проверьте также **базовые пути**. Например, если найдена конечная точка `/api/swagger/v1/users/123`, проверьте:
* `/api/swagger/v1`
* `/api/swagger`
* `/api`

Если нашли `openapi.json` / `swagger.json` или страницу `Swagger UI` — это явный признак, что API документирован в `OpenAPI`/`Swagger`.

Также для поиска документации можно использовать список распространённых путей в **Intruder**.

### 2.2 Использование машиночитаемой документации
Для анализа найденной машиночитаемой документации API можно использовать автоматизированные инструменты.

**Burp Scanner** позволяет сканировать и проверять документацию `OpenAPI`, а также другие документы в форматах JSON и YAML. Документацию `OpenAPI` также можно разобрать с помощью BApp [`OpenAPI Parser`](https://portswigger.net/bappstore/6bf7574b632847faaaa4eb5e42f1757c).

Для тестирования документированных конечных точек можно использовать специализированные инструменты, например [`Postman`](https://www.postman.com/) или [`SoapUI`](https://www.soapui.org/).

### 2.3 Расширение **OpenAPI Parser** упрощает тестирование веб-сервисов, использующих OpenAPI.
Основные возможности:
* Загружает OpenAPI-спецификации из файла или URL.
* Поддерживает OpenAPI 2.0, 3.0 и 3.1.
* Позволяет просматривать и редактировать запросы перед отправкой.
* Отправляет запросы в основные инструменты Burp: **Repeater, Intruder, Scanner, Organizer, Comparer** и другие.
* Позволяет автоматически изменять значения параметров перед отправкой запросов.
* Поддерживает выделение интересующих API-запросов.
* Позволяет экспортировать выбранные запросы в **CSV**.
* Поддерживает форматы **JSON и YAML**.

### 2.4 Postman
**Postman** — инструмент для тестирования API. Он позволяет отправлять HTTP-запросы и проверять ответы API.

Основные возможности:
* Отправка запросов к API и просмотр ответов.
* Работа с **GET, POST, PUT, DELETE** и другими HTTP-методами.
* Импорт API из **OpenAPI, Swagger, cURL** и других форматов.
* Объединение запросов в **коллекции** для удобного тестирования.
* Использование переменных и окружений для разных настроек API.
* Проверка ответов с помощью тестов.
* Экспорт коллекций и их использование в автоматизированном тестировании.

### 2.5 SoapUI
**SoapUI** — инструмент для тестирования **REST и SOAP API**. Он позволяет отправлять запросы к API и проверять полученные ответы.

Основные возможности:
* Создание и отправка **REST-запросов**.
* Поддержка **SOAP/WSDL**.
* Импорт API-описаний, включая **WADL и Swagger**; расширенная версия ReadyAPI также поддерживает OpenAPI и RAML.
* Просмотр и редактирование запросов, заголовков и данных **JSON/XML**.
* Создание тестовых сценариев и проверка ответов с помощью **assertions**.
* Создание **Mock-сервисов** для имитации работы API.
* Поддержка последовательного выполнения нескольких запросов в одном тесте.

| Инструмент | Когда использовать |
| --- | --- |
| **OpenAPI Parser (Burp)** | У тебя **есть OpenAPI/Swagger-документация** → быстро превратить её в запросы Burp и дальше тестировать |
| **Postman** | Нужно **вручную отправлять API-запросы**, изучать API, собирать коллекцию запросов и писать простые тесты |
| **SoapUI** | Нужно тестировать **SOAP или сложные REST-сценарии**, особенно с XML/WSDL и последовательностью запросов |

## 3. Определение конечных точек API
Много информации можно получить, изучая приложения, которые используют API. Это стоит делать даже при наличии документации, поскольку она может быть неточной или устаревшей.

Для этого можно использовать **Burp Scanner**, а затем вручную исследовать интересующие участки с помощью **Burp Browser**.

При просмотре приложения ищите в URL признаки конечных точек API, например `/api/`.

Также обращайте внимание на **JavaScript-файлы**. В них могут находиться ссылки на API, которые не вызываются напрямую через браузер. `Burp Scanner` автоматически находит некоторые такие конечные точки, а для более полного поиска можно использовать `BApp` **JS Link Finder**. JavaScript-файлы также можно просматривать вручную в Burp.

`Burp Extension` для пассивного сканирования файлов JavaScript для конечных ссылок. - Экспорт результатов текстового файла - Исключить конкретные файлы 'js', например jquery, google-analytics

### 3.1 Взаимодействие с конечными точками API
После определения конечных точек взаимодействуйте с ними с помощью **Burp Repeater** и **Burp Intruder**. Это позволяет изучить поведение API и найти дополнительные точки для тестирования. Например, можно проверить реакцию API на изменение HTTP-метода или типа данных.

При работе с API внимательно изучайте **сообщения об ошибках и другие ответы**. Иногда они содержат информацию, которая помогает сформировать корректный HTTP-запрос.

### 3.2 Определение поддерживаемых методов HTTP
Метод HTTP определяет действие, которое нужно выполнить с ресурсом. Например:
* `GET` — получает данные ресурса.
* `PATCH` — частично изменяет ресурс.
* `OPTIONS` — показывает, какие методы HTTP поддерживает ресурс.

Одна конечная точка `API` может поддерживать несколько методов HTTP. Поэтому при исследовании **важно проверить все возможные методы** (GET, POST, t.d.). Это может открыть дополнительную функциональность и расширить поверхность атаки.

Например, конечная точка `/api/tasks` может поддерживать:
* `GET /api/tasks` — возвращает список задач.
* `POST /api/tasks` — создаёт новую задачу.
* `DELETE /api/tasks/1` — удаляет задачу.

Для автоматической проверки разных методов можно использовать встроенный список **HTTP verbs** в `Burp Intruder`.

> **Примечание** - При проверке разных методов HTTP используйте объекты с низким приоритетом. Это помогает избежать случайных последствий, например изменения важных данных или создания большого количества записей.

### 3.3 Определение поддерживаемых типов контента
Конечные точки API часто ожидают данные в определённом формате. Поэтому их поведение может меняться в зависимости от типа содержимого запроса. Изменение типа контента может позволить:
* Вызвать ошибки, раскрывающие полезную информацию.
* Обойти недостаточно надёжные механизмы защиты.
* Найти уязвимости в обработке данных. Например, API может быть защищён при обработке JSON, но уязвим к инъекциям при работе с XML.

Чтобы изменить тип контента, измените заголовок `Content-Type` и соответствующим образом измените тело запроса. Для автоматического преобразования данных между XML и JSON можно использовать BApp **Content Type Converter**.

Расширение **Content Type Converter** преобразует данные между распространёнными форматами:
* JSON → XML
* XML → JSON
* Параметры тела → JSON/XML

Это помогает находить уязвимости, которые проявляются только при изменении формата запроса. Например, преобразовав `JSON` в XML, можно проверить уязвимости вроде **XXE**, которые не проявляются при работе с `JSON`. Также это может помочь обойти фильтры, рассчитанные на определённый формат данных.

**Требуется Java 8 или выше.**

### 3.4 Использование Intruder для поиска скрытых конечных точек
После обнаружения нескольких конечных точек API можно использовать **Intruder** для поиска скрытых.

Например, найдена конечная точка:
```http
PUT /api/user/update
```

Чтобы найти другие конечные точки с похожей структурой, в **Burp Intruder** можно заменить часть `/update` списком распространённых функций, например `delete` и `add`.

> Для поиска используйте **словари с распространёнными названиями API-функций и терминами из предметной области приложения**. Также добавляйте слова, которые подходят конкретно для исследуемого приложения.

## 4.  Поиск скрытых параметров
При разведке API можно найти **недокументированные параметры**, которые поддерживает API. Их можно использовать для изменения поведения приложения. Burp предоставляет несколько инструментов для поиска таких параметров:

* **Burp Intruder** — автоматически проверяет возможные имена параметров с помощью словаря. Можно заменять существующие параметры или добавлять новые. Также стоит использовать имена, связанные с конкретным приложением.
* **Param Miner** — автоматически перебирает до 65 536 имён параметров за запрос и подбирает имена, связанные с приложением.
* **Content Discovery** — помогает находить скрытый контент, который не связан с видимыми страницами приложения, включая параметры.

### 4.1 Param Miner
**Param Miner** — расширение Burp для поиска скрытых и не связанных с интерфейсом параметров. Особенно полезно при поиске уязвимостей **отравления веб-кэша**.

Расширение перебирает до **65 536 имён параметров на один запрос**, используя встроенный словарь и слова, найденные в трафике приложения.

Нажмите правой кнопкой на запрос в Burp и выберите **«Guess (cookies|headers|params)»**. В `Burp Suite Pro` найденные параметры отображаются как проблемы сканера. В других версиях их можно посмотреть в **Extensions → Installed → Param Miner → Output**.

`Param Miner` также позволяет одновременно проверять несколько запросов и автоматически анализировать весь трафик из области тестирования.

### 4.2 Content Discovery
**Content Discovery** помогает находить скрытый контент и функции, которые не видны в приложении и не были найдены Burp Scanner.

Чтобы запустить:
1. Выберите HTTP-запрос в Burp.
2. Нажмите правой кнопкой → **Engagement tools → Discover content**.
3. Нажмите **Session is not running**.

Burp ищет контент с помощью:
* перебора имён;
* веб-сканирования;
* анализа соглашений об именах приложения.

#### Вкладка Control
Показывает состояние поиска: количество запросов, переданные данные, сетевые ошибки и задачи в очереди.

Поиск выполняется **рекурсивно**: найденный каталог приводит к поиску файлов и подкаталогов, а найденный файл — к проверке его вариантов и расширений.

#### Вкладка Config
Здесь настраивается поиск:
* **Target** — начальный каталог и тип объектов для поиска: файлы, каталоги или оба варианта.
* **Filenames** — источники имён файлов и каталогов: встроенные или пользовательские списки, имена из сайта и автоматически предполагаемые имена.
* **File extensions** — расширения, которые Burp проверяет для найденных файлов.
* **Discovery engine** — регистр имён, количество потоков, добавление найденного контента на карту сайта и веб-сканирование найденного контента.

#### Вкладка Site map
Содержит отдельную карту найденного контента в пределах заданной области. Найденные элементы можно автоматически добавлять на основную **Site map** Burp.

### 4.3 Уязвимости массового присваивания
**Массовое присваивание** (mass assignment) возникает, когда фреймворк автоматически связывает параметры запроса с полями внутреннего объекта. В результате приложение может поддерживать скрытые параметры, которые разработчик не планировал использовать.

#### Выявление скрытых параметров
Скрытые параметры можно обнаружить, изучая объекты, которые возвращает API.

Например, запрос `PATCH /api/users/` позволяет изменить имя пользователя и email:
```json
{
    "username": "wiener",
    "email": "wiener@example.com"
}
```

При этом запрос `GET /api/users/123` возвращает:
```json
{
    "id": 123,
    "name": "John Doe",
    "email": "john@example.com",
    "isAdmin": "false"
}
```

Это может означать, что параметры `id` и `isAdmin` также связаны с внутренним объектом пользователя и могут быть доступны для изменения вместе с `username` и `email`.

### 4.4 Тестирование уязвимостей массового присваивания
Чтобы проверить, можно ли изменить параметр `isAdmin`, добавьте его в `PATCH`-запрос:
```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": false
}
```

Затем отправьте запрос с недопустимым значением:
```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": "foo"
}
```
Если приложение по-разному реагирует на эти запросы, это может означать, что параметр `isAdmin` влияет на обработку запроса и потенциально может быть изменён пользователем.

После этого отправьте запрос с `isAdmin: true`:
```json
{
    "username": "wiener",
    "email": "wiener@example.com",
    "isAdmin": true
}
```
Если параметр `isAdmin` связан с объектом пользователя и не проходит достаточную проверку, пользователь `wiener` может получить административные права. Чтобы проверить это, войдите как `wiener` и попробуйте получить доступ к функциям администратора.

## 5. Предотвращение уязвимостей в API
При разработке API безопасность нужно учитывать с самого начала. В частности:

* Защищайте документацию, если API не должен быть общедоступным.
* Поддерживайте документацию в актуальном состоянии, чтобы тестировщики видели всю поверхность атаки.
* Разрешайте только необходимые HTTP-методы.
* Проверяйте ожидаемый тип контента каждого запроса и ответа.
* Используйте общие сообщения об ошибках, не раскрывающие полезную для атакующего информацию.
* Применяйте защиту ко всем версиям API, а не только к текущей.
