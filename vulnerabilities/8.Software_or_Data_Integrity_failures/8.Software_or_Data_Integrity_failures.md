# 8. Нарушения целостности программного обеспечения и данных (Software or data integrity failures)
Нарушения целостности программного обеспечения и данных возникают, когда приложение, процесс сборки или инфраструктура не обеспечивают проверку и защиту от использования изменённого, подменённого или недоверенного кода и данных.

Проблема заключается в том, что система может выполнить код или обработать данные, источник и содержимое которых не были проверены. Например, приложение может подключать сторонние библиотеки, плагины или модули из непроверенных репозиториев, CDN или других внешних источников. Если такой компонент будет скомпрометирован или заменён злоумышленником, уязвимость может привести к выполнению вредоносного кода внутри приложения.

К этой категории также относятся нарушения безопасности процесса разработки и доставки ПО: 
* отсутствие проверки цифровых подписей, 
* контроля целостности файлов, 
* безопасного управления зависимостями, 
* защиты CI/CD-процессов. 

В результате атакующий может внедрить изменения в исходный код, зависимости, конфигурации или готовые артефакты сборки.

С точки зрения AppSec основная задача — обеспечить доверенную цепочку поставки программного обеспечения: 
* контролировать источники зависимостей, 
* проверять их целостность, 
* отслеживать изменения и не допускать попадания неподтверждённого кода в рабочую среду.

## 8.1 Разница между SSCF и SDIF
В главе о **software supply chain failures** мы рассматривали атаки на уязвимые компоненты цепочки поставки ПО: 
* сторонние библиотеки, 
* фреймворки, 
* инструменты разработки, 
* CI/CD-процессы поставщиков программного обеспечения.

Главная цель злоумышленника при атаке на **software supply chain failures** — скомпрометировать доверенный источник и использовать его для распространения вредоносного кода среди клиентов. В таком случае поставщик становится «доверенным каналом», через который вредоносное ПО попадает в организации, поскольку получаемые от него компоненты или обновления изначально считаются безопасными.

В случае **software or data integrity failures** проблема связана не столько с компрометацией поставщика, сколько с `отсутствием механизмов проверки целостности и подлинности` используемого кода или данных.

Например, уязвимость может возникнуть из-за неправильно настроенного CI/CD-процесса, который загружает зависимости, исходный код или артефакты сборки из внешних источников без дополнительной проверки. 

Если система не проверяет: 
* цифровые подписи, 
* хэши,
* другие признаки подлинности, 

злоумышленник может заменить легитимный компонент на изменённую версию.

Другой распространённый пример — **механизм автоматического обновления программного обеспечения**. Если приложение получает обновления без проверки их целостности и источника, атакующий может подменить пакет обновления и распространить вредоносный код среди всех пользователей этого приложения.

К этой категории также относятся проблемы с обработкой данных, например `небезопасная десериализация`. При таком сценарии приложение принимает сериализованные объекты из недоверенного источника и восстанавливает их без достаточной проверки. 

Если атакующий может изменить содержимое сериализованных данных, это приводит к нарушению целостности информации и потенциально может привести к выполнению произвольного кода.

С точки зрения AppSec основная задача защиты от подобных атак — обеспечить доверие к каждому этапу обработки ПО и данных: 
* проверять происхождение компонентов,
* контролировать целостность файлов и обновлений,
* защищать CI/CD-процессы, 
* безопасно обрабатывать входящие данные.

##  8.2 Как защититься от software or data integrity failures?
Для защиты от нарушений целостности ПО и данных необходимо проверять подлинность и неизменность используемых компонентов. Для этого следует применять:
* цифровые подписи или хэши SHA-256, 
* контрольные суммы,
* другие механизмы проверки целостности программного обеспечения,
* устанавливать библиотеки и зависимости только из доверенных источников.

Устанавливайте библиотеки и зависимости только из доверенных репозиториев. Для контроля сторонних компонентов используйте инструменты `Software Composition Analysis (SCA)`, например **Snyk Open Source**, **GitHub Dependabot** или **OWASP Dependency-Check**. Они позволяют обнаруживать известные уязвимости в зависимостях и контролировать изменения используемых библиотек.

### 8.2.1 Snyk Open Source
`Snyk Open Source` — инструмент `SCA` (Software Composition Analysis) для поиска уязвимостей в сторонних зависимостях приложения. Он анализирует используемые библиотеки, сопоставляет их с базами известных уязвимостей (CVE) и предлагает безопасные версии компонентов.

Пример использования:

Разработчик добавил в проект библиотеку с известной уязвимостью. `Snyk` анализирует файл зависимостей (package.json, requirements.txt, pom.xml) и показывает:
```
Package: log4j-core
Version: 2.14.1
Vulnerability: CVE-2021-44228
Severity: Critical
Fix: Upgrade to 2.17.1
```
Инструмент можно подключить к `CI/CD`, чтобы блокировать сборку при обнаружении критических уязвимостей.

### 8.2.2 GitHub Dependabot
`GitHub Dependabot` — встроенный инструмент GitHub для автоматического поиска уязвимостей в зависимостях и создания `Pull Request` с обновлением безопасных версий библиотек.

Проект использует библиотеку:
```
requests==2.25.0
```
`Dependabot` обнаруживает, что версия содержит известную уязвимость, и автоматически создаёт `Pull Request`:
```
Update requests from 2.25.0 to 2.31.0
Fixes: CVE-2023-32681
```
Разработчик проверяет изменения и принимает обновление.

### 8.2.3 OWASP Dependency-Check
`OWASP Dependency-Check` — бесплатный SCA-инструмент с открытым исходным кодом для поиска известных уязвимостей в сторонних библиотеках.

Он анализирует зависимости проекта и проверяет их по базе уязвимостей `NVD` (National Vulnerability Database).

Запуск анализа Java-проекта:
```
dependency-check.sh \
--project "MyApplication" \
--scan ./target
```
После анализа инструмент формирует отчёт:
```
commons-fileupload-1.3.1.jar

CVE-2016-1000031
Severity: High
Recommendation:
Upgrade to version 1.3.3 or higher
```

## 8.3 `SBOM` (Software Bill of Materials)
Создавайте и поддерживайте `SBOM` (Software Bill of Materials) — список всех компонентов, входящих в состав приложения. Форматы `SBOM`, такие как **CycloneDX** и **SPDX**, помогают отслеживать используемые зависимости и быстро реагировать на компрометацию компонентов.

### 8.3.1 CycloneDX
`CycloneDX` — стандарт формата `SBOM` (Software Bill of Materials), который описывает состав программного обеспечения: 
* библиотеки, 
* версии, 
* зависимости и информацию о поставщиках компонентов.

При сборке приложения создаётся файл:
```
bom.json
```
Содержащий:
```
{
  "component": {
    "name": "openssl",
    "version": "3.0.2"
  }
}
```
Если позже обнаруживается уязвимость в `OpenSSL`, можно быстро определить, какие приложения используют этот компонент.

### 8.3.2 SPDX
`SPDX` — ещё один стандарт `SBOM`, разработанный Linux Foundation. Он используется для описания компонентов ПО, лицензий и информации о происхождении кода.

Пример использования:

При выпуске программного продукта создаётся файл:
```
sbom.spdx
```
В котором указано:
```
PackageName: openssl
PackageVersion: 3.0.2
License: Apache-2.0
Supplier: OpenSSL Foundation
```
Это помогает контролировать сторонние компоненты и выполнять требования безопасности и лицензирования.

## 8.4 Инструменты проверки контейнеров
Для контейнеров используйте проверку образов перед развертыванием. Например, инструменты **Trivy** и **Anchore Grype** позволяют сканировать контейнерные образы, зависимости и конфигурации на наличие известных проблем.

### 8.4.1 Trivy
`Trivy` — инструмент для поиска уязвимостей в контейнерных образах, файловых системах, зависимостях и конфигурациях инфраструктуры.

Проверка Docker-образа:
```
trivy image nginx:latest
```
Результат:
```
nginx:latest

openssl
CVE-2024-XXXX
Severity: HIGH
Installed Version: 3.0.2
Fixed Version: 3.0.8
```
`Trivy` часто используется в `CI/CD` перед публикацией контейнера.

### 8.4.2 Anchore Grype
`Grype` — инструмент `SCA` для поиска уязвимостей в контейнерных образах и файловых системах. Он анализирует пакеты внутри образа и сопоставляет их с базой известных уязвимостей.

Проверка образа:
```
grype myapp:v1.0
```
Результат:
```
Package: libssl
Version: 1.1.1
Vulnerability: CVE-2023-5678
Severity: Medium
Fix: Upgrade package
```
`Grype` часто используется вместе с инструментом создания `SBOM Syft`: сначала создаётся описание состава образа, затем `Grype` выполняет поиск уязвимостей.

## 8.5 CI/CD
Защищайте процессы `CI/CD`: 
* ограничивайте источники загрузки зависимостей,
* фиксируйте версии пакетов через `lock-файлы` (package-lock.json, poetry.lock, requirements.txt с версиями),
* проверяйте целостность артефактов сборки и не допускайте автоматического использования непроверенного кода.

Важно контролировать всю цепочку поставки ПО: проверять используемые зависимости, репозитории, обновления и сторонние компоненты. Нельзя полностью доверять внешним библиотекам или фреймворкам без анализа их содержимого и происхождения.

Без контроля источников кода и данных невозможно построить безопасный процесс разработки и обеспечить защиту приложения от внедрения изменённых или вредоносных компонентов.

## 8.6 Практический процесс в AppSec
Типичный `pipeline` защиты может выглядеть так:
1. Разработчик добавляет зависимость
```
npm install package-name
```
2. `SCA`-инструмент проверяет библиотеку
**Snyk** / **Dependabot** / **OWASP Dependency-Check**
3. Создаётся `SBOM`
**CycloneDX** / **SPDX**
4. Перед сборкой контейнера выполняется сканирование
**Trivy** / **Grype**
5. `CI/CD` блокирует публикацию, если обнаружены критические уязвимости.

Так обеспечивается контроль целостности и безопасности компонентов на всех этапах жизненного цикла приложения.

## 8.7 Атаки на Software or data integrity failures
Атаки на нарушение целостности ПО и данных направлены на изменение доверенного кода, компонентов или информации таким образом, чтобы приложение использовало подменённые данные или выполняло изменённый код.

Основная идея таких атак — **заставить систему принять изменённый компонент как легитимный**. Для этого злоумышленник использует отсутствие проверки источника, цифровой подписи, контрольных сумм или механизмов безопасного обновления.

### 8.7.1. Подмена зависимостей (Dependency Confusion)
**Тип атаки:** атака на управление зависимостями.

При использовании внутренних библиотек разработчики могут случайно настроить систему так, чтобы она загружала пакет с публичного репозитория вместо внутреннего. Злоумышленник публикует пакет с таким же названием в публичном репозитории, но с вредоносным содержимым.

**Пример атаки:** Компания использует внутреннюю библиотеку:
```
company-auth-utils
```
`CI/CD` настроен искать зависимости одновременно во внутреннем и публичном репозитории. Атакующий публикует в публичном репозитории пакет:
```
company-auth-utils v1.1.0
```
с вредоносным кодом.

При следующей сборке система загружает пакет атакующего и выполняет его код внутри `CI/CD`.

**Защита:**
* использовать приватные репозитории для внутренних пакетов;
* фиксировать источники зависимостей;
* проверять подписи и хэши пакетов;
* применять SCA-инструменты.

### 8.7.2. Атаки на цепочку поставок ПО (Software Supply Chain Attacks)
**Тип атаки:** компрометация доверенного поставщика.

В этом случае атакующий не атакует конечное приложение напрямую, а внедряет вредоносный код в компонент, которому доверяет организация.

**Пример атаки:** Злоумышленник получает доступ к инфраструктуре разработчика популярной библиотеки и изменяет исходный код. После выпуска новой версии:
```
library-name v2.0
```
пользователи автоматически обновляют библиотеку и получают версию с вредоносным кодом.

**Примеры подобных атак:**
* компрометация обновлений ПО;
* внедрение вредоносного кода в библиотеки;
* атаки на CI/CD поставщика.

**Защита:**
* проверка цифровых подписей обновлений;
* контроль версий зависимостей;
* анализ компонентов через SCA;
* использование SBOM.

### 8.7.3. Подмена обновлений приложения (Insecure Update Mechanism)
**Тип атаки:** атака на механизм автоматического обновления.

Многие приложения автоматически скачивают и устанавливают обновления. Если приложение не проверяет подлинность обновления, атакующий может заменить пакет обновления на вредоносный.

**Пример атаки:** Приложение выполняет запрос:
```
https://update.example.com/latest.zip
```
и автоматически устанавливает полученный файл.

Атакующий получает возможность изменить файл:
```
latest.zip
```
и заменяет его на пакет с вредоносным кодом.

После обновления все пользователи получают скомпрометированную версию приложения.

**Защита:**
* использовать HTTPS;
* проверять цифровые подписи обновлений;
* проверять контрольные суммы файлов;
* использовать безопасные каналы доставки обновлений.

### 8.7.4. Атаки на CI/CD pipeline
**Тип атаки:** изменение процесса сборки и доставки ПО.

`CI/CD`-системы имеют высокий уровень доверия, так как они могут собирать код, создавать артефакты и отправлять их в production. Если злоумышленник получает доступ к `pipeline`, он может изменить процесс сборки или внедрить вредоносный код.

**Пример атаки:** Атакующий получает доступ к `GitLab CI`:
```yaml
build:
  script:
    - compile_application
    - upload_release
```
и изменяет pipeline:
```yaml
build:
  script:
    - download malware.sh
    - execute malware.sh
    - compile_application
```
В результате вредоносный код попадает в итоговый продукт.

**Защита:**
* ограничение доступа к `CI/CD`;
* обязательная `MFA`;
* защита секретов;
* проверка изменений `pipeline`;
* разделение прав доступа.

### 8.7.5. Небезопасная десериализация (Insecure Deserialization)
**Тип атаки:** изменение сериализованных данных.

При сериализации объект преобразуется в формат, который можно сохранить или передать. Если приложение принимает такие данные без проверки, атакующий может изменить их содержимое.

**Пример атаки:** Приложение получает объект:
```json
{
  "role": "user"
}
```
Атакующий изменяет его:
```json
{
  "role": "admin"
}
```
Если приложение доверяет этим данным после десериализации, пользователь получает повышенные права. В некоторых технологиях небезопасная десериализация может привести к выполнению произвольного кода.

**Защита:**
* не десериализовать данные из недоверенных источников;
* использовать безопасные форматы (например, JSON вместо нативных бинарных объектов);
* проверять структуру и значения данных;
* применять allowlist допустимых классов.

### 8.7.6. Подмена артефактов сборки (Build Artifact Tampering)
**Тип атаки:** изменение готовых компонентов приложения.

После сборки приложение обычно распространяется в виде артефактов: Docker-образов, пакетов, бинарных файлов. Если отсутствует контроль целостности, атакующий может заменить эти файлы.

**Пример атаки:** В хранилище появляется:
```
application-v1.0.tar
```
Вместо оригинального файла атакующий размещает изменённую версию. Пользователи или сервер развёртывания скачивают поддельный артефакт.

**Защита:**
* подписывать артефакты;
* проверять хэши файлов;
* использовать доверенные registry;
* сканировать контейнерные образы перед deployment.

Для AppSec специалиста ключевой вывод: **Software or data integrity failures возникают там, где система доверяет коду или данным без проверки их происхождения и неизменности. Поэтому основные точки контроля — зависимости, CI/CD, обновления, артефакты сборки и обработка пользовательских данных.**
