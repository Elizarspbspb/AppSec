# Software and Data Integrity Failures (Нарушения целостности программного обеспечения и данных).

## 1. Что это такое?
`Software or Data Integrity Failures` — это класс уязвимостей, возникающий, когда код или данные принимаются и выполняются системой без проверки их подлинности и неизменности.

* **Суть проблемы**: Слепое доверие источнику. Если злоумышленник подменит библиотеку, файл обновления или сериализованный объект, система этого не заметит и выполнит вредоносный код.
* **Отличие от Supply Chain Attacks (SSCF)**: При Supply Chain атакуют непосредственно вендора/разработчика, чтобы через него заразить клиентов. При Integrity Failures проблема на нашей стороне — у нас отсутствуют механизмы проверки (контрольные суммы, подписи, lock-файлы), из-за чего подмена в принципе становится возможной.

## 2. Методы поиска
В AppSec-процессе целостность контролируется на разных этапах пайплайна:
* **SCA** (Software Composition Analysis): Поиск уязвимых и недоверенных сторонних зависимостей в манифестах (package.json, requirements.txt). Инструменты: Snyk, GitHub Dependabot, `OWASP Dependency-Check`.
* **Контейнерное сканирование**: Проверка слоев Docker-образов перед деплоем. Инструменты: `Trivy`, `Grype`.
* **Аудит SBOM** (Software Bill of Materials): Анализ декларативного состава ПО (в форматах CycloneDX, SPDX) для выявления недоверенных компонентов.
* **SAST/Code Review**: Поиск в коде небезопасных функций десериализации и вызовов обновлений по HTTP.

## 3. Примеры уязвимостей с кодом
* `Небезопасная десериализация` (Insecure Deserialization)

Атакующий передает измененный сериализованный объект, который при восстановлении выполняет код на сервере.
```py
import pickleimport base64
# Приложение принимает данные из куки/запроса без проверки целостности
def handle_session(cookie_data):
    # Злоумышленник может передать payload, содержащий __reduce__ для RCE
    user_data = pickle.loads(base64.b64decode(cookie_data)) 
    return user_data
```
```js
const serialize = require('node-serialize');
// Передача JSON с функцией внутри: {"rce":"_$$ND_FUNC$$_function(){...}"}
app.use((req, res) => {
    if (req.cookies.profile) {
        let str = Buffer.from(req.cookies.profile, 'base64').toString();
        let obj = serialize.unserialize(str); // Приводит к выполнению кода (RCE)
    }
});
```
* `Dependency Confusion` (Подмена зависимостей)

Сборщик ищет внутренний пакет во внешнем репозитории и скачивает вредоносную версию с более высоким тегом.
```js
"dependencies": {
  "my-private-internal-package": "^1.0.0" 
}
// Если злоумышленник зальет в публичный npm пакет с таким же именем и версией 9.9.9,
// npm install без lock-файла выкачает вредоносный код.
```
## 4. Методы защиты
1. **Защита зависимостей**: Использовать приватные прокси-репозитории (Nexus, Artifactory), жестко фиксировать версии через `package-lock.json` / `poetry.lock` и проверять хэши (SHA-256).
2. **Контроль целостности кода**: Использовать цифровые подписи для обновлений и артефактов сборки (например, Cosign для Docker-образов).
3. **Безопасная доставка**: Обновления только по `HTTPS` с обязательной валидацией контрольных сумм.
4. **Безопасные форматы данных**: Отказаться от нативных бинарных форматов сериализации (pickle, node-serialize, Marshal) в пользу чистого JSON или Protocol Buffers с валидацией по строгой схеме.
5. **Защита CI/CD**: Харденинг пайплайнов, подпись коммитов, изоляция секретов и запрет скачивания недоверенных скриптов в процессе сборки.
